# 5.3 — `tests/test_loaders.py`: the round trip that must survive

## One-line answer

The day's test file asserts one thing about each store — that a frame written to it and read back is
the frame you started with — and the value of the file is that **one of those tests asserts a
failure**, because the CSV cannot keep that promise and the suite says so out loud.

---

## The story

Somebody in the flat fixes the aisle problem properly. They work out the argument that keeps `07` as
`07`, put it in the shared script, check it, and tell everybody it is sorted.

Three weeks later it is broken again.

Nobody undid the fix on purpose. Somebody tidied the script, saw an argument they did not recognise,
thought it looked like clutter, and took it out. Everything still ran. Nothing complained. The
numbers were slightly different and no one looked at the aisle column for a fortnight.

That is the thing worth noticing. The fix was correct and it did not survive, because nothing in the
project knew it mattered. A comment would not have helped; the person tidying up read the line and
removed it anyway.

What was missing was something that stops being green when the argument goes away.

---

## The idea in plain language

A **round trip** is writing data out and reading it back. The question a round-trip test asks is
simple: **is what came back the same as what went in?**

It is the sharpest test you can write about a storage format, because it needs no fixture of expected
values — the input is the expectation. And on this day it is the exact question the whole subject has
been circling. Parquet keeps the types ([3.2](../03-parquet/3.2-the-round-trip-that-keeps-dtypes.md)),
SQLite keeps them except the date ([4.4](../04-sql/4.4-to-sql-and-what-sqlite-invents.md)), and a CSV
keeps none of them at all ([1.1](../01-the-csv/1.1-a-csv-has-no-types-in-it.md)).

The tool is `pd.testing.assert_frame_equal`, which compares two frames **including their dtypes** and
raises `AssertionError` with a message naming the first column that differs. Plain `==` on two frames
gives you a frame of booleans rather than an answer
([Day 26, 1.3](../../../day-26-frames-and-copy-on-write/parts/01-the-two-objects/1.3-a-table-of-columns.md)),
and `.equals()` gives a bare `True` or `False` that tells you nothing about *why*.

The idea that makes this file worth reading, though, is the second kind of test in it. Most tests
assert that something works. **One test here asserts that something fails**, using
`pytest.raises`. That is not cynicism; it is documentation with teeth. The CSV round trip *is* lossy,
that is a fact about the format rather than a bug in our code, and a test that pins it means the fact
cannot be quietly forgotten — and that the day pandas changes its inference, the suite tells us.

The last piece is Principle 7, which this file exists to satisfy: **a test nobody has seen fail is not
a test.** A suite that is green from the moment it is written might be checking nothing at all. So
the end of this part deletes one argument from the module and watches four tests go red, which is the
only evidence that the file does what it claims.

---

## Why Setu needs it

- **[5.1](5.1-the-loaders-module.md)** wrote down the module's promises in prose; this file writes
  the same promises in a form that can fail.
- **[5.2](5.2-the-file-that-does-not-fit.md)** found that the chunked total and the whole-file total
  differ in the last bits, which is why one test here uses `pytest.approx`.
- **[1.3](../01-the-csv/1.3-when-the-guess-is-wrong.md)** is the bug this whole file is built around,
  and the test named after it is the one that goes red first.
- **Day 30 onwards**, every model reads data before it fits anything. A loader whose behaviour is
  pinned is what makes an experiment reproducible; an unpinned loader means last week's result cannot
  be reproduced and nobody can say why.
- **Day 233** builds the project's eval suite. The pattern here — assert the promise, then assert the
  known limitation — is the shape every eval in it takes.

## The mechanism

The head of the file: one fixture, used by everything:

```python
"""Every store must produce the same typed frame, and the ones that cannot must say so."""

from __future__ import annotations

import sqlite3
from pathlib import Path

import pandas as pd
import pytest

from setu import loaders as ld

ROWS = (
    "item,need,price,aisle,bought\n"
    "milk,2,1.15,07,2026-08-30\n"
    "bread,1,1.40,03,2026-08-30\n"
    "eggs,6,0.32,07,\n"
    "rice,1,2.05,11,2026-08-24\n"
)


@pytest.fixture
def csv_path(tmp_path: Path) -> Path:
    path = tmp_path / "shopping.csv"
    path.write_text(ROWS, encoding="utf-8")
    return path
```

**Line by line:**

- `from setu import loaders as ld` — the module imported under a short alias, so every test reads
  `ld.load_csv` and it is always obvious which code is under test.
- `ROWS` is the same four lines the whole day has used, written as a string in the test file. **The
  test owns its input**; it does not read `data/shopping.csv`, because a test that depends on a file
  in the repository fails for reasons that have nothing to do with the code.
- `tmp_path` is pytest's built-in fixture giving a fresh empty directory per test
  ([Day 2, 3.2](../../../day-02-quality-gate/parts/03-pytest/3.2-fixtures-and-tmp-path.md)). Every test
  here writes files, and this is what stops them writing over each other or leaving litter behind.
- `csv_path` builds on `tmp_path` rather than duplicating it, so the four-line file is written in one
  place and every test that needs one asks for it by name.
- `encoding="utf-8"` stated, exactly as [1.1](../01-the-csv/1.1-a-csv-has-no-types-in-it.md) argued.
  A test that writes with the platform default and reads with it too would pass everywhere and prove
  nothing.

The tests that assert the module's promises:

```python
def test_load_csv_declares_every_dtype(csv_path: Path) -> None:
    """The read is closed: four dtypes declared, one date parsed, nothing inferred."""
    frame = ld.load_csv(csv_path)
    assert {name: str(frame[name].dtype) for name in ld.SCHEMA} == ld.SCHEMA
    assert str(frame["bought"].dtype) == "datetime64[us]"


def test_the_aisle_keeps_its_leading_zero(csv_path: Path) -> None:
    """The one column inference destroys, and the reason dtype= is not optional."""
    assert ld.load_csv(csv_path)["aisle"].tolist() == ["07", "03", "07", "11"]


def test_parquet_round_trip_is_lossless(csv_path: Path, tmp_path: Path) -> None:
    """Parquet carries its own types, so the frame that comes back is the frame that went in."""
    original = ld.load_csv(csv_path)
    target = tmp_path / "shopping.parquet"
    original.to_parquet(target, index=False)
    pd.testing.assert_frame_equal(original, ld.load_parquet(target))
```

**Line by line:**

- `{name: str(frame[name].dtype) for name in ld.SCHEMA} == ld.SCHEMA` — the frame's actual dtypes
  built into a dictionary and compared against the declared one **in a single assertion**. This is
  why `SCHEMA` holds dtype *names* rather than dtype objects
  ([1.4](../01-the-csv/1.4-dtype-at-read-time.md)): the comparison needs no translation, and a
  failure prints both dictionaries side by side.
- `"datetime64[us]"` asserted separately, because `bought` is deliberately not in `SCHEMA` — dates
  are parsed rather than converted ([1.5](../01-the-csv/1.5-parse-dates-and-the-date-that-stayed-text.md)).
  The test's shape mirrors the module's shape.
- `["07", "03", "07", "11"]` — the assertion is about the **values**, not the dtype. The previous test
  already checked the dtype, and this one catches the case
  [1.3](../01-the-csv/1.3-when-the-guess-is-wrong.md) warned about, where a column is cast back to
  text after the zero has already been destroyed. **A dtype check alone would pass on `["7", "3"]`.**
- `index=False` on the write — otherwise the row numbers become a column and the round trip fails for
  a reason that has nothing to do with types ([4.4](../04-sql/4.4-to-sql-and-what-sqlite-invents.md)).
- `assert_frame_equal(original, ld.load_parquet(target))` — **the whole frame, in one line**,
  including every dtype. There is no list of expected values anywhere, because the frame that went in
  is the expectation.

The test that asserts a failure:

```python
def test_csv_round_trip_is_not_lossless(csv_path: Path, tmp_path: Path) -> None:
    """A CSV written and read back without dtype= loses the aisle. This is the day's point."""
    original = ld.load_csv(csv_path)
    target = tmp_path / "again.csv"
    original.to_csv(target, index=False)
    naive = pd.read_csv(target)
    assert str(naive["aisle"].dtype) == "int64"
    with pytest.raises(AssertionError, match="aisle"):
        pd.testing.assert_frame_equal(original, naive)
```

**Line by line:**

- The frame is written by our own `to_csv` and read back by a **bare** `pd.read_csv` — deliberately
  the version with no arguments, because that is what somebody else will write when they open our
  file ([1.2](../01-the-csv/1.2-read-csv-and-what-it-guessed.md)).
- `assert str(naive["aisle"].dtype) == "int64"` — the loss stated positively first. It is not enough
  to say the frames differ; the test names *how*, so a future change that breaks it differently
  cannot slip through.
- `with pytest.raises(AssertionError, match="aisle")` — **the assertion that a comparison fails.**
  `pytest.raises` passes when the block raises and fails when it does not, so this test goes red the
  day a CSV round trip starts working
  ([Day 18, 4.4](../../../day-18-exceptions/parts/04-in-anger/4.4-pytest-raises.md)).
- `match="aisle"` — not merely "something raised", but **that the failure was about the right
  column**. Without it, a round trip broken in some entirely different way would keep this test green,
  which is the most common way a `raises` test rots.
- The docstring says *this is the day's point*, because a test asserting a failure looks like a
  mistake to a reader in a hurry, and the next person to see it needs to know it is deliberate.

The rest of the suite, in brief — the SQL round trip, the dispatcher, and the chunked reader:

```python
def test_sql_keeps_text_but_loses_nothing_we_did_not_ask_for(
    csv_path: Path, tmp_path: Path
) -> None:
    """The table declares its types, so aisle survives with no dtype= anywhere."""
    db = tmp_path / "shop.db"
    original = ld.load_csv(csv_path)
    with sqlite3.connect(db) as con:
        original.assign(bought=original["bought"].dt.strftime("%Y-%m-%d")).to_sql(
            "shopping", con, index=False, if_exists="replace"
        )
    back = ld.load_sql(db)
    assert back["aisle"].tolist() == ["07", "03", "07", "11"]
    assert str(back["bought"].dtype) == "datetime64[us]"


def test_load_refuses_a_format_it_has_no_reader_for(tmp_path: Path) -> None:
    target = tmp_path / "shopping.xlsx"
    target.write_text("not really a spreadsheet", encoding="utf-8")
    with pytest.raises(ld.LoadError, match="no reader for '.xlsx'"):
        ld.load(target)


def test_chunked_total_matches_the_whole_file_total(csv_path: Path) -> None:
    """The chunked read is an optimisation, not a different answer."""
    whole = ld.load_csv(csv_path)
    expected = float((whole["need"] * whole["price"]).sum())
    assert ld.total_in_chunks(csv_path, chunksize=2) == pytest.approx(expected)
```

**Line by line:**

- `.dt.strftime("%Y-%m-%d")` before the write — the date turned to text **on purpose, in a chosen
  format**, because SQLite has no date type and letting the driver decide adds a midnight nobody
  typed ([4.4](../04-sql/4.4-to-sql-and-what-sqlite-invents.md)).
- `ld.load_sql(db)` with no `parse_dates` argument at the call site — the module already passes it
  ([5.1](5.1-the-loaders-module.md)), and the test asserts the *module's* promise rather than pandas'.
- `match="no reader for '.xlsx'"` on `LoadError` — the **message** is asserted, not just the type,
  because the message is the interface for an error a human reads
  ([Day 18, 3.3](../../../day-18-exceptions/parts/03-your-own/3.3-the-message-is-an-interface.md)).
- `chunksize=2` on a four-row file — deliberately tiny, so the file is split into two chunks and the
  loop actually runs more than once. A chunk size larger than the file would test nothing.
- `pytest.approx(expected)` and **not** `==`. This is [5.2](5.2-the-file-that-does-not-fit.md)'s
  finding turned into code: the chunk boundaries change the order of the additions, so the last bits
  of the two totals differ. `==` would pass here on four rows and fail on half a million
  ([Day 23, 1.6](../../../day-23-ufuncs-and-statistics/parts/01-ufuncs/1.6-isclose-and-allclose.md)).

## When it breaks

**The mutation — delete one argument and watch.** In `src/setu/loaders.py`, change `load_csv` from
this:

```python
return pd.read_csv(path, usecols=COLUMNS, dtype=SCHEMA, parse_dates=list(DATES))
```

to this, which is what somebody tidying up would write:

```python
return pd.read_csv(path, usecols=COLUMNS, parse_dates=list(DATES))
```

**Line by line:**

- Only `dtype=SCHEMA` is gone. The read still works, still returns five columns, still parses the
  date, and every printed frame still looks like a shopping list.
- This is the story at the top of this part, reproduced exactly: an argument that looks like clutter,
  removed by somebody with good intentions.

Then run the suite:

```text
$ uv run pytest tests/test_loaders.py -q
```

```text
FAILED tests/test_loaders.py::test_load_csv_declares_every_dtype - AssertionE...
FAILED tests/test_loaders.py::test_the_aisle_keeps_its_leading_zero - Asserti...
FAILED tests/test_loaders.py::test_csv_round_trip_is_not_lossless - Assertion...
FAILED tests/test_loaders.py::test_sql_keeps_text_but_loses_nothing_we_did_not_ask_for
4 failed, 8 passed in 0.83s
```

**Four tests from one deleted argument, and the fourth is the interesting one.**

The first two are direct: the dtypes no longer match the schema, and the aisle lost its zero. Exactly
what they were written for.

The third fails in a way worth reading, because it is the `pytest.raises` test and it failed for the
*wrong reason*:

```text
E       AssertionError: Regex pattern did not match.
E         Expected regex: 'aisle'
E         Actual message: 'Attributes of DataFrame.iloc[:, 4] (column name="bought") are different
E
E         Attribute "dtype" are different
E         [left]:  datetime64[us]
E         [right]: <StringDtype(na_value=nan)>'
```

The CSV round trip still failed — but on `bought`, not on `aisle`, because with the aisle now an
integer on both sides the first difference `assert_frame_equal` reaches is the date. **`match="aisle"`
is what caught that.** Without it this test would have stayed green while the thing it exists to
document had changed completely, and that is the argument for always constraining a `raises` test to
the message.

The fourth is the one that shows why this suite is worth having:

```text
E       AssertionError: assert [7, 3, 7, 11] == ['07', '03', '07', '11']
E
E         At index 0 diff: 7 != '07'
```

That is the **SQL** test. Nothing about the database changed. It failed because the test builds its
table from `load_csv`'s output, so a broken CSV loader put integers into the table, and the table
faithfully stored what it was given. **A defect at the boundary reached a store two steps away**,
which is the whole reason the loader is a boundary in the first place.

Put `dtype=SCHEMA` back and all twelve pass again.

## In production

**What a professional writes instead of the teaching version.** Five near-identical round-trip tests
become one parameterised test, so adding a sixth store means adding a line:

```python
import pytest

LOSSLESS = [
    pytest.param("parquet", id="parquet"),
    pytest.param("sql", id="sqlite"),
]


@pytest.mark.parametrize("store", LOSSLESS)
def test_the_aisle_survives_every_lossless_store(store, csv_path, tmp_path, write_to) -> None:
    """Whatever the store, 07 comes back as 07. The CSV is tested separately, and fails."""
    original = ld.load_csv(csv_path)
    back = write_to(store, original, tmp_path)
    assert back["aisle"].tolist() == original["aisle"].tolist()
    assert str(back["aisle"].dtype) == "str"
```

**Line by line:**

- `@pytest.mark.parametrize` runs the body once per entry, and a failure names which one, so a broken
  Parquet round trip does not read as "the round-trip test failed"
  ([Day 2, 3.3](../../../day-02-quality-gate/parts/03-pytest/3.3-markers-and-exit-code-five.md)).
- `id="sqlite"` — the label in the output. Without it pytest invents one from the value, and readable
  test names matter most on the day something fails at three in the morning.
- `LOSSLESS` names what the list *means*. **The CSV is deliberately absent**, and its own test asserts
  the failure. A list called `STORES` with a CSV exception buried in the body would hide the day's
  main finding.
- `write_to` is a fixture returning a helper that writes and re-reads for a named store. Pushing the
  per-store difference into one fixture is what keeps the test body about the *claim*.
- The dtype and the values are both asserted, for the reason the aisle test gave: `["7", "3"]` has the
  right dtype and the wrong data.

**What changes at scale.** Three things.

Round-trip tests grow into **property-based** ones. Instead of four fixed rows, a library such as
Hypothesis generates hundreds of frames — empty ones, one-row ones, ones with every value null, ones
with unicode in the item names — and asserts the same property about all of them. That is where the
genuinely surprising failures live, and an empty frame is the one that finds most of them, because
an empty CSV has no values to infer a dtype from at all.

The suite also gains a **schema contract test** that runs against the real upstream file on a
schedule rather than in the pull request. A unit test proves your loader is correct about a file you
wrote; it says nothing about the file the shop will send next month. Those two need different
cadences, and mixing them makes the fast suite slow and flaky.

And the pins matter more than they look. Every dtype string in this file — `"str"`,
`"datetime64[us]"`, `<StringDtype(na_value=nan)>` in the failure message — is **specific to pandas
3.0.5**. On pandas 2.x, `"str"` was `object` and this suite would fail everywhere
([Day 26, 2.4](../../../day-26-frames-and-copy-on-write/parts/02-the-str-dtype/2.4-dtypes-equals-object-finds-nothing.md)).
That is not fragility; it is the point of Principle 4. The test suite is where an unpinned upgrade
gets caught, and a suite loose enough to pass on either version would have caught nothing.

**The failure that only appears with real data.** A round-trip suite passed for a year, then the
upstream file arrived with a completely empty optional column. Every value was null, so there was
nothing to infer from, and the column came back as `float64` full of `NaN` instead of text — through
a code path no test had, because the fixture had always had at least one value in every column. The
lesson is that the interesting inputs are the degenerate ones: the empty frame, the single row, the
all-null column. Add those three to a fixture list before adding a fourth realistic case.

**The review comment a senior engineer leaves.** *"Good — I especially like the test that asserts the
CSV round trip fails. Two things: `pytest.raises(AssertionError)` without `match=` would pass on any
failure, so keep the match and make it specific. And there is no test for an empty frame; that is
where dtype inference behaves differently and where this will break first."*

**The interview question.** *"How would you test a data loader?"* The answer that shows you have
maintained one: round-trip it — write the frame out and read it back, and compare with
`assert_frame_equal` so that dtypes are part of the comparison rather than just values. Then the two
things that separate a real suite from a demo. **Test the known limitations explicitly**, with a test
that asserts the lossy format is lossy, so the limitation is documented where it cannot be forgotten.
And **mutate the module to prove the suite can fail** — delete the argument the loader depends on and
count the red tests, because a suite nobody has watched fail is not evidence of anything. The
follow-up is usually about fixtures, and the answer is that a loader test should build its own input
in `tmp_path` rather than reading a committed file, so a failure is always about the code.
