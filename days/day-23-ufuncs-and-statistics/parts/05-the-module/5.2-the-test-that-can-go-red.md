# 5.2 — `tests/test_summary.py` — asserting a claim, not a number

## One-line answer

A test that pins the mean to `9106.7` proves the code has not changed; a test that asserts the mean was
divided by the number of **recorded** days proves it is right — and only the second kind can go red for a
reason worth knowing about.

---

## The story

Somebody writes their first test for the summary. They run the code, see that the average comes out at
9 106.7, and write that number into the test.

It passes. It passes every day for a month. Then somebody changes how a missing day is handled, the
average becomes 9 004.1, the test goes red, and the person fixing it does the only thing the test makes
possible: they update the number to 9 004.1 and it passes again.

The test caught the change. It said nothing at all about whether the change was right, and the person had
no way to find out from the test, so they guessed. That is the whole problem with a test written against
an answer instead of against a reason.

The version that would have helped says something different: whatever the average is, it must equal the
total of the recorded days divided by how many were recorded. That sentence stays true when the numbers
change and stops being true when the behaviour is wrong, which is exactly the right way round.

---

## The idea in plain language

A test asserts something. The interesting question is **what**, and there are two answers that look
similar in code and behave completely differently over a year.

A **snapshot** assertion pins the output: `assert result.mean == 9106.7`. It is easy to write, and it
fails whenever anything changes — including changes that are correct. Every failure asks the same
unanswerable question: is this new number better than the old one? Snapshots have their place, in the
outer layer of a system where the output is genuinely a contract, and they are the wrong tool for a
statistics module.

A **property** assertion states a relationship that must hold whatever the numbers are: the mean equals
the recorded total over the recorded count; the sample standard deviation exceeds the population one by
exactly the square root of `n/(n-1)`; the positions returned by `top_k` are the same set a full sort would
have produced. Each of these can be checked against a value computed a different way, and each fails only
when the behaviour is wrong.

Three test-design ideas do most of the work in this file, and each of them is a lesson from earlier in the
day made executable.

**The fixture must be able to tell things apart.** A `(7, 7)` fixture cannot distinguish `axis=0` from
`axis=1` ([2.2](../02-statistics/2.2-axis-the-one-that-disappears.md)), so this month is `(4, 7)`. An
ascending fixture cannot distinguish a real top-k from "the last three elements"
([3.3](../03-sorting-and-searching/3.3-top-k-and-argpartition.md)), so this month is unsorted. **A fixture
is a piece of design**, and picking one that happens to be square or sorted disables half the suite
silently.

**Assert against a differently-computed answer.** The best check on `top_k` is `np.argsort`, which is the
slow, obvious implementation the fast one replaced. Comparing two independent routes to the same answer is
worth far more than comparing one route to a constant somebody typed.

**Compare sets when order is not promised.** `argpartition` promises which `k` are best, not the
arrangement of everything else, so asserting the array equals a sorted array would produce a test that
passes today and fails when the array grows
([3.3](../03-sorting-and-searching/3.3-top-k-and-argpartition.md)). A flaky test is worse than no test,
because it teaches people to ignore red.

And one rule that stands above all of them: **a test you have never seen fail is not yet a test**
(Principle 7). The last section of this document breaks the module twice, on purpose, and reads what
comes out.

## The mechanism

The fixtures, which are half the design:

```python
"""Day 23's eval: every promise the summary module makes, asserted."""

from __future__ import annotations

import numpy as np
import pytest

from setu.summary import MIN_DAYS_FOR_SPREAD, Summary, hit_rate, summarise, top_k

# Twenty-eight days, four weeks. Deliberately NOT square and deliberately not sorted:
# a (7, 7) fixture cannot tell axis=0 from axis=1, and an ascending one cannot tell a
# top-k from a tail slice.
MONTH = np.array(
    [
        [8213, 10442, 6180, 9000, 12007, 9631, 7204],
        [7788, 9120, 11345, 8402, 6733, 14210, 5096],
        [9004, 8765, 7621, 10188, 9950, 8317, 11002],
        [6540, 12488, 9873, 7106, 8899, 10540, 9218],
    ],
    dtype=np.float64,
)


@pytest.fixture
def month() -> np.ndarray:
    return MONTH.copy()


@pytest.fixture
def gappy(month: np.ndarray) -> np.ndarray:
    month[0, 3] = np.nan
    return month
```

**Line by line:**

- The comment above `MONTH` explaining the shape choice — **this is the most important comment in the
  file**. Without it, the first person who needs a quick fixture makes it `(5, 5)` and four tests quietly
  stop being able to fail.
- `dtype=np.float64` on the constant — the module refuses integers
  ([5.1](5.1-the-summary-module.md)), and a fixture that cannot be passed to the code under test is a
  slow start.
- `month` returning `MONTH.copy()` — **a fresh array per test**. `gappy` writes a `nan` into it, and
  without the copy that write would leak into every later test in the file, which is the kind of failure
  that depends on test ordering and takes a day to find
  ([Day 21, 2.1](../../../day-21-indexing-and-views/parts/02-the-view-trap/2.1-a-slice-does-not-copy.md)).
- `gappy` taking `month` as an argument — fixtures composing, so the gap is defined in exactly one place
  and every test that wants a month with a hole in it gets the same hole.
- `month[0, 3] = np.nan` — the Thursday of week one, the same missing day the whole day has been using.
  Reusing it means a reader who has read [2.5](../02-statistics/2.5-the-nan-family.md) already knows what
  the correct answers are.

The assertions that state a relationship rather than a number:

```python
def test_summary_counts_only_recorded_days(gappy):
    result = summarise(gappy)
    assert result.observed == 27
    assert result.expected == 28
    assert result.complete is False


def test_mean_ignores_the_missing_day_and_divides_by_the_survivors(gappy):
    result = summarise(gappy)
    live = gappy.ravel()[~np.isnan(gappy.ravel())]
    assert result.mean == pytest.approx(live.sum() / 27)


def test_ddof_changes_the_answer_by_the_known_ratio(month):
    sample = summarise(month, sample=True).std
    population = summarise(month, sample=False).std
    assert sample > population
    assert sample / population == pytest.approx(np.sqrt(28 / 27))


def test_the_input_is_never_modified(gappy):
    before = gappy.copy()
    summarise(gappy)
    assert np.array_equal(before, gappy, equal_nan=True)
```

**Line by line:**

- `result.complete is False` with `is` rather than `==` — `complete` is documented as a `bool`, and `is`
  asserts the type as well as the value. A property that accidentally returned `np.False_` would pass an
  `==` check and fail this one, which is the point.
- `live.sum() / 27` — **the answer computed a different way**, from the array the test built itself. If
  `summarise` ever starts dividing by 28, this fails; if the fixture changes, it still passes. No number is
  typed into the test.
- `pytest.approx` rather than `==` — two float routes to the same value need not produce identical bits
  ([2.6](../02-statistics/2.6-float-summation-and-the-drift.md)), and asserting exact float equality is
  how a suite becomes flaky on a different machine
  ([1.6](../01-ufuncs/1.6-isclose-and-allclose.md)).
- `sample / population == pytest.approx(np.sqrt(28 / 27))` — **the `ddof` relationship as arithmetic**. The
  ratio of the two variances is exactly `n/(n-1)`
  ([2.3](../02-statistics/2.3-std-var-and-ddof.md)), so the ratio of the standard deviations is its square
  root. This test knows nothing about step counts and would hold for any data at all.
- `assert sample > population` before the ratio — a cheap direction check that fails with a readable
  message. When both assertions would fail, the first one is the one you want to read.
- `np.array_equal(before, gappy, equal_nan=True)` — the no-mutation promise. **`equal_nan=True` is
  required**, because the fixture contains a `nan` and `nan != nan`
  ([2.5](../02-statistics/2.5-the-nan-family.md)), so without it this assertion fails on a module that is
  behaving perfectly.

The tests for the operation the day was really about:

```python
def test_top_k_agrees_with_a_full_sort(month):
    flat = month.ravel()
    assert set(top_k(month, 4).tolist()) == set(np.argsort(flat)[-4:].tolist())


def test_top_k_is_ordered_best_first(month):
    values = month.ravel()[top_k(month, 5)]
    assert np.all(np.diff(values) < 0)


def test_top_k_never_returns_a_missing_day(gappy):
    best = top_k(gappy, gappy.size)
    assert not np.isnan(gappy.ravel()[best]).any()
    assert best.size == 27


def test_top_k_of_nothing_is_still_an_index():
    empty = top_k(np.full(3, np.nan), 2)
    assert empty.size == 0
    assert np.array_equal(np.full(3, np.nan)[empty], np.array([]))
```

**Line by line:**

- `set(...) == set(...)` — **comparing sets, deliberately**. `argpartition` promises the membership of the
  top `k` and not their order, so an array comparison would assert something the function never agreed to
  ([3.3](../03-sorting-and-searching/3.3-top-k-and-argpartition.md)).
- `np.argsort(flat)[-4:]` as the reference — the slow, obvious implementation, used as an oracle. This is
  the highest-value line in the file: it checks the optimisation against the thing it replaced.
- `np.all(np.diff(values) < 0)` — **strictly** decreasing, which asserts the ordering promise `top_k` does
  make. `np.diff` gives the gaps between neighbours
  ([2.1](../02-statistics/2.1-a-reduction-turns-many-into-one.md)), and strict `<` also rules out
  duplicates being returned twice.
- `top_k(gappy, gappy.size)` — asking for **all** twenty-eight, which is the case where a filtering bug is
  most visible. A `nan` that survives filtering has to appear somewhere in twenty-eight results, and
  cannot hide outside a top-three.
- `best.size == 27` alongside the `isnan` check — two assertions of one promise. The first says no missing
  day came back; the second says the clamp counted the live scores rather than the array length.
- `np.full(3, np.nan)[empty]` — **indexing with the empty result**, which is the real assertion. The size
  being zero is not enough; the empty array has to still be a legal index, which is what `np.intp` gives
  and a `float64` empty array does not
  ([5.1](5.1-the-summary-module.md)).

## When it breaks

**Break one: remove the translate-back in `top_k`.** Change the last line to
`return np.argsort(flat[candidates])[::-1]`, dropping the `candidates[...]` that converts
positions-within-the-shortlist into positions in the original array
([3.3](../03-sorting-and-searching/3.3-top-k-and-argpartition.md)).

```text
$ uv run python -m pytest tests/test_summary.py -q
    def test_top_k_agrees_with_a_full_sort(month):
        flat = month.ravel()
>       assert set(top_k(month, 4).tolist()) == set(np.argsort(flat)[-4:].tolist())

E
E         Extra items in the left set:
E         0
E         1
E         2
E         3
E         Extra items in the right set:...

=========================== short test summary info ===========================
FAILED tests/test_summary.py::test_top_k_returns_positions_not_values - assert False
FAILED tests/test_summary.py::test_top_k_is_ordered_best_first - assert np.False_
FAILED tests/test_summary.py::test_top_k_agrees_with_a_full_sort - AssertionError: ...
FAILED tests/test_summary.py::test_top_k_never_returns_a_missing_day - AssertionErr...
4 failed, 19 passed in 0.31s
```

**What it means.** Four tests caught it, and the message from the third is the one that explains the bug
without any thinking: `assert {0, 1, 2, 3} == {4, 9, 12, 22}`. The broken version returned positions 0 to
3 — the first four days of the month — because `np.argsort` of a four-element shortlist can only return 0
to 3. **That is exactly what this bug always looks like**, and a snapshot test asserting
`mean == 9106.7` would have stayed green throughout, because `summarise`'s statistics are untouched by it.
Note also which test failed *most usefully*: the set comparison against `argsort` names both the wrong
answer and the right one.

**Break two: ignore the caller's `ddof` choice.** Change `ddof=1 if sample else 0` to `ddof=0`.

```text

        sample = summarise(month, sample=True).std
        population = summarise(month, sample=False).std

E       assert 1996.6628395645469 > 1996.6628395645469

=========================== short test summary info ===========================

1 failed, 22 passed in 0.28s
```

**What it means.** One test, and its message is a sentence: the same number is not greater than itself.
This is the bug that would otherwise be invisible — the module still returns a standard deviation, it is
still a correct population standard deviation, and the `sample=True` argument has silently stopped doing
anything. Nothing about the value looks wrong; only the *relationship* between two calls does. **This is
the clearest case in the day for asserting a property rather than a number**, because there is no number
you could have pinned that would have caught it.

**The failure that is a bad test rather than bad code:**

```text
$ uv run python -c "
import numpy as np
gappy = np.array([1.0, np.nan, 3.0])
before = gappy.copy()
print('equal_nan=True  :', np.array_equal(before, gappy, equal_nan=True))
print('equal_nan=False :', np.array_equal(before, gappy))
"
equal_nan=True  : True
equal_nan=False : False
```

**What it means.** The array was not touched, and the default comparison says it changed. `nan != nan`, so
`np.array_equal` without `equal_nan=True` reports any array containing a missing value as unequal to a
perfect copy of itself ([2.5](../02-statistics/2.5-the-nan-family.md)). A no-mutation test written without
that keyword fails permanently on correct code, and the usual response is to delete the test. **A test
that cannot pass is worse than a missing one**, because it costs somebody an afternoon before it is
removed.

## In production

**What a professional writes instead of the teaching version.** The properties that hold for *any* input
get checked against many inputs rather than one:

```python
from __future__ import annotations

import numpy as np
import pytest

from setu.summary import summarise, top_k

SEEDS = [0, 1, 2, 7, 20260902]


@pytest.mark.parametrize("seed", SEEDS)
@pytest.mark.parametrize("size", [4, 5, 28, 1000])
def test_top_k_always_agrees_with_argsort(seed: int, size: int) -> None:
    rng = np.random.default_rng(seed)
    scores = rng.random(size)
    k = min(3, size)
    assert set(top_k(scores, k).tolist()) == set(np.argsort(scores)[-k:].tolist())


@pytest.mark.parametrize("seed", SEEDS)
def test_ddof_ratio_holds_for_any_data(seed: int) -> None:
    rng = np.random.default_rng(seed)
    values = rng.normal(9000, 2000, size=40)
    ratio = summarise(values, sample=True).std / summarise(values, sample=False).std
    assert ratio == pytest.approx(np.sqrt(40 / 39))
```

**Line by line:**

- Two stacked `@pytest.mark.parametrize` decorators — twenty combinations from six lines, and each one is a
  separately named test in the output so a failure says exactly which size and seed broke it.
- `SEEDS` as a module constant of **fixed** numbers — not `rng = np.random.default_rng()` with no seed. A
  test that generates fresh random data each run fails intermittently and cannot be reproduced from the
  failure message, which is the worst property a test can have
  ([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)).
- `size` including `4` — the smallest input the module accepts, because boundaries are where the clamp and
  the guard live. Testing only at 1 000 tests only the easy case.
- `k = min(3, size)` inside the test — the test must not ask for more than exists, which is the caller's
  responsibility and not a promise being checked here.
- `set(...) == set(...)` again, for the same reason as before — and now across twenty inputs, which is
  where the difference between `argpartition` and `argsort` on larger arrays would finally show up. The
  small fixture in the main suite genuinely cannot catch it
  ([3.6](../03-sorting-and-searching/3.6-stability-and-kind.md)).
- `np.sqrt(40 / 39)` derived from the size written just above it — the relationship stated as arithmetic
  rather than as the constant `1.0129`, so changing the size changes both halves together.

**What changes at scale.** Three things about the tests themselves rather than the code. Test data grows
until the suite is slow, and a slow suite is a suite people stop running — so the property tests use a
thousand values and a separate, marked benchmark handles the millions
([Day 25, 4.2](../../../day-25-copy-view-and-the-gate/parts/04-the-benchmark/4.2-timeit-honestly.md)).
Floating-point tolerances stop being a formality: two routes to the same sum over a million `float32`
values genuinely differ ([2.6](../02-statistics/2.6-float-summation-and-the-drift.md)), so `pytest.approx`
needs a stated `rel=` rather than its default once the arrays are large. And the highest-value test in a
mature numerical codebase is usually the one comparing the fast implementation against the slow obvious
one on random inputs — the pattern in `test_top_k_always_agrees_with_argsort` — because it is the only
kind that finds the bug nobody thought of. That style has a name, **property-based testing**, and the
library that generalises it is Hypothesis, which generates the awkward inputs for you instead of you
listing seeds.

**The failure that only appears with real data.** A numerical library's test suite asserted its fast top-k
against hard-coded expected positions on a twelve-element fixture. The fast path had a boundary bug that
only triggered above a size threshold, where the underlying algorithm switched strategies — the same kind
of threshold that hides an unstable sort
([3.6](../03-sorting-and-searching/3.6-stability-and-kind.md)). Every test passed. The bug shipped, and was
found by a user with a large array. A single parametrised test comparing against `argsort` at four sizes
would have caught it before the release.

**The review comment a senior engineer leaves.** *"`assert result.mean == 9106.7` — when this fails, what
should the next person do? There is no way to tell from the test whether a new number is right. Assert the
mean against the recorded total over the recorded count, so the test says what it believes rather than what
it saw."*

**The interview question.** *"How do you test a statistics function?"* Not by pinning its output. Pinning a
number catches change and says nothing about correctness, so every failure becomes "update the constant".
Assert properties instead: the mean equals the recorded total over the recorded count, the sample standard
deviation exceeds the population one by exactly the square root of `n/(n-1)`, the fast top-k returns the
same **set** of positions a full `argsort` would — the set, because `argpartition` never promised an order.
The design details that show experience: the fixture must not be square, or it cannot distinguish two axes,
and must not be sorted, or it cannot distinguish a top-k from a tail slice; a no-mutation check on data
containing `nan` needs `equal_nan=True` or it fails on correct code; and comparing the optimised
implementation against the slow obvious one across parametrised sizes and fixed seeds is the single
highest-value test in numerical code, because it finds the boundary bugs a small fixture is structurally
incapable of reaching.
