# 2.4 — `dtypes == "object"` finds nothing now

## One-line answer

Every pandas program written before 2026 finds its text columns by asking which ones are `object`, and
in pandas 3.0 the answer is **none** — so the loop that cleaned every text column now runs zero times
and reports success.

---

## The story

A block of flats has a caretaker's note pinned inside the bin store: *the bins that need putting out
are the green ones*. It has been there for years and it works. Every Tuesday somebody wheels out the
green bins.

Then the council changes the colour scheme. Recycling bins are now blue.

Nobody removes the note, because the note is not wrong about anything — it is a perfectly accurate
description of a world that stopped existing. On Tuesday somebody reads it, goes into the bin store,
looks for green bins, finds none, and wheels out nothing.

They have followed the instructions exactly. No bins go out. Nobody notices until the store is full,
because "I put out all the green bins" and "there were no green bins" produce the same report at the
end of the day: *done*.

---

## The idea in plain language

For fifteen years, the way to find text columns in a DataFrame was to look for `object`, because text
was the only common thing that ended up there
([2.1](2.1-text-used-to-be-object.md)). The idiom appears in every tutorial, every notebook and most
production codebases, in about four spellings:

```text
df.dtypes == "object"
df.select_dtypes("object")
df.select_dtypes(include=["object"])
[c for c in df.columns if df[c].dtype == object]
```

In pandas 3.0, text is `str` ([2.2](2.2-str-the-dtype-pandas-3-infers.md)). So the first spelling and
the last one now match **nothing at all**.

The danger is not that they raise. They do not. They return an empty selection, and empty selections
are perfectly legal:

- A `for` loop over no columns runs zero times and finishes successfully.
- A `.apply` over an empty selection returns an empty frame.
- An `if` on an empty list takes the else branch.

**Every one of those is silent.** The stripping never happened, the normalising never happened, the
whitespace is still there — and the pipeline reports that it cleaned the data.

pandas anticipated this for the `select_dtypes` spellings, and those two behave differently: asking for
`"object"` still returns the text columns **and emits a deprecation warning** telling you to say `"str"`
instead. That is a kindness, and it is temporary — the warning says the behaviour will be removed.

So of the four spellings, two break silently and two warn. The two that warn are the ones that go
through `select_dtypes`, which is a good argument for having used it all along.

The fix is short in every case:

| Old | New |
|---|---|
| `df.dtypes == "object"` | `df.dtypes == "str"` |
| `df.select_dtypes("object")` | `df.select_dtypes("str")` |
| `df[c].dtype == object` | `str(df[c].dtype) == "str"` |
| anything that must work on both versions | `pd.api.types.is_string_dtype(df[c])` |

That last row is the one to reach for in a library or in code that has to straddle pandas 2 and 3.
`pd.api.types.is_string_dtype` is a **public helper** that answers "is this a text column" without you
having to know which dtype the answer is spelled with this year.

The whole change is written up in the pandas migration guide for the new string dtype, *Migration guide
for the new string data type (pandas 3.0)*, at
<https://pandas.pydata.org/docs/user_guide/migration-3-strings.html> — which is the same URL the
deprecation warning prints, and it has a section specifically about `select_dtypes`.

## The mechanism

The idiom, and what it now finds:

```python
import pandas as pd

shop = pd.DataFrame(
    {
        "item": ["milk", "bread", "eggs", "rice"],
        "need": [2, 1, 6, 1],
    }
)
print("dtypes:", shop.dtypes.to_dict())
print('dtypes == "object" ->', shop.columns[shop.dtypes == "object"].tolist())
print('dtypes == "str"    ->', shop.columns[shop.dtypes == "str"].tolist())
```

**Line by line:**

- `shop.dtypes.to_dict()` — printed first so there is no doubt that `item` really is a text column and
  really is present.
- `shop.dtypes == "object"` — a boolean Series with `False` everywhere. It does not raise, it does not
  warn, and `shop.columns[...]` selects nothing from it.
- **The result is `[]`, and `[]` is a valid answer to a valid question.** Nothing downstream can tell
  the difference between "there are no text columns" and "I asked the wrong question".
- `shop.dtypes == "str"` — the same expression with the name updated, finding `item` as it should.

```text
dtypes: {'item': <StringDtype(na_value=nan)>, 'need': dtype('int64')}
dtypes == "object" -> []
dtypes == "str"    -> ['item']
```

The silent failure in its natural habitat — a cleaning loop:

```python
import pandas as pd

shop = pd.DataFrame({"item": ["  milk ", "BREAD "], "need": [2, 1]})
cleaned = 0
for name in shop.columns[shop.dtypes == "object"]:
    shop[name] = shop[name].str.strip().str.lower()
    cleaned += 1
print(f"cleaned {cleaned} text columns")
print(repr(shop["item"].tolist()))
```

**Line by line:**

- The loop body is correct. `strip` and `lower` are the right operations and they would work perfectly
  if they ever ran.
- `shop.columns[shop.dtypes == "object"]` is empty, so **the loop body never executes**.
- `cleaned` stays at 0, and the report says "cleaned 0 text columns" — which is technically true and
  reads like success. On a wider frame with a dozen text columns the message is identical.
- `repr(...)` on the values, so the surviving whitespace is visible. Printing them without `repr` shows
  `milk` and looks fine, which is how this survives a casual check
  ([Day 7, 3.3](../../../day-07-strings/parts/03-formatting/3.3-repr-and-the-debugging-f-string.md)).
- The damage is downstream: `'  milk '` and `'milk'` are different labels, so a later join or `groupby`
  splits one item into two ([Day 28, 4.4](../../../day-28-selection-and-alignment/parts/04-alignment/4.4-the-index-is-the-join-key.md)).

```text
cleaned 0 text columns
['  milk ', 'BREAD ']
```

`select_dtypes`, which does warn:

```python
import pandas as pd

shop = pd.DataFrame({"item": ["milk", "bread"], "need": [2, 1]})
print('select_dtypes("object") ->', shop.select_dtypes("object").columns.tolist())
print('select_dtypes("str")    ->', shop.select_dtypes("str").columns.tolist())
```

**Line by line:**

- `select_dtypes("object")` — still returns `['item']`, because pandas kept the old behaviour on purpose
  for one release cycle. **It also prints the warning shown below**, which is the only reason this
  spelling is survivable.
- `select_dtypes("str")` — the same answer with no warning, and the form to write.
- Both return a **DataFrame**; `.columns.tolist()` is only here to print compactly.
- The asymmetry is worth holding on to: `select_dtypes` gets a compatibility shim and a warning, while
  the bare `dtypes ==` comparison gets neither, because pandas cannot intercept an equality test between
  a Series and a string.

```text
select_dtypes("object") -> ['item']
select_dtypes("str")    -> ['item']
```

with, on standard error:

```text
Pandas4Warning: For backward compatibility, 'str' dtypes are included by select_dtypes when 'object'
dtype is specified. This behavior is deprecated and will be removed in a future version. Explicitly
pass 'str' to `include` to select them, or to `exclude` to remove them and silence this warning.
See https://pandas.pydata.org/docs/user_guide/migration-3-strings.html#string-migration-select-dtypes
for details on how to write code that works with pandas 2 and 3.
```

Which spelling does what:


The two red boxes are why this document exists. They are the spellings that most code uses.

## When it breaks

**The per-column check, which is the other silent one:**

```text
$ uv run python -c "
import pandas as pd
shop = pd.DataFrame({'item': ['  milk ', 'BREAD '], 'need': [2, 1]})
print('list-comp == object :', [c for c in shop.columns if shop[c].dtype == object])
print('is_object_dtype     :', [c for c in shop.columns if pd.api.types.is_object_dtype(shop[c])])
print('select include list :', shop.select_dtypes(include=['object']).columns.tolist())
" 2>/dev/null
list-comp == object : []
is_object_dtype     : []
select include list : ['item']
```

**What it means.** Three spellings of the same intention, and they no longer agree. The two that ask a
column directly — comparing `dtype` against the built-in `object`, and the `is_object_dtype` helper —
both return nothing and say nothing. Only the `select_dtypes` route gets the compatibility shim, and it
gets it in both the bare-string and list forms.

`is_object_dtype` is the cruel one here, because reaching for a `pandas.api.types` helper is exactly
the defensive habit that usually protects you. It is behaving correctly: it answers "is this the
`object` dtype", and the honest answer is no. The helper that asks the question you meant is
`is_string_dtype`, and the difference between the two names is the whole bug.

**The assertion that passed for the wrong reason:**

```text
$ uv run python -c "
import pandas as pd
shop = pd.DataFrame({'item': ['milk', None], 'need': [2, 1]})
text_cols = shop.columns[shop.dtypes == 'object']
assert not shop[text_cols].isna().any().any(), 'text columns must have no gaps'
print('validation passed')
"
validation passed
```

**What it means. This is the worst version.** The frame plainly has a missing item name, and the
validation that exists to catch exactly that reports success — because `text_cols` is empty, so
`shop[text_cols]` is a frame with no columns, and `.any().any()` over nothing is `False`
([Day 23, 2.1](../../../day-23-ufuncs-and-statistics/parts/02-statistics/2.1-a-reduction-turns-many-into-one.md)).
A check that cannot fail is worse than no check, because it is also a claim that somebody trusts.
**Every guard written over a dtype-based column selection should assert that the selection is
non-empty**, and that one extra line would have turned this into a loud failure.

**The warning, when it does fire:**

```text
$ uv run python -c "
import pandas as pd
shop = pd.DataFrame({'item': ['milk', 'bread'], 'need': [2, 1]})
print(shop.select_dtypes('object').columns.tolist())
"
<string>:4: Pandas4Warning: For backward compatibility, 'str' dtypes are included by select_dtypes
when 'object' dtype is specified. This behavior is deprecated and will be removed in a future version.
Explicitly pass 'str' to `include` to select them, or to `exclude` to remove them and silence this
warning.
See https://pandas.pydata.org/docs/user_guide/migration-3-strings.html#string-migration-select-dtypes
for details on how to write code that works with pandas 2 and 3.
['item']
```

**What it means.** This is the good outcome: the code still works *and* pandas tells you it will not
forever. `Pandas4Warning` is the class, so a codebase mid-migration can turn exactly this into an error
with `warnings.simplefilter("error", pd.errors.Pandas4Warning)` and find every site in one test run.
Doing that in CI is the cheapest possible migration plan.

## In production

**What a professional writes instead of the teaching version.** A selector that works on both pandas
versions and refuses to select nothing:

```python
import pandas as pd
from pandas.api.types import is_string_dtype


def text_columns(frame: pd.DataFrame, *, required: bool = True) -> list[str]:
    """Names of the text columns, however this pandas version spells the dtype."""
    names = [name for name in frame.columns if is_string_dtype(frame[name])]
    if required and not names:
        raise ValueError(
            f"no text columns found among {frame.dtypes.to_dict()}; "
            "if this frame really has none, pass required=False"
        )
    return names
```

**Line by line:**

- `from pandas.api.types import is_string_dtype` — the **public** helper, under `pandas.api`, which is
  the namespace pandas promises to keep stable. It answers the question without naming a dtype, so it
  survives this change and the next one.
- `is_string_dtype(frame[name])` — asked per column, because the helper takes a column rather than a
  frame.
- `required: bool = True` as a **keyword-only** argument, after the `*`
  ([Day 10, 1.5](../../../day-10-functions/parts/01-the-signature/1.5-keyword-only-and-positional-only.md)), so a call
  site reads `text_columns(df, required=False)` and never `text_columns(df, False)`.
- **The empty check is the whole point of the function.** Returning `[]` is what caused every failure
  above, so the default is to treat it as an error and make the caller say so explicitly when a frame
  legitimately has no text.
- The message prints `frame.dtypes.to_dict()` — the actual dtypes, so whoever reads the error can see
  immediately whether the frame is wrong or the expectation is.
- A caller that genuinely handles the empty case passes `required=False` and gets the old behaviour,
  which keeps the function usable in both situations without a second function.

**What changes at scale.** The migration cost is not writing the fix, it is **finding the sites**, and
that is what the warning class is for. Turning `pd.errors.Pandas4Warning` into an error in CI surfaces
every `select_dtypes("object")` in one run. The bare `dtypes == "object"` comparisons cannot be found
that way, because there is no warning to promote — those need a grep, and `grep -rn "object" --include=
"*.py"` over a large codebase returns mostly noise. The practical approach is to grep for the four
spellings specifically, fix them, and then add the non-empty assertion above so that the *next* silent
selection failure is loud. In a large organisation the far bigger risk is notebooks and scheduled jobs
that nobody greps at all, which is why the assertion matters more than the grep.

**The failure that only appears with real data.** A feature pipeline routed columns to transformers by
dtype: numeric columns to a scaler, `object` columns to a one-hot encoder. After the pandas upgrade the
`object` selector matched nothing, so **every categorical feature was dropped from the model** — not
error, not warning, just a narrower feature matrix. The pipeline trained, the tests passed, and the
model's accuracy fell by a few points, which was inside the range the team had seen from ordinary data
drift. It took two months and an unrelated audit to find. **A model that silently loses features still
produces predictions**, and that is the property that makes this class of bug so expensive: every
downstream signal that something is wrong is a soft one. Asserting the expected column count after
selection — not just the dtype — is what catches it.

**The review comment a senior engineer leaves.** *"This selects `object` columns to decide what to
one-hot encode, and on pandas 3 that is the empty set. Use `is_string_dtype` and assert that the
selection is non-empty, because the failure mode here is a model quietly trained without its
categorical features."*

**The interview question.** *"You upgrade a codebase to pandas 3.0 and the data-cleaning step stops
doing anything, with no error. What would you look at first?"* How the code finds its text columns.
Before 3.0 text fell back to `object`, so `dtypes == "object"` was the standard idiom; in 3.0 text has
its own `str` dtype, so that comparison matches nothing and any loop over the result runs zero times —
silently, because an empty selection is legal. `select_dtypes("object")` still works but warns, so
promoting `Pandas4Warning` to an error in CI finds those sites; the bare comparisons have to be grepped
for. The durable fix is `pandas.api.types.is_string_dtype`, plus an assertion that the selection is not
empty, since that is the check that would have caught the original failure whatever the dtype was
called.
