# 4.5 — `asyncio`: one thread, a queue of paused functions

## One-line answer

One thread, one list of paused functions, and a loop that resumes whichever one is ready — so a thousand
waits cost almost nothing, and any function that *works* instead of waiting stops everything.

---

## The story

The busiest counter in the branch has one clerk and no queue.

Instead there is a numbered ticket rail. You come in, say what you want, and if it needs the depot she
rings them, puts your ticket on the rail, and calls the next person. When the depot rings back she takes
your ticket off the rail and finishes with you.

At any instant she is dealing with exactly one person — she has not been cloned — and there might be forty
tickets on the rail. Forty people are being served, in the sense that all forty pieces of work are in
progress, and none of them is occupying her while it waits.

The rail costs almost nothing. A ticket is a bit of card. Adding a second clerk would mean a second
counter, a second till and a second wage; adding a fortieth ticket means writing a number on some card.

And there is exactly one way to break it. If somebody hands her a shoebox of loose coins to count, she
counts it — and for those four minutes she is not answering the phone, not calling the next person, and
not taking anybody off the rail. One person doing something that is *work* rather than *waiting* stops
the whole room.

---

## The idea in plain language

`asyncio` is concurrency without threads. One thread, one **event loop**, and a collection of functions
that have paused.

The pieces:

- **A coroutine** is what `async def` produces. Calling it does not run it; it makes an object that is
  ready to run — the same idea as a generator
  ([Day 11, 2.1](../../../day-11-iterators-and-generators/parts/02-generators/2.1-yield-the-function-that-pauses.md)),
  which is a function that pauses.
- **`await` is where it pauses.** At an `await`, the coroutine says "I am waiting for this" and hands
  control back to the loop.
- **The event loop** keeps the paused coroutines, watches what they are waiting for, and resumes whichever
  is ready. `asyncio.run(main())` starts one, runs `main` to completion, and stops it.
- **A task** is a coroutine the loop has been told to run *alongside* whatever else is happening —
  `asyncio.create_task(...)`, or the whole group at once with `asyncio.gather`
  ([4.7](4.7-gather-and-twenty-fetches.md)).

The comparison with threads ([4.3](4.3-threads.md)) is worth having in a table, because the two solve the
same problem at very different prices:

| | threads | asyncio |
|---|---|---|
| how many is a lot | hundreds — each one costs memory and switching | tens of thousands |
| who decides when to switch | the operating system, at any moment | **you**, at each `await` |
| race conditions | yes, anywhere | only across an `await` |
| what breaks it | nothing in particular | one blocking call |
| library support | anything | only libraries written for it |

The second row is the one that changes how it feels to write. A thread can be interrupted **between any
two bytecodes** ([4.2](4.2-the-gil.md)), so any shared state can race. A coroutine is only ever
interrupted **at an `await`**, which is a keyword you can see. Code between two awaits runs without
interruption, so most of [4.3](4.3-threads.md)'s race conditions cannot happen — and the ones that remain
are visible, because there is a keyword marking the gap.

The fourth row is the price. **The loop is one thread**, so anything that occupies it — a Python loop, a
`time.sleep`, a `requests.get`, a big `json.loads` — stops every other coroutine dead. That is the
shoebox of coins, and it is the single failure mode of asyncio code
([4.6](4.6-async-await.md)).

The fifth row is the practical constraint: **a library has to be written for it.** `requests` blocks;
`httpx` has an async client. `psycopg` has async support; many drivers do not. Mixing a blocking library
into async code produces something that looks concurrent and runs sequentially, which is the failure in
[4.6](4.6-async-await.md).

**When to choose it over threads**: many concurrent waits — hundreds or thousands — or a library that is
already async. **When not to**: a handful of waits, where a thread pool is simpler; CPU-bound work, where
neither helps ([4.4](4.4-processes.md)); or a codebase where the libraries you need are blocking.

## The mechanism

The smallest thing that shows the rail working:

```python
import asyncio
import time


async def wait_for_depot(name, seconds):
    print(f"  {name}: ringing the depot")
    await asyncio.sleep(seconds)
    print(f"  {name}: they answered")
    return name


async def main():
    start = time.perf_counter()
    results = await asyncio.gather(
        wait_for_depot("bristol", 0.3),
        wait_for_depot("leeds", 0.2),
        wait_for_depot("cardiff", 0.1),
    )
    print("results:", results)
    print(f"elapsed: {time.perf_counter() - start:.2f}s for 0.3 + 0.2 + 0.1 of waiting")


asyncio.run(main())
```

**Line by line:**

- `async def wait_for_depot(...)` — a **coroutine function**. Calling it returns a coroutine object and
  runs none of the body ([4.6](4.6-async-await.md)).
- `await asyncio.sleep(seconds)` — the pause. **`asyncio.sleep`, not `time.sleep`**: this one yields to the
  loop, and the other one blocks it. That single substitution is the most important line in the file.
- `async def main():` — the entry point. Nearly all async programs have one, because `await` is only legal
  inside an `async def` ([4.6](4.6-async-await.md)).
- `await asyncio.gather(...)` — start all three and wait for all three
  ([4.7](4.7-gather-and-twenty-fetches.md)). Results come back **in the order the arguments were given**,
  not in the order they finished.
- `asyncio.run(main())` — **the only line that is not async.** It creates a loop, runs `main` until it
  finishes, and closes the loop. One of these, at the top of the program.

Run on Python 3.12.12 on 2026-09-02:

```
  bristol: ringing the depot
  leeds: ringing the depot
  cardiff: ringing the depot
  cardiff: they answered
  leeds: they answered
  bristol: they answered
results: ['bristol', 'leeds', 'cardiff']
elapsed: 0.30s for 0.3 + 0.2 + 0.1 of waiting
```

**Three things to read off that.**

All three "ringing" lines print before any "answered" — one thread, starting all three, then waiting.

They answer in **duration order**, shortest first, because the loop resumes whichever is ready.

And `elapsed` is 0.30s, not 0.60s: **the longest wait, not the sum.** Meanwhile `results` is in *argument*
order, which is `gather`'s promise and is what makes it usable.

Now the shoebox of coins:

```python
import asyncio
import time


async def blocking(n):
    time.sleep(0.2)  # WRONG: blocks the whole loop
    return n


async def yielding(n):
    await asyncio.sleep(0.2)
    return n


async def main():
    for name, fn in (("time.sleep      ", blocking), ("asyncio.sleep   ", yielding)):
        start = time.perf_counter()
        await asyncio.gather(*(fn(i) for i in range(10)))
        print(f"{name}: {time.perf_counter() - start:.2f}s for 10 tasks of 0.2s each")


asyncio.run(main())
```

**Line by line:**

- `async def blocking(n):` with `time.sleep` inside — **an `async def` that never awaits anything.** It is
  a coroutine by declaration and blocking by behaviour, which is the exact shape of the bug.
- `await asyncio.sleep(0.2)` in the other — the same duration, yielding.
- `asyncio.gather(*(fn(i) for i in range(10)))` — ten of each, started together
  ([Day 8, 1.4](../../../day-08-containers/parts/01-sequences/1.4-unpacking-and-star-rest.md) for the
  `*`).
- the same measurement for both, so the difference is the two sleep calls and nothing else.

```
time.sleep      : 2.01s for 10 tasks of 0.2s each
asyncio.sleep   : 0.20s for 10 tasks of 0.2s each
```

**Ten times slower, from one wrong function name.** `time.sleep` occupies the thread, and there is one
thread, so the other nine tasks cannot run. No error, no warning, and code that reads as concurrent.

The rail:

```mermaid
sequenceDiagram
    participant L as event loop
    participant A as task A
    participant B as task B
    L->>A: run
    A-->>L: await — waiting for the depot
    L->>B: run
    B-->>L: await — waiting for the depot
    Note over L: both on the rail;<br/>the loop is free
    Note over L: B's reply arrives first
    L->>B: resume
    B-->>L: done
    L->>A: resume
    A-->>L: done
```

## When it breaks

**Forgetting `asyncio.run` and calling the coroutine:**

```text
$ uv run python -c "
import asyncio

async def main():
    print('this never prints')

main()
" 2>&1 | tail -3
<string>:6: RuntimeWarning: coroutine 'main' was never awaited
RuntimeWarning: Enable tracemalloc to get the object allocation traceback
```

**What it means.** `main()` built a coroutine object and nothing ran it. The program exits successfully,
prints nothing, and leaves a `RuntimeWarning` that is easy to miss in a busy terminal — and that is
**suppressed by default in some configurations**, in which case there is no output at all.
[4.6](4.6-async-await.md) is this failure in full.

**`asyncio.run` called inside a running loop:**

```text
$ uv run python -c "
import asyncio

async def inner():
    return 1

async def main():
    return asyncio.run(inner())

asyncio.run(main())
" 2>&1 | tail -2
RuntimeError: asyncio.run() cannot be called from a running event loop
sys:1: RuntimeWarning: coroutine 'inner' was never awaited
```

**What it means.** `asyncio.run` creates a loop, and there can be one per thread. Inside async code the
loop already exists, so the call is `await inner()`. This appears when somebody refactors a top-level
script into a function and keeps the `asyncio.run` — and it is the reason `asyncio.run` belongs at the
very top of a program and nowhere else. It is also why the same call fails inside a Jupyter notebook,
which already has a loop running.

**A blocking library in async code:**

```text
$ uv run python -c "
import asyncio, time

async def fetch(n):
    time.sleep(0.2)   # stands in for requests.get, or any blocking client
    return n

async def main():
    start = time.perf_counter()
    await asyncio.gather(*(fetch(i) for i in range(10)))
    print(f'{time.perf_counter() - start:.2f}s - and it looked concurrent')

asyncio.run(main())
"
2.01s - and it looked concurrent
```

**What it means.** Every keyword is right — `async def`, `await`, `gather` — and it runs strictly one at a
time, because the library inside blocks. **This is the most common asyncio bug**, and the only clue is
that the timing does not improve. The rules that prevent it: use async-native libraries, and if you must
call a blocking one, push it onto a thread with `asyncio.to_thread(...)`, which hands it to a worker and
lets the loop carry on.

**A Python loop in a coroutine:**

```text
$ uv run python -c "
import asyncio, time

async def crunch(n):
    total = 0
    for i in range(8_000_000):
        total += i % 7
    return total

async def ping():
    for _ in range(5):
        await asyncio.sleep(0.05)
        print('  ping')

async def main():
    start = time.perf_counter()
    await asyncio.gather(crunch(1), ping())
    print(f'{time.perf_counter() - start:.2f}s')

asyncio.run(main())
"
  ping
  ping
  ping
  ping
  ping
1.73s
```

**What it means.** `ping` was supposed to print five times spread over a quarter of a second, and instead
it printed all five in a burst after `crunch` finished — because `crunch` never awaits, so the loop never
got control back. In a service that is every other request waiting behind one piece of arithmetic. The
fix is `await asyncio.to_thread(crunch, 1)`, or a process pool if it is genuinely heavy
([4.4](4.4-processes.md)).

## In production

**The professional rule is that async code is async all the way down.** One `asyncio.run` at the entry
point, async libraries throughout, and any blocking call explicitly pushed to a thread with
`asyncio.to_thread`. A codebase that mixes the two without saying so has the worst of both: the
complexity of coroutines and the throughput of sequential code.

**What changes at scale is that asyncio's advantage over threads is memory, not speed.** For ten
concurrent waits, threads and asyncio perform about the same and threads are simpler. For ten thousand,
threads are impossible — each has a stack, measured in megabytes — and coroutines are a few hundred bytes
each. That is why every high-concurrency Python server is async, and why a script doing four things does
not need to be.

**The failure that only appears with real data is the coroutine that became CPU-bound.** A handler that
was pure I/O — fetch, hand back — grows a parsing or scoring step, and at small sizes it is invisible.
At real sizes that step takes tens of milliseconds, blocks the loop, and every other request's latency
grows by it. The symptom is a service whose *tail* latency degrades sharply while average throughput looks
fine, and the measurement is [4.1](4.1-waiting-is-not-working.md)'s processor-time ratio applied to the
handler.

**The review comment a senior engineer leaves.** *"This handler calls `requests.get`, which blocks the
event loop for the whole request — so our 'async' service is serving one request at a time. Use the async
client, or wrap it in `asyncio.to_thread`. The load test does not show it because it runs one request at a
time."*

**The interview question.** *"How does asyncio differ from threads?"* One thread and an event loop rather
than many threads: coroutines pause at `await` and the loop resumes whichever is ready, so switching is
cooperative and visible in the source rather than pre-emptive and arbitrary. Two consequences worth
naming: far cheaper per concurrent wait, so tens of thousands are practical; and far fewer race
conditions, because code between two awaits cannot be interrupted. The cost is that one blocking call
stops everything, so the libraries have to be async-native or the blocking call has to be pushed onto a
thread.
