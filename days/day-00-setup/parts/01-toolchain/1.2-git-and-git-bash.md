# 1.2 — Git, and why a Unix shell on a Windows machine

## One-line answer

Git is the program that remembers every version of your work and who wrote it, and installing it on
Windows also gives you **Git Bash** — a Unix-style shell, which is the language every command in
these 241 documents is written in.

---

## The story

Two folders, on two different laptops, on the same team.

The first belongs to someone who has not met version control. It contains
`analysis.py`, `analysis_v2.py`, `analysis_v2_FINAL.py`, `analysis_v2_FINAL_fixed.py`, and
`analysis_USE_THIS_ONE.py`. Somewhere among those five files is the version that produced the number
in last quarter's report. Nobody knows which. The person who wrote it does not know which. The
timestamps are useless, because a file was opened and re-saved during the search.

The second folder contains one file: `analysis.py`. It looks like less work has happened in it. In
fact it holds every version that has ever existed, each one labelled with the exact change, the
reason, the author and the moment — and the person sitting at it can bring back the state of the
world on any past date with one command, compare any two versions line by line, and prove which
version produced the report.

Same amount of work. One of them can answer questions about it.

Then, a second scene. That same person opens the terminal that came with their Windows machine and
types the first command from a tutorial: `mkdir -p src/setu`. It fails. They try `touch app.py`.
Nothing called `touch` exists. They try `cat > file <<'EOF'`. A parser error. Every command in the
tutorial is written in a language their terminal does not speak, and they now have two problems to
solve at once — the actual task, and translation.

Installing Git fixes both. It is the memory *and* the common language.

---

## The idea in plain language

**Version control** is the practice of recording your project as a series of snapshots instead of a
single mutable pile of files. **Git** is the program that does it, and it is the one the software
industry standardised on. It is not a website and it is not connected to anything by default — it is
a program on your machine, writing to a hidden folder inside your project. (The website you have
heard of — GitHub — is a place to *host copies* of Git repositories. Git works perfectly with no
account, no network and no company involved. You will use it entirely offline today.)

The word for one snapshot is a **commit**. A commit records what every tracked file contained at that
moment, who made it, when, and a message saying why. Commits are linked in order, so the chain of
them is the history of the project. You will build one at the end of today in
[4.2](../04-first-commit/4.2-the-first-commit.md); how commits actually work underneath is [2.3](../02-skeleton/2.3-git-init-and-what-a-repo-is.md).

Now the second half, which is Windows-specific and worth understanding rather than obeying.

A **shell** is the program that reads what you type in a terminal and runs it. It is not the same
thing as the window it appears in. The shell defines the *language*: what `mkdir -p` means, whether
`&&` chains two commands, how quoting works. There are several, and they are genuinely different
languages, not dialects:

| Shell | Where it comes from | `create folders a/b/c` |
|---|---|---|
| **bash** | the Unix world; the default on Linux, near-universal in CI and servers | `mkdir -p a/b/c` |
| **PowerShell** | Windows | `New-Item -ItemType Directory -Force a/b/c` |
| **cmd.exe** | Windows, much older | `mkdir a\b\c` |

Every server this project ever touches runs Linux. Every CI job in `.github/workflows/` runs on
Linux. Every code example in the wider Python world is written for a Unix shell. So on Windows you
have two options: translate every command for 240 days, or install a Unix shell and stop translating.

**Git Bash** is that shell. The Git for Windows installer bundles a genuine `bash` plus the Unix
commands that go with it — `ls`, `grep`, `cat`, `touch`, `chmod`, `curl` — so a bash command from any
tutorial, any Dockerfile, or any Linux server runs unchanged on your Windows laptop. It is not an
emulator or a virtual machine; it is those programs, compiled for Windows.

> **On macOS or Linux?** You already have a Unix shell — your normal terminal is `bash` or `zsh`, and
> every command in these documents works as written. You still need Git; install it with your package
> manager instead of the Windows installer. Nothing else in these 241 documents changes.

---

## Why Setu needs it

- **Principle 1 says no commit means the day is not done.** The daily gate is `./m done N`, and its
  last act is a `git commit`. Without Git there is no way to finish a day.
- **Every one of these 241 documents is written in bash.** `mkdir -p`, heredocs (`cat > f <<'EOF'`),
  `chmod +x`, `./m` — all of it. The `./m` script you write in section 3 is a bash script and simply
  cannot run under PowerShell.
- **Day 2 puts the same commands into GitHub Actions**, which runs Linux. Commands you have been
  typing all along work there unchanged — that is not a coincidence, it is the reason for this choice.
- **Every commit carries your identity**, which is why you configure it below rather than later. A
  history with `unknown <unknown@localhost>` on it is not a portfolio artifact, and Principle 10 says
  the artifacts are the point.

## The mechanism

**Windows.** Download and run the installer from <https://git-scm.com/download/win>. Accept the
defaults, with one exception: when it asks which editor Git should use for commit messages, choose
one you actually know how to exit. (The default on some builds is `vim`, which is excellent and also
the subject of a long-running joke about people unable to quit it. It is `Esc` then `:q!` then Enter.)

Then open **Git Bash** from the Start menu — not PowerShell, not Command Prompt — and verify:

```bash
git --version
```

**Line by line:**

- `git` — the program itself. That the shell finds it at all is half of what this command proves:
  the installer put it on `PATH`, the folder list from [1.1](1.1-why-one-tool-owns-the-environment.md).
- `--version` — prints the installed version and exits. A trivial command chosen deliberately: it
  touches nothing, so it is safe to run anywhere, and a version number is proof of both installation
  and reachability. If it prints `bash: git: command not found`, the install did not finish or you
  are in the wrong terminal, and nothing else today will work.

macOS: `brew install git` (or Xcode command-line tools). Debian/Ubuntu: `sudo apt install git`.

Now tell Git who you are — this is written into every commit you will ever make:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
```

**Line by line:**

- `git config` — read or write a Git setting. Settings live in plain text files, not a registry or
  database; you can open and read them, which is worth doing once.
- `--global` — write to `~/.gitconfig`, your per-user file, so it applies to every repository on this
  machine. Without it, the setting lands in the current repository only. (`~` means your home folder.)
  There is a third level, `--system`, for the whole machine, which you almost never want.
- `user.name` / `user.email` — the author stamped into every commit. Git does not verify these; they
  are text you supply. Two consequences: your history is only as trustworthy as your habits, and if
  you ever want your commits associated with a hosting account, the **email** must match the one that
  account knows. The name may be anything you are happy to have read back to you in an interview.
- `init.defaultBranch main` — new repositories start on a branch named `main` rather than the older
  `master`. A **branch** is a movable label pointing at a commit; you get one automatically and will
  work on it all year. Setting this now removes a warning that would otherwise appear every time you
  run `git init`.

Confirm all three landed, and see where they live:

```bash
git config --global --list --show-origin | grep -E "user\.|defaultBranch"
```

**Line by line:**

- `--list` — print every setting at this level as `key=value`.
- `--show-origin` — prefix each line with the file it came from. This is the part worth seeing: it
  proves the settings are ordinary text in an ordinary file, and tells you exactly which file to open
  when a setting is not what you expect.
- `| grep -E "user\.|defaultBranch"` — the `|` is a **pipe**: it feeds the left command's output into
  the right command as input. `grep` prints only lines matching a pattern; `-E` selects extended
  regular expression syntax, in which `|` means "or". The `\.` is an escaped dot, matching a literal
  `.` rather than the regex "any character". So: show me only the three lines I just set.

## When it breaks

**The one everyone hits, on their first commit:**

```text
$ git commit -m "day-00: toolchain, skeleton, ./m"
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'me@LAPTOP.(none)')
```

**What it means.** Git refuses to write a commit it cannot attribute. The parenthesised guess —
`me@LAPTOP.(none)` — is Git assembling a fallback address from your username and hostname and
correctly deciding it is not good enough to put in permanent history. Run the two `git config`
commands above and re-run the commit; nothing was lost, the commit simply was not created.

**The Windows-specific one, and it is quiet:**

```text
$ ./m check
bash: ./m: /usr/bin/env^M: bad interpreter: No such file or directory
```

**What it means.** Read the `^M`. Windows ends lines with two characters (carriage return + line
feed, `\r\n`); Unix uses one (`\n`). Git has a setting, `core.autocrlf`, that can rewrite line
endings as files move in and out of the repository. When it converts a shell script, the `\r`
survives on the end of the first line — so the system tries to run an interpreter literally named
`env\r`, which does not exist. The error is telling you the truth; the truth just contains an
invisible character.

The fix, and why it is the right one:

```text
$ git config --global core.autocrlf input
```

`input` means "convert CRLF to LF when committing, but never convert back on checkout" — files stay
Unix-style in your working folder, which is what scripts, Docker images and Linux servers expect. On
macOS and Linux the default is already effectively this. You will meet the same `^M` again the first
time a teammate on Windows edits a `.sh` file without this setting, and now you will recognise it on
sight.

**And the one that is not an error at all:**

```text
$ mkdir -p src/setu
mkdir : A positional parameter cannot be found that accepts argument 'src/setu'.
```

That is PowerShell answering. You are in the wrong terminal. Open Git Bash.

## In production

**Identity is not cosmetic — it is the audit trail.** In a company, `git log` answers questions that
matter: who introduced this line (`git blame`), which change broke the build, who to ask about a
subsystem. Tooling reads the author field to route code review, enforce `CODEOWNERS` rules, and
attribute security findings. A repository where several people committed as `unknown` has lost
information that cannot be recovered, because commits are immutable — rewriting them changes every
commit hash after the edit, which is a coordinated migration, not a fix. Configure it before your
first commit, not after your fiftieth.

**Signed commits.** Because `user.email` is unverified text, anyone can commit as anyone. Serious
repositories therefore require **signed** commits (GPG or SSH keys), so the hosting platform can show
a "verified" badge and reject unsigned pushes to protected branches. You do not need this on Day 0 —
it is the same `git config` mechanism with `user.signingkey` and `commit.gpgsign true` — but you
should know *why* it exists: the author field is a claim, and a signature is the proof.

**Message discipline is machine-readable.** Teams converge on structured commit messages
(`feat:`, `fix:`, `docs:`, a scope, a body) because tools then generate changelogs, decide semantic
version bumps, and link commits to tickets automatically. This project's `./m done N` writes
`day-NN: complete` — a deliberately boring, greppable, machine-parseable convention, which is why
`./m status` can find your last completed day with a single `git log --grep`. Consistency is what
makes history queryable.

**Line endings are a real production incident.** The classic version: a Docker build on a Linux
runner fails with `exec /entrypoint.sh: no such file or directory` even though the file plainly
exists. The cause is CRLF, introduced by a Windows contributor. The professional fix is not to ask
everyone to configure their laptop — it is a `.gitattributes` file committed to the repository:

```text
* text=auto eol=lf
*.sh text eol=lf
*.py text eol=lf
```

That enforces the rule **for the repository**, on every machine, regardless of anyone's personal
settings. Rule of thumb worth carrying: *a convention that lives in someone's laptop configuration
will be broken by the next person to join; a convention committed to the repository will not.*

**Why bash literacy is a professional skill, not a Windows workaround.** Every Dockerfile `RUN` line,
every CI step, every `kubectl exec` into a pod, and every SSH session onto a server is a Unix shell.
Choosing Git Bash today means the commands you type for 240 days are the same commands you will type
into production systems. That transfer is the actual reason for this choice; not having to translate
tutorials is a side benefit.

**The interview question.** *"What does `git config --global` change, and where does it live?"* — an
easy-sounding warm-up that separates people who have memorised commands from people who understand
that Git's configuration is three plain-text files (system, global, repository) resolved in order,
with the most specific winning. Follow-up: *"How would you enforce LF line endings across a team?"*
The answer they want is `.gitattributes`, committed — not an instruction in the README.

## Check yourself

```bash
git --version && git config --global --list --show-origin | grep -E "user\.|defaultBranch|autocrlf"
```

You should see a version number, your name, your email, `main`, and the file each came from. If
`autocrlf` is missing and you are on Windows, set it to `input` now — it costs nothing today and
saves the `^M` hunt later.
