# 1.3 — `uv`, the one binary that owns the environment

## One-line answer

`uv` is a single program that does the four jobs previously split across four tools — install a
Python, create the environment, resolve and lock dependencies, and run your code inside it — which is
exactly the "one owner" that [1.1](1.1-why-one-tool-owns-the-environment.md) said the environment
needs.

---

## The story

Read a Python setup guide written a few years ago and count the tools it asks you to install.

You need `pyenv`, because your project needs Python 3.12 and your machine has 3.11. You need `venv`
to make the isolated folder. You need `pip` to install packages into it. But `pip` only records what
you *asked* for, not the versions of everything those packages dragged in, so you need `pip-tools`
to compile a real lockfile. Then someone mentions that `pip`'s dependency resolver can take a very
long time on a large project, so a colleague suggests `poetry` instead, which replaces three of the
four but has its own project file format and its own opinions.

Five tools. Four configuration files. Two competing standards. And every one of them is itself a
Python package — which means the tools that manage your Python environment are installed *into* a
Python environment, and now you have a chicken-and-egg problem to reason about at 9pm.

None of that complexity was invented carelessly. Each tool solved a real gap, in order, over a
decade. But a beginner does not arrive at the end of that story; they arrive in the middle of it, and
the middle is a mess.

`uv` is the consolidation. One executable, written in Rust, that contains all four jobs. It is not a
Python package, so it has no bootstrap problem. It reads and writes the standard project file that
the Python packaging standards define, so it is not a private dialect. And it is fast enough that the
old workflows' pauses simply stop being part of your day.

You will type `uv` several thousand times over 240 days. You will not type `pip`, `venv`, `pyenv` or
`poetry` even once.

---

## The idea in plain language

Start from zero. A **package** is a reusable piece of code someone else wrote and published — pandas,
NumPy, pytest. A **package manager** is the program that fetches packages and puts them somewhere
your interpreter can find them (the `site-packages` folder from
[1.1](1.1-why-one-tool-owns-the-environment.md)).

The job is less trivial than it sounds, because packages depend on other packages. Ask for pandas and
you also need NumPy, and something that parses dates, and something that handles time zones — and
each of those has its own requirements, with version constraints that must all be satisfied
simultaneously. Working out one set of versions that satisfies every constraint at once is called
**dependency resolution**, and it is a genuine search problem, not a download.

Here are the four jobs, stated plainly, and who used to do each:

| The job | In plain words | Old tool | Now |
|---|---|---|---|
| Get a Python | put an interpreter of a specific version on this machine | `pyenv`, installers | `uv python install` |
| Make an environment | create the private folder that holds this project's packages | `venv` | `uv` (automatic) |
| Resolve and install | choose versions satisfying every constraint, fetch them, record them | `pip` + `pip-tools` | `uv add` |
| Run code in it | execute a command against *this* project's interpreter | `activate` then `python` | `uv run` |

Two properties make `uv` different in kind rather than degree, and both matter to this project:

**It is a standalone binary.** `uv` is not written in Python and is not installed by `pip`. It is one
compiled executable that depends on nothing. So it can install a Python for you without needing a
Python to run — the bootstrap problem disappears.

**It writes a lockfile by default.** Every `uv add` updates `uv.lock`, which records the exact
resolved version of *every* package in the tree — including the ones you never named — plus
cryptographic hashes of the files. That file is committed to Git, and from it anyone can rebuild your
environment byte-for-byte. This is Principle 4 (*pin everything*) made mechanical rather than
aspirational. You will look inside that file in [2.4](../02-skeleton/2.4-uv-init-pyproject-and-the-lockfile.md).

One more idea to retire early. In the old workflow you would **activate** an environment — a command
that edits `PATH` in your current shell so that `python` means this project's Python. It works, but
it is stateful and invisible: a forgotten activation is another way to run the wrong interpreter.
`uv run <command>` does the same thing without the state, per command. There is no mode to be in and
no mode to forget. [2.5](../02-skeleton/2.5-the-venv-you-never-activate.md) is entirely about that shift.

## Why Setu needs it

- **Principle 4 requires a committed lockfile.** `uv` produces one as a side effect of ordinary use,
  so there is no separate step to remember and no way to drift.
- **Principle 5 is zero budget, and the currency is your own time and RAM.** Over 240 days you will
  create and rebuild environments many times; a resolver that is slow is a tax you pay repeatedly.
- **Day 1's entire job is to re-verify every version pin against live PyPI and freeze it.** That day
  is written assuming `uv add` semantics: install, pin, and lock in one action.
- **Day 2 puts this in CI.** A single binary with no Python prerequisite is trivial to install in a
  GitHub Actions job, and the same lockfile that builds your laptop's environment builds CI's — which
  is what makes "works on my machine" a checkable claim rather than an excuse.

## The mechanism

**macOS / Linux / Git Bash on Windows:**

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

**Line by line:**

- `curl` — a program that fetches a URL. It comes with Git Bash.
- `-L` — **follow redirects.** Download URLs commonly redirect to a CDN; without this you save the
  redirect page instead of the file.
- `-s` — **silent**: no progress meter. Wanted here because the output is being piped, and a progress
  bar in a pipe is noise.
- `-S` — **show errors anyway.** `-s` alone silences real failures too; `-sS` together mean "quiet on
  success, loud on failure", which is what you actually want in any script.
- `-f` — **fail on HTTP errors.** Without it, a 404 makes `curl` exit successfully having downloaded
  an HTML error page — which the next stage would then execute as a shell script. This flag is the
  difference between a failed download and running a web server's error page as code.
- `| sh` — pipe the downloaded text into the shell to run it. **Piping the internet into a shell
  deserves suspicion in general**, which is why the URL is written out in full here rather than
  shortened: `astral.sh` is the official installer domain for `uv`. If you would rather read before
  running — a good instinct — drop the pipe, save the file, open it, then run it.

Windows without Git Bash (PowerShell), for completeness:

```text
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

Now **close Git Bash and open it again**, then:

```bash
uv --version
```

**Line by line:**

- Reopening the shell is not optional. The installer appends `uv`'s folder to `PATH`, and **a shell
  reads `PATH` once, when it starts.** Your already-open window is still holding the old list. This
  is the single most common "the installer lied to me" moment, and it is not the installer's fault —
  it is the fact from [1.1](1.1-why-one-tool-owns-the-environment.md) doing exactly what it always does.
- `uv --version` — proves the binary exists and is reachable. Same reasoning as `git --version`:
  harmless, and it answers both questions at once.

Look at what you just installed:

```bash
which uv && uv --help | head -20
```

**Line by line:**

- `which uv` — the full path of the binary that will run. Note there is no `site-packages` anywhere in
  it: `uv` lives outside every Python environment, which is precisely why it can manage them all.
- `&&` — run the right-hand command **only if the left one succeeded** (exit status zero). Every
  program returns a number when it ends; zero means success by convention. You will use `&&` all year
  to stop a sequence at the first failure.
- `uv --help` — the command list. Reading it once now is worth more than looking up each command
  later; you will recognise `add`, `run`, `sync`, `lock`, `python`.
- `| head -20` — print only the first 20 lines. `head` truncates output; without it the help text
  scrolls past. (This is a line count, not a duration.)

## When it breaks

**Immediately after installing:**

```text
$ uv --version
bash: uv: command not found
```

**What it means.** Almost always the un-reopened shell. Close the window, open a new Git Bash, try
again. If it still fails, the installer's `PATH` edit did not apply to this shell's startup file —
check where it landed and confirm the folder is listed:

```text
$ ls ~/.local/bin/uv
$ echo "$PATH" | tr ':' '\n' | grep -n "local/bin"
```

If the binary is there but the folder is not in `PATH`, you can call it by full path once
(`~/.local/bin/uv --version`) to confirm it works, then fix your shell profile — the installer prints
which file it modified.

**Behind a corporate proxy or a filtered network:**

```text
$ curl -LsSf https://astral.sh/uv/install.sh | sh
curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed
```

**What it means.** The TLS handshake was intercepted or blocked — typically a proxy that presents its
own certificate, which `curl` correctly refuses to trust silently. The wrong fix is disabling
certificate verification (`-k`); that turns a detected interception into an undetected one. The right
fix is to install the corporate root certificate, or to download the release archive from the
project's GitHub releases page over the browser your organisation has already configured, and unpack
the binary yourself. `uv` is a single file, so "download it manually" is a complete solution.

**And the one that is not `uv`'s fault at all:**

```text
$ uv add pandas==3.0.1
error: Distribution `pandas==3.0.1` can't be installed because it doesn't have a source
distribution or wheel for the current platform
```

**What it means.** The version exists, but not for your Python version, operating system, or CPU
architecture. **A wheel** is a pre-built package file, and it is built for specific combinations —
`cp312` (CPython 3.12) on `win_amd64`, and so on. The fix is a compatible version, not a compatible
belief; `uv add "pandas>=3"` briefly, read what it resolved, then pin *that* exactly. This is also the
first hint of why [1.4](1.4-python-3-12-under-uv.md) picks its Python version deliberately rather
than taking the newest.

## In production

**Why the resolver's speed changes behaviour, not just comfort.** A dependency resolve that is slow
is one that gets skipped. Teams start caching aggressively, reusing stale virtual environments, and
adding `--no-deps` to "make it quick" — each of which quietly breaks reproducibility. When creating a
fresh, fully-resolved environment is cheap, the correct habit (rebuild from the lockfile) becomes the
convenient one. Tooling that is fast enough changes what people actually do, and that is worth more
than the elapsed wall-clock saving.

**A single static binary is a deployment property.** In a container image, `pip` requires a Python
interpreter to exist before it can install anything, so the base image, its system Python, and its
`pip` version all become part of your build's inputs. `uv` is one file you can `COPY` in — the
official images ship a `/uv` binary precisely so a multi-stage build can install dependencies in a
builder stage and copy only the resulting environment into a slim runtime image. Fewer inputs means
fewer things that can silently differ between your laptop and production.

**The lockfile is a security artifact, not just a convenience.** `uv.lock` records hashes, so an
install verifies that the file it downloaded is byte-identical to the one that was resolved. That
defends against a compromised mirror or a package re-uploaded under the same version. It is also the
input to vulnerability scanning: when a CVE is announced for a transitive dependency three levels
down, the question "are we affected, and in which services?" is answered by grepping lockfiles. A
project without one cannot answer it.

**The professional's version of `uv run`.** In CI and in containers, the two commands that matter are
`uv sync --locked` (build the environment from the lockfile exactly, and **fail** if the lockfile
disagrees with `pyproject.toml` rather than silently updating it) and `uv run --no-sync <cmd>` (run
without re-checking). `--locked` is the important one: it converts "someone edited dependencies and
forgot to commit the lock" from a mystery into a build failure with a clear message. Do not confuse
it with `--frozen`, which *skips* the up-to-date check rather than enforcing it. This is the
general shape of good production tooling — make the wrong state loud and early.

**The review comment a senior engineer leaves.** On a pull request that changes `pyproject.toml` but
not `uv.lock`: *"Lockfile not updated — CI will resolve differently from your laptop. Run the add
through the tool and commit both files."* And on a Dockerfile using `pip install` with a
`requirements.txt` that has no hashes: *"This build is not reproducible; two builds of the same
commit can produce different images."*

**The interview question.** *"What is the difference between `pyproject.toml` and a lockfile, and why
do you commit both?"* The answer they are listening for: the project file states your **intent**
(direct dependencies and their acceptable ranges), the lockfile records the **resolution** (every
transitive package, exact version, with hashes). You commit both because intent is what a human
edits and the resolution is what a machine must reproduce — and because without the second, "it
worked yesterday" is not something you can prove or restore.
