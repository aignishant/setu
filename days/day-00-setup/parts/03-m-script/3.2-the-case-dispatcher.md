# 3.2 — The `case` dispatcher, and why `./m` has one

## One-line answer

`./m` is a single script whose whole body is one `case` statement that reads the first argument and
picks a branch — which is how five different daily commands live in one file and one word of muscle
memory.

---

## The story

A team's repository has a `scripts/` folder. Inside: `run_tests.sh`, `run-tests-fast.sh`,
`lint.sh`, `check_all.sh`, `ci_check.sh`, `setup_env.sh`, `setup.sh`.

Nobody knows which are current. `check_all.sh` and `ci_check.sh` overlap but not exactly, and the
difference is three lines that nobody can explain. Two of the scripts have not run successfully in a
year, but nothing deletes them because nothing proves they are dead. When a new person joins, the
onboarding document lists four of the seven, and the other three are discovered by accident.

Down the corridor, a different team has one file called `run`. Typing `./run` with no arguments prints
the list of things it can do. There is exactly one place to look, exactly one place to add a command,
and the list of commands cannot drift from reality because the list *is* the implementation.

The second team is not more disciplined. They made one structural decision — a single entry point —
and the discipline followed from it, because there was nowhere else to put anything.

That decision costs about fifteen lines of bash, and you are about to write them.

---

## The idea in plain language

Three ideas, each small, that together make a command-line tool.

**Positional parameters.** When you run `./m start 4`, bash makes the arguments available inside the
script as numbered variables: `$0` is the script's own name, `$1` is `start`, `$2` is `4`. They are
positional — meaning identified by *where* they appear, not by a name — which is why `./m 4 start`
would be nonsense.

**The `case` statement.** Bash's multi-way branch. It compares one value against a list of patterns
and runs the first matching block:

```text
case "$WORD" in
  hello)  echo "hi" ;;
  bye)    echo "goodbye" ;;
  *)      echo "I do not know that word" ;;
esac
```

Three things to notice, because they are unlike most languages. The block ends with `;;` rather than
falling through to the next one. `*` is a wildcard matching anything, so it serves as the default
case — and it must come last, since the first match wins. And `esac` is `case` backwards, which is
bash's convention for closing a block (`if` closes with `fi` for the same reason).

The patterns are **glob patterns**, not regular expressions — the same syntax as filenames, so
`start|begin)` matches either word and `s*)` matches anything beginning with `s`. That makes command
aliases free.

**Functions.** A named block you can call, defined as `name() { ... }`. Two things about bash
functions that surprise people coming from other languages: their arguments are also `$1`, `$2`
(shadowing the script's), and they return an **exit status**, not a value. To get output from a
function you print it and capture that with `$( )` — the command substitution from
[2.3](../02-skeleton/2.3-git-init-and-what-a-repo-is.md).

Put the three together and you have a **subcommand dispatcher**: one executable, many verbs. It is
the shape of `git commit`, `docker run`, `uv add` — and the reason that shape is everywhere is the
story above. One entry point means one place to look, one place to extend, and a help listing that
cannot go stale.

One more decision worth stating, because it looks arbitrary and is not. **The default case is help.**
Running `./m` with no arguments prints the usage rather than doing something or failing silently. A
tool that explains itself when invoked bare is a tool people can use without documentation — and for
a script you will run for 240 days, the day you forget an argument is a certainty, not a risk.

## Why Setu needs it

- **Principle 1 is a daily habit**, and habits survive on low friction. `./m start 4`, `./m check`,
  `./m done 4` is three words to remember for 240 days. Seven script names is not a habit; it is a
  lookup.
- **`./m done N` is the gate that enforces Principle 1 and Principle 7**
  ([3.3](3.3-the-done-gate.md)). A gate has to be one obvious thing, or it gets routed around.
- **Day 2 adds CI**, which calls `./m check`. The same entry point runs on your laptop and on
  GitHub's runner, so there is no second implementation to drift — the same argument as bash in
  [1.2](../01-toolchain/1.2-git-and-git-bash.md) and `uv run` in
  [2.5](../02-skeleton/2.5-the-venv-you-never-activate.md).
- **`make` is not installed on Windows.** This script replaces it, which is why nothing in these 241
  documents ever mentions a `Makefile`.

## The mechanism

Write the script. This is the version for today; it grows as the project does.

```bash
cat > m <<'EOF'
#!/usr/bin/env bash
# Project Setu daily driver. Replaces `make` (not installed on Windows).
set -euo pipefail

DAY="${2:-}"
pad() { printf "%02d" "$1"; }

daydir() {
  local n="$1"
  if [ -d "days/day-$(pad "$n")" ]; then echo "days/day-$(pad "$n")"
  elif [ -d "days/day-$n" ]; then echo "days/day-$n"
  else echo ""; fi
}

case "${1:-help}" in
  start)
    [ -z "$DAY" ] && { echo "usage: ./m start <day>"; exit 1; }
    D="$(daydir "$DAY")"
    [ -n "$D" ] || { echo "no lesson written yet for day $DAY"; exit 1; }
    echo "-> open $D/LESSON.md"
    ;;
  scaffold)
    [ -z "$DAY" ] && { echo "usage: ./m scaffold <day>"; exit 1; }
    mkdir -p "days/day-$(pad "$DAY")/lab"
    echo "-> created days/day-$(pad "$DAY")/lab"
    ;;
  check)
    uv run ruff check .
    uv run ruff format --check .
    uv run python -m pytest -q -m "not live"
    echo "OK all green"
    ;;
  *)
    cat <<'USAGE'
usage: ./m <command> [day]

  start N        point at day N's lesson
  scaffold N     create days/day-NN/lab/
  check          ruff + ruff format + offline pytest
USAGE
    ;;
esac
EOF
chmod +x m
```

**Line by line:**

- `#!/usr/bin/env bash` and `set -euo pipefail` — the shebang and strict mode from
  [3.1](3.1-set-euo-pipefail.md). Line one and line three of every script you write from now on.
- `DAY="${2:-}"` — the second argument, defaulting to empty. Without `:-` this would trip `-u` the
  moment anyone ran `./m check` with no day, which is most of the time. This is
  [3.1](3.1-set-euo-pipefail.md)'s "unbound variable" fix, applied before it can happen.
- `pad() { printf "%02d" "$1"; }` — a function turning `4` into `04`. `printf` formats text;
  `%02d` means "a **d**ecimal integer, at least **2** wide, **0**-padded". This exists so `day-04`
  sorts next to `day-05` rather than after `day-40` — an alphabetical sort puts `day-4` after
  `day-39`, which is exactly the kind of small wrongness that becomes annoying at scale.
- `daydir()` — resolves a day number to its folder, tolerating both `day-04` and `day-4`. It handles
  the fact that Day 0 lives in `day-00-setup` at the call site rather than complicating the helper.
- `local n="$1"` — **`local` makes the variable scoped to the function.** Without it, every variable
  in bash is global, so a function would silently overwrite a variable of the same name in the caller.
  This is the single most important habit in bash function-writing.
- `[ -d "<path>" ]` — the **test** command: true if the path exists and is a **d**irectory. `[ -z
  "$X" ]` is true if `X` is empty (**z**ero length); `[ -n "$X" ]` is true if it is **n**on-empty.
  The quotes are not optional: with an empty, unquoted variable the test collapses to `[ -z ]`, which
  is a syntax error.
- `case "${1:-help}" in` — dispatch on the first argument, **defaulting to `help`**. So a bare `./m`
  falls through to `*)` and prints usage rather than erroring — the decision from the section above,
  expressed in seven characters.
- `[ -z "$DAY" ] && { ...; exit 1; }` — if no day was given, print usage and exit non-zero. The
  braces group multiple commands into one unit; the semicolon before `}` is **required** by bash's
  grammar and is a common source of confusion the first time. Exiting non-zero matters: a wrapper
  script or CI must be able to tell that this failed.
- `D="$(daydir "$DAY")"` — command substitution, capturing the function's printed output. The nested
  quotes are correct and necessary: the inner pair protects `$DAY`, the outer pair protects the
  result.
- `[ -n "$D" ] || { ...; exit 1; }` — `||` runs the right side only on failure, from
  [2.5](../02-skeleton/2.5-the-venv-you-never-activate.md). Read it as "either we have a directory, or bail".
- Each `uv run` in `check` — the no-activation rule from
  [2.5](../02-skeleton/2.5-the-venv-you-never-activate.md). A script inherits no shell state, so every command
  names its environment.
- `-m "not live"` — skip tests marked `live` (ones that hit a real API). CI runs this, so your
  free-tier quota is never spent by a test run — Principle 5, enforced by a flag.
- `*)` with a nested heredoc — the default branch, printing usage. A heredoc inside a heredoc works
  because the markers differ (`USAGE` inside `EOF`); reusing the same marker would end the outer one
  early, which is a genuinely confusing bug to hit.
- `chmod +x m` — **ch**ange **mod**e, adding the e**x**ecutable bit, so `./m` runs the file rather
  than reporting a permission error. Without it you would need `bash m` every time.

Run it three ways:

```bash
./m && ./m check && ./m start 99
```

**Line by line:**

- `./m` — bare, so `${1:-help}` supplies `help` and you get the usage listing.
- `./m check` — runs ruff and pytest against an empty project. It should pass trivially and print
  `OK all green`; there is nothing to lint and nothing to test yet, and a gate that is green on an
  empty project is a gate you can trust to go red later for a real reason.
- `./m start 99` — a day that does not exist, so `daydir` returns empty and the script exits 1. The
  `&&` chain therefore stops here, which is the correct behaviour and worth seeing once.

## When it breaks

**The permission error, on the very first run:**

```text
$ ./m check
bash: ./m: Permission denied
```

**What it means.** The executable bit is not set — `chmod +x m` was skipped, or the file was deleted
and recreated (permissions belong to the file, not the name, so recreating loses them). `ls -l m`
shows the mode: `-rw-r--r--` lacks the `x` that `-rwxr-xr-x` has. Fix with `chmod +x m`, and note
that Git records this bit, so committing it once means everyone who clones gets an executable script.

**The `case` block that runs the wrong branch:**

```text
$ ./m status
usage: ./m <command> [day]
  ...
```

**What it means.** `status` is not a pattern in the `case`, so it fell through to `*)`. This is
correct behaviour meeting an incomplete script — you are about to add `status` and `done` in
[3.3](3.3-the-done-gate.md). It is worth seeing, because it demonstrates the property that makes this
structure safe: **an unknown command produces help, never a partial action.** Compare with a script
that runs a chain of steps and stops halfway.

**The missing `;;`, which produces the strangest symptom in this part:**

```text
$ cat -A m | sed -n '20,24p'
  scaffold)$
    mkdir -p "days/day-$(pad "$DAY")/lab"$
  check)$
```

and then:

```text
$ ./m scaffold 4
-> created days/day-04/lab
error: Failed to spawn: `ruff`
```

**What it means.** Without the `;;` terminator, bash reports a syntax error at the next pattern —
or, in some arrangements, the block simply does not end where you think it does and adjacent commands
run. `cat -A` displays a `$` at each line end, which is how you *see* structure that is otherwise
invisible (it is also how you would spot the `^M` from [1.2](../01-toolchain/1.2-git-and-git-bash.md)). Every
branch ends with `;;`, without exception.

**And the quoting bug that only appears on someone else's machine:**

```text
$ ./m start 4
./m: line 12: [: too many arguments
```

**What it means.** A variable containing a space was expanded unquoted, so the shell split it into
several words and `[` received more arguments than it expects. On a path like
`/c/Users/Firstname Lastname/Projects` this is guaranteed; on a path without spaces it never happens,
which is why it shows up on a colleague's laptop rather than yours. **Quote every variable
expansion, always** — every `"$DAY"`, `"$D"` and `"$1"` in the script above is deliberate, not
decorative.

## In production

**The single-entry-point pattern is everywhere, under different names.** `make`, `just`, `task`,
`npm run`, `cargo`, and thousands of repositories with a `./scripts/dev` or `./bin/run`. They exist
because the story's seven-script folder is the default outcome, and the fix is structural. When you
join a codebase, finding its entry point is the fastest way to learn what the team actually does
daily — and if there is not one, adding it is high-value, low-risk work.

**The rule that makes it hold: CI calls the same entry point.** If your pipeline duplicates the lint
and test commands in YAML instead of calling `./m check`, the two will drift, and you will get the
worst version of that — a build that fails in CI for something you cannot reproduce locally, or vice
versa. One implementation, two callers. This is the reason `./m check` exists as a named command
rather than being three lines you happen to type.

**Argument parsing has a ceiling.** Positional arguments are fine for a fixed shape like
`./m done 4`. As soon as you need flags — `--verbose`, `--dry-run`, optional values — hand-rolled
parsing becomes a bug farm, and bash's `getopts` (or moving to Python) is the answer. The related
professional habit is `--dry-run` on anything destructive: print what would happen without doing it.
`./m done` is destructive in the sense that it commits, which is why its safety comes from refusing
rather than from a flag ([3.3](3.3-the-done-gate.md)).

**Idempotency is a design property, not an accident.** `./m scaffold 4` uses `mkdir -p`, so running
it twice is harmless — the same reasoning as [2.1](../02-skeleton/2.1-the-folder-skeleton.md). Operational
scripts get re-run constantly: after a failure, by a retry, by a person who is not sure whether the
first run worked. A script that is safe to re-run is a script people will re-run when they should,
instead of guessing.

**Exit codes are the tool's contract with everything that calls it.** Zero for success, non-zero for
failure — that is what `&&`, CI, and schedulers read. The story in
[3.1](3.1-set-euo-pipefail.md) was a script that returned zero while failing. Every early exit in
`./m` is `exit 1` for exactly this reason, and returning the *right* status is more important than
printing a good message, because only one of the two is machine-readable.

**The review comment a senior engineer leaves.** On a pull request adding an eighth script to
`scripts/`: *"Can this be a subcommand of the existing entry point? We already have three scripts
that do overlapping things."* And on a dispatcher with no default branch: *"A typo'd command should
print usage, not silently do nothing — add a `*)` case."*

**The interview question.** *"How do you keep local development commands and CI from drifting
apart?"* The answer they want is the structural one: a single entry point in the repository that
both a developer and the pipeline invoke, so there is one implementation of "run the checks". If you
add that the entry point should be self-documenting when run bare, and that its exit status is what
CI actually consumes, you have described the whole of this part without needing the word `case`.
