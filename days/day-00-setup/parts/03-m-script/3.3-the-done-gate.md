# 3.3 — The `done` gate, and why a checklist you can skip is decoration

## One-line answer

`./m done N` refuses to commit while any checkbox in the day's `CHECKLIST.md` is unticked or any
check is red — and that refusal, not the checklist, is what makes the day's definition of done real.

---

## The story

A team writes a definition of done. It is a good one: tests pass, the linter is clean, the change is
documented, a second person has read it. It goes on the wiki. Everyone agrees with it.

Six months later, roughly a third of merged changes meet it. Not because anyone decided to stop —
nobody decided anything. It went like this: a release was urgent, so one change went in with the
documentation "to follow". That was reasonable, and it was fine. The next time, the precedent
existed. Then someone new joined, read the code rather than the wiki, and learned the definition of
done from what they saw merged. Within two quarters the written standard and the actual standard were
different documents, and only one of them was enforced.

Down the corridor, a different team has a shorter definition of done and a script that will not
commit until it holds. Their standard has not moved in two years. Not because they are more
disciplined — because on the urgent day, the path of least resistance was to satisfy the check rather
than to argue with it.

The difference is not the quality of the list. It is that one of them is enforced by a machine that
does not have a bad week.

---

## The idea in plain language

A **gate** is a check that must pass before something can proceed, where "must" is enforced
mechanically rather than socially. The distinction from a *reminder* is the whole idea:

| | Reminder | Gate |
|---|---|---|
| Form | a list, a wiki page, a comment | a program that returns non-zero |
| On a bad day | skipped | still blocking |
| Drifts | yes, silently | no |
| Costs | nothing to ignore | something to bypass |

`./m done 4` is a gate with three conditions, checked in order:

1. **No unticked checkboxes** in `days/day-04/CHECKLIST.md`.
2. **`./m check` is green** — linting, formatting, and the offline tests.
3. Only then: stage everything and commit.

Condition one is mechanically simple. A Markdown checkbox is the literal text `- [ ]` when unticked
and `- [x]` when ticked, so "are there unticked boxes?" is a search for a fixed string. The gate is
a `grep`, and `grep`'s exit status — zero when it found a match, one when it did not — is exactly the
signal needed. That is the trick worth remembering: **the check is trivial; the value is entirely in
the refusal.**

Why does refusal work when a reminder does not? Because the moment where standards actually erode is
the moment where the correct action costs more than the incorrect one. A reminder loses that moment
every time. A gate wins it, because the cheapest way forward is through the check. The gate does not
require you to be conscientious at 11pm; it requires you to be conscientious at the point where you
wrote the check, when you were calm.

Two honest caveats, stated now so you understand what kind of tool this is:

**A local gate can be bypassed.** You could run `git commit` directly. The gate is not a security
control; it is a **default**, and defaults are powerful precisely because deviating from them is a
deliberate act rather than a drift. In a team, the authoritative version of this check lives in CI,
where it cannot be skipped — the same local-convenience-versus-authoritative-gate split as
[1.5](../01-toolchain/1.5-the-editor-and-the-interpreter-trap.md)'s formatter and
[2.3](../02-skeleton/2.3-git-init-and-what-a-repo-is.md)'s hooks.

**A gate is only as good as its checks.** If the checklist is vague, the gate enforces vagueness
punctually. This is why every day's checklist has a "break it, watch it go red, fix it" box: it makes
you prove the test *can* fail, which is Principle 7 turned into an action rather than an intention.

---

## Why Setu needs it

- **Principle 1: no commit, no day.** `./m done N` is the only way a day is marked complete, and the
  commit it writes is what `docs/TRACKER.md` and `./m status` read. Progress therefore cannot be
  claimed, only demonstrated.
- **Principle 7: evals before features.** The gate runs the tests. A day whose test can never go red
  has not met the principle, and the checklist box that forces you to break it on purpose is how
  that gets caught.
- **240 days is long enough for standards to drift**, and the story above is what drift looks like.
  The gate is the answer to "how will you still be doing this properly on Day 180?"
- **Day 2 puts `./m check` into GitHub Actions**, making the same conditions authoritative rather
  than local — the point at which this stops being a personal habit and becomes an engineering
  control.

## The mechanism

Add the last two branches to `./m`. Open the file and insert these before the `*)` default case:

```bash
  status)
    uv run python scripts/tracker.py --summary 2>/dev/null \
      || git log --oneline --grep='^day-' -1 --pretty='last completed: %s'
    ;;
  done)
    [ -z "$DAY" ] && { echo "usage: ./m done <day>"; exit 1; }
    D="$(daydir "$DAY")"
    [ -n "$D" ] || { echo "no day folder for $DAY"; exit 1; }
    C="$D/CHECKLIST.md"
    if grep -q '^- \[ \]' "$C"; then
      echo "FAIL unticked boxes remain in $C"
      grep -n '^- \[ \]' "$C"
      exit 1
    fi
    "$0" check
    git add -A && git commit -m "day-$(pad "$DAY"): complete"
    echo "OK day $DAY committed"
    ;;
```

**Line by line:**

- `status)` — reports progress. It tries the tracker script first and falls back to reading Git
  history, so it works today (when `scripts/tracker.py` does not exist yet) and improves later.
- `\` at the end of a line — a **line continuation**: the command continues on the next line. Used to
  keep a long command readable rather than letting it run off the screen.
- `2>/dev/null` — discard error output, from [2.5](../02-skeleton/2.5-the-venv-you-never-activate.md), so the
  fallback is clean when the script is missing.
- `|| git log ...` — the fallback, running only if the left side failed
  ([2.5](../02-skeleton/2.5-the-venv-you-never-activate.md)).
- `--grep='^day-' -1 --pretty='...'` — find the most recent commit whose message starts with `day-`
  and print it in a custom format. This works **because** the commit message convention below is
  strict; a machine-readable convention is what makes history queryable, which is
  [1.2](../01-toolchain/1.2-git-and-git-bash.md)'s point about message discipline paying off.
- `C="$D/CHECKLIST.md"` — the checklist path, built from the resolved day folder.
- `grep -q '^- \[ \]' "$C"` — **the gate itself.** `-q` is quiet: print nothing, just set the exit
  status. `^` anchors to the start of a line. `\[` and `\]` escape the brackets, because unescaped
  they would mean "a character class" in a regular expression rather than literal brackets. So this
  is: "does any line begin with an unticked checkbox?"
- `if grep -q ...; then` — note that `grep`'s **failure** (finding nothing) is the *success* case
  here. This is also one of [3.1](3.1-set-euo-pipefail.md)'s `set -e` exemptions in action: a command
  in an `if` condition is being tested, so a non-zero status does not exit the script — which is
  exactly what makes this pattern possible.
- `grep -n '^- \[ \]' "$C"` — on failure, print the offending lines **with line numbers** (`-n`). A
  gate that says "no" without saying where is a gate people learn to resent; one that points at the
  line is one they use.
- `exit 1` — refuse, with a non-zero status so any caller can tell.
- `"$0" check` — re-invoke **this same script** with the `check` command. `$0` is the script's own
  path from [3.2](3.2-the-case-dispatcher.md). This is deliberate reuse: there is exactly one
  definition of "green", and `done` calls it rather than repeating it. If `check` fails, `set -e`
  from [3.1](3.1-set-euo-pipefail.md) stops the script before the commit — the two parts combining
  into a property neither has alone.
- `git add -A` — stage **a**ll changes, including deletions and new files.
  [2.2](../02-skeleton/2.2-gitignore-before-secrets-exist.md) is what makes this safe: `-A` would otherwise
  stage `.env`, and that ordering was the entire point of writing the ignore file first.
- `&& git commit -m "day-$(pad "$DAY"): complete"` — commit only if staging succeeded, with the
  zero-padded, greppable message that `status` above depends on.

Now try to pass a gate you should fail:

```bash
mkdir -p days/day-00-setup && printf -- '- [ ] a box nobody ticked\n' > days/day-00-setup/CHECKLIST.md && ./m done 0; echo "exit: $?"
```

**Line by line:**

- `printf -- '...'` — write the file. The bare `--` marks the end of options, so a string starting
  with `-` is treated as data rather than a flag — a small habit that prevents a confusing class of
  error.
- `'- [ ] a box nobody ticked\n'` — one unticked checkbox. `printf` interprets `\n` as a newline,
  which `echo` does not do portably; this is why `printf` is preferred in scripts.
- The gate should print `FAIL unticked boxes remain`, list the line, and exit **1** — and **no commit
  should have been created**. Verify that with `git log --oneline`: it will be empty. Watching the
  gate refuse once is worth more than reading about it, because it converts a claim into something
  you have seen.

## When it breaks

**The gate refusing, which is the gate working:**

```text
$ ./m done 4
FAIL unticked boxes remain in days/day-04/CHECKLIST.md
23:- [ ] break the test, watch it go red, fix it
41:- [ ] say the interview line out loud
exit: 1
```

**What it means.** Exactly what it says, with the line numbers so you can go straight there. The
correct response is to do the two things, not to edit the checkbox. That sentence is the whole
discipline of this part, and it is worth noticing that the gate cannot tell the difference — which is
why the value is in your relationship with it, and why bypassing it costs you the only thing it was
protecting.

**The check failing after the checklist passed:**

```text
$ ./m done 4
src/setu/stats.py:12:1: F401 [*] `math` imported but unused
Found 1 error.
```

**What it means.** All boxes were ticked, so the gate moved to `"$0" check`, and ruff found an unused
import. `set -e` stopped the script there — **before** `git add`. Nothing was committed and nothing
was staged. This ordering is deliberate: the commit is the last statement in the branch, so every
earlier failure leaves the repository untouched.

**The one that is genuinely confusing the first time:**

```text
$ ./m done 4
FAIL unticked boxes remain in days/day-04/CHECKLIST.md
17:- [ ]  extra space after the bracket
```

**What it means.** You ticked it as `- [x]` but the line still matches. Look closely at the pattern:
`^- \[ \]` requires exactly one space inside the brackets. A line written `- [  ]` (two spaces) or
`-  [ ]` (two spaces before the bracket) does not match the *ticked* form either, so it can end up
matching nothing you expect. Markdown renderers are forgiving about this; `grep` is not. Keep to the
exact form `- [ ]` and `- [x]`, which is also what every Markdown viewer renders as a real checkbox.

**And the failure that only appears once you have a remote:**

```text
$ ./m done 4
On branch main
nothing to commit, working tree clean
```

**What it means.** `git commit` failed because there was nothing staged — you had already committed
the work by hand. `set -e` then aborts the script before the success message, so the day is not
marked. Harmless, and a useful demonstration that the gate has no memory: it checks the current
state, every time, and does not know what you did earlier.

## In production

**This is the "definition of done" made executable, and it scales up almost unchanged.** In a team
the same three conditions live in three places: a **pre-commit hook** for instant local feedback, a
**CI pipeline** that runs the authoritative checks on every push, and **branch protection** rules
that refuse to merge a pull request until CI is green and a review is recorded. The local gate is
convenience; branch protection is the one that cannot be bypassed, because it is enforced by the
server rather than by the machine of the person in a hurry. Recognising which layer you are looking
at — and that only the server-side one is a control — is the professional version of this part.

**Fast gates get run; slow gates get bypassed.** This is a real design constraint, not a
nice-to-have. `./m check` runs the linter and the offline tests, which is why `-m "not live"` excludes
anything touching a network. Teams that put a twenty-step integration suite in the pre-commit hook
end up with a team that commits with `--no-verify`. The standard split is: fast checks locally,
everything on the server, and the slowest tier on a schedule. Optimise the gate people meet most
often.

**Gates are a psychological tool as much as a technical one.** The reason they work is that they move
the decision from the moment of weakness (11pm, tired, one box left) to the moment of clarity (when
you wrote the check). This is the same principle behind writing tests before the fix, and behind
`.gitignore` before the secret exists ([2.2](../02-skeleton/2.2-gitignore-before-secrets-exist.md)). If you
notice that framing recurring across this whole day, that is not a coincidence — it is the single
idea the day is built on.

**The `--no-verify` conversation is worth having explicitly.** Every local gate has an escape hatch,
and it should: emergencies exist. The healthy version is that using it is visible and rare — a
comment in the pull request saying why. The unhealthy version is that it is in someone's shell alias.
If you find yourself bypassing a gate routinely, the gate is wrong, and fixing the gate is the work —
not building tolerance for ignoring it.

**Machine-readable conventions compound.** `day-04: complete` looks like a triviality. Because it is
strict, `./m status` can find it with one `git log --grep`, `scripts/tracker.py` can reconcile it
against the filesystem, and progress reporting needs no separate database. Teams get the same effect
from conventional commit messages driving changelogs and version bumps. **A convention a machine can
read is worth ten a human has to remember**, and the cost of adopting one is a decision made once.

**The review comment a senior engineer leaves.** On a pull request adding a check to CI but not to
the local script: *"Add this to the local entry point too — otherwise the first time anyone sees it
is a red build."* And on a pre-commit hook that runs the full integration suite: *"This is going to
push everyone to `--no-verify`. Move it to CI and keep the hook fast."*

**The interview question.** *"Your team has a definition of done that nobody follows. What do you
do?"* Weak answers involve reminding people or adding it to the onboarding document — both are
reminders, and the story explains what happens to those. The strong answer is to make it mechanical:
pick the two or three conditions that genuinely matter, encode them as a check that runs
automatically, put the authoritative version where it cannot be skipped, and keep it fast enough that
nobody wants to. Adding that a standard which is not enforced will drift to whatever gets merged —
regardless of what the wiki says — shows you understand *why*, not just *what*.

## Check yourself

```bash
printf -- '- [ ] deliberately unticked\n' > days/day-00-setup/CHECKLIST.md && ./m done 0; echo "gate exit: $?"; git log --oneline | wc -l
```

The gate must refuse with exit **1**, and the commit count must be unchanged. Then tick the box
(`- [x]`), run it again, and watch it proceed to `./m check` instead.
