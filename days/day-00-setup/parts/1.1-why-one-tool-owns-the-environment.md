# 1.1 — Why one tool must own the environment

## One-line answer

A "Python environment" is just **one interpreter plus one folder of installed packages**, and almost
every mysterious `ImportError` in a beginner's life happens because the interpreter that ran the code
and the folder that received the package belonged to two different environments.

---

## The story

An engineer joins a team on a Monday. Their first task is small: run a script the team has used for
a year, `report.py`, and confirm it produces the same numbers as last week.

They open a terminal and type `python report.py`.

```text
ModuleNotFoundError: No module named 'pandas'
```

Reasonable. They install it: `pip install pandas`. The terminal fills with a progress bar and ends
with `Successfully installed pandas-3.0.1`. They run the script again.

```text
ModuleNotFoundError: No module named 'pandas'
```

They stare at it. They run `pip install pandas` again — `Requirement already satisfied`. They can see
the package. They open a file explorer and *find the folder it went into*. It is there. It is
definitely there. The script still cannot see it.

They lose the afternoon. Eventually a colleague leans over, types one command, and reads the output
aloud: there are four Pythons on this laptop. One came from the python.org installer. One came
bundled with an editor. One came from a data-science distribution installed in 2023 and never
removed. One is the Windows Store shim. `pip` belonged to the third. `python` was the fourth.

Nothing was broken. Two different words on the same keyboard were pointing at two different machines
that happened to live on the same disk.

That afternoon is the single most common way a first month is lost. Today exists so it never happens
to you — not on Day 4, and not on Day 155 when the thing that fails is a vector database and you
have real work to lose.

---

## The idea in plain language

Let us build the vocabulary from nothing. Three words: **interpreter**, **site-packages**, and
**PATH**.

**An interpreter is a program.** `python.exe` (or `python` on macOS/Linux) is an executable file
sitting somewhere on your disk, exactly like a game or a text editor. It reads a `.py` file and
carries out the instructions in it. You can have as many of these programs on one machine as you
like, in as many folders as you like, and they neither know nor care about each other. This is the
first fact people get wrong: **"Python" is not a thing installed on your computer. It is a *file*,
and you can have twelve.**

**Every interpreter owns one folder of packages, called `site-packages`.** When you install a
library — pandas, NumPy, anything — the files land in a folder that sits next to a *specific*
interpreter. There is no global, shared, machine-wide library shelf. Interpreter A cannot see
interpreter B's `site-packages`, in the same way your documents folder cannot see mine.

```mermaid
flowchart TB
    subgraph A["Interpreter A  (C:\\Python312\\python.exe)"]
        SPA["site-packages/<br/>pandas · numpy"]
    end
    subgraph B["Interpreter B  (AppData\\...\\python.exe)"]
        SPB["site-packages/<br/>requests"]
    end
    A -. "cannot see" .-> SPB
    B -. "cannot see" .-> SPA
```

**`PATH` decides which one you get when you type a word.** When you type `python` and press Enter,
your shell does not perform a search of your whole disk. It walks a list of folders — that list is
the environment variable named `PATH` — in order, top to bottom, and runs **the first file it finds
with that name**. It then stops looking. (An *environment variable* is simply a named piece of text
that your shell holds in memory and passes to every program it starts. `PATH` is one of them, and it
holds a list of folder names.)

Now the whole trap is visible in one sentence:

> `pip` is itself a program on `PATH`, and it installs into the `site-packages` of **whichever
> interpreter that particular `pip` belongs to** — which is not necessarily the interpreter that the
> word `python` resolves to.

The engineer in the story had a `pip` from the third Python earlier on `PATH` than the `pip` from the
fourth. Both commands succeeded perfectly. They just talked to different machines.

**A virtual environment** — the phrase you will see everywhere — is the fix the Python world settled
on. It is not magic and not a container: it is a *folder* holding a link to one interpreter plus its
own private `site-packages`. "Activating" it means temporarily putting that folder at the front of
`PATH`, so `python` and `pip` resolve to the pair inside it. One project, one folder, one
interpreter, one set of packages, no crosstalk.

And **that** is the idea this whole day is built on: *something must own the environment.* If nothing
owns it, `PATH` does — and `PATH` is a list of accidents accumulated by every installer you have ever
run. In this project the owner is a single program called `uv`, which you meet in
[1.3](1.3-uv-the-one-binary.md). It creates the environment, installs into it, records exactly what
it installed, and runs your code inside it. One owner, four jobs, no ambiguity.

## Why Setu needs it

This is not a Day 0 nicety. Three specific places it decides whether you have a good evening:

- **Day 26 (pandas 3.0).** That day's whole lesson is that `df[col][mask] = v` silently does nothing
  under Copy-on-Write. To learn that, you must be *certain* you are running pandas 3.x. If a second
  interpreter with pandas 2.x is reachable on your machine, you will spend the evening arguing with a
  bug that does not exist in the version you think you are running.
- **Day 128 onward (PyTorch).** Deep-learning packages are large and version-sensitive. Installing
  one into the wrong interpreter is not a five-second mistake to undo.
- **Every day with a test.** `./m check` runs `pytest`. If `pytest` and your code resolve to
  different environments, your tests import a *different copy* of your own library than the one you
  just edited — and you get a green suite for code you did not write. That failure is far worse than
  a red one, because you believe it.

There is a bigger reason. This project's Principle 4 is *pin everything*: exact versions, a committed
lockfile, nothing floating. **A pin is meaningless if you cannot say which environment it applies
to.** Reproducibility starts here or it does not start.

## The mechanism

You are going to look at your own machine and count. Open **Git Bash** — you will install it in
[1.2](1.2-git-and-git-bash.md) if you do not have it yet; if you are on macOS or Linux, your normal
terminal is fine.

```bash
which -a python python3 pip pip3
```

**Line by line:**

- `which` — asks the shell "if I typed this word, which file would actually run?" It answers by
  walking `PATH` exactly as the shell would.
- `-a` — **all** matches, not just the winner. This is the flag that makes the command useful: without
  it you see the one that wins and remain unaware of the three queued behind it. The winner is
  printed **first**.
- `python python3 pip pip3` — four separate words, because on a real machine they routinely resolve
  to different places. `python3` existing while `python` does not is normal on macOS and Linux;
  `pip` pointing somewhere `python` does not is the bug from the story.

On Windows there is a second, sharper tool:

```bash
py -0p
```

**Line by line:**

- `py` — the **Python launcher for Windows**, a small dispatcher installed by the python.org
  installer. Its job is to find Pythons for you.
- `-0` — "list the interpreters you know about" (that is a zero, not a capital O).
- `p` — appended to `-0`, adds the full **p**ath of each one. `py -0` alone gives you names;
  `py -0p` gives you the addresses, which is what you actually need.
- If this prints `bash: py: command not found`, you have no python.org install — which is a
  *cleaner* starting point, not a problem.

Now the decisive question — not "is pandas installed?" but "installed *where*?":

```bash
python -c "import sys; print(sys.executable); print(sys.prefix)"
```

**Line by line:**

- `python -c "<code>"` — run the string as a program and exit. No file needed. `-c` for **c**ommand.
- `import sys` — `sys` is the standard-library module describing the running interpreter itself.
  Nothing to install; it is part of Python.
- `sys.executable` — the **full path of the interpreter currently running this line**. This is the
  ground truth. Not what you typed, not what you assume: the actual file.
- `sys.prefix` — the root of the environment this interpreter belongs to. Its `site-packages` lives
  underneath. When you are inside a virtual environment, `sys.prefix` points at that environment's
  folder; when you are not, it points at the base installation. Comparing the two is how you tell.
- The two `print` calls are separated by `;` so a single `-c` string runs both statements.

And the same question asked of `pip`:

```bash
pip -V
```

**Line by line:**

- `-V` — print pip's version **and**, crucially, the path it is operating from. The output ends with
  something like `from C:\...\site-packages\pip (python 3.11)`. That parenthesised version and that
  path tell you which interpreter this `pip` installs for.
- Compare it to `sys.executable` above. **If those two disagree, you have reproduced the story's bug
  on your own machine**, and you now know how to detect it in ten seconds instead of an afternoon.

## When it breaks

Here is the failure in full, as it actually appears:

```text
$ pip install pandas
Requirement already satisfied: pandas in c:\users\me\appdata\roaming\python\python311\site-packages (3.0.1)

$ python report.py
Traceback (most recent call last):
  File "report.py", line 1, in <module>
    import pandas as pd
ModuleNotFoundError: No module named 'pandas'
```

**What the traceback is telling you.** Read the two paths, not the words. `pip` reported success into
a `python311` folder. Now ask `python` who it is:

```text
$ python -c "import sys; print(sys.executable)"
C:\Users\me\AppData\Local\Programs\Python\Python312\python.exe
```

`311` versus `312`. Two interpreters. `pip` did its job perfectly and `python` did its job perfectly;
they were simply not the same environment. **`ModuleNotFoundError` almost never means "the package is
missing from your computer". It means "the package is missing from *this* interpreter."**

**The smallest fix**, and the one to reach for any time you are unsure:

```text
$ python -m pip install pandas
```

`python -m pip` means "ask *this specific interpreter* to run its own pip module". It removes the
`PATH` lottery entirely, because the interpreter is named explicitly and pip is found through it
rather than beside it. If you learn exactly one habit from this part: **never type bare `pip` again.**

In this project you will not type either, because `uv` handles installation itself
([1.3](1.3-uv-the-one-binary.md)) — but you will meet machines that are not this project, and this is
the twenty-second diagnosis for all of them.

## In production

This stops being a laptop annoyance and becomes an outage the moment code leaves your machine.

**The same bug, wearing a suit.** A service works locally and crashes on deploy with
`ModuleNotFoundError`. The Dockerfile ran `pip install -r requirements.txt` as `root`, and the
container starts the app as an unprivileged user with a different `PATH` — or the base image ships
its own system Python and the app runs under a second one. Identical mechanism, different building.
The production version of `which -a python` is `docker run --rm <image> python -c "import sys;
print(sys.executable)"`, and it is the first thing to run when a container says a module is missing.

**Why professionals never install into the system Python.** On Linux distributions the operating
system itself is written partly in Python, and `apt`/`yum` depend on specific versions of specific
libraries in the system interpreter's `site-packages`. `sudo pip install` into it can upgrade a
dependency out from under the package manager and leave a machine that cannot install software any
more. This is why modern Python refuses by default and prints
`error: externally-managed-environment` (PEP 668) — a guard rail added precisely because so many
people broke their machines this way. **Rule: the system Python belongs to the operating system. Your
project gets its own.**

**What the professional's version looks like.** In a serious codebase, the environment is never
described in prose ("install pandas and numpy") — it is *declared in a file and locked*: a manifest
listing direct dependencies with exact versions, and a lockfile pinning the full transitive tree with
hashes. Anyone, anywhere, on any machine, materialises the identical environment from those two
files. That is what you build in [2.4](2.4-uv-init-pyproject-and-the-lockfile.md), and it is why
Principle 4 exists.

**What degrades at scale.** With one project, ambiguity costs an afternoon. With forty services, an
unowned environment costs you the ability to answer "what is actually running in production right
now?" — and that question turns up during incidents, security audits (which package version has the
CVE?), and compliance reviews. The whole supply-chain-security discipline rests on a machine-readable,
exact answer, which a `PATH` accident cannot give.

**The review comment a senior engineer leaves.** On a pull request containing `pip install foo` in a
CI script or a Dockerfile: *"Pin this and install it through the project's lockfile — an unpinned
install means CI can pass today and fail tomorrow with no commit in between."* The unstated point is
that an unpinned build is not reproducible, and a build you cannot reproduce is one you cannot roll
back to.

**The interview question.** *"A developer tells you `pip install requests` succeeded but their script
still raises `ModuleNotFoundError`. Walk me through your diagnosis."* They are not testing whether
you know the word "virtualenv". They want to hear you (1) ask what `sys.executable` prints, (2) ask
what path `pip -V` reports, (3) name the mismatch, and (4) reach for `python -m pip` — and ideally
(5) say that the real fix is that the project should own its environment rather than relying on
`PATH`. Answering with the mechanism instead of the incantation is the entire difference between
sounding junior and sounding senior.

## Check yourself

Run this now, before installing anything:

```bash
which -a python python3 pip pip3 2>/dev/null; echo "---"; py -0p 2>/dev/null || echo "no py launcher"
```

Write the answer down somewhere — you want to know what your machine looked like *before* today, so
that if something is strange on Day 40 you can tell what changed.

**Answer out loud, without scrolling up:**

> I type `pip install pandas` and it succeeds. I type `python` and `import pandas` fails. Explain
> exactly what happened, using the words *interpreter*, *site-packages* and *PATH* — and then give
> the one command that would have avoided it.
