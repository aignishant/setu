# 4.1 — The README that grows

## One-line answer

The README is the only document every visitor to your repository will read, and it is written on
Day 0 as four lines rather than on Day 239 from a blank page — because a file that grows alongside
the work stays true, and a file written at the end is written from memory.

---

## The story

Two people finish a portfolio project in the same week and put it on a public repository.

The first has an impressive system: a retrieval pipeline, an agent loop, an approval gate. The README
says the project's name, and underneath, `TODO: write this up`. They meant to. The final push was the
interesting part, and documentation was the boring thing left for later, and later did not come. A
recruiter opens it, sees a wall of folders and no instructions, and closes it inside ten seconds.
Nothing in that repository is discoverable without reading the source, and nobody reads the source of
a stranger's project to find out whether it is worth reading.

The second person's system is slightly less ambitious. Their README opens with one sentence saying
what it does, a command block showing how to run it, and a short section on the three decisions they
would defend. The same recruiter reads it, runs the two commands, sees it work, and forwards the
link.

The gap between them is not engineering. It is that one of them treated the README as the interface
to their work and the other treated it as paperwork about their work.

And there is a second, quieter cost. When the first person is asked in an interview to explain a
design decision from four months ago, they reconstruct it badly, because the reasoning was never
written down anywhere while it was still fresh. The person who wrote as they went is reading their
own notes.

---

## The idea in plain language

A **README** is a file named `README.md` in the root of a repository. Every code-hosting platform
renders it automatically on the project's front page, which is what makes it structurally different
from every other document you will write: **it is the default view.** Nobody has to choose to read it.

`.md` is **Markdown**, a plain-text format where a few characters mean formatting — `#` for a
heading, `**bold**`, a fenced block of triple backticks for code. It stays readable as raw text,
which is why it is the standard for documentation kept next to code: it diffs cleanly in Git and it
does not require a special program to open.

The question worth answering is *what a README is for*, and the useful framing is that it serves four
readers, in this order:

| Reader | What they need in the first screen |
|---|---|
| **Someone deciding whether to care** | one sentence: what this is and who it is for |
| **Someone trying to run it** | the exact commands, in order, that take them from clone to working |
| **Someone about to contribute** | how to run the tests and what the standards are |
| **You, later** | the decisions and their reasons, which you will otherwise forget |

Notice that three of those four are *action*, not description. The commonest README failure is a page
of prose about what the project does, with no way to run it. The second commonest is instructions
that were true once.

Which brings us to the reason this is a Day 0 part rather than a Day 239 one. **Documentation written
at the end is written from memory, and memory is exactly the thing that failed.** A README that grows
with the project gets updated on the day a command changes, because the change and the documentation
are in the same commit. One written afterwards is reconstructed, and reconstruction is where the
inaccuracies come from — the step you forgot you had already done, the environment variable that is
set on your machine and nowhere else.

Today's README is four lines and a command block. That is not a placeholder; it is the correct size
for a project that currently does one thing. It will be a portfolio piece on Day 239 because it will
have been edited two hundred times, each time by someone who had just done the thing they were
describing.

## Why Setu needs it

- **Principle 10 says every artifact should be defensible to a hiring panel.** The README is the
  first artifact anyone sees, and the only one some people will see.
- **`docs/adr/` holds the decision records** ([2.1](../02-skeleton/2.1-the-folder-skeleton.md)), and the README
  is what points at them. A decision nobody can find has not been recorded.
- **The daily loop is three commands** ([3.2](../03-m-script/3.2-the-case-dispatcher.md)). Writing them down
  today means that on Day 40, after a break, you read your own instructions rather than reconstructing
  them.
- **Day 239 is a portfolio day.** Its work is far smaller if the file has been maintained than if it
  starts blank.

## The mechanism

In the project root:

````bash
cat > README.md <<'EOF'
# Project Setu

A 240-day journey from Python to a multi-agent research system, built one committed day at a time.

- **The plan:** `docs/00_MASTER_PLAN_DS_GENAI.md`
- **The day map:** `docs/CURRICULUM_INDEX_DS.md`
- **Start here:** `days/day-00-setup/LESSON.md`

## Daily rhythm

```bash
./m status      # where am I
./m start N     # open day N's hub, and list its parts
./m scaffold N  # create day N's lab folder
./m check       # lint + format + offline tests
./m done N      # refuses to commit until the checklist is ticked and checks are green
```

## Rules this repo runs on

1. Every day produces committed, runnable code.
2. From scratch before library.
3. Exact version pins, committed lockfile, nothing floating.
4. A behaviour is not done until a test can go red when it regresses.
EOF
````

**Line by line:**

- `cat > README.md <<'EOF' … EOF` — the heredoc from
  [2.2](../02-skeleton/2.2-gitignore-before-secrets-exist.md). The quoted `'EOF'` matters more than usual
  here, because the content contains backticks; unquoted, the shell would try to execute them as
  commands.
- `# Project Setu` — a level-one heading, rendered as the page title. One `#` per document, at the
  top; more than one confuses both readers and the tools that extract a title.
- The one-sentence description immediately under it — this is the highest-value line in the file. It
  answers "should I keep reading?" for the first reader in the table. Write it as a claim about what
  the project *is*, not a list of technologies.
- The three bullet links — orientation for someone who wants more. Relative paths, so they work in a
  clone as well as on the web.
- ` ```bash ` fenced block — the commands, exactly as typed, with `#` comments explaining each. This
  is the section the second reader needs, and putting it above the philosophy is deliberate: the
  person trying to run your project should not have to scroll past your reasoning to find the
  command.
- The numbered rules — four of the eighteen from the plan. They exist so that a reader (including
  you, on Day 90) can tell what kind of project this is: opinionated, test-gated, pinned. This is the
  seed of the fourth reader's section, and it will grow.
- Note what is **not** here: no badges, no long feature list, no architecture diagram. The project
  does not have those things yet, and a README describing things that do not exist is worse than a
  short one.

Check that it renders as you expect:

```bash
head -20 README.md && grep -c '```' README.md
```

**Line by line:**

- `head -20` — read the first twenty lines back, which is roughly what fits on a first screen. If the
  answer to "what is this and how do I run it?" is not visible in those lines, reorder the file.
- `grep -c '```' README.md` — count the fence markers. It must be **even**; an odd number means an
  unclosed code block, which silently swallows the rest of the document when rendered. This is the
  most common Markdown bug and the fastest one to check.

## When it breaks

**The heredoc that ends early:**

```text
$ cat > README.md <<'EOF'
> # Project Setu
> ```bash
> ./m check
> ```
> EOF
$ cat README.md
# Project Setu
```

**What it means.** Nothing here — this one actually works, and it is worth knowing why, because the
near-miss is instructive. A heredoc ends at a line containing **exactly** the marker, so a line
reading ` ``` ` is fine. But if your content ever contains a line that is exactly `EOF`, the block
ends there and the rest of your text is interpreted as shell commands. This is why marker names like
`USAGE` and `MDEOF` show up in real scripts: the marker must be a string that cannot appear in the
content.

**The unclosed fence, which is the common one:**

```text
$ grep -c '```' README.md
7
```

**What it means.** An odd number of fence markers, so one code block is never closed. Rendered, the
remainder of your README becomes a single grey code block — including your headings. It looks
dramatic and the cause is one missing line. The check above catches it in one command; run it after
any edit that adds a code block.

**And the failure that has no error message at all:**

```text
$ git log --oneline -- README.md
a1b2c3d  day-00: toolchain, skeleton, ./m
```

**What it means.** One commit, on Day 0, and nothing since — while the project has moved on for
weeks. The instructions in it are now describing a version of the project that no longer exists, and
every person who follows them will fail at a step you cannot see. **A stale README is worse than a
missing one**, because a missing one sets expectations correctly. The fix is habit rather than
tooling: when a command changes, the README changes in the same commit
([4.2](4.2-the-first-commit.md) is about what makes that natural).

## In production

**The README is an onboarding cost multiplier, and that is how teams justify time on it.** Every new
engineer, every contractor, every person returning to a service after a year pays the cost of a bad
one — and pays it again each time. The measurable version of this is *time to first successful local
run*, and mature teams treat that number as a real metric. A README that gets someone from clone to
running in three commands saves days per person; one that omits a step costs an hour of someone
else's time to answer the same question repeatedly.

**The test that matters: can a stranger run this on a clean machine?** Not "does it work for me" —
your machine has an environment variable set six months ago and a tool you forgot you installed.
Professional teams verify this by having a new joiner follow the README verbatim and fix every place
they get stuck, or by running the quickstart in CI on a fresh container so a broken instruction fails
the build. That second technique — documentation as an executed test — is the only way instructions
stay true at scale.

**Structure conventions exist and are worth following.** Larger projects split into `README.md`
(what and quickstart), `CONTRIBUTING.md` (how to work on it), `ARCHITECTURE.md` (how it is built),
`docs/adr/` (why the decisions were made), `SECURITY.md` (how to report a vulnerability), and
`CHANGELOG.md`. The rule that makes this work is that the README stays short and *links out*; it is
an index, not an encyclopaedia. The moment it exceeds a screen or two of scrolling, the excess should
become a linked document.

**README-driven development is a real technique.** Write the README first — describing how the tool
*will* be used — before implementing it. It is a cheap design review: interfaces that are awkward to
document are usually awkward to use, and you discover that before writing the code rather than after.
This is the same instinct as writing the test first, applied to the interface instead of the
behaviour.

**Documentation rots because it is not executed.** Code is verified continuously; prose is not.
Everything professionals do about this is an attempt to make documentation executable or adjacent
enough to code that it moves with it: doctests, tested example scripts, generated API references,
quickstarts run in CI. Where that is impossible, the fallback is proximity and habit — the change and
its documentation in the same commit, reviewed together, which is a thing a reviewer can actually
enforce.

**The review comment a senior engineer leaves.** On a pull request changing a CLI flag with no
documentation change: *"This changes the command in the README quickstart — please update it in this
PR, not a follow-up."* And on a new service with an empty README: *"Add a quickstart before this
merges. If nobody can run it without asking you, you are now its only maintainer."*

**The interview question.** Often it is not a question at all — they open your repository and read
the front page while you are talking. What they are assessing is whether you can explain your own
work to someone who was not there: a clear statement of what it does, a runnable quickstart, and
evidence that you made decisions rather than accepting defaults. If your README has a short "why it
is built this way" section pointing at real trade-offs, you have handed the interviewer their next
three questions, on ground you have already prepared.
