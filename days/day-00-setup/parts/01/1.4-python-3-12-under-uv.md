# 1.4 — Python 3.12, and why not the newest one

## One-line answer

This project runs **Python 3.12** — not the newest release — because 3.12 is the only version every
library in the 240 days can agree on, and `uv python install 3.12` gives you a private copy of it
that cannot collide with anything already on your machine.

---

## The story

Someone starts a new deep-learning project on the day a new Python version is released. Newer is
better, so they install it. Everything is fine for a week: they are writing plain Python, and plain
Python barely changes between versions.

Then they reach the part of the project that needs a numerical library — the kind with compiled C
and CUDA code inside it. They run the install and get a wall of red text about a missing compiler,
ending in a message about no matching distribution. They try another library. Same shape of failure.

Nothing they did was wrong, and nothing is broken. The libraries simply have not been *built* for
that Python yet. Compiled packages ship pre-built files, one per Python version and platform
combination, and building them for a brand-new release takes the maintainers time — sometimes
months, because the ecosystem is deep and each layer waits for the one below it.

The person on the newest Python is not at the front of the queue. They are standing in a room the
rest of the ecosystem has not moved into yet.

Meanwhile a second person, on a version two releases older, installs everything in one go and never
learns that any of this exists. That is the boring outcome you want for the next 240 days.

---

## The idea in plain language

**A Python version is a compatibility contract, not a feature list.** Version numbers look like
`3.12.4`, and the three parts mean different things:

- `3` — the **major** version. Effectively fixed; the move from 2 to 3 was a decade-long migration.
- `12` — the **minor** version. This is the one that matters. A new minor version appears roughly
  once a year, may change the internals that compiled libraries plug into, and is what package
  authors build against. `3.11` and `3.12` are meaningfully different targets.
- `4` — the **patch** version. Bug fixes and security fixes only, no new behaviour. Upgrading patch
  versions is safe and expected.

Now the part that decides today's choice. Many important libraries are not pure Python: NumPy,
PyTorch and TensorFlow contain compiled C, C++ or Fortran that must be built for a specific Python
minor version and a specific platform. Rather than make you compile them, maintainers publish
pre-built files called **wheels**, named for exactly what they fit — for example
`numpy-2.5.2-cp312-cp312-win_amd64.whl`, meaning *CPython 3.12, on 64-bit Windows*. Install on a
Python with no matching wheel and you either get a slow, fragile source build or a flat refusal.

So the version question is not "what is newest?" but **"what is the intersection of everything I will
need?"** For this project that intersection was computed from live package metadata and recorded in
`docs/PINS_DS.md`:

| Package | Supported Pythons (read 2026-08-21) |
|---|---|
| numpy 2.5.2 | ≥ 3.12 — **the floor** |
| tensorflow 2.21.0 | 3.10 – 3.13 — **the ceiling** |
| torch 2.13.0 | 3.10 – 3.14 |
| langgraph 1.2.11 | 3.10 – 3.13 |
| transformers 5.15.1 | ≥ 3.10 |

The floor is 3.12 and the ceiling is 3.13, so the intersection is **3.12 or 3.13**, and the plan
takes **3.12** — the wider margin against a library that has not caught up. Being one minor version
behind the leading edge is not timidity in a 240-day project; it is the reason all of the libraries
install on the same day.

The last idea: **where that 3.12 comes from.** `uv python install 3.12` does not run a system
installer, does not touch any Python you already have, and does not need administrator rights. It
downloads a **standalone build** — a self-contained interpreter, in a folder `uv` manages — and
registers it for its own use. Your machine's other Pythons from
[1.1](1.1-why-one-tool-owns-the-environment.md) are left exactly as they were. That isolation is the
whole point: you are adding a Python, not resolving a conflict between existing ones.

## Why Setu needs it

- **Day 20 (NumPy) has a hard floor.** NumPy 2.5.2 requires ≥ 3.12. On 3.11, Phase 3 does not start.
- **Phase 16 needs TensorFlow**, which has a ceiling of 3.13 today. Choosing 3.14 now would mean
  discovering in Phase 16 — a hundred-plus days from now — that the environment must be rebuilt.
- **Principle 4 says pin everything.** `requires-python = "==3.12.*"` in `pyproject.toml`
  ([2.4](2.4-uv-init-pyproject-and-the-lockfile.md)) is that principle applied to the language
  itself. The `.*` accepts patch upgrades (3.12.4 → 3.12.7, safe) while refusing a minor jump
  (3.13, not safe) — a distinction worth internalising now.
- **Day 1's job is to re-verify this table**, not to trust it. If a library has moved its floor or
  ceiling since it was written, Principle 14 applies: amend the plan first, then change the pin.

## The mechanism

```bash
uv python install 3.12
```

**Line by line:**

- `uv python` — the subcommand group for managing *interpreters* rather than packages. This is the
  job `pyenv` used to do, from [1.3](1.3-uv-the-one-binary.md)'s table.
- `install 3.12` — fetch a standalone CPython 3.12 build and register it with `uv`. Note what is
  **not** here: no administrator prompt, no installer window, no change to your system `PATH`, no
  interference with any Python already present. Note also that you asked for `3.12`, not
  `3.12.4` — `uv` selects the newest patch release of that minor line, which is the correct
  granularity to ask for.

Now see the result:

```bash
uv python list
```

**Line by line:**

- Lists every interpreter `uv` can see: the ones it manages **and** the ones already on your system,
  each with its version and full path. Read this output carefully — it is the same census you took
  in [1.1](1.1-why-one-tool-owns-the-environment.md), now with the newcomer visible among them. Being
  able to see all of them at once, and knowing which one your project will use, is the entire
  difference between an owned environment and an accidental one.

Prove it works, without disturbing anything:

```bash
uv run --python 3.12 python -c "import sys; print(sys.version); print(sys.executable)"
```

**Line by line:**

- `uv run <command>` — run a command inside the project's environment, creating it if needed. This
  is the `activate`-free workflow from [1.3](1.3-uv-the-one-binary.md); [2.5](2.5-the-venv-you-never-activate.md)
  covers it fully.
- `--python 3.12` — pin *this one invocation* to 3.12. You will not normally pass this, because
  `pyproject.toml` will state the requirement permanently. It is here so the check is unambiguous
  before that file exists.
- `python -c "..."` — the interpreter and the code to run, exactly as in
  [1.1](1.1-why-one-tool-owns-the-environment.md).
- `sys.version` — the full version string, including the build date and compiler. `sys.executable` —
  the interpreter's path. Together they answer "which Python am I *actually* running", which is the
  only question that ever matters.

## When it breaks

**Asking for a version that does not exist yet, or is spelled wrong:**

```text
$ uv python install 3.1
error: No download found for request: cpython-3.1-windows-x86_64-none
```

**What it means.** `uv` builds a precise request from your argument — implementation, version,
platform, architecture — and no published build matches it. Nine times in ten this is a typo (`3.1`
for `3.12`) rather than a missing release. Run `uv python list --all-versions` to see what is
actually available before assuming the download is at fault.

**The mismatch that appears later, once `pyproject.toml` exists:**

```text
$ uv run python -c "print(1)"
error: The requested interpreter resolved to Python 3.11.9, which is incompatible with the
project's Python requirement: `==3.12.*`
```

**What it means.** This is a *good* error — the exact class of failure that
[1.1](1.1-why-one-tool-owns-the-environment.md)'s story suffered silently, caught loudly instead.
Something pointed at a 3.11 interpreter while the project declares 3.12. The fix is `uv python
install 3.12` and letting `uv` select it; the lesson is that the declared requirement is doing its
job. Compare this message with `ModuleNotFoundError` from 1.1: same underlying confusion, but here
the project's own declaration turned it into a precise sentence.

**The wheel failure from the story, in full:**

```text
$ uv add numpy==2.5.2
  × No solution found when resolving dependencies:
  ╰─▶ Because numpy==2.5.2 has no wheels with a matching Python ABI tag (e.g., `cp311`)
      and your project depends on numpy==2.5.2, we can conclude that your project's
      requirements are unsatisfiable.
```

**What it means.** Read the tag: `cp311` is **CPython 3.11's ABI**. An *ABI* — application binary
interface — is the low-level convention compiled code uses to talk to the interpreter, and it changes
between minor versions, which is exactly why wheels are named per version. The resolver is telling
you your interpreter is 3.11 and this package publishes nothing for 3.11. The fix is the right
interpreter, never a downgrade of the package to whatever happens to install — that path leads to a
NumPy old enough to break pandas 3.

## In production

**"Use the latest" is not a strategy; a support window is.** Each Python minor version gets about
five years of support — roughly two of full fixes, then security fixes only, then end of life.
Professional teams sit deliberately in the middle of that window: new enough that the ecosystem has
built wheels and security fixes still arrive, old enough that every dependency supports it. The
common policy is *n-1*: adopt a minor version once the libraries you depend on have shipped wheels
for it, not on release day. That is exactly the reasoning behind 3.12 here, and it is a defensible
answer in a design review in a way that "it was the newest" is not.

**Where the version is declared matters.** In a real repository the version appears in several
places, and they must agree: `requires-python` in `pyproject.toml`, the base image in the
`Dockerfile`, the `python-version` in the CI workflow, and possibly a `.python-version` file. When
they drift, you get the worst failure mode in this whole subject — code that passes CI on one version
and runs in production on another. The professional habit is a single source of truth with the others
derived from it, and a CI check that fails when they disagree.

**Upgrading a minor version is a project, not a command.** The sequence a team follows: read the
"What's New" and the deprecations, check every dependency's wheel availability for the new tag, add
the new version to the CI test matrix *alongside* the old one, run both until green, then flip the
default and drop the old one. The reason it is not one command is that compiled dependencies, not
your code, are usually what break — the very thing this part is about.

**Standalone builds versus system Python, in a container.** The same reasoning as
[1.1](1.1-why-one-tool-owns-the-environment.md)'s "the system Python belongs to the operating
system", now inside an image: a distribution's Python is entangled with the distribution's package
manager. Modern Python images and `uv`-based builds install an independent interpreter for the
application, so an OS security update cannot change the interpreter your service runs on. Isolation
you chose beats isolation you inherited.

**The review comment a senior engineer leaves.** On a pull request bumping a base image from
`python:3.12-slim` to `python:3.13-slim` in one line: *"Is every compiled dependency publishing
cp313 wheels? Add 3.13 to the test matrix first and let it run green alongside 3.12 before we
switch."* And on a `pyproject.toml` that says `requires-python = ">=3.9"` while CI tests only 3.12:
*"We are claiming support for versions we never test — either narrow the claim or widen the matrix."*

**The interview question.** *"How do you choose which Python version a new service runs on?"* A
junior answer names the newest. A senior answer names the constraint set — the dependencies'
supported ranges intersected, the security support window, what the deployment platform offers, and
what the rest of the estate already runs — then says where that decision gets written down so it
cannot drift. If you can also explain why a compiled dependency is what constrains you, and use the
word *wheel* or *ABI* correctly, you have answered it better than most.
