# 2.1 — The folder skeleton, and why each folder exists

## One-line answer

Every folder you create today answers one question about a file — *is this code that must survive, a
test of that code, data, a document, or a scratchpad?* — and putting the library under `src/` rather
than at the top level is a deliberate choice that makes it impossible to accidentally test code you
have not actually installed.

---

## The story

A project that has been going for a year, laid out the way it grew:

```text
project/
  analysis.py
  utils.py
  utils2.py
  cleaned_data.csv
  cleaned_data_v2.csv
  model.pkl
  Untitled.ipynb
  Untitled1.ipynb
  notes.txt
  test.py
```

Every file in it was a reasonable idea at the time. Together they are unanswerable. Which of the two
`cleaned_data` files produced `model.pkl`? Was `cleaned_data_v2.csv` downloaded or generated — and if
generated, by which of the notebooks? Is `utils2.py` a newer `utils.py` or a different concern? Is
`test.py` a test suite or a scratch file called test?

Nobody can tell, including the person who wrote it, and the reason is not untidiness. It is that
**the folder structure records no decisions.** Every file is in the same place, so the layout says
nothing about what any file *is*, and all that information now lives only in one person's memory —
where it decays.

Here is the same project with a structure that answers questions:

```text
project/
  src/project/       -> code that must survive
  tests/             -> proof that the code works
  data/raw/          -> downloaded, never edited
  data/processed/    -> generated, always reproducible
  notebooks/         -> scratch, never a deliverable
  docs/              -> decisions, written down
```

`cleaned_data.csv` is now unambiguously in `data/processed/`, which means it can be deleted and
regenerated. `utils.py` is in `src/`, which means it has a test. The notebook is in `notebooks/`,
which means nothing depends on it. The layout is doing the remembering.

---

## The idea in plain language

A project layout is a set of **claims about files**, made by where you put them. A good layout makes
each claim unmistakable and hard to violate by accident.

Here is every folder you create today, and the claim it makes:

| Folder | The claim |
|---|---|
| `src/setu/` | **This code must survive.** Anything here is imported by other code, has a test, and is reviewed. |
| `tests/` | **This proves the code works.** Mirrors `src/` one file per module, so finding a module's test is mechanical. |
| `days/` | The 241 lesson folders — the teaching material, not the program. |
| `docs/` | Written decisions and plans. `docs/adr/` holds *architecture decision records*: short documents saying what was chosen, what was rejected, and why. |
| `data/raw/` | **Downloaded, never edited.** If you modify a file here, you have destroyed your ability to reproduce anything downstream of it. |
| `data/processed/` | **Generated, always reproducible.** Safe to delete, because a script can rebuild it. If it is not rebuildable, it belongs in `raw/`. |
| `notebooks/` | **Scratch.** Principle 6: a notebook is where you think, never what you ship. Anything worth keeping graduates into `src/setu/` with a test, the same day. |
| `scripts/` | Small operational programs that act *on* the project rather than being part of it — the tracker, the depth check. |

Two of these carry more weight than the rest.

**`data/raw` versus `data/processed` is the whole idea of reproducibility, in two folder names.** Raw
data is an input you cannot recreate — if you overwrite it, the chain of steps that produced your
result has a broken first link, permanently. Processed data is an output; deleting it should cost
nothing but time. The moment you cannot say which of the two a file is, you have lost the ability to
answer "how was this number produced?", and that question is the one that arrives during an interview
or an audit.

**And `src/` needs its own explanation**, because it is the one choice here that looks like
bureaucracy and is not.

There are two common layouts:

```text
flat layout                     src layout
project/                        project/
  setu/                           src/
    __init__.py                     setu/
    stats.py                          __init__.py
  tests/                              stats.py
                                  tests/
```

They differ in one consequence. When Python runs, it searches a list of folders for modules
(`sys.path`), and **the current working directory is often on that list.** In the flat layout, `setu/`
sits in the working directory, so `import setu` finds the folder on disk — whether or not the package
was ever properly installed into your environment.

That sounds harmless. It is the source of a specific, expensive class of bug: your tests import your
code from the *folder*, while your users import it from the *installed package*. Anything that only
exists in the folder — a file you forgot to include in the package, a data file, a module you never
declared — works perfectly in your tests and fails on the user's machine. The tests were never
testing the thing being shipped.

With the `src` layout, `import setu` **cannot** be satisfied by the working directory, because
`src/setu/` is not directly in it. The only way to import your code is to install it into the
environment — which is exactly what your users will do. Your tests and reality are then running the
same thing by construction, rather than by luck.

One more small file with a large job: **`__init__.py`**. An empty file of that name inside a folder
marks the folder as a **package** — a unit Python can import as a whole, so `from setu.stats import
mean` works. Modern Python can sometimes import without it, but relying on that produces subtle
discovery problems in test runners and packaging tools. Create it explicitly; it costs one `touch`.

---

## Why Setu needs it

- **Principle 6** says the notebook is a scratchpad and everything worth keeping graduates to
  `src/setu/` with a test the same day. That principle is only enforceable if there is somewhere
  obvious to graduate *to* — and somewhere obviously disposable to graduate *from*.
- **Principle 9** says every dataset has provenance. `data/raw/SOURCE.md` records where a dataset
  came from, its licence and when it was pulled. The folder split is what makes that record
  meaningful: it applies to inputs, and only inputs.
- **Principle 10** says every phase ends with a written decision record you could defend to a hiring
  panel. `docs/adr/` is where those thirteen documents live, starting in Phase 1.
- **Days 79 onward** build a machine-learning pipeline where Principle 8 (leakage is the enemy) is
  the recurring danger. Being able to say with certainty which files are inputs and which are
  generated is a structural defence against a whole category of that mistake.

## The mechanism

From [1.2](../01/1.2-git-and-git-bash.md)'s Git Bash, go to wherever you keep projects and create the
folder:

```bash
cd ~/OneDrive/Desktop/Projects
mkdir -p setu
cd setu
```

**Line by line:**

- `cd <path>` — **c**hange **d**irectory: move the shell's current location. Every relative path you
  type afterwards is interpreted from there, which is why this comes first.
- `~` — your home folder, expanded by the shell. In Git Bash on Windows this is your Windows user
  folder, so `~/OneDrive/Desktop/Projects` is a real path. Adjust it if your projects live elsewhere;
  nothing later depends on this particular location.
- `mkdir -p setu` — **m**a**k**e **dir**ectory. `-p` means two things at once: create intermediate
  folders as needed, and **do not error if it already exists.** That second effect is why every
  `mkdir` in these documents has `-p` — it makes the command safe to re-run, and commands you can
  re-run without thinking are commands you will actually re-run when something looks wrong.

Now the skeleton, in one command:

```bash
mkdir -p src/setu tests days docs/adr data/raw data/processed notebooks scripts
touch src/setu/__init__.py tests/__init__.py
```

**Line by line:**

- `mkdir -p a b c` — `mkdir` accepts many paths at once, so this is eight folders in one line rather
  than eight commands. `docs/adr` and `data/raw` also create their parents, which is the other half
  of what `-p` does.
- `touch <file>` — create an empty file if it does not exist, and do nothing to its contents if it
  does. (Its original job was updating a file's timestamp; creating empty files is the use you will
  actually have.) It is safe to re-run, for the same reason `mkdir -p` is.
- `src/setu/__init__.py` — the empty file that makes `setu` an importable package rather than a
  folder of loose scripts.
- `tests/__init__.py` — the same for the test suite. This one is about ambiguity: without it, two
  test files with the same name in different folders can collide during test collection, producing an
  error message that does not mention the real cause.

Confirm the shape:

```bash
find . -type d -not -path "*/.*" | sort
```

**Line by line:**

- `find .` — walk the tree starting at the current directory (`.` means "here").
- `-type d` — directories only, so files do not drown the output.
- `-not -path "*/.*"` — exclude anything on a path containing a dot-prefixed component, which hides
  `.git`, `.venv` and other machinery. Dot-prefixed names are conventionally hidden on Unix; this is
  the flag that respects that convention.
- `| sort` — alphabetical order, so the output is stable and easy to compare against the table above.

## When it breaks

**The import failure the `src` layout is designed to force into the open:**

```text
$ uv run python -c "import setu"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'setu'
```

**What it means.** Exactly what it says, and it is *correct*: `src/setu/` is not on the module search
path, because that is the point of the layout. The package becomes importable when the project
declares itself installable and the environment installs it — the `[tool.hatch.build.targets.wheel]`
block and `packages = ["src/setu"]` in [2.4](2.4-uv-init-pyproject-and-the-lockfile.md). Until then,
this error is the layout working, not failing. Recognising a *correct* error is a skill in itself.

**The flat-layout bug, which never shows an error at all:**

```text
$ pytest
=================== 41 passed ===================

$ pip install ./dist/mypackage-1.0.tar.gz
$ python -c "from mypackage import helpers"
ModuleNotFoundError: No module named 'mypackage.helpers'
```

**What it means.** `helpers.py` exists in the source folder but was never included in the built
package — a missing entry in the packaging configuration. The test suite passed because it imported
from the folder next to it, not from anything installed. There is no error to read on the left-hand
side, which is what makes this expensive: the failure is discovered by a user, after release. This is
the entire argument for `src/`, and it is why the layout is worth adopting on Day 0 rather than
regretting on Day 200.

**The test-collection collision `tests/__init__.py` prevents:**

```text
$ pytest
import file mismatch:
imported module 'test_stats' has this __file__ attribute:
  /project/tests/unit/test_stats.py
which is not the same as the test file we want to collect:
  /project/tests/integration/test_stats.py
HINT: remove __pycache__ / consider __init__.py files
```

**What it means.** Two test files share a module name, and without `__init__.py` files there is no
package path to distinguish them — so the second import finds the first one's already-imported
module and refuses. The hint in the error is the fix, and you have already applied it by creating
`tests/__init__.py` today.

## In production

**The `src` layout is the default in serious Python codebases**, and the reason is the one above:
it makes "tested" and "shipped" the same artifact. Related professional habits that follow from it —
`pip install -e .` (an *editable* install, where the environment points at your source folder so
edits take effect without reinstalling), and CI that builds the package and runs the tests **against
the built artifact** rather than the repository. If you ever see a CI job that installs the wheel
into a clean environment before testing, that is this idea taken to its conclusion.

**`data/` in a repository is usually a mistake, and the folders exist to make that decision
explicit.** Git stores every version of every file forever; a 400 MB CSV committed once makes every
future clone slow, permanently, because history cannot be edited without rewriting every commit
after it. So `data/raw/` and `data/processed/` are created and then **ignored** in
[2.2](2.2-gitignore-before-secrets-exist.md) — the folders are part of the structure, the contents
are not part of the repository. What *is* committed is `data/raw/SOURCE.md`: where the data came
from, its licence, when it was pulled, and what you may do with it. In a company this is not
politeness — data licensing is a legal question, and "we do not know where this dataset came from" is
an unacceptable answer to it. Teams that version data properly use a dedicated tool or object storage
with versioning, and reference it from the repository rather than storing it in one.

**`notebooks/` is the folder with the strongest professional convention attached.** Notebooks store
output alongside code in a JSON file, which means they produce unreadable diffs, they merge badly,
they invite hidden state (cells run out of order), and they leak — output cells can contain
credentials, customer records, or query results that should never enter a repository. The rule most
teams settle on is exactly Principle 6: notebooks are for exploration; anything that matters moves
into a tested module. Where notebooks are committed, teams add tooling to strip outputs before commit.

**Decision records earn their folder.** `docs/adr/` looks like ceremony until the first time someone
asks "why is this a queue instead of a direct call?" eighteen months after the person who decided
left. An ADR is short — context, decision, consequences, alternatives rejected — and its real value
is that it captures *what was rejected and why*, which is the part no code comment ever records and
the part that stops a team relitigating the same argument annually.

**The review comment a senior engineer leaves.** On a pull request adding a top-level `utils.py`:
*"What is in here? `utils` becomes the folder where things go to avoid being named — split it by
what it actually does."* And on one adding a 12 MB CSV under `data/`: *"Please don't commit data.
Add it to the ignore list and record its source in SOURCE.md — otherwise every clone from now on
carries this file."*

**The interview question.** *"Why do many Python projects put their package under `src/`?"* It sounds
like trivia and is a genuine discriminator: the answer is that it removes the current working
directory as an accidental import path, so tests must import the installed package and therefore
exercise what users actually get. Candidates who have only ever worked in one repository usually
answer "convention"; candidates who have shipped a package answer with the failure it prevents.
