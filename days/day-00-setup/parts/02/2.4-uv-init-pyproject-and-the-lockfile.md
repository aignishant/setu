# 2.4 — `uv init`, `pyproject.toml`, and the lockfile

## One-line answer

`pyproject.toml` is the file where you declare your **intent** — which packages this project needs and
which Python it runs on — and `uv.lock` is the machine-written record of the **exact resolution** of
that intent, which is what makes an environment reproducible on someone else's machine a year from
now.

---

## The story

A model is trained in March. It scores 0.91 on the held-out set, the number goes into a report, and
the work moves on.

In September, someone needs to retrain it on newer data. They clone the repository, install the
requirements — the file says `scikit-learn`, `pandas`, `numpy`, with no versions — and run the
training script.

It scores 0.87.

Nothing about the code changed; they check `git log` and there is one commit since March, a
docstring fix. But the environment they just built is not the environment from March. `scikit-learn`
released a new minor version in June that changed a default. `pandas` changed how it handles a dtype.
Neither is a bug — both are documented, deliberate improvements — but together they moved the number,
and now nobody can say whether 0.91 was real, whether 0.87 is the truth, or which of the dozen
packages is responsible.

They cannot go back, either. The requirements file never recorded what March actually installed. The
information does not exist anywhere.

The whole cost — a week of work, and a number in a report that can no longer be defended — is the
absence of one file that a tool would have written for free.

---

## The idea in plain language

Two files, two different jobs, and confusing them is the root of the story above.

**`pyproject.toml` is written by you.** It is the project's declaration: its name, the Python it
requires, the packages it directly depends on, and the configuration of its tools. It is short,
human-readable, and edited deliberately. TOML — *Tom's Obvious Minimal Language* — is a plain-text
configuration format built around `key = value` lines grouped under `[section]` headers; if you have
seen an `.ini` file, you can read TOML.

**`uv.lock` is written by the tool.** When you ask for a package, the resolver works out which exact
version of it, **and of everything it depends on**, satisfies every constraint at once — then writes
all of it down with cryptographic hashes. You never edit this file. You commit it.

The distinction that matters:

| | `pyproject.toml` | `uv.lock` |
|---|---|---|
| Written by | you | the tool |
| Contains | direct dependencies | **every** package, including transitive ones |
| Says | what you want | what was actually resolved |
| Read by | humans | machines |
| Committed | yes | **yes** |

The phrase to internalise is **transitive dependency**: a package your package needs. You ask for
pandas; pandas needs NumPy; NumPy needs nothing further. You declared one dependency and installed
two. A real project declares fifteen and installs two hundred, and *those* are the ones that moved
under the team in the story — nobody had written down a single one of them.

Then there is pinning. In a dependency specification the operator matters enormously:

| Written | Means | Verdict here |
|---|---|---|
| `pandas` | any version at all | never |
| `pandas>=3.0` | 3.0 or anything newer, forever | a wish, not a pin |
| `pandas~=3.0.5` | 3.0.5 up to but excluding 3.1 | still a range |
| `pandas==3.0.5` | exactly this | **this project, always** |

Principle 4 says exact `==`, and the story is why: a range means the version is decided by *when* you
install, and "when" is not a thing you can put in a report. Ranges have a legitimate use — in a
**library** that other people install alongside their own dependencies, an over-tight pin makes your
package impossible to combine with anything. This project is an **application**: nothing installs
alongside it, so exactness costs nothing and buys everything.

The last idea is the one people skip: **the two files must agree, and something must check that
they do.** If you hand-edit `pyproject.toml` and do not re-lock, the declaration and the resolution
have drifted, and your laptop and CI will build different environments from the same commit. That is
what `uv sync --locked` is for — it refuses rather than silently re-resolving.

## Why Setu needs it

- **Principle 4 is the whole of this part.** Exact versions, a committed lockfile, nothing floating.
- **Day 1's entire job** is re-verifying every pin against live PyPI and freezing whatever *today*
  says. It cannot be done without understanding what it is freezing into.
- **Phase 12 onward trains models and reports metrics.** Principle 15 — never demo on the training
  set — is worthless if the environment that produced a number cannot be rebuilt. The story above is
  a Phase 12 failure that starts on Day 0.
- **Day 2 puts this in CI**, where the lockfile is the contract that makes CI's environment identical
  to yours. Without it, "works on my machine" is not a joke but an accurate description of the
  situation.
- **`docs/PINS_DS.md`** exists to be regenerated, not trusted. This file is where its output lands.

## The mechanism

In the `setu/` folder, with `.gitignore` and `.git` already in place
([2.2](2.2-gitignore-before-secrets-exist.md), [2.3](2.3-git-init-and-what-a-repo-is.md)):

```bash
uv init --python 3.12 --no-workspace
```

**Line by line:**

- `uv init` — write a starter `pyproject.toml` (and a `.python-version` file) for this folder. It
  does not install anything yet; it declares.
- `--python 3.12` — record the interpreter requirement chosen in
  [1.4](../01/1.4-python-3-12-under-uv.md), so the decision lives in the repository rather than in
  your memory.
- `--no-workspace` — do not treat this as a member of a larger multi-package workspace. A
  **workspace** is one repository containing several installable packages that share a lockfile;
  useful later, wrong now, and stating it explicitly beats inheriting a default (Principle 4 applies
  to tool flags too).

Now add the first dependencies:

```bash
uv add "python-dotenv==1.2.3"
uv add --dev "ruff==0.16.4" "pytest==9.1.1"
```

**Line by line:**

- `uv add "<pkg>==<version>"` — one command with **three** effects: resolve and install into the
  environment, record the pin in `pyproject.toml`, and update `uv.lock`. That third effect is exactly
  what the story's team was missing, and it is why `pip install` is never used in this project — `pip`
  installs and writes nothing down.
- The quotes around `"python-dotenv==1.2.3"` — some shells treat `==` and `>` specially. Quoting
  every dependency specification is a habit that costs nothing and prevents a confusing class of
  shell error.
- `python-dotenv` — reads a `.env` file into the process environment. Day 3 needs it for the API keys
  that [2.2](2.2-gitignore-before-secrets-exist.md) already arranged to keep out of Git.
- `--dev` — put these in the **development** dependency group. Tools you need to *build and test* the
  project, not to *run* it. The distinction is real: a container image that runs the application does
  not need a linter or a test framework, and shipping them enlarges the image and its attack surface
  for no benefit.
- `ruff` — linter and formatter, one tool. `pytest` — the test framework Principle 7 depends on.
  Both pinned exactly, like everything else.

Look at what was written:

```bash
cat pyproject.toml
```

**Line by line:**

- `[project]` — the standard, tool-independent section defined by Python packaging standards. Any
  compliant tool reads this, which is why `pyproject.toml` replaced the older `setup.py`.
- `name = "setu"` — the importable/distributable name.
- `version = "0.1.0"` — required by the standard. It matters when publishing; here it is a formality.
- `requires-python = "==3.12.*"` — the pin from [1.4](../01/1.4-python-3-12-under-uv.md). The `.*`
  accepts any **patch** release of 3.12 (3.12.4 → 3.12.9, safe, security fixes) while refusing 3.13
  (a **minor** jump, which can break compiled wheels). That single line is the version reasoning of
  that part, made executable.
- `dependencies = [...]` — what the application needs at runtime.
- `[dependency-groups]` with `dev = [...]` — the standardised location for development-only
  dependencies.
- `[build-system]` with `requires = ["hatchling"]` — which **build backend** turns this source tree
  into an installable package. It is needed because the project installs itself, which is what makes
  `import setu` work with the `src/` layout from [2.1](2.1-the-folder-skeleton.md).
- `[tool.hatch.build.targets.wheel]` with `packages = ["src/setu"]` — tells that backend where the
  package actually lives. **This is the line that makes the `src` layout work**, and its absence is
  why `import setu` failed in [2.1](2.1-the-folder-skeleton.md)'s "When it breaks".
- `[tool.ruff]`, `[tool.pytest.ini_options]` — tool configuration, kept in the same file so the
  project has one configuration file rather than five.

Now look at the file you did not write:

```bash
head -30 uv.lock && grep -c "name = " uv.lock
```

**Line by line:**

- `head -30` — the first 30 lines, because this file is long by design.
- Each `[[package]]` entry has a name, an exact version, and `[package.wheels]` entries with a
  `hash = "sha256:..."` for each downloadable file. The hash is the security half: an install
  verifies the bytes it received match the bytes that were resolved, so a tampered mirror is caught.
- `grep -c "name = "` — count matching lines. `-c` prints the count rather than the lines. The number
  is larger than the three packages you asked for, and **the difference is the transitive
  dependencies** — precisely the packages nobody in the story had recorded.

Prove the whole point, from a clean slate:

```bash
rm -rf .venv && uv sync --locked && uv run python -c "import dotenv; print(dotenv.__name__, 'ok')"
```

**Line by line:**

- `rm -rf .venv` — delete the environment entirely. Safe, because it is rebuildable; that is the
  claim being tested. (`-r` recursive, `-f` no complaints if it is already gone.)
- `uv sync` — build the environment to match the lockfile exactly.
- `--locked` — **refuse to update the lockfile; error if it is not up to date.** This is the flag
  that turns "someone edited dependencies and forgot to lock" from a silent divergence into a loud
  error, and it is the correct flag in CI and in a Dockerfile. Its neighbour `--frozen` is subtly
  different — it runs *without checking* that things are up to date, which is what you want inside a
  built image where the environment is already correct by construction. Day 1's part 3.2 pulls the
  two apart properly; the short version is **`--locked` verifies, `--frozen` skips verifying.**
- The final `import` proves the rebuilt environment works. You have just demonstrated, in three
  commands, the property the team in the story did not have.

## When it breaks

**The drift `--locked` exists to catch:**

```text
$ uv sync --locked
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
To update the lockfile, run `uv lock`.
```

**What it means.** `pyproject.toml` was edited by hand — someone typed a dependency in directly
instead of using `uv add` — so the declaration and the resolution no longer match. Run `uv lock` to
re-resolve, then **commit both files together**. Committing one without the other is the specific
mistake that makes CI and your laptop build different environments from the same commit.

**Two pins that cannot both be satisfied:**

```text
$ uv add "numpy==1.26.4"
  × No solution found when resolving dependencies:
  ╰─▶ Because pandas==3.0.5 depends on numpy>=2.0 and your project depends on numpy==1.26.4,
      we can conclude that your project's requirements are unsatisfiable.
```

**What it means.** This is a *good* failure, and worth appreciating rather than resenting: the
resolver read every constraint in the tree and proved no combination satisfies them all — before
installing anything. The alternative, which older tools did, is to install something anyway and let
you discover the incompatibility at runtime. Read the explanation as the proof it is: pandas 3.0.5
requires NumPy ≥ 2.0, you demanded 1.26.4, and both cannot be true. Choose which constraint is real.

**The import failure that means the project is not installed:**

```text
$ uv run python -c "from setu import __version__"
ModuleNotFoundError: No module named 'setu'
```

**What it means.** Either the `[build-system]` block is missing — so the project is not installable
and `uv` treated it as a bare script folder — or `packages = ["src/setu"]` does not point at your
package. This is the `src`-layout consequence promised in
[2.1](2.1-the-folder-skeleton.md): the code is only importable once it is genuinely installed, which
is the entire benefit. Check that both blocks exist in `pyproject.toml`, then `uv sync`.

**And the one that looks like the tool's fault:**

```text
$ uv add pandas
$ git commit -am "add pandas"
$ git show --stat HEAD
 pyproject.toml | 1 +
```

**What it means.** Only one file was committed. `uv.lock` was regenerated but is not staged, because
`git commit -a` stages only **tracked** files that changed — and if `uv.lock` had never been
committed before, it is untracked and silently skipped. Now the repository declares pandas with no
resolution recorded. Check `git status` before committing, every time; this is the quiet version of
the story's failure.

## In production

**The lockfile is the contract between every environment you have.** Laptop, CI, staging, production,
and the container image all build from the same `uv.lock`, so "works on my machine" becomes a
falsifiable claim rather than a defence. The professional shape is: `uv sync --locked` in CI and in
the Dockerfile's dependency layer; `uv add` only on a developer's machine; both files always
committed in the same commit. When those three hold, an environment difference between two machines is *impossible* rather
than merely unlikely.

**Applications pin exactly; libraries do not.** This is the nuance that separates people who have
published a package from people who have not. If you pin `requests==2.31.0` inside a *library*, then
anyone whose project needs `requests==2.32.0` cannot use your library at all — you have made your
package uninstallable in half the world. Libraries therefore declare compatible **ranges**
(`requests>=2.28,<3`) and let the application resolve. Applications — services, pipelines, this
project — pin exactly, because nothing installs alongside them. Knowing *which* you are writing is
the actual skill, and answering "it depends on whether it is a library or an application" to a
pinning question marks you as someone who has shipped both.

**Pinning is not the end of the story; it is the start of a maintenance loop.** Exact pins freeze
your security posture too — a pinned dependency with a published vulnerability stays vulnerable until
someone bumps it. Real teams pair exact pins with automated dependency-update pull requests
(Dependabot, Renovate) that raise a small, reviewable, individually-testable bump. The combination —
frozen by default, updated deliberately, with tests as the gate — is what makes exact pinning
responsible rather than negligent. This project's version of that loop is Principle 13, the Friday
freshness check.

**Hashes are supply-chain defence.** Because `uv.lock` records a `sha256` per artifact, an install
verifies that what it downloaded is byte-identical to what was resolved. That defends against a
compromised package mirror and against a maliciously re-uploaded version — the class of attack that
has hit real ecosystems repeatedly. It is also what makes the lockfile the input to vulnerability
scanning: when a CVE lands on a transitive dependency four levels down, the question "which of our
services ship it?" is answered by scanning lockfiles. A project without one cannot answer it, which
is a compliance problem long before it is an engineering one.

**Dev dependencies are a security boundary, not just tidiness.** Everything installed in a production
image is code that could execute there. Linters, test frameworks, notebook kernels and plotting
libraries have no business in a running service. `--dev` keeps them out of the runtime install, which
shrinks both image size and attack surface — one flag doing two jobs.

**The review comment a senior engineer leaves.** On a PR touching `pyproject.toml` with no
`uv.lock` in the diff: *"Lockfile missing — this commit builds differently on CI than on your
machine."* On a `Dockerfile` running a bare `uv sync`: *"Add `--locked`, otherwise the image can
resolve new versions at build time and two builds of the same commit produce different images."* And on `dependencies = ["pandas"]` with no version: *"Pin it — this is an application, and
an unpinned dependency means the build is a function of the date."*

**The interview question.** *"Your model scored 0.91 in March and 0.87 today, with no code changes.
How do you find out why, and how do you prevent it?"* This is the story, asked as a scenario. The
expected shape: check whether the environment is reproducible (is there a lockfile? does it cover
transitive dependencies?), reconstruct March's environment from the lockfile if one exists, diff the
resolved versions, read the changelogs of anything that moved — and prevent it by committing an
exact, hashed lockfile and pinning `random_state` on every estimator. If you can also say why the
requirements file listing three unversioned packages was never going to be enough, you have answered
it fully.

## Check yourself

```bash
cat pyproject.toml && echo "--- packages in lock: ---" && grep -c "^name = " uv.lock && rm -rf .venv && uv sync --locked -q && uv run python -c "import dotenv; print('rebuilt from lock: ok')"
```

The last three commands delete the environment and rebuild it from the lockfile alone. If that
prints `ok`, your project is reproducible — which is a stronger claim than most repositories on the
internet can make.
