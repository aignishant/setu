# 1.1 — The file that did not fit

## One-line answer

A table on disk and the same table in memory are different sizes, the gap is a number you can
measure rather than guess, and the day pandas stops working is the day that number crosses the
amount of memory your machine actually has.

---

## The story

The flat has been keeping its shopping file for three years now.

It started as a page of lines — bread, eggs, milk, rice — with the part of the shop next to each
one, the pack size, the price, and how many were needed that week. Somebody typed it up every week
and never stopped. Nobody ever deleted anything, because why would you.

Somebody sits down to add up what each part of the shop cost over the whole three years. They open
the file the way they have opened it a hundred times. The laptop's fan comes on. The cursor sits
there. Nothing appears.

Then the window closes and there is a line of red text about memory.

The strange part is the file itself. They go and look at it in the folder, and it is twenty
megabytes. Twenty. There are photographs on the same laptop bigger than that, and the laptop opens
those without complaining. So the obvious question, and it is a completely fair one: **how does a
twenty-megabyte file run a machine with twelve gigabytes in it out of room?**

That question has an exact answer, and it is not "the laptop is old".

---

## The idea in plain language

Two different things are being called "the file", and they are different sizes.

**On disk**, the file is written in a format called Parquet, which stores each column separately and
squeezes it. When a column holds the word `dairy` five million times, Parquet does not write the
word five million times. It writes the word once, in a small list of the words that appear, and then
writes five million references to that list — and it packs those references very tightly. That is
called **dictionary encoding**, and it is why a file of endlessly repeating words is so small.
Day 27 introduced the format
([Day 27, 3.1](../../../day-27-reading-and-writing/parts/03-parquet/3.1-columns-on-disk-with-types.md))
and measured its size against a CSV
([Day 27, 3.3](../../../day-27-reading-and-writing/parts/03-parquet/3.3-the-size-and-the-speed-measured.md)).

**In memory**, a pandas DataFrame is not squeezed at all. **Memory** is the working space a program
has while it runs — the place the table lives once it has been read off disk. It is much smaller
than a disk and it is not compressed. When pandas reads that column, it writes the letters of
`dairy` out again, once per row, exactly as
[Day 34, 1.1](../../../day-34-categories-and-describe/parts/01-the-repeated-word/1.1-the-same-short-word-over-and-over.md)
measured. The squeezing that made the file small is undone the moment the file is read.

So there are two numbers, and the interesting one is the ratio between them. Call it the
**expansion multiple**: the bytes a table takes in memory, divided by the bytes it takes on disk.
People quote folk numbers for this — "pandas needs five times the file size", "ten times" — and the
folk numbers are worthless, because the multiple depends entirely on what is in the columns. A file
full of repeated short words expands enormously. A file of random floating-point numbers barely
expands at all.

There is a third number, and it is the one that actually kills the laptop. Reading a file and then
answering a question about it does not use only the memory the final table takes. Every step along
the way makes another table, and for a moment several of them exist at the same time. The number
that matters is the **peak** — the largest amount of memory the program held at any single instant,
not the amount it holds at the end.

This part measures all three, on the flat's file, at three sizes. It fixes nothing. Fixing is what
the rest of the day is for.

## The mechanism

The flat's file, built the same way every time so that every part of this day reads identical bytes.

```python
import numpy as np
import pandas as pd

ITEMS = ["bread", "eggs", "milk", "rice"]
AISLES = {"bread": "bakery", "eggs": "dairy", "milk": "dairy", "rice": "dry goods"}
SIZES = ["small", "medium", "large"]


def flat_receipts(rows: int, seed: int = 35) -> pd.DataFrame:
    """The flat's shopping file, `rows` lines long, built the same way every time."""
    rng = np.random.default_rng(seed)
    item = rng.choice(ITEMS, rows)
    return pd.DataFrame(
        {
            "item": pd.Series(item, dtype="str"),
            "aisle": pd.Series([AISLES[i] for i in item], dtype="str"),
            "size": pd.Series(rng.choice(SIZES, rows), dtype="str"),
            "price": np.round(rng.normal(2.0, 0.5, rows), 2),
            "need": rng.integers(1, 4, rows),
        }
    )
```

**Line by line:**

- `AISLES` is a dictionary, not a list, because the part of the shop is **determined** by the item.
  Bread is always bakery. If `aisle` were drawn at random, the file would contain eggs in the dry
  goods aisle, and every join later in the day would be meaningless.
- `np.random.default_rng(seed)` with `seed: int = 35` — the day number. A seeded generator object
  rather than the old global functions, so the numbers in this document are the numbers on your
  machine. The draws come out in the order the code asks for them, so moving one line changes every
  line after it.
- `dtype="str"` written out on each text column rather than left to inference. pandas 3.0 infers
  `str` anyway ([Day 26,
  2.2](../../../day-26-frames-and-copy-on-write/parts/02-the-str-dtype/2.2-str-the-dtype-pandas-3-infers.md)),
  but a stated dtype is the pin, and this frame is about to be compared against two other libraries
  that have their own opinions about text.
- `rng.normal(2.0, 0.5, rows)` — prices scattered around two pounds. `np.round(..., 2)` at the point
  of creation, because a price with fifteen decimal places is not a price.
- `rng.integers(1, 4, rows)` — how many of that thing were needed, from 1 up to 3. `4` is excluded.
  This is the column the day's question filters on.
- `rows` is a parameter with no default. Every measurement below states its size, and a size that is
  implicit is a size somebody will get wrong.

Write it out at three sizes and measure both numbers.

```python
from pathlib import Path

import pandas as pd

MB = 1024 * 1024

for rows in (100_000, 1_000_000, 10_000_000):
    path = Path(f"receipts_{rows}.parquet")
    flat_receipts(rows).to_parquet(path, index=False)
    frame = pd.read_parquet(path)
    memory = int(frame.memory_usage(deep=True).sum())
    disk = path.stat().st_size
    print(
        f"rows {rows:>10,}  disk {disk / MB:8.2f} MiB  memory {memory / MB:8.2f} MiB"
        f"  multiple {memory / disk:5.1f}x  bytes/row {memory / rows:5.1f}"
    )
    del frame
```

**Line by line:**

- `to_parquet(path, index=False)` — `index=False` because this frame's index is a plain row counter
  that carries no information ([Day 26,
  1.2](../../../day-26-frames-and-copy-on-write/parts/01-the-two-objects/1.2-the-index-is-not-a-row-number.md)).
  Writing it would add a column to the file that the other two tools in this day do not have, and
  the whole point is that all three read the same bytes.
- `frame.memory_usage(deep=True).sum()` — the frame's own report of what it occupies, summed across
  columns. `deep=True` is the argument that says *follow what the column points at rather than
  counting the pointer*; without it a text column reports only its bookkeeping
  ([Day 34, 1.2](../../../day-34-categories-and-describe/parts/01-the-repeated-word/1.2-what-memory-usage-actually-counts.md)).
- `path.stat().st_size` — the bytes the operating system says the file takes. Not an estimate.
- `MiB` rather than `MB`: `1024 * 1024`, which is what every memory tool on the machine reports, and
  saying which one you meant costs one word.
- `del frame` at the end of each pass. Without it, three frames are alive at once and the largest
  measurement is taken while two others are still holding memory.

```text
rows    100,000  disk     0.21 MiB  memory     5.32 MiB  multiple  25.4x  bytes/row  55.8
rows  1,000,000  disk     2.06 MiB  memory    53.24 MiB  multiple  25.9x  bytes/row  55.8
rows 10,000,000  disk    20.55 MiB  memory   532.48 MiB  multiple  25.9x  bytes/row  55.8
```

**Twenty-six times.** Not five, not ten. The twenty-megabyte file becomes half a gigabyte of frame,
and the multiple is stable across all three sizes because it is a property of the columns, not of
the row count. **55.8 bytes per row** is the number to carry forward; it is the one that turns "how
many rows" into "how much memory".

Where do 55.8 bytes go? Ask per column.

```python
frame = pd.read_parquet("receipts_1000000.parquet")
print(frame.memory_usage(deep=True))
```

**Line by line:**

- Calling `memory_usage` on the **frame** rather than on a column returns a Series with one entry
  per column plus one for the index. It is a table, not a number, and code that expects a number
  will fail later somewhere confusing.

```text
Index         132
item     12249978
aisle    14247318
size     13333368
price     8000000
need      8000000
dtype: int64
```

The two number columns cost exactly eight bytes a row each, which is what a 64-bit float and a
64-bit integer are. The three text columns cost between twelve and fourteen bytes a row, which is
the characters plus an eight-byte offset per value — the layout
[Day 34, 1.1](../../../day-34-categories-and-describe/parts/01-the-repeated-word/1.1-the-same-short-word-over-and-over.md)
pulled apart. **Three columns holding four, three and three distinct words between them account for
seventy per cent of the memory.**

Now the third number: the peak. Answer the day's question on the ten-million-row file and watch the
working set while it happens.

```python
import ctypes
from ctypes import wintypes


class PMC(ctypes.Structure):
    _fields_ = [
        ("cb", wintypes.DWORD),
        ("PageFaultCount", wintypes.DWORD),
        ("PeakWorkingSetSize", ctypes.c_size_t),
        ("WorkingSetSize", ctypes.c_size_t),
        ("QuotaPeakPagedPoolUsage", ctypes.c_size_t),
        ("QuotaPagedPoolUsage", ctypes.c_size_t),
        ("QuotaPeakNonPagedPoolUsage", ctypes.c_size_t),
        ("QuotaNonPagedPoolUsage", ctypes.c_size_t),
        ("PagefileUsage", ctypes.c_size_t),
        ("PeakPagefileUsage", ctypes.c_size_t),
    ]


_k32 = ctypes.WinDLL("kernel32", use_last_error=True)
_psapi = ctypes.WinDLL("psapi", use_last_error=True)
_k32.GetCurrentProcess.restype = wintypes.HANDLE
_psapi.GetProcessMemoryInfo.argtypes = [wintypes.HANDLE, ctypes.POINTER(PMC), wintypes.DWORD]


def working_set() -> tuple[int, int]:
    """(bytes held right now, largest ever held) for this process."""
    counters = PMC()
    counters.cb = ctypes.sizeof(PMC)
    _psapi.GetProcessMemoryInfo(_k32.GetCurrentProcess(), ctypes.byref(counters), counters.cb)
    return counters.WorkingSetSize, counters.PeakWorkingSetSize
```

**Line by line:**

- `memory_usage` asks the frame what it thinks it holds. `working_set` asks the **operating system**
  what the process actually holds, which includes the interpreter, every imported library, and every
  buffer a library allocated on the way. The two answers differ, and the second one is the one that
  runs out.
- `ctypes.Structure` with `_fields_` in this exact order — it mirrors a C struct the operating
  system fills in, and a field in the wrong place gives a plausible-looking wrong number rather than
  an error.
- `_k32.GetCurrentProcess.restype = wintypes.HANDLE` is not optional. Without it `ctypes` assumes
  the return value is a 32-bit `int`, silently truncates the 64-bit process handle, and the call
  quietly reports zero bytes for everything. That was the first version of this code and it printed
  `0.0 MiB` four times in a row before the cause was found.
- `PeakWorkingSetSize` is kept by the operating system across the whole life of the process, so it
  can be read *after* the peak has passed. That is the only reason this measurement is possible
  without a second thread watching.

```python
import pandas as pd

MB = 1024 * 1024


def show(tag: str) -> None:
    now, peak = working_set()
    print(f"{tag:22s} working set {now / MB:8.1f} MiB   peak {peak / MB:8.1f} MiB")


show("pandas imported")
frame = pd.read_parquet("receipts_10000000.parquet")
show("after read")
wanted = frame[frame["need"] > 1]
show("after filter")
totals = wanted.groupby("aisle")["price"].sum().sort_values(ascending=False)
show("after group + sort")
```

**Line by line:**

- `show("pandas imported")` before anything else, to establish the floor. Every later number has to
  be read against it.
- `frame[frame["need"] > 1]` is the day's filter: keep the lines where more than one was needed. The
  inner expression makes a column of `True`/`False`, and the outer brackets keep the rows where it
  is `True` ([Day 28, 2.2](../../../day-28-selection-and-alignment/parts/02-masks/2.2-selecting-with-a-mask.md)).
- `.groupby("aisle")["price"].sum()` — split the rows by the part of the shop, add up the prices in
  each ([Day 31, 2.1](../../../day-31-groupby/parts/02-aggregating/2.1-one-number-for-each-group.md)).
- `.sort_values(ascending=False)` — biggest first
  ([Day 29, 4.1](../../../day-29-iteration-and-order/parts/04-sorting/4.1-sort-values-the-order-you-asked-for.md)).
  Those four steps are the whole question this day asks, in every tool.

```text
pandas imported        working set     77.6 MiB   peak     77.6 MiB
after read             working set    819.2 MiB   peak    819.2 MiB
after filter           working set   1362.2 MiB   peak   1429.0 MiB
after group + sort     working set   1171.0 MiB   peak   1429.0 MiB
```

Read that against the file: **20.55 MiB on disk, 1429 MiB at peak.** Not twenty-six times. **Seventy
times.**

The extra comes from two places. The read itself needs more than the finished frame — 819 MiB held
for a frame that reports 532 MiB, because the reader builds Arrow buffers and then converts them.
And the filter makes a *second* whole table: the 6.67 million rows that survive, sitting alongside
the ten million rows they came from, both alive at the same instant.

So the arithmetic that answers the story. This machine has 11.75 GiB of memory, of which roughly
2.66 GiB were free with a browser and an editor open. At 55.8 bytes a row the frame alone hits
11.75 GiB at about **226 million rows** — but the peak is 2.7 times the frame, so in practice the
wall is around **84 million rows**, and with only 2.66 GiB actually free it is nearer **19 million**.

Three years of a flat's shopping is nowhere near that. Three years of a shop's till receipts is well
past it. That is the whole subject of the day.

## When it breaks

Ask for the file at a billion lines, which is what the arithmetic above says will not fit:

```text
$ uv run python -c "
from gen import flat_receipts
big = flat_receipts(1_000_000_000)
print(len(big))
"
Traceback (most recent call last):
  File "<string>", line 5, in <module>
  File "gen.py", line 19, in flat_receipts
    item = rng.choice(ITEMS, rows)
           ^^^^^^^^^^^^^^^^^^^^^^^
  File "numpy/random/_generator.pyx", line 1015, in numpy.random._generator.Generator.choice
numpy._core._exceptions._ArrayMemoryError: Unable to allocate 18.6 GiB for an array with shape (1000000000,) and data type <U5
```

**What it means.** `_ArrayMemoryError` is a subclass of Python's built-in `MemoryError`, so
`except MemoryError:` catches it. The message is unusually good: it names the exact number of bytes
that were asked for, the shape, and the dtype. `<U5` is a fixed-width Unicode string of five
characters — four bytes per character, five characters, twenty bytes a row, a billion rows, 18.6
GiB. Nothing was written and nothing was corrupted; the request was simply refused before it
started.

The important detail is *where* it stopped: on the very first line of the function, before pandas
was involved at all. The memory ran out building the raw column, not building the frame.

The same wall, reached from the other direction — reading the file that exists and stacking it up:

```text
$ uv run python -c "
import pandas as pd
df = pd.read_parquet('receipts_1000000.parquet')
three_years = pd.concat([df] * 5000, ignore_index=True)
print(len(three_years))
"
Traceback (most recent call last):
  File "<string>", line 4, in <module>
  File "pandas/core/reshape/concat.py", line 466, in concat
    result = _get_result(
             ^^^^^^^^^^^^
  File "pandas/core/reshape/concat.py", line 657, in _get_result
    new_data = concatenate_managers(
               ^^^^^^^^^^^^^^^^^^^^^
  File "pandas/core/internals/concat.py", line 133, in concatenate_managers
    values = np.concatenate(vals, axis=1)  # type: ignore[arg-type]
             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
numpy._core._exceptions._ArrayMemoryError: Unable to allocate 37.3 GiB for an array with shape (1, 5000000000) and data type float64
```

**What it means.** The traceback goes through four pandas frames and lands, again, in NumPy. That is
the honest picture of where pandas's memory ceiling lives: pandas asks NumPy for one contiguous
block per column, and NumPy asks the operating system, and the operating system says no. `37.3 GiB`
is five billion rows times eight bytes for the `price` column **alone** — the columns are allocated
one at a time and it failed on the first big one.

Both failures are the good case. The bad case is the one with no traceback at all: a request that
the operating system agrees to and then services by moving pages out to disk. Nothing raises,
nothing is logged, and a job that used to finish now does not, because every array read is a disk
read. The only sign is the fan.

## In production

**What a professional writes instead of the teaching version.** Not `read_parquet` and hope. A
Parquet file carries a footer describing itself, and reading the footer costs nothing:

```python
import pyarrow.parquet as pq

handle = pq.ParquetFile("receipts_10000000.parquet")
meta = handle.metadata
print("rows       :", meta.num_rows)
print("row groups :", meta.num_row_groups)
print("columns    :", handle.schema_arrow.names)
print("estimate   :", round(meta.num_rows * 55.8 / 1024**2, 1), "MiB in memory")
```

**Line by line:**

- `pq.ParquetFile(path)` opens the file and reads only its footer. No column data is touched, so
  this is safe on a file far larger than memory — which is exactly when you need it.
- `meta.num_rows` is written in the footer by whoever produced the file. It is the row count without
  a read.
- `meta.num_row_groups` is how many independent chunks the file is split into. That number is the
  unit of a chunked read, and [1.3](1.3-the-three-answers.md) uses it.
- `55.8` is **this file's** measured bytes per row, from the table above. A professional keeps that
  constant next to the loader with a comment saying which file it was measured on, and re-measures
  when the schema changes. A constant copied from a blog post is a guess with a decimal point.

```text
rows       : 10000000
row groups : 10
columns    : ['item', 'aisle', 'size', 'price', 'need']
estimate   : 532.1 MiB in memory
```

532.1 estimated against 532.48 measured. The estimate is good because the multiple is a property of
the schema, and the schema is in the footer.

**What degrades at scale.** The expansion multiple is not stable across *files*, only across sizes
of the same file. Ask the footer what each column costs on disk and the reason becomes visible:

```text
column     compressed   uncompressed
item           267155         266889
aisle          267652         267385
size           267236         266969
price         1188009        1189449
need           268605         268341
```

The three text columns cost about 267 KB each in a file whose rows they dominate in memory, because
dictionary encoding replaced each word with a small code. The `price` column is four times bigger on
disk than any of them, because a million distinct rounded floats have no repetition to exploit.
**The columns that are cheap on disk are the expensive ones in memory, and vice versa.** A file that
is mostly random floats will expand by a factor near one; a file that is mostly repeated words will
expand by twenty-six or more. Any rule of thumb that does not ask what is in the columns is wrong on
half of all files.

Note also that `compressed` and `uncompressed` are within a rounding error of each other, and for
three columns compressed is *larger*. The general-purpose compressor had nothing left to do after
dictionary encoding, and paid a few hundred bytes of framing for the privilege.

**The failure that only shows with real data.** A daily job read a Parquet file, filtered it, grouped
it, and wrote a summary. It ran for two years. Then an upstream team added a `user_agent` column —
long, text, high-cardinality — and the file on disk grew by fifteen per cent, because such strings
compress well. In memory it grew by a factor of four, and the job started being killed by the
container's memory limit. The team's first theory was that the data had grown. The data had grown by
fifteen per cent. **The file size told them nothing, because the file size is the compressed number
and the limit is on the uncompressed one.**

**The review comment a senior engineer leaves.** *"This calls `read_parquet` on a path that comes
from configuration, so you have no idea how big it is at review time. Open the footer first, multiply
`num_rows` by the bytes-per-row you measured, and raise a clear error if the estimate is over the
container limit. A `MemoryError` from inside NumPy at three in the morning is a much worse message
than the one you could have written."*

**The interview question.** *"You have a 200 MB Parquet file and a machine with 8 GB of RAM. Will
pandas read it?"* The answer that shows you have done this is not yes or no. It is: *it depends
entirely on the columns, so let me look at the footer.* Repeated short text expands by twenty-plus
and 200 MB becomes five gigabytes; random floats expand by roughly one and 200 MB stays 200 MB. Then
the second half, which is the half that catches people out: even if the frame fits, the **peak** is
roughly two to three times the frame, because reading builds buffers and every filter makes a second
table. On this machine a 20 MiB file peaked at 1429 MiB, which is seventy times the file.
