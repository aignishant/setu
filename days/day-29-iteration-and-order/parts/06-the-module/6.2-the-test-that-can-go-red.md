# 6.2 — `tests/test_order.py`: the test that could not fail

## One-line answer

The day's suite tests determinism by sorting the same rows twice from different starting orders — and
the first version of that test **passed even with the tie-breaker deleted**, because the fixture had
no tie in it.

---

## The story

The suite is written, it is green, and the mutation is run: delete the tie-breaker from the sort key,
which is the one line the whole of section 4 exists to justify.

Nothing goes red. Twelve tests pass, exactly as before.

The test that was supposed to catch it sorts the fixture forwards and backwards and checks the two
results match. It is the right test. It ran. It passed both before and after the change, because the
four rows in the fixture all differ on aisle or price, so there was never a tie for the tie-breaker to
break.

The test was correct, well-named, and testing nothing.

---

## The idea in plain language

This suite has the three kinds of assertion Day 28's had — what a function returns, what it does not
do, and what it refuses
([Day 28, 6.2](../../../day-28-selection-and-alignment/parts/06-the-module/6.2-the-test-that-can-go-red.md))
— plus one that belongs specifically to ordering:

**Determinism.** Run the operation on the same rows in a different order and assert the results are
identical. That is the only way to test a property like "this sort is total", because a single run
cannot tell you whether it got lucky.

And it has the failure the story describes, which is worth more than the tests around it: **a
determinism test is only as good as the ties in its fixture.** If nothing ties, every sort is total and
the test is a tautology. The fix is not a different test; it is a fixture that contains the case, plus
an assertion that it does:

```text
assert tied.duplicated(od.SHOP_ORDER).any(), "the fixture must contain a real tie"
```

That line is the pattern to carry away. **When a test exists to catch a specific condition, assert that
the fixture contains the condition** — otherwise a change to the fixture, months later, silently
disarms the test and nothing tells you.

This is Principle 7's rule with teeth: a test nobody has watched fail is not a test, and the way to
watch is to break the module on purpose and count what goes red. Here that count was zero the first
time, which is the most useful result a mutation can give.

## The mechanism

The fixture and the ordinary assertions:

```python
"""Ordering is deterministic, vectorised, and refuses to decide a tie on the caller's behalf."""

from __future__ import annotations

import pandas as pd
import pytest

from setu import order as od


@pytest.fixture
def shop() -> pd.DataFrame:
    return pd.DataFrame(
        {
            "item": pd.Series(["milk", "bread", "eggs", "rice"], dtype="str"),
            "need": [2, 1, 6, 1],
            "price": [1.15, 1.40, 0.32, 2.05],
            "aisle": pd.Series(["07", "03", "07", "11"], dtype="str"),
        }
    ).set_index("item")


def test_line_totals_does_not_touch_the_caller_frame(shop: pd.DataFrame) -> None:
    before = shop.copy(deep=True)
    od.line_totals(shop)
    pd.testing.assert_frame_equal(shop, before)


def test_rank_shares_the_best_rank_on_a_tie(shop: pd.DataFrame) -> None:
    tied = shop.assign(price=[5.0, 5.0, 3.0, 5.0])
    ranked = od.with_rank(tied)
    assert ranked["rank"].tolist() == [1, 1, 4, 1]
```

**Line by line:**

- The fixture returns a **fresh frame per test**, which matters because several tests here check that a
  function did not mutate its argument
  ([Day 2, 3.2](../../../day-02-quality-gate/parts/03-pytest/3.2-fixtures-and-tmp-path.md)).
- `copy(deep=True)` — **`deep=True` stated**, because under Copy-on-Write a shallow copy shares data
  until written to ([Day 26, 3.2](../../../day-26-frames-and-copy-on-write/parts/03-copy-on-write/3.2-the-copy-that-has-not-happened-yet.md))
  and this test needs an independent snapshot.
- `assert_frame_equal(shop, before)` — the **whole frame** including dtypes, not just the column list.
  A function that changed a value without adding a column would slip past a shape check.
- `[1, 1, 4, 1]` — the tie test asserts the **exact** ranks, so it pins `method="min"` rather than just
  "some ranking happened". Under the default `average` it would be `[2, 2, 4, 2]` and this test would
  go red ([5.2](../05-ranking/5.2-the-five-ways-to-rank-a-tie.md)).
- `shop.assign(price=[...])` builds the tied case **inside the test**, so the shared fixture stays
  simple and each test states the condition it needs.

The determinism test, in the version that works:

```python
def test_shop_order_is_the_same_whatever_the_input_order(shop: pd.DataFrame) -> None:
    """The sort is total, so a reshuffled input gives an identical result.

    The fixture is deliberately amended so two rows tie on the whole of SHOP_ORDER —
    without a genuine tie this test passes even when the tie-breaker is removed.
    """
    tied = shop.assign(
        aisle=pd.Series(["07", "07", "07", "11"], index=shop.index, dtype="str"),
        price=[1.15, 1.15, 1.15, 2.05],
    )
    assert tied.duplicated(od.SHOP_ORDER).any(), "the fixture must contain a real tie"
    forwards = od.in_shop_order(tied)
    backwards = od.in_shop_order(tied.iloc[::-1])
    pd.testing.assert_frame_equal(forwards, backwards)
```

**Line by line:**

- The docstring's second paragraph exists because **the first version of this test did not work**, and
  the next person to simplify the fixture needs to know why it is the shape it is.
- `tied` gives three rows the same aisle **and** the same price, so they tie on the whole of
  `SHOP_ORDER` and only the index can separate them.
- `pd.Series([...], index=shop.index, dtype="str")` — the index is given, because a bare list assigned
  through `assign` would be fine but a `Series` without one would align to nothing
  ([Day 28, 4.2](../../../day-28-selection-and-alignment/parts/04-alignment/4.2-alignment-is-automatic.md)).
- **`assert tied.duplicated(od.SHOP_ORDER).any()` is the important line.** It asserts the *fixture*, not
  the code — if somebody later changes those prices, this fails loudly rather than quietly making the
  test meaningless ([4.2](../04-sorting/4.2-the-tie-that-broke-the-report.md)).
- `shop.iloc[::-1]` — the same rows, reversed. Not sorted differently, not re-generated: **the same
  data in a different arrangement**, which is the only variable being tested.
- `assert_frame_equal` on the two results, so the assertion is about the whole frame in order.

And the empty case, which is the one that never happens in development:

```python
def test_empty_frame_survives_every_public_function() -> None:
    """The case that never happens in development and always happens in production."""
    empty = pd.DataFrame(
        {
            "item": pd.Series([], dtype="str"),
            "need": pd.Series([], dtype="int64"),
            "price": pd.Series([], dtype="float64"),
            "aisle": pd.Series([], dtype="str"),
        }
    ).set_index("item")
    assert len(od.line_totals(empty)) == 0
    assert len(od.in_shop_order(empty)) == 0
    assert len(od.with_rank(empty)) == 0
    with pytest.raises(ValueError):
        od.top_n(empty, 0)
```

**Line by line:**

- The empty frame is built **with its dtypes stated**, so it is the shape a filter would have produced
  rather than a shapeless `pd.DataFrame()`
  ([Day 28, 2.5](../../../day-28-selection-and-alignment/parts/02-masks/2.5-the-mask-that-matched-nothing.md)
  showed those two are not interchangeable).
- Three functions are asserted to **return empty rather than raise**, which is the decision
  [6.1](6.1-the-order-module.md) made: an empty input is a valid input.
- `top_n(empty, 0)` raises for the `n` rather than for the emptiness, which is the correct reason —
  and asserting it here pins that `n < 1` is checked before anything touches the frame.

Green, with the module finished:


## When it breaks

**The mutation that changed nothing — the first attempt.** In `src/setu/order.py`, replace the total
sort with a partial one:

```text
    keys = [*SHOP_ORDER, shop.index.name]
    ordered = shop.sort_values(by=keys, ascending=[*SHOP_DIRECTION, True], kind="stable")
```

with:

```text
    ordered = shop.sort_values(by=SHOP_ORDER, ascending=SHOP_DIRECTION)
```

**Line by line:**

- The tie-breaker is gone and so is `kind="stable"`. This is exactly the change
  [4.2](../04-sorting/4.2-the-tie-that-broke-the-report.md) says makes a sort non-deterministic.
- It is also precisely what a reviewer tidying up would write, because the two removed pieces look
  like ceremony.

Run the suite against the **original** fixture — the one where all four rows differ on aisle or price:

```text
$ uv run pytest tests/test_order.py -q
```

```text
............                                                             [100%]
12 passed in 0.58s
```

**Twelve passed. The determinism test did not notice.**

Nothing is wrong with the test's logic: it sorts forwards, sorts backwards, and compares. The problem
is the data. In that fixture `milk` and `eggs` share aisle `07` and have different prices, so the two
sort keys already separate every row — **there was no tie for the tie-breaker to break**, and removing
it changed nothing to observe.

Now add the tie to the fixture, as the mechanism above does, and run the same mutation:

```text
$ uv run pytest tests/test_order.py -q
```

```text
E   AssertionError: DataFrame.index are different
E
E   DataFrame.index values are different (50.0 %)
E   [left]:  Index(['milk', 'bread', 'eggs', 'rice'], dtype='str', name='item')
E   [right]: Index(['eggs', 'bread', 'milk', 'rice'], dtype='str', name='item')
E   At positional index 0, first diff: milk != eggs

=========================== short test summary info ===========================
FAILED tests/test_order.py::test_shop_order_is_the_same_whatever_the_input_order
1 failed, 11 passed in 0.56s
```

**What it means.** Now it fails, and the message is exactly the finding: the same three tied rows came
out as `milk, bread, eggs` from one input order and `eggs, bread, milk` from the other. Fifty per cent
of the index differs, from data that is identical.

**The lesson is not "write a determinism test".** It is that a test for a specific condition has to
*contain* that condition, and the only way to know it does is to break the code and watch. A green
suite is not evidence; a suite you have seen go red is.

**A mutation that the suite catches immediately — the rank method:**

```text
$ uv run pytest tests/test_order.py -q -k rank
```

Change `method="min"` to `method="average"` in `with_rank` and:

```text
E       assert [2, 2, 4, 2] == [1, 1, 4, 1]
E
E         At index 0 diff: 2 != 1
E         Use -v to get more diff

FAILED tests/test_order.py::test_rank_shares_the_best_rank_on_a_tie - assert ...
1 failed, 2 passed, 9 deselected in 0.63s
```

**What it means.** This one works, because the test asserts the **exact ranks** rather than "there is a
rank column". Asserting the values pins the method; asserting the dtype or the length would not.

Note that the ranks are still whole numbers under `average` here — `[2, 2, 4, 2]` — so a test that
only checked "the ranks are integers" would also have passed. **The assertion has to be as specific as
the behaviour you are protecting.**

**The one that is not caught by anything — the vectorisation:**

```text
$ uv run python -c "
import pandas as pd
from setu import order as od
shop = pd.DataFrame(
    {'need': [2, 1], 'price': [1.15, 1.40]},
    index=pd.Index(['milk', 'bread'], name='item'),
)
loop_version = pd.Series(
    [r.need * r.price for r in shop.itertuples()], index=shop.index
).round(2)
print('module :', od.line_totals(shop).tolist())
print('a loop :', loop_version.tolist())
print('equal? :', od.line_totals(shop).equals(loop_version))
"
```

```text
module : [2.3, 1.4]
a loop : [2.3, 1.4]
equal? : True
```

**What it means.** Replacing `line_totals`' one expression with a loop over `itertuples` produces the
**identical** result, so **no correctness test can catch it.** The suite would stay green while the
function became hundreds of times slower ([3.2](../03-the-measurement/3.2-the-four-ways-timed.md)).

That is a genuine limit of a correctness suite, and there are two honest responses. The docstring says
"Vectorised; no Python runs per row" so a reviewer knows the property is deliberate
([6.1](6.1-the-order-module.md)). And a **performance test** — a timing with a generous ratio-based
threshold, run separately from the fast suite — is the only automated defence
([Day 25, 5.2](../../../day-25-copy-view-and-the-gate/parts/05-the-gate/5.2-the-performance-test-in-ci.md)).

## In production

**What a professional writes instead of the teaching version.** The determinism property is tested
once, generically, over every ordering function:

```python
import pandas as pd
import pytest

from setu import order as od

ORDERINGS = [
    pytest.param(od.in_shop_order, id="in_shop_order"),
    pytest.param(lambda f: od.with_rank(f), id="with_rank"),
]


@pytest.mark.parametrize("operation", ORDERINGS)
def test_is_deterministic_under_reordering(operation, tied_shop: pd.DataFrame) -> None:
    """Same rows, different arrival order, identical result. Requires a fixture that ties."""
    assert tied_shop.duplicated(od.SHOP_ORDER).any(), "fixture must contain a real tie"
    forwards = operation(tied_shop)
    backwards = operation(tied_shop.iloc[::-1])
    pd.testing.assert_frame_equal(forwards.sort_index(), backwards.sort_index(), check_like=True)
```

**Line by line:**

- `ORDERINGS` is a **list of the functions that promise determinism**, so adding a sixth function to
  the module means adding a line here rather than hoping somebody writes a test.
- `id=` on each param, so a failure names the function
  ([Day 2, 3.3](../../../day-02-quality-gate/parts/03-pytest/3.3-markers-and-exit-code-five.md)).
- The fixture assertion is **inside the shared test**, so it protects every case at once — this is the
  line whose absence caused the whole story.
- `.sort_index()` on both before comparing, because `with_rank` does not change the row order and
  `in_shop_order` does; comparing on a common index tests the **values** rather than the arrangement.
  For `in_shop_order` the arrangement is separately tested by the non-parameterised test above.
- `check_like=True` ignores column order, so a function that adds its column in a different position is
  not a failure ([Day 27, 5.3](../../../day-27-reading-and-writing/parts/05-the-module/5.3-the-round-trip-test.md)).

**What changes at scale.** Three things.

**Determinism testing wants generated data, not a fixture.** Four rows can contain one kind of tie;
Hypothesis can generate frames with ties everywhere, ties nowhere, all values equal, and a single row,
and assert the property over all of them. That is where the fixture-has-no-tie failure stops being
possible by construction rather than by remembering.

**Mutation testing automates the exercise this part did by hand.** A tool makes hundreds of small
changes and reports which ones the suite failed to notice; the tie-breaker deletion would have appeared
in that report on day one. It is expensive and belongs on a schedule rather than in every pull request.

**And the performance property needs its own suite.** Timings are slow and machine-dependent, so they
do not belong beside the correctness tests. The shape that survives CI is a **ratio** — the loop
against the expression on the same machine in the same run — with a generous threshold, exactly as
[Day 25, 5.2](../../../day-25-copy-view-and-the-gate/parts/05-the-gate/5.2-the-performance-test-in-ci.md)
argued.

**The failure that only appears with real data.** A team had a determinism test on their ranking
pipeline, written properly, running nightly. Their fixture was a slice of production data captured
eighteen months earlier, when scores were floats with six decimal places and ties were essentially
impossible. Production later began rounding scores to two places, ties became common, and the ranking
became non-deterministic — **while the test kept passing**, because the fixture still had the old
high-precision values in it. The test was not wrong; it was testing a world that no longer existed.

**The review comment a senior engineer leaves.** *"Good determinism test — please assert that the
fixture actually contains a tie, or it will pass whether or not the tie-breaker is there. I would also
add the empty frame to the parameterised cases; three of these functions have never been run on zero
rows."*

**The interview question.** *"How do you test that a sort is deterministic?"* Run it on the same rows in
two different arrival orders and assert the results are identical. Then the part that matters more:
**the fixture has to contain a tie**, or the test passes trivially — a sort with no ties is total
whatever key you give it, so removing the tie-breaker changes nothing and the test cannot fail. The way
to find that out is to **mutate the module and count what goes red**; a mutation that nothing catches
is a gap in the suite, not a safe change. And the honest limit: a correctness suite cannot catch a
vectorised function being rewritten as a loop, because the answers are identical — that needs a
docstring for the reviewer and a separate, ratio-based performance test for CI.
