# 5.3 — Vector or raster — which file to write

## One-line answer

A PNG is a grid of coloured dots and stops looking good the moment you enlarge it past the dots you
recorded; an SVG or a PDF is the list of instructions for drawing the picture and is sharp at any
size — so the extension you type in `savefig` is a decision about where the picture is going, and
the only thing that reliably decides it is how many marks the chart contains.

---

## The story

The flat's chart has been on the fridge for a while now. Somebody wants a big copy for the
noticeboard in the hall, so everybody can see it on the way in.

The first attempt is the obvious one. A flatmate photographs the fridge sheet with their phone,
takes the photo to the shop, and asks for it printed at poster size. It comes back blurry. Zoom in
on the word "household" and you can see the little squares the phone recorded, stretched out and
soft at the edges. The photo did not have any more detail in it than the phone captured, and
printing it bigger did not invent any.

The second attempt is easier than the first. The person who drew the chart still has the numbers. They get
a bigger sheet and draw it again — same four bars, same four labels, same shape, just larger. Every
line is as crisp as it was on the small one, because it is not a copy of the small one. It is the
same instructions, carried out at a different size.

A recording of the picture, and the instructions for the picture. Both are the chart; only one of
them survives being made bigger.

---

## The idea in plain language

Those two attempts are the two kinds of image file, and they have names.

A **raster** image is a rectangular grid of coloured dots, called pixels, with a colour written down
for each one. That is the phone photo. It has a fixed number of dots — `600 x 400`, as
[5.2](5.2-savefig-dpi-and-bbox-inches.md) measured — and enlarging it can only spread those dots
over more space. PNG, JPEG and WebP are raster formats.

A **vector** image is a list of drawing instructions: move to this point, draw a line to that one,
fill this rectangle in this colour, put this letter here in this typeface at this size. That is the
person redrawing the chart on a bigger sheet. There are no dots in the file at all. Whatever opens
it — a browser, a printer, a phone — carries out the instructions at whatever size it is displaying
at, so the result is as sharp as that device can manage. SVG and PDF are vector formats.

Two more words, both of which will appear in the measurements.

**Compression** is how a file avoids writing the same thing twice. PNG compression is **lossless**,
which means the file can be turned back into exactly the pixels that went in, with nothing thrown
away — that is why a chart, which is mostly flat blocks of one colour, compresses so well. JPEG
compression is **lossy**: it discards detail the eye is unlikely to miss, which suits photographs
and puts smeared grey halos around the sharp edges of text.

A **point** is a unit of length used in printing and equal to one seventy-second of an inch. It is
how a vector file states its natural size. You will see it in the SVG below, and it is the reason a
6-inch-wide figure comes out as `432pt`.

The rule that falls out of all this is not "vector is better". It is a trade. A vector file's size
grows with the **number of marks in the picture**; a raster file's size grows with the **number of
pixels**. Four bars is a handful of marks and millions of pixels. Fifty thousand scattered points is
fifty thousand marks and the same millions of pixels. The two formats swap places somewhere in
between, and the measurements below find the crossover.

## The mechanism

The same figure, written out in six formats.

```python
from pathlib import Path

import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]

OUT = Path("out")
OUT.mkdir(exist_ok=True)


def build():
    fig, ax = plt.subplots(figsize=(6, 4))
    ax.bar(AISLES, TOTALS)
    ax.set_title("What each aisle cost")
    ax.set_ylabel("pounds spent over four weeks")
    return fig


for ext in ("png", "svg", "svgz", "pdf", "eps", "webp"):
    fig = build()
    path = OUT / f"fridge.{ext}"
    fig.savefig(path)
    plt.close(fig)
    print(f"fridge.{ext:<5} {path.stat().st_size:>8} bytes")
```

**Line by line:**

- The opening four lines are the standard start from
  [5.1](5.1-backends-and-the-script-with-no-window.md). The backend is `Agg`, and the point of this
  block is that it does not matter: `savefig` swaps in a format-specific writer based on the
  extension, so a PDF comes out of an `Agg` session perfectly happily.
- `build()` returns a fresh figure each time, so nothing that one save does can affect the next.
- `for ext in (...)` names the formats by their file extension only. **The extension is the whole
  interface.** There is no `format=` argument here and there does not need to be one.
- `svgz` is an SVG that matplotlib gzips as it writes. `eps` is Encapsulated PostScript, the older
  vector format that some publishers still ask for. `webp` is a newer raster format.
- `plt.close(fig)` after each save, for the reason [5.4](5.4-the-figures-you-never-closed.md) is
  about.
- `path.stat().st_size` is the byte count from the filesystem, not an estimate.

```text
fridge.png      14630 bytes
fridge.svg      23254 bytes
fridge.svgz      5114 bytes
fridge.pdf      10859 bytes
fridge.eps      17627 bytes
fridge.webp      6314 bytes
```

**For this chart the vector PDF is the smallest of the uncompressed formats, and the gzipped SVG
beats everything.** Four bars, some ticks and three pieces of text is a very short list of
instructions. The 14 630-byte PNG is spending almost all of its bytes describing 240 000 pixels of
white background. One honest caveat: `svgz` is gzip, and gzip records a timestamp, so its byte count
wobbles by a handful between runs. The others are reproducible to the byte.

Now the property that actually separates them.

```python
for dpi in (100, 200, 300, 600):
    for ext in ("png", "svg"):
        fig = build()
        path = OUT / f"fridge_{dpi}.{ext}"
        fig.savefig(path, dpi=dpi)
        plt.close(fig)
        print(f"{ext} at dpi={dpi:<4} {path.stat().st_size:>8} bytes")
```

**Line by line:**

- The loop is the same save four times over, changing only `dpi` — the dots per inch from
  [5.2](5.2-savefig-dpi-and-bbox-inches.md).
- `dpi` is passed to **both** formats deliberately. It is legal for both. Whether it does anything
  is the measurement.
- The filename carries the dpi so the files can be told apart afterwards without guessing.

```text
png at dpi=100     14630 bytes
svg at dpi=100     23254 bytes
png at dpi=200     34740 bytes
svg at dpi=200     23254 bytes
png at dpi=300     54107 bytes
svg at dpi=300     23254 bytes
png at dpi=600    124959 bytes
svg at dpi=600     23254 bytes
```

**The PNG column grows by a factor of eight and a half; the SVG column does not move by one byte.**
That is the whole idea, measured. `dpi` is a question about how finely to record dots, and a file
made of instructions has no dots to record. Matplotlib does not warn you that the argument did
nothing — it accepts it, uses it internally to work out where text sits, and writes the identical
file.

What the vector file says about its own size instead:

```python
header = (OUT / "fridge.svg").read_text(encoding="utf-8").splitlines()[3]
print(header[:96])
```

**Line by line:**

- `read_text(encoding="utf-8")` reads the file as text, because an SVG **is** text — you can open
  one in an editor. `encoding=` is passed explicitly rather than left to the platform, which is
  [Day 16, 2.2's](../../../day-16-files-and-context-managers/parts/02-reading-and-writing/2.2-encoding.md)
  rule.
- `.splitlines()[3]` picks the fourth line, which is where matplotlib puts the opening `<svg>` tag,
  after the XML declaration and the two-line document type line.
- `[:96]` trims the tag, which is long, down to the part that carries the size.

```text
<svg xmlns:xlink="http://www.w3.org/1999/xlink" width="432pt" height="288pt" viewBox="0 0 432 28
```

**`432pt` by `288pt`.** Six inches times 72 points to the inch is 432; four times 72 is 288. The
file states a physical size and a coordinate system, and never a pixel count.

The raster file records something too, and it is worth looking at because it is where the format's
specification becomes visible.

```python
from PIL import Image

for dpi in (100, 300):
    path = OUT / f"fridge_{dpi}.png"
    image = Image.open(path)
    print(f"saved at dpi={dpi:<4} size={image.size}  the file says dpi={image.info['dpi']}")

raw = (OUT / "fridge.png").read_bytes()
print("first eight bytes  :", raw[:8])
print("first chunk name   :", raw[12:16])
```

**Line by line:**

- `Image.open(path)` uses Pillow, which arrives as one of matplotlib's own dependencies, so nothing
  new is installed.
- `image.size` is the pixel grid. `image.info["dpi"]` is the physical resolution the file records
  about itself, which is a different thing and is stored in the file rather than inferred.
- `read_bytes()` returns the raw bytes with no decoding, because a PNG is not text and
  `read_text` on it would raise.
- `raw[:8]` is the fixed signature every PNG starts with. `raw[12:16]` is the name of the first
  chunk, which the format requires to be the header chunk.

```text
saved at dpi=100  size=(600, 400)  the file says dpi=(99.9998, 99.9998)
saved at dpi=300  size=(1800, 1200)  the file says dpi=(299.9994, 299.9994)
first eight bytes  : b'\x89PNG\r\n\x1a\n'
first chunk name   : b'IHDR'
```

**Look at that `99.9998`.** You asked for 100 and the file says 99.9998, and it is not a rounding
bug in matplotlib. A PNG records physical resolution in a chunk called `pHYs` that stores whole
numbers of **pixels per metre**, per the *Portable Network Graphics (PNG) Specification (Third
Edition)* (2025, W3C Recommendation 24 June 2025, <https://www.w3.org/TR/png-3/>), which also fixes
the eight-byte signature printed above. One hundred dots per inch is 3937.0079 pixels per metre,
which is stored as `3937`, and `3937 × 0.0254` is 99.9998 inches' worth. The 300-dpi file loses the
same way: `11811 × 0.0254` is 299.9994. This is a whole class of bug in one line — a value that
looks like a floating-point mistake and is actually a unit conversion through an integer.

Finally, the trade, at the point where it reverses.

```python
import numpy as np

rng = np.random.default_rng(36)
x = rng.normal(size=50_000)
y = rng.normal(size=50_000)

for rasterized in (False, True):
    for ext in ("png", "svg", "pdf"):
        fig, ax = plt.subplots(figsize=(6, 4))
        ax.scatter(x, y, s=1, rasterized=rasterized)
        ax.set_xlabel("one measurement")
        ax.set_ylabel("another")
        path = OUT / f"cloud_{rasterized}.{ext}"
        fig.savefig(path, dpi=200)
        plt.close(fig)
        print(f"rasterized={str(rasterized):<5} .{ext:<3} {path.stat().st_size:>9} bytes")
```

**Line by line:**

- `np.random.default_rng(36)` is a seeded generator. The seed is part of the result, which is
  [Day 20, 4.2's](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)
  rule, and it is what makes these byte counts reproducible rather than approximately right.
- `rng.normal(size=50_000)` draws fifty thousand numbers. The underscore is a digit separator and
  changes nothing except how easily you can read it.
- `ax.scatter(x, y, s=1)` draws fifty thousand small marks. `s=1` is the marker area in square
  points, small enough that the cloud is readable.
- `rasterized=True` is the interesting argument. It tells matplotlib to draw **this artist** as
  pixels even inside a vector file, while leaving the axes, ticks and labels as instructions. It is
  the mixed answer, and it only exists because the trade below is real.
- `dpi=200` matters for the rasterized case and for the PNG, and does nothing for the pure vector
  cases, exactly as the earlier block showed.

```text
rasterized=False .png    109500 bytes
rasterized=False .svg   5405690 bytes
rasterized=False .pdf    774555 bytes
rasterized=True  .png    109500 bytes
rasterized=True  .svg    104693 bytes
rasterized=True  .pdf     54931 bytes
```

**Five point four megabytes of SVG for a picture a PNG stores in 110 kilobytes.** The SVG is
carrying fifty thousand separate `<path>` elements because that is what fifty thousand marks means.
The PNG has not changed at all between the two runs, because a raster file was already pixels. And
the third row of the second block is the professional's answer: a rasterized PDF at 54 931 bytes,
where the cloud is a small image and the axis labels are still real text you can select, search and
zoom into.

## When it breaks

**Handing a vector file to something that expects pixels:**

```text
$ uv run python -c "
from PIL import Image
Image.open('out/fridge.svg')
"
Traceback (most recent call last):
  File "<string>", line 3, in <module>
  File "...\PIL\Image.py", line 3715, in open
    raise UnidentifiedImageError(msg)
PIL.UnidentifiedImageError: cannot identify image file 'out/fridge.svg'
```

**What it means.** Pillow reads raster images. An SVG has no pixel grid to read, so there is nothing
for it to identify — the message is literal, not evasive. This is the failure that shows up when a
report pipeline switches its charts to SVG for sharpness and a downstream step that stitches images
together, or measures them, or embeds them in a spreadsheet, quietly turns out to be a raster tool.
The fix is to decide the format at the point where you know the consumer, not at the point where you
like the look.

**The argument that is accepted and ignored.** There is no error at all for this one:

```text
$ uv run python -c "
import matplotlib
matplotlib.use('Agg')
import matplotlib.pyplot as plt
from pathlib import Path
for dpi in (100, 600):
    fig, ax = plt.subplots(figsize=(6, 4))
    ax.bar(['dairy','bakery','produce','household'], [21.85, 9.80, 27.00, 13.80])
    ax.set_title('What each aisle cost')
    ax.set_ylabel('pounds spent over four weeks')
    p = Path('out') / ('q%d.svg' % dpi)
    fig.savefig(p, dpi=dpi)
    plt.close(fig)
    print('dpi', dpi, '->', p.stat().st_size, 'bytes')
"
dpi 100 -> 23254 bytes
dpi 600 -> 23254 bytes
```

**What it means.** Somebody asked for a high-resolution SVG, got a file, and believed they had one.
They had the same file twice. The lesson generalises past matplotlib: an argument that a library
accepts is not an argument that a library uses, and the only way to know the difference is to
measure the output.

**The other silent one — transparency into a format that has none:**

```text
$ uv run python -c "
import matplotlib
matplotlib.use('Agg')
import matplotlib.pyplot as plt
from PIL import Image
fig, ax = plt.subplots()
ax.bar(['dairy'], [21.85])
fig.savefig('out/t.jpg', transparent=True)
print('mode of the written file:', Image.open('out/t.jpg').mode)
"
mode of the written file: RGB
```

**What it means.** JPEG has no alpha channel — no way to record that a pixel is see-through — so
`transparent=True` was accepted, applied, and then flattened onto white when the bytes were written.
`RGB` rather than `RGBA` is the proof. If you need transparency, the format has to be one that can
hold it: PNG, WebP or a vector format.

## In production

**What a professional writes instead of the teaching version.** The format is not chosen at the call
site by whoever is typing. It is a policy, written once, with a reason attached:

- **PNG at the display resolution for anything automated** — dashboards, nightly reports, images
  attached to a build. It opens everywhere, it is one predictable file size, and every downstream
  tool can read it. This is what [6.1](../06-the-module/6.1-the-figures-module.md) makes the default.
- **PDF or SVG for anything a person will enlarge** — a printed page, a poster, a figure in a
  document that gets zoomed. Sharp at any size, and the text stays text.
- **Rasterized vector for a dense chart that also needs sharp labels** —
  `ax.scatter(..., rasterized=True)` and save as PDF. The measurement above turned 774 555 bytes
  into 54 931 with no visible loss on the cloud and no loss at all on the axes.

**What degrades at scale, and the failure that only appears with real data.** The whole trap of this
part is that vector files are tested on small charts. A scatter of four points and a scatter of
fifty thousand produce the same code and files that differ by a factor of fifty. Every one of those
5.4-megabyte SVGs committed to a repository stays in its history for ever, every clone pays for
them, and no diff of one is readable. The version that catches it is a guard rather than a rule
somebody has to remember: after saving, check the byte count, and refuse or fall back to PNG above a
threshold you have chosen on purpose.

There is a second scale problem that is easy to miss. A vector file is drawn by whoever opens it, so
a browser asked to render fifty thousand `<path>` elements does that work on the reader's machine.
The file being small enough to send is not the same as the file being pleasant to open.

**The text question, which is the one that decides real arguments.** By default matplotlib writes
SVG text as outlines — `svg.fonttype` is `"path"` — so the letters become shapes and no longer exist
as letters. Setting it to `"none"` keeps them as text and asks the viewer to supply the font:

```text
svg.fonttype=path    23254 bytes  the word produce is searchable: False
svg.fonttype=none     9332 bytes  the word produce is searchable: True
```

Less than half the size, and the labels can be selected, searched and re-styled. The cost is that
the file now depends on the reader having that font, and if they do not, the layout you carefully
arranged in [4.4](../04-many-axes/4.4-constrained-layout.md) moves. Outlines are the safe default
for a file leaving your control; `"none"` is the right choice when you own both ends.

**The review comment a senior engineer leaves.** *"This writes SVG for every chart. The aisle bar
charts are fine, but `plot_embeddings` draws 200 000 points and the last run put a 21 MB file in
`reports/`. Either save that one as PNG, or pass `rasterized=True` on the scatter and keep the PDF.
Also please stop passing `dpi=300` to the SVG saves — measure it, the files are byte-identical
without it."*

**The interview question.** *"PNG or SVG for this chart?"* The answer that shows experience names
the trade rather than a preference: SVG for a small number of marks that somebody will enlarge, PNG
once the mark count is high, because a vector file's size tracks the number of things drawn while a
raster file's tracks the number of pixels. The follow-up is *"what if you need both — a sharp
printed figure with a dense scatter in it?"* — and the answer is `rasterized=True` on the dense
artist with a vector container, which keeps the text as text and turns the cloud into an embedded
image.
