# 5.2 — savefig, dpi, and bbox_inches

## One-line answer

`fig.savefig(path)` is the one call that turns the sheet into a file, and its three arguments that
matter — `dpi`, `bbox_inches` and `transparent` — decide how many pixels you get, how much white
space comes with them, and whether the background is there at all.

---

## The story

The flat prints the shopping chart at last. Somebody carries it back from the shop and holds it up
to the fridge.

Two things are wrong with it, and neither of them is the chart.

The first is that the drawing is sitting in the middle of a big white page. There is a hand's width
of nothing all the way round, so under the magnet the bars end up hidden behind the takeaway menu.
Somebody gets the scissors and trims it, leaving a thin white edge so it does not look chopped.

The second only shows up later. One of the flatmates photographs the sheet to send to a friend, and
the friend pinches to zoom in on the household bar. The letters go blocky. The chart on the wall is
crisp; the copy that went down the wire is not, because the phone recorded a certain number of dots
and there were never any more than that.

Trimming the white edge, and deciding how many dots to record. Two separate choices, made after the
drawing was finished, neither of them changing a single number.

---

## The idea in plain language

Everything so far has built a **figure** — the sheet — in memory. A figure is a description:
[1.1](../01-the-two-objects/1.1-the-paper-and-the-frame.md) called it the paper, and
[5.1](5.1-backends-and-the-script-with-no-window.md) named the **backend**, the module that turns
that description into real output. `savefig` is the call that asks the backend to do it.

Three words need defining before the code.

A **pixel** is one dot of colour in an image file. A picture that is 600 dots across and 400 down
is a 600 by 400 image, and there is no more detail in it than that, however large you display it.

**dpi** stands for **dots per inch**. It is the bridge between the figure's size, which matplotlib
stores in inches, and the file's size, which is counted in pixels. A figure that is 6 inches by 4
inches, saved at 100 dots per inch, is 600 by 400 pixels. Saved at 200, it is 1200 by 800. The
drawing is identical; the recording is finer. That is the phone camera in the story.

A **bounding box** is the smallest rectangle that contains everything actually drawn. By default
`savefig` writes the whole sheet, white margins included, because the sheet is what you asked for.
`bbox_inches="tight"` tells it to write the bounding box instead — the scissors. `pad_inches` is
how much white you deliberately leave outside the cut.

The last word is **transparent**. An image can record, for every pixel, not just a colour but how
opaque it is. A fully transparent pixel shows whatever is behind it. `transparent=True` makes the
sheet's background transparent, so the chart can sit on a coloured slide without a white rectangle
around it.

None of these change the data, the bar heights or the labels. They are all decisions about the
copy, not about the chart.

## The mechanism

Start with the plain call and ask where its numbers come from.

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]

fig, ax = plt.subplots(figsize=(6, 4))
ax.bar(AISLES, TOTALS)
ax.set_title("What each aisle cost")
ax.set_ylabel("pounds spent over four weeks")

print("figsize in inches :", fig.get_size_inches())
print("figure dpi        :", fig.get_dpi())
print("rcParam savefig.dpi:", plt.rcParams["savefig.dpi"])
print("rcParam savefig.bbox:", plt.rcParams["savefig.bbox"])
print("rcParam savefig.pad_inches:", plt.rcParams["savefig.pad_inches"])
```

**Line by line:**

- The first four lines are the standard opening from
  [5.1](5.1-backends-and-the-script-with-no-window.md): pick the file-writing backend, then import
  pyplot.
- `AISLES` and `TOTALS` are the flat's four aisles and their four-week totals, unchanged since
  [1.1](../01-the-two-objects/1.1-the-paper-and-the-frame.md).
- `figsize=(6, 4)` is **inches**, width first. It is not pixels, and this is where nearly everyone
  is caught once.
- `fig.get_dpi()` reads the figure's own resolution — the one used when the figure is displayed.
- `plt.rcParams["savefig.dpi"]` is the *saving* resolution, and its default value is the string
  `"figure"`, meaning "whatever the figure's own dpi is". Two settings, one of which defers to the
  other, is why changing `figure.dpi` silently changes every file you write.
- `savefig.bbox` defaults to `None`, which means "the whole sheet". `savefig.pad_inches` defaults
  to `0.1` and is only consulted when the box is tight.

```text
figsize in inches : [6. 4.]
figure dpi        : 100.0
rcParam savefig.dpi: figure
rcParam savefig.bbox: None
rcParam savefig.pad_inches: 0.1
```

Six inches times 100 dots per inch is 600. Four times 100 is 400. Now save the same figure six
different ways and measure every one.

```python
from pathlib import Path

from PIL import Image

OUT = Path("out")
OUT.mkdir(exist_ok=True)


def build():
    fig, ax = plt.subplots(figsize=(6, 4))
    ax.bar(AISLES, TOTALS)
    ax.set_title("What each aisle cost")
    ax.set_ylabel("pounds spent over four weeks")
    return fig


ways = {
    "plain.png": {},
    "dpi200.png": {"dpi": 200},
    "tight.png": {"bbox_inches": "tight"},
    "clear.png": {"transparent": True},
    "tight_dpi200.png": {"dpi": 200, "bbox_inches": "tight"},
    "tight_pad0.png": {"bbox_inches": "tight", "pad_inches": 0},
}
for name, kwargs in ways.items():
    fig = build()
    path = OUT / name
    fig.savefig(path, **kwargs)
    plt.close(fig)
    width, height = Image.open(path).size
    print(f"{name:>17}  {path.stat().st_size:>7} bytes  {width} x {height} px  {kwargs}")
```

**Line by line:**

- `from pathlib import Path` — a path is an object with methods, not a string you glue together.
  [Day 16, 1.1](../../../day-16-files-and-context-managers/parts/01-the-path/1.1-a-path-is-not-a-string.md)
  is why, and `savefig` accepts a `Path` directly.
- `OUT.mkdir(exist_ok=True)` creates the directory if it is missing and does nothing if it is
  there. Without it the first save raises, and the *When it breaks* section shows exactly how.
- `build()` is a function because a figure can only be saved honestly once per experiment. Reusing
  one figure across all six saves would work, but a `tight` save changes nothing on the figure while
  a `transparent` save does not either — building fresh each time removes the question entirely.
- `from PIL import Image` — Pillow is installed as one of matplotlib's own dependencies, so this
  needs no new package. It is used here only to read the pixel dimensions back out of the file,
  which is the measurement that matters.
- `ways` is a dictionary from filename to the keyword arguments for that save, so the six
  experiments differ in exactly one visible place.
- `fig.savefig(path, **kwargs)` unpacks the dictionary into keyword arguments. `savefig` is a method
  on the **figure**, because saving writes the whole sheet — an axes has no `savefig` at all, which
  [1.1](../01-the-two-objects/1.1-the-paper-and-the-frame.md) proved with an `AttributeError`.
- `plt.close(fig)` releases the figure immediately rather than at the end of the script.
  [5.4](5.4-the-figures-you-never-closed.md) is that line in full, and six figures is already close
  enough to the warning threshold to make the habit worth starting now.
- `path.stat().st_size` is the file's size in bytes, straight from the filesystem.
- `Image.open(path).size` is a `(width, height)` tuple in pixels.

```text
        plain.png    14630 bytes  600 x 400 px  {}
       dpi200.png    34740 bytes  1200 x 800 px  {'dpi': 200}
        tight.png    13804 bytes  532 x 373 px  {'bbox_inches': 'tight'}
        clear.png    11851 bytes  600 x 400 px  {'transparent': True}
 tight_dpi200.png    33424 bytes  1064 x 745 px  {'dpi': 200, 'bbox_inches': 'tight'}
   tight_pad0.png    13539 bytes  512 x 353 px  {'bbox_inches': 'tight', 'pad_inches': 0}
```

**Read the pixel column first.** `dpi=200` doubles both dimensions exactly, as the inches-times-dpi
arithmetic promised, and the file gets about two and a half times bigger rather than four times,
because a PNG stores runs of identical colour cheaply and most of this picture is white.
`bbox_inches="tight"` cut 68 pixels off the width and 27 off the height — that is the scissors, and
it is the reason the tight files are **not** a round 600 by 400. And `transparent=True` produced the
smallest file of all at the same dimensions, because a uniformly transparent background compresses
better than a uniformly white one.

The last line is the one to remember: **a tight save has a size you did not choose.** Every chart
you save that way comes out a slightly different shape, because the crop depends on how long the
longest tick label happened to be.

Now the padding, on its own:

```python
for pad in (0.0, 0.1, 0.5):
    fig = build()
    path = OUT / f"pad{pad}.png"
    fig.savefig(path, bbox_inches="tight", pad_inches=pad)
    plt.close(fig)
    print(f"pad_inches={pad:<4} {Image.open(path).size} px  {path.stat().st_size:>6} bytes")
```

**Line by line:**

- `pad_inches` is in inches, like `figsize`, so at 100 dots per inch a step of `0.1` should add
  0.2 inches of width in total — one tenth on each side — which is 20 pixels.
- `bbox_inches="tight"` has to be present for `pad_inches` to mean anything. On its own,
  `pad_inches` is silently ignored, because there is no cut for it to pad.
- `f"pad{pad}.png"` puts the value into the filename so the files can be compared afterwards
  without guessing which is which.

```text
pad_inches=0.0  (512, 353) px   13539 bytes
pad_inches=0.1  (532, 373) px   13804 bytes
pad_inches=0.5  (612, 453) px   14672 bytes
```

**Twenty pixels per 0.1 inch, exactly as predicted.** `pad_inches=0` is the true bounding box, and
notice it is 512 by 353 — smaller in both directions than the 600 by 400 sheet, which tells you how
much of a default matplotlib figure is margin.

What `transparent=True` actually changed:

```python
for name in ("plain.png", "clear.png"):
    image = Image.open(OUT / name).convert("RGBA")
    print(f"{name:<12} top-left pixel = {image.getpixel((0, 0))}")
```

**Line by line:**

- `.convert("RGBA")` forces four channels — red, green, blue and **alpha** — so both files can be
  compared on the same scale even if one was stored without an alpha channel.
- `getpixel((0, 0))` reads the top-left corner, which is background in both files and nothing else.
- The fourth number is the alpha: `255` is fully opaque, `0` is fully see-through.

```text
plain.png    top-left pixel = (255, 255, 255, 255)
clear.png    top-left pixel = (255, 255, 255, 0)
```

**The colour did not change; the opacity did.** That is worth knowing, because a transparent PNG
opened in a viewer with a white background looks exactly like the opaque one, and the difference
only appears when you drop it onto a dark slide.

Finally, the version that writes no file at all:

```python
import io

fig = build()
buffer = io.BytesIO()
fig.savefig(buffer, format="png")
plt.close(fig)
print("bytes in the buffer:", buffer.getbuffer().nbytes)
print("first eight bytes  :", buffer.getvalue()[:8])
```

**Line by line:**

- `io.BytesIO()` is an in-memory file: it has `write` and `read` like a real file but never touches
  the disk. This is what a web server hands back in a response body.
- `format="png"` is **required** here. With a real path matplotlib reads the extension to choose the
  format; a buffer has no name, so you must say.
- `buffer.getbuffer().nbytes` is the byte count without copying the contents out.
- `getvalue()[:8]` reads the first eight bytes, which for a PNG are a fixed signature —
  [5.3](5.3-vector-or-raster.md) explains what those eight bytes are and where they are specified.

```text
bytes in the buffer: 14630
first eight bytes  : b'\x89PNG\r\n\x1a\n'
```

Exactly the 14 630 bytes that `plain.png` weighed on disk. The file and the buffer are the same
work; only the destination differs.

## When it breaks

**A format matplotlib cannot write:**

```text
$ uv run python -c "
import matplotlib
matplotlib.use('Agg')
import matplotlib.pyplot as plt
fig, ax = plt.subplots()
fig.savefig('fridge.jpg2')
"
Traceback (most recent call last):
  ...
  File "...\matplotlib\backend_bases.py", line 2132, in _switch_canvas_and_return_print_method
    raise ValueError(
ValueError: Format 'jpg2' is not supported (supported formats: avif, eps, gif, jpeg, jpg, pdf,
pgf, png, ps, raw, rgba, svg, svgz, tif, tiff, webp)
```

**What it means.** The extension you typed is how matplotlib chooses which backend does the
writing, and `jpg2` is not one it has. The message doubles as documentation: that parenthesis is
the complete list of what you can ask for. Read `_switch_canvas_and_return_print_method` in the
traceback and you can see the mechanism — the figure's canvas is swapped for a format-specific one
at save time, which is also why `fig.savefig("x.pdf")` works perfectly well while the backend is
`Agg`.

**A directory that is not there:**

```text
$ uv run python -c "
import matplotlib
matplotlib.use('Agg')
import matplotlib.pyplot as plt
fig, ax = plt.subplots()
fig.savefig('reports/2026/fridge.png')
"
Traceback (most recent call last):
  ...
  File "...\PIL\Image.py", line 2706, in save
    fp = builtins.open(filename, "w+b")
FileNotFoundError: [Errno 2] No such file or directory: 'reports/2026/fridge.png'
```

**What it means.** `savefig` opens the file; it does not create the folders above it. The fix is one
line before the save: `Path("reports/2026").mkdir(parents=True, exist_ok=True)`. `parents=True`
makes every missing level, and `exist_ok=True` is what stops the second run of your script from
failing.

**The one that does not raise.** This is the dangerous one:

```text
$ uv run python -c "
import matplotlib
matplotlib.use('Agg')
import matplotlib.pyplot as plt
first, ax1 = plt.subplots(); ax1.bar(['dairy','bakery','produce','household'], [21.85, 9.80, 27.00, 13.80])
second, ax2 = plt.subplots(); ax2.plot([1,2,3,4], [17.20, 14.25, 22.00, 19.00])
plt.savefig('aisles.png')
print('plt.savefig saved figure number', plt.gcf().number)
print('the bar chart is figure number ', first.number)
print('bytes written by plt.savefig   ', __import__('pathlib').Path('aisles.png').stat().st_size)
first.savefig('aisles_right.png')
print('bytes written by fig.savefig   ', __import__('pathlib').Path('aisles_right.png').stat().st_size)
"
plt.savefig saved figure number 2
the bar chart is figure number  1
bytes written by plt.savefig    21570
bytes written by fig.savefig    8990
```

**What it means.** `plt.savefig` is not a different way of saving; it is `savefig` on whatever
figure pyplot currently considers current, which is the last one created. The file called
`aisles.png` contains the line chart. No warning, no traceback, and the two byte counts are the only
evidence that anything went wrong. This is the state machine from
[2.2](../02-the-state-machine/2.2-gca-and-the-axes-you-did-not-choose.md) reaching all the way into
your output directory, and it is the whole argument for
[2.3](../02-the-state-machine/2.3-where-plt-plot-stops-working.md)'s rule: name the figure, then
save the name.

## In production

**What a professional writes instead of the teaching version.** Not a bare `fig.savefig("out.png")`
scattered through a script. One function, used everywhere:

- The path is a `Path`, and its parent is created with `mkdir(parents=True, exist_ok=True)` before
  the save, so the function works on a fresh machine.
- `dpi` is a module constant, not a literal at the call site. Two charts saved at two resolutions
  because somebody typed a different number is the most common defect in a report pack, and it is
  invisible until the images are side by side.
- The function returns the path it wrote, so the caller can log it, assert on it, or attach it,
  without rebuilding the string.
- It closes the figure. That is [5.4](5.4-the-figures-you-never-closed.md), and
  [6.1](../06-the-module/6.1-the-figures-module.md) is where `save(fig, path, dpi=DPI) -> Path` gets
  written down.

**`bbox_inches="tight"` versus a fixed size — the choice that matters.** Tight cropping is the right
answer for a single image dropped into a document, where you want no dead margin. It is the wrong
answer for a set, because the measured output above was 532 by 373 rather than 600 by 400, and that
crop moves whenever a tick label gets longer. A pack of eight charts saved tight has eight different
shapes, and any layout that places them on a grid will show it. The production default is a fixed
`figsize`, `layout="constrained"` from
[4.4](../04-many-axes/4.4-constrained-layout.md) to stop labels overlapping, and **no**
`bbox_inches`, so every file in the pack has identical pixel dimensions.

**What degrades at scale.** File size grows with the pixel count, and the pixel count grows with the
square of `dpi`: the measurements above went from 14 630 bytes at 100 to 34 740 at 200 for the same
picture. A nightly job that writes a few hundred charts at 300 dots per inch because "higher is
safer" produces a directory that is an order of magnitude larger than it needs to be, and email
gateways and repository size limits both notice. Pick the resolution from where the image will be
looked at — a screen wants around 100, a printed page wants 300 — and write it down once.

**The failure that only appears with real data.** A dashboard exported charts with
`bbox_inches="tight"` and pasted them into a fixed-width template. It looked correct for months.
Then a category arrived whose name was three times longer than any before it, the tight box widened
to fit the tick label, the image came back a different width, and every chart on that page was
scaled to a slightly different size by the template. Nothing raised. The bug was a save option
chosen for one chart and inherited by a hundred.

**The review comment a senior engineer leaves.** *"`plt.savefig` here saves the current figure, not
`fig`. In this function two figures exist, so which one lands in the file depends on the order of
the two blocks above. Use `fig.savefig(path)`. While you are in there, make `path` a `Path`, create
the parent, and take `dpi` from the module constant instead of the literal `150`."*

**The interview question.** *"Your saved chart looks fine on screen and blurry in the slide deck.
What do you change?"* The `dpi` on the save, not the figure size — `figsize` sets the physical
dimensions in inches, `dpi` sets how many pixels record each inch, and blur means too few pixels
for the display size. The follow-up that separates people is *"what happens to the file size?"* —
it grows roughly with the square of the resolution, so the honest answer names a target (screen or
print) rather than reaching for the largest number available. A good candidate also mentions that
if the deck is going to be projected or printed, the right fix may be a vector file instead, which
is [5.3](5.3-vector-or-raster.md).
