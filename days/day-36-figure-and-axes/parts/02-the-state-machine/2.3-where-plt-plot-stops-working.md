# 2.3 — Where plt.plot stops working

## One-line answer

The hidden current figure is harmless in exactly one situation — one chart, drawn once, looked at
immediately — and it breaks in the four situations every real program is made of: a function that
another function also draws in, a loop, a test suite, and a cell that gets run twice.

---

## The story

The flat decides one sheet is not enough. Each aisle should get its own sheet: four sheets, four
lines, one line per sheet showing that aisle week by week.

One person volunteers, sits down at the kitchen table with a marker pen and the four columns of
numbers, and starts. Dairy first: four dots, a line joining them, "dairy" written at the top. They
take a photo of it for the group chat.

Then bakery. They pick up the pen, draw four dots and a line — on the same sheet, because the sheet is
still lying there in front of them and nobody said anything about a new one. They write "bakery" at
the top, over the word "dairy". Photo.

Then produce. Then household. Four photos in the chat, and the four photos are of the same sheet at
four stages, getting busier each time. The last one has four lines crossing each other and the word
"household" at the top. There is now exactly one sheet on the table, and three of the four charts
only exist as photographs of a sheet that has since been drawn over.

Nobody did anything unreasonable. Every single step was "draw on the sheet", which is what they were
doing all evening. The step nobody thought to include was *take a clean sheet*, because on the first
chart there had been a clean sheet without asking.

That is a loop, and it is one of the four. The other three are the same omission wearing different
clothes.

---

## The idea in plain language

[2.1](2.1-the-figure-you-never-named.md) showed that a `plt.` drawing call fills in the missing panel
from a pointer inside the `matplotlib.pyplot` module, making a figure if none exists.
[2.2](2.2-gca-and-the-axes-you-did-not-choose.md) showed the four functions that read and move that
pointer, and where it is stored: one dictionary, one per process, shared by everything.

Both of those pages were about mechanism. This page is about consequences, and there are four of
them. They are worth naming separately, because in the wild they arrive as four different bug reports
and nobody connects them.

**One — two functions that both draw.** You write `aisle_chart()` and `weekly_chart()`. Each one is
correct on its own and each one is correct when it is the only thing that runs. Called one after the
other, the second draws into the panel the first one left current. A **call site** is the place in
the code where a function is called; with `plt.`, a function's behaviour depends on what happened at
every earlier call site in the process, which means it cannot be read in isolation.

**Two — a loop.** The kitchen table. The first pass through the body gets a fresh figure because
there was none; every later pass draws onto the one the previous pass left behind.

**Three — a test suite.** `pytest` collects your test functions and runs them in one process, in file
order by default ([Day 02,
3.1](../../../day-02-quality-gate/parts/03-pytest/3.1-the-test-that-can-go-red.md)). The pointer
survives from one test into the next, so a test can pass alone and fail when run after another. This
is called **test pollution**: state left behind by one test changing the result of another. It is the
worst of the four, because the failure message points at the innocent test.

**Four — a notebook cell run twice.** A notebook keeps one Python process alive across cells and lets
you re-run any cell as often as you like. The pointer is part of that process, so the second run of a
drawing cell adds to what the first run drew instead of replacing it.

The fix for all four is a single sentence, and it is the plan's own headline for `VIZ-01`: **never
`plt.plot` — always `fig, ax = plt.subplots()`.** Hold the objects; never consult the pointer.

## The mechanism

### One — two functions that both draw

Each of these is a reasonable function. Read them and try to find the bug before the output.

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]
WEEKS = [1, 2, 3, 4]
WEEKLY = [17.20, 14.25, 22.00, 19.00]


def aisle_chart():
    plt.bar(AISLES, TOTALS)
    plt.title("What each aisle cost")
    plt.ylabel("pounds spent")


def weekly_chart():
    plt.plot(WEEKS, WEEKLY, marker="o")
    plt.title("What the flat spent each week")
    plt.ylabel("pounds spent")


aisle_chart()
weekly_chart()

fig = plt.gcf()
ax = fig.axes[0]
print("figures open :", plt.get_fignums())
print("panels       :", len(fig.axes))
print("bars on it   :", len(ax.patches))
print("lines on it  :", len(ax.lines))
print("title        :", repr(ax.get_title()))
print("x tick labels:", [t.get_text() for t in ax.get_xticklabels()])
```

**Line by line:**

- `aisle_chart` draws the four aisle bars and labels them. It never mentions a figure, so it will use
  whatever is current — or make one.
- `weekly_chart` draws the four weekly totals as a line. `marker="o"` puts a dot on each week so that
  four points read as four points.
- Neither function returns anything. That is not sloppiness; it is what pyplot-style code looks like,
  because there is nothing to return — the objects were never named.
- `aisle_chart()` then `weekly_chart()` is the call order, and it is the only thing in this file that
  decides the outcome.
- `fig = plt.gcf()` and `ax = fig.axes[0]` are the inspection, taking hold of whatever the two calls
  left behind ([2.1](2.1-the-figure-you-never-named.md)).
- `len(ax.patches)` counts bar rectangles and `len(ax.lines)` counts lines
  ([1.3](../01-the-two-objects/1.3-everything-is-an-artist.md)). Printing both on one panel is the
  test: a panel that holds both is a panel that was drawn on twice.
- `ax.get_xticklabels()` returns the `Text` artists along the bottom edge, and `t.get_text()` pulls
  the string out of each. This is the line that shows the damage, rather than merely the mess.

```text
figures open : [1]
panels       : 1
bars on it   : 4
lines on it  : 1
title        : 'What the flat spent each week'
x tick labels: ['dairy', 'bakery', 'produce', 'household']
```

**Look at the last two lines together.** One panel, holding four bars and one line. The title says the
chart is about weeks. The numbers along the bottom say the chart is about aisles. The weekly line has
been drawn against an x axis whose four positions are labelled `dairy`, `bakery`, `produce` and
`household`, so week 2 is sitting over the word `produce`. The picture is not merely crowded; it is
false, and it is labelled confidently.

Same two functions, one word changed in each:

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]
WEEKS = [1, 2, 3, 4]
WEEKLY = [17.20, 14.25, 22.00, 19.00]


def aisle_chart():
    fig, ax = plt.subplots()
    ax.bar(AISLES, TOTALS)
    ax.set_title("What each aisle cost")
    return fig, ax


def weekly_chart():
    fig, ax = plt.subplots()
    ax.plot(WEEKS, WEEKLY, marker="o")
    ax.set_title("What the flat spent each week")
    return fig, ax


fig1, ax1 = aisle_chart()
fig2, ax2 = weekly_chart()
print("figures open :", plt.get_fignums())
print("bars on ax1  :", len(ax1.patches), "| lines on ax1:", len(ax1.lines))
print("bars on ax2  :", len(ax2.patches), "| lines on ax2:", len(ax2.lines))
print("titles       :", repr(ax1.get_title()), repr(ax2.get_title()))
print("gcf is fig2  :", plt.gcf() is fig2)
plt.close(fig1)
plt.close(fig2)
print("after closing:", plt.get_fignums())
```

**Line by line:**

- `fig, ax = plt.subplots()` makes a new figure with one panel and hands back both, as two names. It
  is the whole fix, and [3.1](../03-the-object-api/3.1-fig-ax-subplots.md) is the part that takes it
  apart properly.
- `ax.bar(...)` and `ax.set_title(...)` are methods on a panel this function created and holds. There
  is no pointer to consult, so there is nothing an earlier call site could have moved.
- `return fig, ax` is what makes the function usable by anybody else. A drawing function that returns
  nothing can only ever be the last thing that happens.
- `fig1, ax1 = aisle_chart()` and `fig2, ax2 = weekly_chart()` give the caller four names, and now
  each of the four print lines can ask a specific object a specific question.
- `plt.gcf() is fig2` is printed to be honest: the pointer still exists and still moved, and it still
  points at the most recently created figure. The difference is that no line of this program depends
  on it.
- `plt.close(fig1)` and `plt.close(fig2)` remove both figures from the registry. This is possible
  *because* they have names — the pyplot version above had nothing to pass to `close`, which is the
  connection to [5.4](../05-getting-it-out/5.4-the-figures-you-never-closed.md).

```text
figures open : [1, 2]
bars on ax1  : 4 | lines on ax1: 0
bars on ax2  : 0 | lines on ax2: 1
titles       : 'What each aisle cost' 'What the flat spent each week'
gcf is fig2  : True
after closing: []
```

Two figures, four bars on one, one line on the other, both titles where they belong, and an empty
registry at the end.

### Two — the loop

The kitchen table, in Python.

```python
from pathlib import Path

import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

WEEKS = [1, 2, 3, 4]
BY_AISLE = {
    "dairy": [4.60, 5.75, 4.60, 6.90],
    "bakery": [2.80, 1.40, 2.80, 2.80],
    "produce": [6.30, 7.10, 5.40, 8.20],
    "household": [3.50, 0.00, 9.20, 1.10],
}

out = Path("charts")
out.mkdir(exist_ok=True)

for aisle, weekly in BY_AISLE.items():
    plt.plot(WEEKS, weekly, marker="o")
    plt.title(aisle)
    plt.savefig(out / f"{aisle}.png")

print("figures open :", plt.get_fignums())
print("lines on it  :", len(plt.gca().lines))
print("title on it  :", repr(plt.gca().get_title()))
for aisle in BY_AISLE:
    print(f"{aisle:10s}", (out / f"{aisle}.png").stat().st_size, "bytes")
```

**Line by line:**

- `BY_AISLE` is the flat's table read row-wise: four weeks of spending for each of the four aisles.
  The four rows sum to the totals used everywhere else in this day.
- `Path("charts")` and `out.mkdir(exist_ok=True)` make an output directory next to wherever you run
  this. `exist_ok=True` stops the second run raising `FileExistsError`
  ([Day 16, 1.4](../../../day-16-files-and-context-managers/parts/01-the-path/1.4-exists-mkdir-and-the-race.md)).
- The loop body is three lines, and every one of them is a `plt.` call with no figure named. Read it
  as English: draw a line, set the title, save the picture. Nothing in it says "on a new sheet".
- `plt.savefig(...)` saves the **current figure**, so it writes whatever is on the sheet at that
  moment, including everything previous passes drew.
- `f"{aisle}.png"` names each file after its aisle, so four separate files really are produced. The
  bug is not in the file names.
- `.stat().st_size` reads each file's size in bytes. Sizes are the measurement that turns "the
  pictures look a bit busy" into a number.
- `f"{aisle:10s}"` pads the aisle name to ten characters so the four numbers line up under each
  other.

```text
figures open : [1]
lines on it  : 4
title on it  : 'household'
dairy      22374 bytes
bakery     20991 bytes
produce    26575 bytes
household  37002 bytes
```

**One figure, four lines, and four files that get monotonically heavier.** `dairy.png` has one line on
it and is the only correct file of the four. `household.png` weighs 37 002 bytes — sixty-five per
cent more than `dairy.png` — because it contains all four lines, four sets of markers and a legend's
worth of ink that nobody asked for. The file sizes are the photographs from the story.

The fix is one line at the top of the loop body — `fig, ax = plt.subplots()` — and one at the bottom,
`plt.close(fig)`. [4.1](../04-many-axes/4.1-a-grid-of-axes.md) argues that four charts of the same
shape probably want to be four panels on one sheet instead, which is the better answer to the flat's
actual question.

### Three — the test suite

Two tests, each one obviously correct.

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]
WEEKS = [1, 2, 3, 4]
WEEKLY = [17.20, 14.25, 22.00, 19.00]


def aisle_chart():
    plt.bar(AISLES, TOTALS)
    plt.title("What each aisle cost")
    return plt.gca()


def weekly_chart():
    plt.plot(WEEKS, WEEKLY, marker="o")
    plt.title("What the flat spent each week")
    return plt.gca()


def test_aisle_chart_has_four_bars():
    ax = aisle_chart()
    assert len(ax.patches) == 4


def test_weekly_chart_has_one_line():
    ax = weekly_chart()
    assert len(ax.lines) == 1
    assert len(ax.patches) == 0
```

**Line by line:**

- Both drawing functions now end with `return plt.gca()`, which is the pyplot-style attempt at being
  testable: you cannot assert on a chart you cannot reach, so the function hands back whatever panel
  it happened to draw on.
- `test_aisle_chart_has_four_bars` asserts the count of bar rectangles. This is a good assertion and
  it is not the problem.
- `test_weekly_chart_has_one_line` asserts one line **and** zero bars. The second assertion is the
  one a careful person adds: it says "this panel is a line chart, and nothing else is on it".
- Neither test closes a figure, and neither creates one on purpose. That omission is invisible in the
  file and decisive at run time.
- Both tests are saved as `tests/test_charts.py` and run with `python -m pytest tests/test_charts.py`.

### Four — the cell run twice

A notebook keeps one process alive, so a cell is a function you can call again by pressing a key.

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt

AISLES = ["dairy", "bakery", "produce", "household"]
TOTALS = [21.85, 9.80, 27.00, 13.80]


def cell():
    plt.bar(AISLES, TOTALS)
    plt.ylabel("pounds spent")
    return plt.gca()


ax = cell()
print("first run  — bars:", len(ax.patches), "| figures:", plt.get_fignums())
ax = cell()
print("second run — bars:", len(ax.patches), "| figures:", plt.get_fignums())
ax = cell()
print("third run  — bars:", len(ax.patches), "| figures:", plt.get_fignums())
```

**Line by line:**

- `cell()` is a stand-in for one notebook cell: the three lines somebody would actually type into it,
  wrapped in a function so the behaviour can be shown in a plain script.
- Calling it three times in one process is what re-running a cell three times does. The point of the
  script form is that it can be run, checked and pasted here; a screenshot of a notebook could not be.
- `len(ax.patches)` after each call counts the bars accumulated so far.
- `plt.get_fignums()` after each call answers the obvious follow-up question — whether re-running made
  new figures, or piled onto one.

```text
first run  — bars: 4 | figures: [1]
second run — bars: 8 | figures: [1]
third run  — bars: 12 | figures: [1]
```

**Four, eight, twelve, on one figure.** In a notebook the picture under the cell looks plausible each
time, because twelve bars drawn at four x positions overlap almost exactly — they are the same four
values three times over. You do not see a bug; you see a chart that has quietly stopped being a
statement about your data. The bar heights are right and the count is wrong, which is the hardest
kind of wrong to notice.

### The rule, and what `plt.subplots` still uses the pointer for

The rule for the rest of this day, this phase, and this repository:

> **Never `plt.plot`. Always `fig, ax = plt.subplots()`, then only `ax.` and `fig.` methods.**

Now the honest part, because a rule you half-believe is worse than none. `plt.subplots` is itself a
pyplot function and it has not left the state machine. Its body ends with `fig = figure(**fig_kw)`
followed by `fig.subplots(...)`, and `figure()` is the function that registers a figure in the
process-wide dictionary from [2.2](2.2-gca-and-the-axes-you-did-not-choose.md), gives it a number, and
makes it current.

```python
import matplotlib

matplotlib.use("Agg")
import matplotlib.pyplot as plt
from matplotlib.figure import Figure

fig1, ax1 = plt.subplots()
fig2, ax2 = plt.subplots()
print("plt.subplots registers :", plt.get_fignums())
print("and moves the pointer  :", plt.gcf() is fig2)
print("so close() can find it :", hasattr(fig2, "number"))

plain = Figure(figsize=(6, 4))
plain_ax = plain.add_subplot()
plain_ax.bar(["dairy", "bakery"], [21.85, 9.80])
print("a bare Figure()        :", plt.get_fignums())
print("has no number          :", hasattr(plain, "number"))
```

**Line by line:**

- `from matplotlib.figure import Figure` imports the class itself, bypassing pyplot completely. This
  is the only way to make a figure that the registry never hears about.
- Two calls to `plt.subplots()` are made so that the numbers list has something to show and so the
  pointer has somewhere to move.
- `plt.get_fignums()` proves the registration: `subplots` put both figures in the dictionary.
- `plt.gcf() is fig2` proves the pointer moved to the newer one. `subplots` uses the state machine
  for creation and bookkeeping; what it stops using it for is **finding where to draw**, which is the
  half that caused all four failures above.
- `hasattr(fig2, "number")` is the practical consequence: a registered figure has a number, and
  `plt.close`, `plt.get_fignums` and `plt.show` all work through it. This is a feature, not a leak —
  it is how [5.4](../05-getting-it-out/5.4-the-figures-you-never-closed.md) can count what you forgot
  to close.
- `Figure(figsize=(6, 4))` builds a figure with no pyplot involvement at all. `add_subplot()` gives
  it a panel and `bar` draws on that panel exactly as normal, because none of the drawing code ever
  needed pyplot.
- The last two lines are the trade: the bare figure is invisible to `plt.get_fignums()` and has no
  `.number`, so `plt.close` cannot help you and you are responsible for letting it go yourself. That
  is the right choice inside a long-running web service and the wrong choice in a script.

```text
plt.subplots registers : [1, 2]
and moves the pointer  : True
so close() can find it : True
a bare Figure()        : [1, 2]
has no number          : False
```

So the accurate statement is not "`plt.subplots` avoids the state machine". It is: **`plt.subplots`
uses the state machine to create and track a figure, and then hands you names so that nothing else
ever has to consult it.** Creation is a single call at a known point in your code. Lookup is what was
happening thousands of times, silently, in the wrong place.

## When it breaks

The test-suite failure above is worth one more look, because the shape of it is the thing to
recognise, not the message. Run the failing test **on its own**:

```text
$ python -m pytest tests/test_charts.py::test_weekly_chart_has_one_line -q
.                                                                        [100%]
1 passed in 1.77s
```

**What it means.** The test that just failed passes when it is the only test in the process. Nothing
about the test changed; the only difference is what ran before it. That is the signature of test
pollution, and once you have seen it you will recognise it in code that has nothing to do with charts
— a cached connection, a changed working directory, a module-level list somebody appended to.

The practical diagnosis, in order:

1. Run the failing test alone. If it passes, the test is not the problem.
2. Run the file. If it fails, something earlier in the file is leaking state.
3. Find the shared thing. For matplotlib it is always the figure registry.

And the repair, which is the same two lines as everywhere else on this page:

```text
$ python -m pytest tests/test_charts.py
============================= test session starts =============================
platform win32 -- Python 3.12.12, pytest-9.1.1, pluggy-1.6.0
plugins: anyio-4.14.2
collected 2 items

tests\test_charts.py ..                                                  [100%]
============================== 2 passed in 1.85s ==============================
```

That run is the identical test file with `plt.bar(...)` / `return plt.gca()` replaced by
`fig, ax = plt.subplots()` / `ax.bar(...)` / `return ax` in both drawing functions. No assertion was
changed, no fixture was added, and the pollution is gone — because there is no longer anything shared
to pollute. A fixture that calls `plt.close("all")` after every test is the belt-and-braces version,
and [6.2](../06-the-module/6.2-testing-a-chart-without-looking.md) writes one, but it is a second line
of defence rather than the fix.

## In production

**What a professional writes instead of the teaching version.** Every function that draws creates or
receives a panel, uses only methods on that panel, and returns it. In practice that is the signature
from [3.5](../03-the-object-api/3.5-the-ax-parameter.md) — `def spend_by_aisle(spend, ax=None) ->
Axes` — and it is not a style preference. It is the only shape that survives being called twice, being
called from a loop, being called from a test, and being called from inside a grid. A codebase where
every chart function has that signature can compose charts freely; a codebase of `plt.` functions can
only ever draw one chart per process without care.

**What degrades at scale and under concurrency.** The four failures on this page all get worse the
larger the program is, because they are all failures of *distance*. In a twenty-line script, the call
that moved the pointer is on screen. In a report generator with a chart registry, a template layer and
a plugin that also draws, it is in a file you have not opened. Add threads and it is not even in a
file you can find: the registry is one dictionary per process
([2.2](2.2-gca-and-the-axes-you-did-not-choose.md)), so two workers rendering two customers' reports
share it, and the interleaving is the scheduler's decision, not yours. The output is not a crash. It
is a correct-looking PNG with the wrong customer's line on it.

**The failure that only appears with real data.** A nightly job wrote one chart per region and had
been running for months. It was written and reviewed with the test fixture's single region, where the
current figure is always the only figure, so the loop's missing "new sheet" step was invisible. In
production there were twelve regions. Every night it wrote twelve files; the first was right, and the
twelfth had twelve overlapping lines. Nobody noticed for a long time, because the chart people
actually opened was the alphabetically first one, which is the one case that is always correct. The
data was fine. The tests were green. The bug was entirely in the fact that the second iteration of a
loop is a different situation from the first, and only `plt.` code has that property.

**The review comment a senior engineer leaves.** *"These four functions all draw with `plt.` and
return `None`. That means the module can produce exactly one chart per process and I cannot write a
test for any of them that does not depend on the order of the file. Give each one `ax=None`, create
the axes only when it is `None`, return the axes, and let the caller own the figure. Then delete the
`plt.close('all')` you added in `conftest.py` to make the suite pass — that was a symptom."*

**The interview question.** *"Why do people say to avoid `plt.plot` in favour of the object-oriented
API?"* Because `plt.` functions take their target from a process-wide pointer to the current figure
and axes, so behaviour depends on execution order rather than on arguments. Give the four cases: two
drawing functions in sequence, a loop, a test suite where order decides the target, and a re-run
notebook cell. Then the follow-up that finds out whether you have used it: *"does `plt.subplots` avoid
that?"* — partly. It still creates the figure through pyplot, registers it and makes it current, which
is what lets `plt.close` and `plt.get_fignums` work; what it removes is the lookup, because from that
line on you refer to the figure and the axes by name. If you want no pyplot at all — in a web service,
say — construct `matplotlib.figure.Figure` directly and accept that you must manage its lifetime
yourself.
