# 5.2 — The document Python actually obeys: *PEP 440*

## One-line answer

*PEP 440* is the specification that defines what a Python version string **is**, what it **means**
when two are compared, and exactly what each specifier — `==`, `~=`, `!=`, `===` — selects; it is not
semantic versioning, it normalises input instead of rejecting it, and it is the document `uv` is
obeying when it decides which file to download.

---

| Field | Value |
|---|---|

| **Created** | 18 March 2013 · **Status:** Final · **Accepted:** 22 August 2014 |
| **Canonical URL** | <https://peps.python.org/pep-0440/> — fetched 2026-08-25 |
| **Reference implementation** | `packaging`, which is what `pip` and `uv` use to apply it |

**What to actually read.** Three sections, in this order: **"Version scheme"** (the shape of a legal
version), **"Compatible release"** (the `~=` definition, which is two lines long and settles most
arguments), and **"Version matching"** (why a trailing `.*` behaves differently from everything
else). The normalisation appendix is worth skimming once so you know that the string you typed is
not necessarily the string being compared.

## The story

A package index had been running for years before anyone wrote down what a version string was. The
result was every convention at once: `1.0`, `1.0.0`, `v1.0`, `1.0-alpha`, `1.0a`, `1.0.dev3`,
`2013.04.01`, `1.0-1`, `1.0.post1`, `1.0_final`. Every one of them was on the index, and every one of
them was somebody's release.

That was survivable while humans read the numbers. It stopped being survivable the moment a tool had
to answer a question automatically: *given this requirement, which of these files do I install?* To
answer, the tool must sort the candidates — and to sort them, it must decide whether `1.0-alpha`
comes before or after `1.0a`, whether `v1.0` is the same release as `1.0`, and whether `1.0.post1` is
newer than `1.0` or a variant of it. There was no document to appeal to, so each tool decided for
itself, and two installers could resolve the same requirement to different files.

The fix was not to demand everyone republish under a clean scheme — that is impossible on an index
where releases are immutable. It was to write one specification that (a) defines a canonical form,
(b) defines a total ordering over it, and (c) **maps the historical mess onto the canonical form
wherever it possibly can**, rejecting only what is genuinely undecidable. That third choice is the
one you feel every day, and it is why the packaging layer answered `1.0.0a1` when
[5.1](5.1-semver-2-0-0.md) handed it a semantic version.

---

## The idea in plain language

A PEP 440 version is a sequence of parts, most of them optional, in a fixed order:

```text
[N!]N(.N)*[{a|b|rc}N][.postN][.devN][+local]
 │   │      │           │        │      └── local version: not from the index, ordered, never uploaded
 │   │      │           │        └───────── development release: BEFORE everything it belongs to
 │   │      │           └────────────────── post-release: AFTER the release it belongs to
 │   │      └────────────────────────────── pre-release: alpha, beta, release candidate
 │   └───────────────────────────────────── the release segment: 1.2.3, any number of parts
 └───────────────────────────────────────── epoch: the escape hatch for a changed scheme
```

Four ideas carry the whole document.

**Normalisation comes first.** Before any comparison, a version string is rewritten into canonical
form: case is lowered, `v` prefixes are dropped, `alpha` becomes `a`, `-`/`_` separators become
nothing or `.` as the rules require. `1.0.0-Alpha.1`, `1.0.0alpha1` and `1.0.0a1` are the **same
version**. This is the opposite instinct to a strict grammar: the specification's job was to make
sense of an index that already existed.

**Ordering is total and includes the modifiers.** Within one release, the order is
`dev < a < b < rc < (final) < post`. So `1.0.dev1 < 1.0a1 < 1.0rc1 < 1.0 < 1.0.post1`. Note where the
dev release sits — *before* the alpha, not after the final. And note that the release segment is
**zero-padded** before comparison, so `1.0` and `1.0.0` are equal, which is not true in semantic
versioning's model where the number of parts is fixed at three.

**Pre-releases are excluded unless you ask.** A plain `>=1.0` does not match `2.0rc1`. The
specification says pre-releases are not installed by default even when they satisfy the clause
arithmetically. This is the rule behind
[2.2](../02-pypi-index/2.2-yanked-and-prerelease.md)'s distinction between "newest published" and
"newest stable", and it is why a release candidate can sit on the index for weeks without anyone
accidentally installing it.

**Specifiers are defined, not implied.** Each operator has an exact meaning:

| Operator | Means |
|---|---|
| `== 2.2.1` | exactly this version, after normalisation |
| `== 2.2.*` | **prefix matching** — additional trailing segments are ignored |
| `~= 2.2` | *"compatible release"*: the specification defines it as `>= 2.2` **and** `== 2.*` |
| `~= 2.2.1` | `>= 2.2.1` **and** `== 2.2.*` — the ceiling moves with the number of segments you wrote |
| `!= 2.2.1` | not this version |
| `>= 2.2` | this or later, pre-releases excluded by default |
| `=== 2.2.1` | **arbitrary equality**: string comparison, no normalisation, the escape hatch |

The `~=` row is the one worth memorising, because it is the specifier people most often use without
knowing what they asked for. `~=2.2` allows `2.9.9`. `~=2.2.1` does not — it stops at `2.2.x`. The
number of segments you write *is* the ceiling.

## The mechanism

The two clauses that do the most work in a real `pyproject.toml` are *compatible release* and
*prefix matching*. Both are defined by equivalence to simpler clauses, which means both can be
implemented from the text in a few lines — from scratch before library (Principle 2).

The definitions, verbatim in effect:

- `~= V.N` is equivalent to `>= V.N, == V.*` — the ceiling is formed by dropping the **last**
  segment of what you wrote and prefix-matching on the rest.
- `== V.*` ignores additional trailing segments when deciding whether a candidate matches.

```python
import re

VERSION_RE = re.compile(r"^v?(?:(\d+)!)?(\d+(?:\.\d+)*)$")


def release(version: str) -> tuple[int, tuple[int, ...]]:
    """The epoch and the release segment of a final version."""
    found = VERSION_RE.match(version.strip().lower())
    if not found:
        raise ValueError(f"not a final PEP 440 version: {version!r}")
    epoch = int(found.group(1) or 0)
    return epoch, tuple(int(n) for n in found.group(2).split("."))


def prefix_match(spec: str, candidate: str) -> bool:
    """`== 1.1.*` - trailing segments are ignored, so 1.1.9 matches and 1.2 does not."""
    spec_epoch, spec_release = release(spec.removesuffix(".*"))
    cand_epoch, cand_release = release(candidate)
    if spec_epoch != cand_epoch:
        return False
    return cand_release[: len(spec_release)] == spec_release
```

**Line by line:**

- `VERSION_RE` accepts only *final* versions — an epoch, then a dot-separated release segment. It
  deliberately does **not** accept `a1`, `.post1` or `.dev1`, because this mechanism is about the two
  matching clauses and a partial parser that silently mishandles pre-releases would be worse than one
  that refuses them. Knowing what your parser does not cover is part of writing one.
- `v?` — the optional `v` prefix, dropped during normalisation. `v1.0` and `1.0` are one version, and
  this is the cheapest possible demonstration that the string you type is not the string compared.
- `(?:(\d+)!)?` — the epoch, a non-capturing group wrapping a capturing one. An epoch exists so a
  project that switched schemes (say from date-based `2013.04` to `1.0`) can declare that everything
  after the `!` belongs to a newer era. It is rare, and it is checked **first** in every comparison
  below, because no amount of release-segment arithmetic can cross an epoch boundary.
- `version.strip().lower()` — normalisation, minimally. Case-insensitivity is in the specification,
  not a convenience.
- `tuple(int(n) for n in ...)` — the release segment becomes a tuple of integers, so `1.10` sorts
  above `1.9`. A tuple rather than a list because it must be hashable and comparable, and because it
  is a value, not a container that anyone should mutate.
- `spec.removesuffix(".*")` — the `.*` is stripped, then the remainder is parsed as an ordinary
  version. This is exactly what the specification says prefix matching is: the same version, compared
  on fewer segments.
- `cand_release[: len(spec_release)] == spec_release` — the whole of prefix matching, in one line.
  `== 2.2.*` keeps the first two segments of the candidate and compares them. `2.2.1` keeps `(2, 2)`
  and matches; `2.3` keeps `(2, 3)` and does not.
- `if spec_epoch != cand_epoch: return False` — epochs are not comparable by prefix. `1!2.2` is not
  in `== 2.2.*`, whatever the digits look like.

## The demo

One project, one feature: **a specifier evaluator that answers "which of these releases does this
requirement allow?"** for the two clauses that decide most real pins. No resolver, no downloads, no
dependency graph — the paper's contribution is the *meaning of the specifier*, and that is all this
implements.

```text
pep440-match/
├── pep440_match.py        # compatible release and prefix matching, from the spec text
└── test_pep440_match.py   # checked against `packaging`, the reference implementation
```

`pep440_match.py`, in full:

```python
"""PEP 440's compatible-release and prefix-matching clauses, implemented from the text."""

import re

VERSION_RE = re.compile(r"^v?(?:(\d+)!)?(\d+(?:\.\d+)*)$")


def release(version: str) -> tuple[int, tuple[int, ...]]:
    """The epoch and the release segment of a final version. Pre/post/dev are out of scope here."""
    found = VERSION_RE.match(version.strip().lower())
    if not found:
        raise ValueError(f"not a final PEP 440 version: {version!r}")
    epoch = int(found.group(1) or 0)
    return epoch, tuple(int(n) for n in found.group(2).split("."))


def pad(left: tuple[int, ...], right: tuple[int, ...]) -> tuple[tuple, tuple]:
    """PEP 440: the shorter release segment is zero-padded before comparison."""
    width = max(len(left), len(right))
    return left + (0,) * (width - len(left)), right + (0,) * (width - len(right))


def prefix_match(spec: str, candidate: str) -> bool:
    """`== 1.1.*` - trailing segments are ignored, so 1.1 matches and 1.2 does not."""
    wanted = spec.removesuffix(".*")
    spec_epoch, spec_release = release(wanted)
    cand_epoch, cand_release = release(candidate)
    if spec_epoch != cand_epoch:
        return False
    return cand_release[: len(spec_release)] == spec_release


def compatible(spec: str, candidate: str) -> bool:
    """`~= 2.2` is defined by PEP 440 as `>= 2.2` and `== 2.*` - equivalent, never a new rule."""
    spec_epoch, spec_release = release(spec)
    if len(spec_release) < 2:
        raise ValueError(f"~= needs at least two release segments, got {spec!r}")
    cand_epoch, cand_release = release(candidate)
    left, right = pad(spec_release, cand_release)
    lower_bound_ok = (cand_epoch, right) >= (spec_epoch, left)
    ceiling = ".".join(str(n) for n in spec_release[:-1]) + ".*"
    return lower_bound_ok and prefix_match(ceiling, candidate)
```

**Line by line:** — `release` and `prefix_match` are the mechanism above; only what is new is walked
through here.

- `pad(left, right)` exists because the specification zero-pads the shorter release segment before
  comparing. Without it, `(2, 2) >= (2, 2, 1)` is `False` in Python — a two-element tuple is less than
  a three-element one that shares its prefix — and `~=2.2` would wrongly reject `2.2.1`, the most
  common case there is.
- `(0,) * (width - len(left))` — padding with zeros rather than truncating the longer side, because
  `2.2` *is* `2.2.0` under this specification. Truncating would make `2.2.1` equal to `2.2`.
- `if len(spec_release) < 2: raise ValueError(...)` — the specification forbids `~= 2`, because the
  ceiling is formed by dropping the last segment and there would be nothing left to prefix-match on.
  Raising here rather than guessing is the same instinct as Principle 4: refuse the ambiguous case,
  never invent a default.
- `lower_bound_ok = (cand_epoch, right) >= (spec_epoch, left)` — the `>= V.N` half. Epoch first inside
  the tuple, so an epoch bump dominates every digit after it, exactly as the specification orders it.
- `ceiling = ".".join(...spec_release[:-1]) + ".*"` — the `== V.*` half, and the line that makes `~=`
  behave the way it does. `spec_release[:-1]` drops the **last** segment you wrote: from `2.2` it
  builds `2.*`, from `2.2.1` it builds `2.2.*`. One extra digit in your `pyproject.toml` moves the
  ceiling by an order of magnitude, and this slice is where that happens.
- `return lower_bound_ok and prefix_match(...)` — the two halves ANDed, because the specification
  defines `~=` as exactly the conjunction of two clauses it had already defined. No new comparison
  logic is invented, which is why the implementation is short enough to trust.

`test_pep440_match.py`, in full:

```python
"""Every case here is checked against `packaging`, the reference implementation of PEP 440."""

import pytest
from packaging.specifiers import SpecifierSet
from pep440_match import compatible, prefix_match

CANDIDATES = ["2.1.9", "2.2", "2.2.1", "2.3", "2.9.9", "3.0", "3.0.1"]


@pytest.mark.parametrize("spec", ["~=2.2", "~=2.2.1"])
def test_compatible_agrees_with_packaging(spec):
    mine = {c for c in CANDIDATES if compatible(spec.removeprefix("~="), c)}
    theirs = set(SpecifierSet(spec).filter(CANDIDATES))
    assert mine == theirs


@pytest.mark.parametrize("spec", ["==2.2.*", "==2.*", "==3.0.*"])
def test_prefix_match_agrees_with_packaging(spec):
    mine = {c for c in CANDIDATES if prefix_match(spec.removeprefix("=="), c)}
    theirs = set(SpecifierSet(spec).filter(CANDIDATES))
    assert mine == theirs


def test_tilde_equals_needs_two_segments():
    with pytest.raises(ValueError, match="at least two release segments"):
        compatible("2", "2.2")
```

**Line by line:**

- The oracle is `packaging`, not a hand-written expected list. A from-scratch implementation
  (Principle 2) is only educational if something independent says it is right; comparing against the
  library the installer actually uses turns "I think I understood the clause" into evidence.
- `SpecifierSet(spec).filter(CANDIDATES)` — `filter` rather than a loop of `in` checks, because
  `filter` is where `packaging` applies the pre-release exclusion rule. Using it means the test would
  catch a divergence on pre-releases the moment one entered `CANDIDATES`.
- `set(...) == set(...)` — sets, not lists, because the two implementations have no obligation to
  agree on *order*, only on membership. Asserting order would make the test fail for a reason that is
  not a bug.
- `@pytest.mark.parametrize` — each specifier is its own test case, so a failure names which clause
  broke rather than reporting one opaque red test.
- `pytest.raises(ValueError, match="at least two release segments")` — the refusal is behaviour, and
  behaviour gets a test. `match=` pins the reason, so replacing the message with a vague one is a
  visible change rather than a silent one.

```console
$ uv run --with pytest --with packaging python -m pytest -q
......                                                                   [100%]
6 passed in 0.17s

$ uv run --with packaging python -c "

C=['2.1.9','2.2','2.2.1','2.3','2.9.9','3.0','3.0.1']
for spec in ['2.2','2.2.1']:
    print(f'~={spec:6s} ->', [c for c in C if compatible(spec,c)])
for spec in ['2.2.*','2.*']:
    print(f'=={spec:6s} ->', [c for c in C if prefix_match(spec,c)])"

~=2.2.1  -> ['2.2.1']

==2.*    -> ['2.1.9', '2.2', '2.2.1', '2.3', '2.9.9']
```

Read the first two lines together, because that contrast is the entire reason this demo exists.
`~=2.2` accepted `2.9.9` — seven minor releases of new behaviour, arriving automatically. `~=2.2.1`
accepted nothing but `2.2.1` from this list. One extra digit, a completely different bet.

**What this demo deliberately leaves out.** Pre-release, post-release and dev-release parsing; the
`!=`, `<`, `>` and `===` operators; the normalisation appendix; and the resolver that has to satisfy
*many* specifiers at once — which is [1.3](../01-versions/1.3-the-resolution-problem.md)'s subject and
a genuinely harder problem than anything here. This implements what a specifier *means*, not how a
solver finds a version satisfying twenty of them.

## When it breaks

The failure that costs an evening is not a crash — it is `~=` doing exactly what it was defined to do.

```python
from packaging.specifiers import SpecifierSet

available = ["2.2", "2.2.1", "2.3", "2.9.9", "3.0"]
print(list(SpecifierSet("~=2.2").filter(available)))
```

```text
['2.2', '2.2.1', '2.3', '2.9.9']
```

Nobody who writes `~=2.2` believes they have accepted `2.9.9`. They have. Under the definition, the
ceiling came from dropping the last segment of `2.2`, leaving `== 2.*`. This is the specifier that
quietly turns into [4.1](../04-drift/4.1-the-three-breaking-changes.md)'s silent breaking change,
because minor releases are exactly where behaviour changes.

The second failure is a genuine exception, and it is where the two documents collide:

```python
from packaging.version import Version

print(Version("1.0.0-alpha.beta"))
```

```text
packaging.version.InvalidVersion: Invalid version: '1.0.0-alpha.beta'
```

That string is a legal semantic version — `alpha.beta` is two alphanumeric pre-release identifiers,
and [5.1](5.1-semver-2-0-0.md)'s implementation sorts it happily. PEP 440 has no grammar for a
pre-release whose label is a word followed by another word, so it refuses. The refusal is correct
behaviour: normalisation maps what it can and rejects what it genuinely cannot decide.

**The smallest fix** for the first failure: write the specifier you actually mean. If you mean "patch
releases of 2.2 only", write `~=2.2.1` or `==2.2.*` — not `~=2.2`. For an application, Principle 4's
answer is `==2.2.1` plus a lockfile, and the freshness check on
[4.2](../04-drift/4.2-drift-and-the-amendment-protocol.md) rather than an automatic range. For the
second: a version string crossing from another ecosystem must be *translated*, not passed through.

## What did not survive

**`~=` did not become the default, and probably should not have.** It was designed as the
"compatible release" operator, the ergonomic middle ground between pinning and floating. In practice
the segment-counting rule surprises people often enough that most production Python projects pin
exactly and lock, which is precisely what Principle 4 requires. The operator survives; the intent
behind it — that most projects would use it and be fine — did not.

**Arbitrary equality (`===`) exists and is a confession.** The specification includes an operator
that skips normalisation and compares strings directly, for versions it cannot parse. That is a
document acknowledging that it does not cover the whole index. Meeting `===` in a real
`pyproject.toml` is a signal that something upstream is not PEP 440-compliant at all.

**The scheme grew.** PEP 440 is Final, but it does not stand alone any more: PEP 592 added yanked
releases (which [2.2](../02-pypi-index/2.2-yanked-and-prerelease.md) covers), PEP 508 defined the
dependency-specification grammar around it, and PEP 685 tightened extra-name comparison. Reading PEP
440 alone gives you the version model, not the whole of what an installer obeys. A version scheme
turned out to be one layer of a stack, not a complete answer.

**Nobody expected normalisation to become invisible tooling.** The choice to rewrite rather than
reject was pragmatic, and it worked — so well that most Python programmers do not know it happens.
The cost is a class of bug that is genuinely hard to see: you publish `1.0.0-alpha.1`, the index
stores `1.0.0a1`, your changelog says one thing and your `pip index` output says another, and neither
is wrong.

**The disagreement with semantic versioning is permanent.** `1.0.0+build.2 > 1.0.0+build.1` is `True`
in Python and required to be `False` by the other document. There is no plan to reconcile them, and
none is needed — they answer different questions. What is needed is knowing which one you are
standing in.

## In production

**What a professional writes.** In an application: exact pins plus a committed lockfile, with the
range logic living in the update process rather than in the file. In a library: the *loosest* bound
that is honest, usually `>=` with an upper bound only where a breaking change is known — because a
library that pins exactly makes itself uninstallable alongside anything else, and the resolution
problem in [1.3](../01-versions/1.3-the-resolution-problem.md) is what that causes.

**What changes at scale.** With hundreds of dependencies, the pre-release exclusion rule becomes
load-bearing: without it, one dependency publishing a release candidate would ripple through every
build in the organisation. Large deployments also hit the epoch clause eventually — usually when a
vendored internal package changes its scheme — and discover that the epoch is the only mechanism that
can say "this small-looking number is newer than that big-looking one".

**The review comment a senior engineer leaves.** On `~=2.2`: *"That allows every 2.x minor release.
Did you mean `~=2.2.1`? Say which behaviour you are agreeing to accept automatically."* On a
requirements file with no lockfile: *"These specifiers describe intent; nothing here records what was
resolved. `uv lock` and commit the result."*

**The interview question.** *"What is the difference between `~=2.2` and `~=2.2.1`?"* The answer that
shows you have read the document is not just the ranges — it is *why*: the compatible-release clause
is defined as `>= V.N, == V.*`, the ceiling is formed by dropping the last segment you wrote, so the
number of segments in your specifier is the ceiling. The follow-up is usually *"and would `>=2.2`
install `3.0rc1`?"* — no, because pre-releases are excluded by default, and that is a separate clause
people routinely forget.
