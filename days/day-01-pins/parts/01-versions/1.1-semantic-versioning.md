# 1.1 — Semantic versioning, and what a major bump actually promises

> **The source.** The rules below are not a convention that grew by accident. They are written
> down in one short document: *Semantic Versioning 2.0.0* (2013), <https://semver.org/spec/v2.0.0.html>.

## One-line answer

A version like `3.0.5` is a **claim about compatibility**, not a measure of progress: the first
number changes when the authors have deliberately broken something you were relying on, the second
when they added something, the third when they fixed something — and that claim is a social
convention, kept well by most projects and imperfectly by some.

---

## The story

Someone maintains a small internal service. It has worked untouched for a year. One morning the
nightly build fails, on a line of code nobody has edited.

They look at the diff. There is no diff — no commit since the last green build. They look at the
build log and find a different version number next to one of the dependencies. The requirements file
says `pandas>=2.0`, and overnight, `pandas 3.0.0` was published.

The maintainers of pandas did nothing wrong. They spent a year announcing the change, wrote a
migration guide, shipped deprecation warnings, and put a `3` at the front of the version number
precisely to say: *this release removes behaviour you may depend on.* That number was the warning.

It was a warning nobody read, because `>=2.0` had already agreed to accept it, automatically, at
2am, with no human in the loop.

The version number did its job. The specifier threw the information away.

---

## The idea in plain language

Start from nothing. A **release** is a published, immutable snapshot of a package: someone uploaded
files, and they can never be changed afterwards (they can be withdrawn — see
[2.2](../02-pypi-index/2.2-yanked-and-prerelease.md) — but never edited). A **version** is that release's name.

Almost all Python packages name releases using **semantic versioning**, usually written *semver*.
The shape is three numbers:

```text
MAJOR . MINOR . PATCH
  3   .   0   .   5
```

Each position is a promise about what changed:

| Position | Bumped when | What it means for you |
|---|---|---|
| **PATCH** (`3.0.4` → `3.0.5`) | a bug was fixed | Your code keeps working. Upgrade freely; security fixes arrive here. |
| **MINOR** (`3.0.5` → `3.1.0`) | something was **added** | Your code keeps working. New things exist that you may ignore. |
| **MAJOR** (`3.0.5` → `4.0.0`) | something was **removed or changed** | **Your code may stop working.** Read the migration guide. |

The direction of the promise matters and is easy to get backwards: a minor bump promises that code
written for `3.0` still runs on `3.1`. It does **not** promise the reverse — code written for `3.1`
may use something that does not exist in `3.0`. Compatibility flows forwards, not backwards.

Two refinements you will meet constantly:

**Zero is different.** A version below `1.0.0` — `0.16.4`, `0.28.1` — is conventionally understood
to make *no* stability promise at all. Under semver's own rules, anything may change in a `0.x`
release. Look at your own `pyproject.toml`: `ruff` is `0.16.4`. A ruff `0.17` may legitimately change
behaviour that `0.16` had, which is exactly why it is pinned exactly rather than loosely.

**Python's own version scheme is not semver.** Python releases `3.11`, `3.12`, `3.13` — the *minor*
number is the compatibility boundary, and there is no plan for a `4`. This is why
[Day 0's part 1.4](../../../day-00-setup/parts/01-toolchain/1.4-python-3-12-under-uv.md) treats a 3.12 → 3.13
move as the risky one. The general rule: **read each project's own versioning policy rather than
assuming semver**, because the number's meaning is set by its authors.

And that is the honest core of this part. Semver is a **convention**, not a mechanism. Nothing
enforces it. A project can break you in a patch release by accident, or sit on `0.x` for years while
being rock solid. What the number gives you is a *signal about intent* — and the whole of Day 1 is
about not throwing that signal away.

## The mechanism

Look at the versions you already have, and read them as claims:

```bash
uv run python -c "import importlib.metadata as m; [print(f'{p:20} {m.version(p)}') for p in ('ruff','pytest','python-dotenv')]"
```

**Line by line:**

- `importlib.metadata` — the standard library's interface to installed-package metadata. No
  dependency needed, and it reads what is *actually installed* rather than what a file claims should
  be, which is the difference between evidence and intent.
- `m.version(p)` — the installed version string of package `p`.
- `f'{p:20}'` — an f-string with a **format specification**: pad `p` to 20 characters so the output
  lines up as a column. `f'{value:20}'` left-aligns text; you will use this constantly for readable
  terminal output.
- `[print(...) for p in (...)]` — a list comprehension used for its side effect. It is compact for a
  one-liner, and it is *not* how you would write this in a file — a plain `for` loop is clearer and
  does not build a throwaway list. Day 9 covers comprehensions properly.

Now parse a version rather than eyeballing it:

```bash
uv run python -c "
from packaging.version import Version
for s in ('3.0.5', '3.1.0', '4.0.0', '0.16.4', '2.0.0rc1'):
    v = Version(s)
    print(f'{s:10} major={v.major} minor={v.minor} micro={v.micro} pre={v.is_prerelease}')
"
```

**Line by line:**

- `packaging.version.Version` — the reference implementation of **PEP 440**, Python's own version
  specification. It is already in your environment as a transitive dependency
  ([Day 0, 2.4](../../../day-00-setup/parts/02-skeleton/2.4-uv-init-pyproject-and-the-lockfile.md)), which is
  a small illustration of what a lockfile records.
- Why not split on `.` yourself? Because real versions include forms that a naive split mangles:
  `1.0.post1`, `2.0.0rc1`, `1.0.dev3`, `1!2.0` (an *epoch*, used when a project restarts its
  numbering). Parsing versions by hand is a classic source of subtle bugs; the library exists
  because the format is richer than it looks.
- `v.major`, `v.minor`, `v.micro` — the three positions. Note PEP 440 calls the third **micro**, not
  *patch*, which is a naming difference worth knowing when you read tracebacks and docs.
- `v.is_prerelease` — `True` for `2.0.0rc1`. A **pre-release** is a version published for testing
  before the real one, and tools exclude them by default —
  [2.2](../02-pypi-index/2.2-yanked-and-prerelease.md) is entirely about that.
- The multi-line string passed to `-c` — quoting a whole script inline. Fine for a demonstration;
  anything longer belongs in a file, which is what you build in
  [2.3](../02-pypi-index/2.3-the-check-pins-script.md).

Compare versions the correct way, which is not string comparison:

```bash
uv run python -c "
from packaging.version import Version
print('string compare says 3.10 > 3.9 :', '3.10' > '3.9')
print('Version compare says 3.10 > 3.9:', Version('3.10') > Version('3.9'))
"
```

**Line by line:**

- The first line prints `False`. As **text**, `'3.10' > '3.9'` compares character by character: `1`
  sorts before `9`, so `3.10` is "smaller". This is the same class of bug as day-number padding in
  [Day 0, 3.2](../../../day-00-setup/parts/03-m-script/3.2-the-case-dispatcher.md), and it is why sorting
  version strings alphabetically is always wrong.
- The second prints `True`, because `Version` compares numerically, position by position, with the
  pre-release rules applied.
- **Never compare version strings as strings.** If you remember one mechanical fact from this part,
  make it this one.

## When it breaks

**The story's failure, as it actually appears in a build log:**

```text
Collecting pandas>=2.0
  Downloading pandas-3.0.0-cp312-cp312-manylinux_2_17_x86_64.whl (12.4 MB)
...
Successfully installed pandas-3.0.0

$ python -m pytest
E   TypeError: Cannot set values on a view of a DataFrame
```

**What it means.** Nothing is broken and nothing is a bug. The specifier `>=2.0` said "any version
from 2.0 upward is acceptable to me", the resolver believed it, and pandas 3 removed the behaviour
the test relied on — which is precisely what a major bump announces. The error appears in *your*
test because the incompatibility is between your code and the new major, not inside pandas.

The fix is not to chase the error. It is to stop delegating the decision:
[1.2](1.2-version-specifiers.md) is about the specifier, and
[3.2](../03-freezing/3.2-freezing-into-pyproject-and-the-lock.md) about freezing it.

**The version that sorts wrong, in a script you wrote yourself:**

```text
>>> sorted(['1.9.0', '1.10.0', '1.11.0'])
['1.10.0', '1.11.0', '1.9.0']
```

**What it means.** Alphabetical order on version strings, putting `1.9.0` last when it is the
oldest. A script that picks "the newest version" this way picks the wrong one, silently, and only
once a project crosses from `.9` to `.10` — so it works for months and then quietly stops. The fix
is `sorted(versions, key=Version)`, which sorts by parsed version rather than by text.

**The assumption that semver is enforced:**

```text
$ uv add "some-library==1.4.2"
$ uv run python -m pytest
E   AttributeError: 'Client' object has no attribute 'fetch'
```

...after upgrading from `1.4.1`. **What it means.** A patch release removed a method, which semver
says should not happen. It happens. The lesson is not that versioning is useless — it is that
**semver is a promise, and promises are kept by people.** This is exactly why the defence is an
exact pin plus a test suite, not trust: your tests are what turn a broken promise into a failed
build rather than a production incident.

---

## In production

**Version policy is a written team decision, not a per-developer habit.** Mature teams state theirs:
applications pin exactly and update on a schedule; libraries declare ranges. They also state what to
do when a major lands — typically a ticket, a branch, a read of the migration guide, and the new
major added to a test matrix alongside the old one before it becomes the default. The failure mode
without a policy is not chaos, it is *silence*: nobody upgrades anything until something forces it,
and then five majors land at once.

**Automated dependency bots exist because exact pins freeze your security posture too.** Dependabot
and Renovate open one pull request per bump, so the upgrade is reviewable, individually testable, and
attributable. The professional shape is: pinned by default, upgraded deliberately, tests as the gate.
The bots also read semver — most teams configure minor and patch bumps to auto-merge on green CI, and
major bumps to always require a human. That configuration is this part's table, encoded.

**Calendar versioning is the other convention you will meet.** Some projects version by date
(`2024.10.1`) — it communicates recency rather than compatibility, and it tells you *nothing* about
whether an upgrade is safe. When you see it, the release notes are the only source of truth. Knowing
that two conventions exist, and checking which one a project uses, is the actual skill.

**Deprecation warnings are the mechanism majors are supposed to use, and they are usually
suppressed.** A well-run project raises `DeprecationWarning` for a full release cycle before removing
something — but Python hides those by default outside of test runs. The professional habit is to make
them visible where it is cheap: `filterwarnings = ["error::DeprecationWarning"]` in pytest
configuration turns a future breakage into a failing test *today*, while the old behaviour still
works. That single line converts a major-version surprise into a scheduled piece of work, and it is
one of the highest-leverage settings in a Python project.

**The review comment a senior engineer leaves.** On a dependency added as `requests>=2`:
*"Please pin this. `>=` means a future major can land in an unrelated build with no commit — we
would not be able to tell which change broke it."* And on a patch bump in a PR with no test run:
*"Even a patch can break us; let CI confirm rather than the version number."*

**The interview question.** *"What does it mean when a library goes from 2.x to 3.0, and how should
your project react?"* They want: a major signals intentional backward-incompatible change, so it
requires reading the migration notes and testing, not just a version bump. The stronger answer adds
that semver is a convention rather than a guarantee, that `0.x` promises nothing, and that the real
defence is an exact pin plus a test suite that can fail — because your tests, not the version number,
are what actually detect an incompatibility.

## Check yourself

```bash
uv run python -c "
from packaging.version import Version
vs = ['1.9.0','1.10.0','0.16.4','2.0.0rc1','3.0.5']
print('wrong:', sorted(vs))
print('right:', sorted(vs, key=Version))
print('prereleases:', [v for v in vs if Version(v).is_prerelease])
"
```

The two orderings must differ, and `2.0.0rc1` must be the only pre-release.

> guarantee you about upgrading to `0.17.0`, and what does that imply about how you should pin it?
