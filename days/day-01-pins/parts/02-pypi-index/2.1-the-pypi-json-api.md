# 2.1 — PyPI's JSON API, and why you never take a version from a tutorial

## One-line answer

PyPI publishes machine-readable metadata for every project at
`https://pypi.org/pypi/<project>/json`, so the current version of anything is a request away — which
means a version number copied from a blog post, a book, or a model's memory is a guess when the truth
was available.

---

## The story

Someone writes a setup guide for their team. It is careful work: every dependency listed, every
version pinned, a paragraph explaining each choice. It goes in the repository and people follow it.

Fourteen months later a new joiner follows it exactly and the install fails. Two of the pinned
versions have been withdrawn. One package has moved to a new name. One of the "current" versions in
the document is four majors behind, and the migration guide for the gap is itself out of date.

The document was accurate the day it was written and has been quietly decaying ever since, because
it recorded **answers** rather than **the question and how to ask it**.

Now consider a second document. It contains no version numbers at all. It contains a script that
reads the index and prints today's versions, and a rule for what to do with the answer. It was
written on the same afternoon. It still works, because a version number has a shelf life and a method
does not.

That is the difference this whole day is built on — and it applies to `docs/PINS_DS.md` too, which
is why its own header says *"Your job on Day 1 is not to trust this file."*

---

## The idea in plain language

Start from the bottom. A **package index** is a server that hosts published packages and describes
them. **PyPI** — the Python Package Index, at `pypi.org` — is the default one, and it is where
`uv add pandas` looks unless told otherwise.

An index has two jobs, and it exposes an interface for each:

**The Simple (Index) API** is the machine interface installers use to find *files*. It implements
two standards — **PEP 503** for its HTML form and **PEP 691** for its JSON form — and it is what a
resolver actually talks to. You reach the JSON form by asking for it in the request:

```text
GET https://pypi.org/simple/<project>/
Accept: application/vnd.pypi.simple.v1+json
```

That returns a `"versions"` array of every release, and a `"files"` list where each entry carries
`"filename"`, `"url"`, `"hashes"`, `"requires-python"`, `"yanked"`, `"size"` and `"upload-time"`.
Note the field names use **hyphens** here.

**The JSON API** is the friendlier, project-oriented interface:

```text
GET https://pypi.org/pypi/<project>/json          -> the project, at its latest release
GET https://pypi.org/pypi/<project>/<version>/json -> one specific release
```

Its top-level `info` object is what you want. The fields that matter today:

| Field | What it holds |
|---|---|
| `info.version` | the version string for the release this response describes |
| `info.requires_python` | the interpreter constraint, e.g. `">=3.12"` — the input to [3.1](../03-freezing/3.1-the-python-version-intersection.md) |
| `info.requires_dist` | the list of dependency requirement strings, in PEP 440 grammar ([1.2](../01-versions/1.2-version-specifiers.md)) |
| `urls` | the file objects for this release, each with `yanked` and `yanked_reason` |

Note these use **underscores**, unlike the Simple API's hyphens. Two interfaces, two naming
conventions, and mixing them up produces a `KeyError` rather than an explanation.

Three things worth knowing that you will not guess:

**The `releases` key is deprecated.** The project-level JSON response has historically included a
`releases` object mapping every version to its files, and a great deal of code on the internet is
built on it. PyPI's own documentation now lists it as deprecated and directs you to the Index API for
enumerating versions. Three other keys are deprecated and already inert: `downloads` always returns
`-1`, `has_sig` always `false`, `bugtrack_url` always `null`. **Building on a deprecated key is how
today's correct script becomes next year's broken one** — which is exactly the failure this part is
about, one level up.

**The documentation does not promise that `info.version` excludes yanked releases.** It describes it
as the latest release in the response's context and says no more. So if "is this version safe to
pin?" matters — and on Day 1 it is the entire question — you check the release's own `yanked` flag
rather than assuming. That is [2.2](2.2-yanked-and-prerelease.md).

**The documentation states no rate limits and no caching guidance.** That is not permission to
hammer it. It means the politeness is your responsibility, by construction: one request per package,
a timeout, a real `User-Agent`, and a cached result you reuse rather than re-fetching
([2.3](2.3-the-check-pins-script.md)).

And the meta-point, which is the reason this part exists at all: **everything above was read from
PyPI's live documentation while writing this lesson, not recalled.** A version number, a field name
and an API's deprecation status are all facts with expiry dates. The habit is not "know them" — it is
"check them, and write down where you checked."

## The mechanism

Ask the index a question, using nothing but the standard library:

```bash
uv run python -c "
import json, urllib.request
req = urllib.request.Request(
    'https://pypi.org/pypi/pytest/json',
    headers={'User-Agent': 'setu-pins/1.0 (learning project)'},
)
with urllib.request.urlopen(req, timeout=10) as r:
    info = json.load(r)['info']
print('version         :', info['version'])
print('requires_python :', info['requires_python'])
print('summary         :', info['summary'])
"
```

**Line by line:**

- `urllib.request` — HTTP in the standard library. Deliberate: today adds **no new dependency**,
  which respects the rule that packages arrive on the day they are first needed. `httpx` is in the
  plan for Phase 27, and it is a better tool for real work; it is not needed to read one JSON
  document.
- `urllib.request.Request(url, headers=...)` — build a request object rather than passing the URL
  directly, because that is the only way to set headers.
- `'User-Agent': 'setu-pins/1.0 (learning project)'` — **identify yourself.** The default urllib
  agent is anonymous and some services reject it. More importantly, when an index operator sees
  unusual traffic, a named agent is the difference between a conversation and a block. This is basic
  courtesy toward free infrastructure, which Principle 5 depends on.
- `timeout=10` — **never make a network call without a timeout.** The default is to wait
  indefinitely, so a hung connection hangs your script forever with no error to read. This is the
  single most common omission in scripts that talk to the network.
- `with ... as r:` — a context manager, so the connection is closed even if something raises. Day 16
  covers these properly; use them now.
- `json.load(r)` — parse from a file-like object. (`json.loads` parses a *string*; the `s` is the
  difference, and confusing them is a routine ten-second bug.)
- `['info']` — the object described in the table above.

Now the two fields that drive the rest of the day:

```bash
uv run python -c "
import json, urllib.request
def fetch(pkg):
    req = urllib.request.Request(f'https://pypi.org/pypi/{pkg}/json',
                                 headers={'User-Agent': 'setu-pins/1.0'})
    with urllib.request.urlopen(req, timeout=10) as r:
        return json.load(r)['info']
for pkg in ('pytest', 'ruff', 'python-dotenv'):
    i = fetch(pkg)
    print(f\"{pkg:15} {i['version']:10} python{i['requires_python'] or ' (unstated)'}\")
"
```

**Line by line:**

- `def fetch(pkg)` — the same request, factored into a function, because you are about to call it
  once per package and repetition in a loop is where copy-paste errors live.
- `f'https://pypi.org/pypi/{pkg}/json'` — an f-string building the URL. Safe here because the names
  are literals you control; a name that came from user input would need `urllib.parse.quote`.
- `i['requires_python'] or ' (unstated)'` — this field can be `None` when a project declares no
  interpreter constraint. `or` supplies a fallback for any falsy value — a Python idiom you will use
  constantly, and one to be careful with when `0` or `""` are legitimate values.
- **Compare the printed versions against `docs/PINS_DS.md`.** Any difference is drift, and
  [4.2](../04-drift/4.2-drift-and-the-amendment-protocol.md) is what to do about it.

See the deprecation for yourself rather than taking my word for it:

```bash
uv run python -c "
import json, urllib.request
req = urllib.request.Request('https://pypi.org/pypi/ruff/json', headers={'User-Agent':'setu-pins/1.0'})
with urllib.request.urlopen(req, timeout=10) as r:
    doc = json.load(r)
print('top-level keys:', sorted(doc))
print('deprecated but still present:', [k for k in ('releases','downloads','has_sig','bugtrack_url') if k in doc])
print('info.downloads (always -1):', doc['info'].get('downloads'))
"
```

**Line by line:**

- `sorted(doc)` — iterating a dict yields its keys, so this lists the top-level keys alphabetically.
- The second line shows which deprecated keys the server still returns. **Present is not the same as
  supported.** A key that exists today and is documented as deprecated is a key your script should
  not depend on — this is the concrete lesson in reading documentation rather than reading responses.
- `doc['info'].get('downloads')` — prints the inert `-1`. A field that once meant something, now
  frozen. If you had built a download-count dashboard on it, it would still be returning numbers, and
  they would be lies.

## When it breaks

**The name that does not exist, or is spelled differently:**

```text
urllib.error.HTTPError: HTTP Error 404: Not Found
```

**What it means.** No project by that name. Usually a spelling difference rather than a missing
package: the import name and the distribution name are often not the same — you `import sklearn` but
install `scikit-learn`, you `import dotenv` but install `python-dotenv`, you `import yaml` but
install `PyYAML`. **The index knows distribution names.** Project names are also normalised
case-insensitively with `_`, `-` and `.` treated as equivalent, so `Python_DotEnv` finds the same
project — but a genuinely wrong name is a 404 with no suggestion.

**The call that never returns:**

```text
^C
Traceback (most recent call last):
  File "<string>", line 5, in <module>
KeyboardInterrupt
```

**What it means.** You omitted `timeout=`, the connection stalled, and the script waited forever
until you interrupted it. There is no error message because nothing failed — it is still politely
waiting. In a script that loops over sixty packages this turns a quick check into a hang with no
diagnosis. **Every network call gets a timeout**, and in a loop it also gets error handling so one
bad package does not abort the other fifty-nine ([2.3](2.3-the-check-pins-script.md)).

**The key that is not there:**

```text
KeyError: 'requires-python'
```

**What it means.** You used the Simple API's hyphenated spelling against the JSON API's response,
where it is `requires_python`. Two interfaces, two conventions, as flagged above. The general defence
in code that consumes an API you do not control is `.get()` with a default, so a missing field is a
value you handle rather than an exception that stops the run.

**And the failure with no error at all, which is the one this part is really about:**

```text
# a tutorial from 2023
$ uv add "transformers==4.35.0"
Resolved 21 packages
```

**What it means.** It installed. Nothing failed. You are now on a **major version behind** the one
this plan targets, so every `transformers` example you follow from Phase 16 will diverge from your
installed API in ways that produce confusing errors far from their cause. This is why the plan marks
`transformers` ⚠️ major and why every Phase-16 lesson ends with a live-docs link. **A stale version
that installs cleanly is more expensive than one that fails**, because the failure is deferred to
somewhere unrelated.

## In production

**Nobody queries PyPI by hand at work; they automate it and cache it.** The professional versions of
this script are dependency bots that open pull requests when a new release appears, and vulnerability
scanners that map your lockfile against advisory databases. Both are built on exactly the interfaces
above. Understanding the data source means you can debug those tools when they behave oddly — and
occasionally write the small piece of glue nobody has built.

**Private and mirrored indexes are the norm at scale.** Companies run an internal index that mirrors
PyPI, for three reasons: availability (builds do not stop when the public index has an incident),
control (a package can be blocked or vetted before it is available), and audit (a record of what was
downloaded, which matters after a supply-chain incident). Anything that speaks the Simple API can be
that index, which is why PEP 503 and PEP 691 are worth knowing by name. The related trap is
**dependency confusion** from [1.3](../01-versions/1.3-the-resolution-problem.md): if a tool is configured to
consult both a private and a public index, a public package with the same name and a higher version
can win. Index configuration is a security control, not a convenience setting.

**Politeness toward free infrastructure is a professional obligation.** The docs state no rate limit,
which means the constraint is social rather than technical. Behave as if it were enforced: a
descriptive `User-Agent`, a timeout, sequential rather than parallel bursts, results cached to disk,
and a `Retry-After` respected if you ever receive one. Principle 5's entire zero-budget premise
depends on free services staying free and available, and that is a shared resource.

**Metadata is only as trustworthy as the uploader.** `summary`, `home_page` and project descriptions
are attacker-controlled text — typosquatting packages routinely copy a legitimate project's
description wholesale. The fields worth *trusting* are the structural ones: `hashes` (cryptographic),
`requires_python` and `requires_dist` (used by the resolver, so wrong values break the package
itself). Never render an index description into a page or a terminal without treating it as untrusted
input, and never choose a package because its description sounded right.

**The review comment a senior engineer leaves.** On a script fetching in a loop with no timeout and
no error handling: *"Add a timeout and catch per-package failures — one slow response should not hang
the whole job."* And on code indexing `data["releases"]`: *"That key is deprecated on PyPI; use the
Index API's `versions` list before this breaks silently."*

**The interview question.** *"How would you find out whether a dependency has a newer release, and
how would you automate it?"* The shallow answer names a website. The strong answer: query the index's
machine interface, note that the Simple API is what installers actually use and the JSON API is
convenient for project-level metadata, cache and rate-limit yourself, and then say that in practice
you would not write this at all — you would configure a dependency bot to open a reviewable pull
request per bump, because the hard part is not detecting the release, it is testing and landing it
safely.

uv run python -c "
import json, urllib.request
req = urllib.request.Request('https://pypi.org/pypi/pytest/json', headers={'User-Agent':'setu-pins/1.0'})
with urllib.request.urlopen(req, timeout=10) as r:

import importlib.metadata as m
