# 5.1 — `tests/test_stats.py` — one test per criterion, each seen to fail

## One-line answer

The gate's five criteria from [3.1](../03-the-module/3.1-the-gate-as-a-list.md) become five named tests
plus the checks they lean on, and each one is broken on purpose once so that the suite has been *seen* to
go red rather than assumed to be able to.

---

## The story

The flat has a rule about the wall chart: nobody edits it except to add today's number.

Somebody says the rule is being followed. How would anyone know? The chart looks fine. It has always
looked fine. It would also look fine if the rule had been broken in March and nobody had noticed, because
a chart that has been quietly altered looks exactly like a chart that has not.

So one evening they try it. They deliberately change a number, and then they check the copy they took at
the start of the week. The numbers do not match, which is what they hoped for — it means the check works.
Then they put the number back.

Before that evening they had a rule. After it, they had a rule and a way of finding out. Those are
different things, and the difference is entirely in having watched the check fail once.

---

## The idea in plain language

A test that has never failed is not evidence. It might be checking the thing you meant, or it might be
checking that `1 == 1` in a very elaborate way, and from the outside those look identical: both print a
dot and both take no time.

**The only way to know a test can catch something is to make it catch something.** Break the code on
purpose, watch the test go red, read the failure message, put the code back. That loop takes a minute and
it is the difference between a suite and a decoration.

This part turns [3.1](../03-the-module/3.1-the-gate-as-a-list.md)'s five criteria into
`tests/test_stats.py`. Each criterion gets a test named after it — the `checked_by` field in the criterion
list is that test's name, so a criterion with no test is visible as a name that does not exist. Around
those five sit the supporting checks: the ones that pin down the refusals, the in-place function that is
*supposed* to modify its argument, and the memory ceiling that makes "exactly one copy" observable.

Two of the criteria are the ones people leave out, and they are the ones this whole day exists for.
**Criterion 3 — never modifies the array it was given.** **Criterion 4 — never returns anything that
aliases the input.** A module can be fast, correct and green on every other test while quietly sorting its
caller's data in place ([2.1](../02-the-bug/2.1-ravel-changed-it-flatten-did-not.md)).

---

## Why Setu needs it

- **[5.2](5.2-the-performance-test-in-ci.md)** takes criterion 5's test and asks what happens when it runs
  on a machine you do not control.
- **[5.3](5.3-the-phase-closed.md)** closes the phase on this file being green and on both breaks having
  been seen.
- **[3.1](../03-the-module/3.1-the-gate-as-a-list.md)** is where the criteria were written down with their
  `checked_by` names; this is the other half of that link.
- **[2.3](../02-the-bug/2.3-the-defences.md)** named the assertion — `before = arr.copy()` then
  `np.array_equal` — as the third defence, and criterion 3's test is that assertion, parametrised over
  every public function.
- **Day 23's test suite** established the habit of asserting a claim rather than a number
  ([Day 23, 5.2](../../../day-23-ufuncs-and-statistics/parts/05-the-module/5.2-the-test-that-can-go-red.md)),
  and this file is the same habit at the scale of a phase gate.

---

## The mechanism

The whole file, criterion by criterion:

```python
"""Phase 3's gate. One test per criterion from Day 25, 3.1, plus what they lean on."""

from __future__ import annotations

import math
import timeit
import tracemalloc

import numpy as np
import pytest

from setu import stats

MONTH = np.array(
    [
        [8402.0, 11930.0, 6011.0, np.nan, 9877.0, 14210.0, 5096.0],
        [9120.0, 7734.0, 10402.0, 8890.0, 12005.0, 13877.0, 6210.0],
        [7788.0, 9002.0, 11566.0, 9341.0, 8120.0, 12994.0, 7003.0],
        [10440.0, 8877.0, 9210.0, 11002.0, 7654.0, 13120.0, 5988.0],
    ]
)

GATE_SIZE = 7_000
GATE_RATIO = 50.0


@pytest.fixture
def month() -> np.ndarray:
    """A fresh copy per test, so one test's writes cannot reach the next."""
    return MONTH.copy()
```

**Line by line:**

- `MONTH` as a **module-level constant** and the fixture returning `MONTH.copy()` — this is the whole
  subject of the day applied to the test file itself. If the fixture returned `MONTH`, then
  `test_centre_inplace_does_change_its_argument` would centre the shared array and every test that ran
  after it would be looking at different data. Test isolation is a copy-or-view decision
  ([1.1](../01-the-decision/1.1-six-operations-one-question.md)).
- The `nan` at `[0, 3]` — week one's Thursday, the missing reading the whole day has been using.
- `GATE_SIZE` and `GATE_RATIO` as named constants at the top — criterion 5's two numbers, in one place,
  where a reviewer can see them without reading the test
  ([4.3](../04-the-benchmark/4.3-the-number-measured.md)).

### Criteria 1 and 2 — the answers, and the missing reading

```python
def test_matches_a_hand_computation(month):
    live = month[~np.isnan(month)]
    s = stats.summarise(month)
    assert s.mean == pytest.approx(live.mean())
    assert s.std == pytest.approx(live.std(ddof=1))
    assert s.smallest == pytest.approx(live.min())
    assert s.largest == pytest.approx(live.max())
    assert s.spread == pytest.approx(s.largest - s.smallest)


def test_sample_and_population_std_differ_by_ddof(month):
    live = month[~np.isnan(month)]
    assert stats.summarise(month, sample=True).std == pytest.approx(live.std(ddof=1))
    assert stats.summarise(month, sample=False).std == pytest.approx(live.std(ddof=0))
    assert stats.summarise(month, sample=True).std > stats.summarise(month, sample=False).std


def test_counts_only_recorded_readings(month):
    s = stats.summarise(month)
    assert (s.observed, s.expected, s.complete) == (27, 28, False)
    assert not any(math.isnan(v) for v in (s.mean, s.std, s.smallest, s.largest))


def test_integer_input_is_refused_because_it_cannot_hold_a_gap():
    with pytest.raises(TypeError, match="float dtype"):
        stats.summarise(np.arange(28).reshape(4, 7))


def test_too_few_readings_is_refused_rather_than_answered():
    thin = np.full(28, np.nan)
    thin[:3] = 1.0
    with pytest.raises(ValueError, match="refusing to summarise"):
        stats.summarise(thin)
```

**Line by line:**

- `live = month[~np.isnan(month)]` computed **in the test**, a second way of getting the same answer. The
  test does not hardcode 9106.74; it recomputes the expectation from the data, so changing the fixture does
  not require editing five numbers
  ([Day 23, 5.2](../../../day-23-ufuncs-and-statistics/parts/05-the-module/5.2-the-test-that-can-go-red.md)).
- `pytest.approx` on every float — the module accumulates in `float64` and the test's comparison does the
  same arithmetic in a different order, so exact equality is not owed
  ([Day 23, 2.6](../../../day-23-ufuncs-and-statistics/parts/02-statistics/2.6-float-summation-and-the-drift.md)).
- `s.std > ` the population version, on the last line of the ddof test — **the direction, not just the
  value.** If somebody swapped the two branches, both `approx` assertions would still pass in a world where
  `ddof` was ignored; this line fails.
- `(s.observed, s.expected, s.complete) == (27, 28, False)` as **one tuple comparison** — a single failure
  message showing all three, rather than three assertions where only the first one to break is reported.
- `not any(math.isnan(v) ...)` — criterion 2's other half. Reporting 27 of 28 is worthless if the mean is
  `nan` anyway ([Day 23, 2.5](../../../day-23-ufuncs-and-statistics/parts/02-statistics/2.5-the-nan-family.md)).
- `match="float dtype"` and `match="refusing to summarise"` on the two `pytest.raises` — asserting the
  message, not just the exception type. A `TypeError` from somewhere else entirely would otherwise pass.
- `np.full(28, np.nan)` with three real values — three is below `MIN_FOR_SPREAD`, which is four, so this is
  the boundary case and not a comfortable distance from it.

### Criteria 3 and 4 — the two everyone forgets

```python
@pytest.mark.parametrize("name", ["summarise", "centre", "freeze"])
def test_input_is_never_modified(month, name):
    before = month.copy()
    getattr(stats, name)(month)
    assert np.array_equal(month, before, equal_nan=True)


def test_centre_inplace_does_change_its_argument(month):
    """The one function that is allowed to, and says so in its name."""
    before = month.copy()
    stats.centre_inplace(month)
    assert not np.array_equal(month, before, equal_nan=True)
    assert np.nanmean(month) == pytest.approx(0.0, abs=1e-9)


def test_centre_inplace_refuses_a_frozen_view(month):
    with pytest.raises(ValueError, match="read-only"):
        stats.centre_inplace(stats.freeze(month))


def test_nothing_returned_aliases_the_input(month):
    assert not np.shares_memory(month, stats.centre(month))
    s = stats.summarise(month)
    for value in (s.mean, s.std, s.smallest, s.largest):
        assert type(value) is float
    assert type(s.observed) is int


def test_freeze_shares_memory_on_purpose_and_refuses_writes(month):
    view = stats.freeze(month)
    assert np.shares_memory(month, view)
    with pytest.raises(ValueError, match="read-only"):
        view[0, 0] = 0.0
```

**Line by line:**

- `@pytest.mark.parametrize("name", [...])` over the three read-only functions — criterion 3 is about
  **every** public call, so the test iterates the list rather than naming one. Adding a fourth read-only
  function means adding a string, and forgetting to is visible.
- `getattr(stats, name)(month)` and **the return value discarded** — the test is about the side effect, and
  binding a name to something it does not use would only invite a reader to think it mattered.
- `equal_nan=True` on every `array_equal` — the month has a `nan` in it and `nan != nan`, so without this
  the test fails on correct code. That false alarm is the failure block in
  [2.3](../02-the-bug/2.3-the-defences.md).
- `test_centre_inplace_does_change_its_argument` asserting the **opposite** of criterion 3 — this is not an
  exception to the rule, it is the rule's other half. A function named `_inplace` that quietly stopped
  modifying its argument would be just as broken, and nothing else in the file would notice.
- `np.nanmean(month) == pytest.approx(0.0, abs=1e-9)` — `abs=` rather than the default relative tolerance,
  because the expected value is zero and a relative tolerance around zero is meaningless
  ([Day 23, 1.6](../../../day-23-ufuncs-and-statistics/parts/01-ufuncs/1.6-isclose-and-allclose.md)).
- `type(value) is float`, not `isinstance` — deliberately strict. `np.float64` **is** a subclass of `float`,
  so `isinstance` would pass on a value that is still a NumPy scalar
  ([Day 20, 2.3](../../../day-20-arrays-and-dtypes/parts/02-dtypes/2.3-floats-nan-and-precision.md)). The
  claim in the docstring is "plain Python numbers", and `type(...) is` is the only check that means it.
- `test_freeze_...` asserting `shares_memory` is **True** — for `freeze`, sharing is the feature, and the
  read-only flag is what makes it safe ([1.3](../01-the-decision/1.3-writeable-the-flag.md)). A test that
  asserted no aliasing here would be asserting the function is broken.

### The one-copy ceiling

```python
def test_summarise_makes_one_copy_not_five():
    """Peak memory says how many copies of the readings existed at once.

    Three allocations are expected and accounted for: the boolean mask (an eighth of
    the data), the gathered copy (about 1x), and the full-size temporary that .std()
    builds for the squared deviations (about 1x). That is a shade over 2x. A defensive
    copy of the input, or a second gather, pushes it past 2.5x.
    """
    rng = np.random.default_rng(20260902)
    data = rng.normal(9000, 2000, 1_000_000)
    data[rng.choice(data.size, 10_000, replace=False)] = np.nan
    tracemalloc.start()
    stats.summarise(data)
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    assert peak < 2.5 * data.nbytes, f"peak {peak:,} is {peak / data.nbytes:.2f}x the data"
```

**Line by line:**

- The docstring **accounting for every expected allocation** — a memory threshold with no explanation is a
  number somebody will raise the next time it fails. Written out, the 2.5 is a decision with a derivation
  behind it.
- The `.std()` temporary named explicitly, because it is the surprising one: it is a full-size array of
  squared deviations, and it is also why `std` was 51% of the function's time in
  [4.3](../04-the-benchmark/4.3-the-number-measured.md). The same fact explains both measurements.
- `tracemalloc.get_traced_memory()` returning `(current, peak)` and only the **peak** being used — the
  question is how many copies coexisted, not what survived.
- A million readings rather than the month's twenty-eight, because at 28 elements the peak is dominated by
  Python's own objects and the ratio means nothing.
- The **f-string in the assertion message** — a bare `assert peak < 2.5 * data.nbytes` says `False is not
  True`. This one says `peak 24,841,760 is 3.11x the data`, which is a diagnosis.

### Criterion 5 — the speed, with its baseline committed beside it

```python
def loop_one_pass(counts: np.ndarray) -> tuple[int, float, float, float, float]:
    """The committed baseline. Do not tune it and do not make it worse."""
    values = []
    rows, cols = counts.shape
    for i in range(rows):
        for j in range(cols):
            x = counts[i, j]
            if not math.isnan(x):
                values.append(float(x))
    n = len(values)
    total = 0.0
    for x in values:
        total += x
    mean = total / n
    sq = 0.0
    for x in values:
        sq += (x - mean) ** 2
    return n, mean, math.sqrt(sq / (n - 1)), min(values), max(values)


def gate_data() -> np.ndarray:
    """7,000 float64 readings, 1% missing, contiguous, seed 20260902."""
    rng = np.random.default_rng(20260902)
    data = rng.normal(9000, 2000, GATE_SIZE).reshape(-1, 7)
    positions = rng.choice(GATE_SIZE, GATE_SIZE // 100, replace=False)
    data[np.unravel_index(positions, data.shape)] = np.nan
    return data


def test_the_loop_and_the_module_agree():
    """Criterion 5 is meaningless unless both sides compute the same five numbers."""
    data = gate_data()
    s = stats.summarise(data)
    assert np.allclose(loop_one_pass(data), (s.observed, s.mean, s.std, s.smallest, s.largest))


@pytest.mark.slow
def test_beats_the_loop_by_fifty():
    data = gate_data()
    assert data.flags.c_contiguous, "a strided input measures a different code path"
    n = 20
    t_np = min(timeit.repeat(lambda: stats.summarise(data), number=n, repeat=7)) / n
    t_lp = min(timeit.repeat(lambda: loop_one_pass(data), number=n, repeat=7)) / n
    ratio = t_lp / t_np
    assert ratio >= GATE_RATIO, f"{ratio:.1f}x is below the gate's {GATE_RATIO:.0f}x"
```

**Line by line:**

- `loop_one_pass` living **in the test file**, not in a notebook — the baseline is half the claim, so it is
  committed, reviewable and diffable ([4.1](../04-the-benchmark/4.1-what-fifty-times-is-against.md)).
- Its docstring saying *"do not tune it and do not make it worse"* — both directions are cheating, and the
  second is the easier one to do by accident during a tidy-up.
- `gate_data()` with the size, dtype, missing fraction, layout and seed **in its docstring** — the four
  properties that change the answer ([4.4](../04-the-benchmark/4.4-the-benchmark-that-lied.md)).
- `rng.choice(..., replace=False)` — exactly seventy distinct positions become missing, so "1%" is true.
  `rng.integers` would repeat some and the real fraction would be slightly lower.
- `np.unravel_index(positions, data.shape)` — flat positions turned into row and column indices, so the
  assignment goes through `data` itself and works whether or not the array is contiguous
  ([4.4](../04-the-benchmark/4.4-the-benchmark-that-lied.md)).
- `test_the_loop_and_the_module_agree` as a **separate, fast test** — correctness of the comparison is
  checked even when the slow test is deselected, and a failure here means the ratio is meaningless rather
  than just wrong.
- `assert data.flags.c_contiguous` inside the timing test — the layout assumption stated as an assertion,
  because a strided input measures a different code path and the difference is about 30%
  ([4.4](../04-the-benchmark/4.4-the-benchmark-that-lied.md)).
- `@pytest.mark.slow` — the marker is registered in `pyproject.toml`, and
  [5.2](5.2-the-performance-test-in-ci.md) is about when this test should and should not run.
- `min(timeit.repeat(...)) / n` on both sides, same `number`, same `repeat`, timed seconds apart in the same
  process ([4.2](../04-the-benchmark/4.2-timeit-honestly.md)).

## When it breaks

**Break one — `freeze` forgets to clear the flag:**

Delete one line from `stats.freeze`:

```python
def freeze(counts: np.ndarray) -> np.ndarray:
    view = counts.view()
    # BROKEN: the flag is never cleared
    return view
```

```text
        assert np.shares_memory(month, view)
>       with pytest.raises(ValueError, match="read-only"):
             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
E       Failed: DID NOT RAISE ValueError

test_stats.py:111: Failed
=========================== short test summary info ===========================
FAILED test_stats.py::test_centre_inplace_refuses_a_frozen_view - Failed: DID...
FAILED test_stats.py::test_freeze_shares_memory_on_purpose_and_refuses_writes
2 failed, 13 passed in 0.49s
```

**What it means.** `DID NOT RAISE` is the failure mode of a guard that has stopped guarding. Two tests went
red for one deleted line, and that is the right ratio: `freeze` is used by `centre_inplace`'s refusal as
well as on its own, so both call sites notice.

The important thing about this break is what did **not** go red. Every statistic is still correct. Nothing
crashes. `test_input_is_never_modified` still passes, because `freeze` itself still does not modify
anything — it just hands out a loaded window ([1.5](../01-the-decision/1.5-the-api-contract.md)). Without
these two tests, a module returning a writeable view of its caller's data would be entirely green.

**Break two — a defensive copy nobody asked for:**

Add one line at the top of `summarise`:

```python
def summarise(counts: np.ndarray, *, sample: bool = True) -> Summary:
    if counts.dtype.kind != "f":
        raise TypeError(f"missing readings need a float dtype, got {counts.dtype}")
    counts = counts.copy()  # BROKEN: a defensive copy nobody asked for
    flat = counts.reshape(-1)
    ...
```

```text
E       AssertionError: peak 24,841,760 is 3.11x the data
E       assert 24841760 < (2.5 * 8000000)
E        +  where 8000000 = array([ 8022.93667353,  8990.56420601, 10469.02810037, ...,
        8816.6763207 ,  7846.51575452,  7784.55697798], shape=(1000000,)).nbytes

test_stats.py:130: AssertionError
=========================== short test summary info ===========================
FAILED test_stats.py::test_summarise_makes_one_copy_not_five - AssertionError...
1 failed, 14 passed in 0.48s
```

**What it means.** The added line is not wrong. It is *safe* — safer, arguably, than the real version,
because now nothing downstream could possibly reach the caller's array. It is exactly the reflex from
[2.3](../02-the-bug/2.3-the-defences.md), applied where it is not needed, and it costs a full extra copy of
the data: 2.11× became 3.11×.

**Every other test stayed green**, including all of criterion 3 and criterion 4 — the copy makes those
*more* true. Only the memory ceiling noticed. That is what a resource assertion is for: it catches the
class of change that is correct and expensive, which no correctness test can see.

The failure message earns its keep here. `peak 24,841,760 is 3.11x the data` says what happened; `assert
24841760 < 20000000` would have sent somebody to the debugger.

**Both breaks reverted, the suite is green again** — and now the fifteen dots mean something, because two
of them have been watched to fail for known reasons.

## In production

**What a professional writes instead of the teaching version.** The two breaks stop being something you did
once and become something the file records:

```python
# Seen to fail (re-verify when this file changes shape):
#   test_freeze_shares_memory_on_purpose_and_refuses_writes
#   test_centre_inplace_refuses_a_frozen_view
#     -> delete `view.flags.writeable = False` from stats.freeze
#     -> Failed: DID NOT RAISE ValueError                       (2 red)
#   test_summarise_makes_one_copy_not_five
#     -> add `counts = counts.copy()` at the top of summarise
#     -> AssertionError: peak 24,841,760 is 3.11x the data      (1 red)
```

**Line by line:**

- The **mutation written out**, not described — "delete this line" is reproducible; "break the freeze
  logic" is not.
- The **observed failure text**, so the next person knows what red is supposed to look like and can tell a
  real regression from a changed message.
- "(2 red)" and "(1 red)" — the blast radius. If a future edit makes the first mutation produce one red
  instead of two, a test has stopped covering something.
- The heading saying *re-verify when this file changes shape* — the record is a claim with a date on it,
  and a large refactor invalidates it.

Beyond the comment, three things separate a real gate suite from this one. **Mutation testing** does what
those two breaks did, automatically and exhaustively: tools in this family change operators and delete
statements across the module and report which mutations no test noticed. **Property-based testing**
generates the inputs instead of picking them, which is how you find the month where every reading is
identical and the standard deviation is zero. And **the fixtures move to a conftest** once more than one
test module needs the month, so the copy-per-test discipline is enforced in one place rather than
remembered in several.

**What changes at scale.** Two of these tests get expensive and one gets fragile. The memory test allocates
eight megabytes and runs `tracemalloc`, which slows the interpreter down substantially — fine here, and a
problem when a hundred such tests run on every commit, at which point it moves to a nightly job. The timing
test is fragile on shared hardware, which is [5.2](5.2-the-performance-test-in-ci.md). And criterion 3's
parametrised test grows a row per public function for ever, which is the intention: the cost of adding a
function includes the cost of proving it does not modify its input.

The other thing that changes is who reads the failure. On a team, the person who sees `peak 24,841,760 is
3.11x the data` at 2 a.m. did not write the module and has not read this day. Everything they need has to
be inside the message and the docstring above it.

**The failure that only appears with real data.** A team had a test named
`test_does_not_modify_input` that had passed for two years. It compared the input to a saved copy with
`np.array_equal`, without `equal_nan=True`, and their fixture had no missing values in it. When the
fixture was regenerated from a production sample it acquired some, and the test began failing on code that
had not changed. The two days spent on that were not wasted: the same missing `equal_nan` was in four other
test files, and one of those was hiding a real modification that `nan != nan` had been masking.

**The review comment a senior engineer leaves.** *"Fifteen tests, all green — which ones have you seen
fail? Delete `view.flags.writeable = False` and paste what happens. And `assert peak < 2.5 * data.nbytes`
needs the f-string message and a docstring saying where 2.5 comes from, otherwise the next person to hit it
will just raise the number."*

**The interview question.** *"How do you know your tests are any good?"* The answer is not coverage. It is
that you have watched each of them fail for the reason it exists: break the code on purpose, see red, read
the message, revert. Then say what that habit finds — tests that assert something trivially true, tests
whose failure message is useless at 2 a.m., and the gap where a criterion has no test at all. The strongest
version names the class of bug that only a resource assertion catches: a change that is correct and
expensive, like a defensive copy, which every correctness test will happily approve.
