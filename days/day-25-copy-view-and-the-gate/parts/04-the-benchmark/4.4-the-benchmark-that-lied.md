# 4.4 — The benchmark that lied — three that followed every rule

## One-line answer

A benchmark can pick an honest baseline, take the minimum of its repeats, keep setup outside the timed
region — and still be wrong, because the thing it timed did no work, or the data it timed was not shaped
like the real thing.

---

## The story

Somebody times themselves totalling the month and it comes out at four seconds.

Four seconds is not believable and they know it, so they look at what they actually did. They read down the
column, and at the bottom they wrote "add these up later" and put the pen down. They timed the reading, not
the adding. The stopwatch was honest, the technique was fine, and the answer was nonsense, because the work
had not happened yet when the watch stopped.

The second time, they use a chart from a week where five of the seven days were blank. It goes very fast,
and they write down the time. It is a true time for that chart. It is not a time for a normal week, because
a normal week has seven numbers in it and this one had two.

Neither of those is carelessness with the stopwatch. Both are the same mistake in different clothes: the
thing being timed was not the thing they wanted to know about.

---

## The idea in plain language

Parts [4.1](4.1-what-fifty-times-is-against.md) and [4.2](4.2-timeit-honestly.md) covered the two questions
people usually ask about a benchmark — what did you compare against, and how did you time it. This part is
the third question, which is asked less often and catches more mistakes: **was the thing you timed the
thing you meant to time?**

Three ways it goes wrong, and all three produce clean, plausible-looking numbers.

**The work never happened.** Some expressions in Python describe work rather than doing it. A generator
expression builds an object and returns immediately; nothing is computed until something consumes it. Time
one of those against a list comprehension and you have compared building a plan with carrying it out.

**The data was the wrong shape.** Not the wrong size — the wrong *shape*, in the memory sense. An array
that is a slice of a bigger one is laid out with gaps, and code that assumes it is laid out end to end
quietly does more work ([2.1](../02-the-bug/2.1-ravel-changed-it-flatten-did-not.md)). A benchmark that
builds a fresh, tidy array and a production system that hands over a column of something bigger are running
different code paths under the same function name.

**The data was too clean.** Real data has holes in it, and how many holes there are changes what the code
does. Benchmark on a chart with nothing missing and you have measured the easy case.

The common thread is that none of these is a mistake in *method*. You can do everything in 4.2 correctly and
still hit all three. **The only defence is to look at what you handed the function and ask whether it
resembles what production hands it.**

---

## Why Setu needs it

- **[4.3](4.3-the-number-measured.md)** is the gate's number, and it is only worth having if it survives
  these three questions.
- **[5.2](../05-the-gate/5.2-the-performance-test-in-ci.md)** runs a speed assertion on every commit; a
  benchmark that measures nothing will pass for ever and tell you nothing.
- **[3.2](../03-the-module/3.2-the-stats-module.md)**'s `reshape(-1)` comment says "a view when `counts` is
  contiguous, else a copy" — the second failure below is where that qualification stops being pedantry.
- **Day 100's latency work** and **Day 190's retrieval evaluation** both quote numbers to other people, and
  these three are how those numbers go wrong without anybody lying.

## The mechanism

### One — the work that never happened

```python
import timeit

data = list(range(1_000_000))
lazy = min(timeit.repeat(lambda: (x * 2 for x in data), number=100, repeat=5)) / 100
eager = min(timeit.repeat(lambda: [x * 2 for x in data], number=3, repeat=5)) / 3
print(f"generator expression {lazy * 1e6:10.2f} us")
print(f"list comprehension   {eager * 1e6:10.2f} us")
print(f"'speedup'            {eager / lazy:10.0f}x")
```

**Line by line:**

- `(x * 2 for x in data)` — round brackets, so this is a **generator expression**. Evaluating it creates a
  generator object and stops. Not one multiplication has been done when the expression finishes.
- `[x * 2 for x in data]` — square brackets, a **list comprehension**, which does all million
  multiplications and builds a list.
- The two differ by **one character at each end**, which is exactly why this happens to people. A
  refactor from a list to a generator looks like a speedup and is a deferral.
- `number=100` for the lazy version and `number=3` for the eager one — chosen so each timed region is long
  enough to measure ([4.2](4.2-timeit-honestly.md)), and a reminder that the two `number` values must be
  divided out before the results are comparable, which the `/ 100` and `/ 3` do.

```text
generator expression       0.16 us
list comprehension     51103.70 us
'speedup'                 323441x
```

**Three hundred thousand times faster.** Nothing in the method is wrong: the minimum of five repeats, the
data built outside, `number` chosen sensibly. The measurement is completely accurate and completely
meaningless, because the timed expression did not do the work.

**How to catch it: make the benchmark use the result.** If the timed lambda had been
`lambda: sum(x * 2 for x in data)`, the generator would have had to run and the two would have come out
within a small factor of each other. A number that is thousands of times better than expected is a bug
report about the benchmark, not a result.

### Two — the array that was not laid out the way you assumed

```python
import numpy as np

from setu import stats

rng = np.random.default_rng(20260902)
base = rng.normal(9000, 2000, 1_400_000).reshape(-1, 14)
strided = base[:, :7]
tidy = np.ascontiguousarray(strided)
for name, a in [("tidy", tidy), ("strided", strided)]:
    flat = a.reshape(-1)
    print(
        f"    {name:8} c_contiguous={a.flags.c_contiguous!s:5} "
        f"reshape(-1) shares memory: {np.shares_memory(a, flat)}"
    )
```

**Line by line:**

- `base[:, :7]` — the first seven columns of a fourteen-column array. This is a **view**
  ([Day 21, 1.4](../../../day-21-indexing-and-views/parts/01-one-element/1.4-a-whole-column.md)): the
  values are the ones you want, and between each row's seven and the next row's seven sit seven values you
  do not.
- `np.ascontiguousarray(strided)` — the same numbers copied into a fresh block with no gaps. Same shape,
  same values, different layout.
- `a.reshape(-1)` on each, and `np.shares_memory` on the result — the probe from
  [1.2](../01-the-decision/1.2-the-three-probes.md), asking the only question that matters here.

```text
    tidy     c_contiguous=True  reshape(-1) shares memory: True
    strided  c_contiguous=False reshape(-1) shares memory: False
```

**`reshape(-1)` is a view on one and a copy on the other.** It cannot be a view on the strided array,
because there is no set of strides that walks 700,000 values while skipping the gaps. So NumPy silently
allocates and copies, which is documented behaviour and is invisible at the call site.

Now the same difference as a timing:

```python
import timeit

base = rng.normal(9000, 2000, 1_400_000).reshape(-1, 14)
base.reshape(-1)[rng.integers(0, base.size, base.size // 100)] = np.nan
strided = base[:, :7]
tidy = np.ascontiguousarray(strided)
print("same values:", np.array_equal(tidy, strided, equal_nan=True))
t_tidy = min(timeit.repeat(lambda: stats.summarise(tidy), number=1, repeat=9))
t_str = min(timeit.repeat(lambda: stats.summarise(strided), number=1, repeat=9))
print(f"summarise(tidy)     {t_tidy * 1000:7.3f} ms")
print(f"summarise(strided)  {t_str * 1000:7.3f} ms   {t_str / t_tidy:.2f}x slower")
```

**Line by line:**

- `np.array_equal(tidy, strided, equal_nan=True)` printed first — the proof that the two arrays hold
  **identical values**, so any timing difference is layout and nothing else. Without this line the
  comparison proves nothing.
- `equal_nan=True` again, because the arrays have missing readings in them
  ([2.3](../02-the-bug/2.3-the-defences.md)).
- Both timed with the same `number` and `repeat`, in the same process, seconds apart.

```text
same values: True
summarise(tidy)       6.565 ms
summarise(strided)    8.537 ms   1.30x slower
```

**Thirty per cent, for the same numbers.** Most of it is the copy that `reshape(-1)` had to make, and the
rest is that the mask and the boolean selection now walk memory with gaps in it
([Day 22, 3.3](../../../day-22-broadcasting-and-shape/parts/03-transpose/3.3-contiguity-and-the-speed-you-lose.md)).

**Why this is a lie and not just a fact.** Benchmarks build their own data, and data you build yourself with
`rng.normal(...).reshape(...)` is always contiguous. Data that arrives in a real system is very often a
column of something wider, a transpose, or a slice. So the benchmark systematically measures the fast path
and production systematically runs the slow one, and the gap is invisible because both are spelled
`summarise(counts)`.

**How to catch it: benchmark the shape you are given, not the shape you can make.** If the caller hands you
a slice, put a slice in the benchmark. If you do not know, run both and publish both.

### Three — the data that had no holes in it

```python
size = 7_000
for frac in [0.0, 0.01, 0.30, 0.90]:
    data = rng.normal(9000, 2000, size).reshape(-1, 7)
    k = int(size * frac)
    if k:
        data.reshape(-1)[rng.choice(size, k, replace=False)] = np.nan
    n = 30
    t_np = min(timeit.repeat(lambda: stats.summarise(data), number=n, repeat=7)) / n
    t_lp = min(timeit.repeat(lambda: loop_one_pass(data), number=n, repeat=7)) / n
    print(
        f"    {frac:5.0%} missing   loop {t_lp * 1e6:8.1f} us   "
        f"summarise {t_np * 1e6:7.1f} us   {t_lp / t_np:6.1f}x"
    )
```

**Line by line:**

- `frac` sweeping 0%, 1%, 30% and 90% — the size is held fixed at seven thousand so the only thing changing
  is how much of it is missing.
- `rng.choice(size, k, replace=False)` rather than `rng.integers` — sampling **without replacement**, so
  exactly `k` distinct positions become missing and the label on the row is true. With `integers` some
  positions would repeat and 30% would really be about 26%.
- `data.reshape(-1)[...] = np.nan` — assigning through a flat view of a contiguous array, which writes into
  `data` ([2.1](../02-the-bug/2.1-ravel-changed-it-flatten-did-not.md)). Here that is the intention.

```text
       0% missing   loop   1902.9 us   summarise    33.7 us     56.5x
       1% missing   loop   1899.3 us   summarise    34.4 us     55.2x
      30% missing   loop   1664.5 us   summarise    38.7 us     43.0x
      90% missing   loop    933.5 us   summarise    25.7 us     36.3x
```

**The ratio slides from 56.5× to 36.3× as the data gets worse**, and both sides move for different reasons.
The loop gets *faster* with more holes, because a missing reading is one comparison and then nothing —
there is no `float()`, no `append`, and no work in the three later passes. `summarise` gets *slower* first
and then faster: at 30% missing the boolean selection is doing more scattered work than at 1%, and at 90%
it is copying a tenth of the data and the reductions afterwards are tiny.

**A benchmark on clean data reports 56.5× for a function that will see 43× on data that is a third
missing.** Nothing was measured wrongly. The data was simply not the data.

**How to catch it: put the missing fraction in the record**
([4.3](4.3-the-number-measured.md)), and measure at the fraction your real data has. If you do not know
what that is, that is a more urgent problem than the benchmark.

## When it breaks

**The three above are the failures**, so this section is the one that catches them. Here is the check that
would have caught all three, run against a suspicious result:

```python
import numpy as np


def describe_the_input(name: str, arr: np.ndarray) -> None:
    """Everything about a benchmark array that can change the answer."""
    flat = arr.reshape(-1)
    print(
        f"{name:10} shape={arr.shape} dtype={arr.dtype} "
        f"contiguous={arr.flags.c_contiguous} "
        f"reshape_is_view={np.shares_memory(arr, flat)} "
        f"missing={np.count_nonzero(np.isnan(flat)) / flat.size:.1%} "
        f"bytes={arr.nbytes:,}"
    )


rng = np.random.default_rng(20260902)
base = rng.normal(9000, 2000, 1_400_000).reshape(-1, 14)
base.reshape(-1)[rng.integers(0, base.size, base.size // 100)] = np.nan
describe_the_input("tidy", np.ascontiguousarray(base[:, :7]))
describe_the_input("strided", base[:, :7])
describe_the_input("float32", np.ascontiguousarray(base[:, :7]).astype(np.float32))
```

**Line by line:**

- `flat = arr.reshape(-1)` computed **inside the describer**, only so that `shares_memory` can be asked
  about it — this is the one property that cannot be read off `arr` on its own
  ([1.2](../01-the-decision/1.2-the-three-probes.md)).
- `arr.flags.c_contiguous` and `reshape_is_view` **both** printed, because they are not quite the same
  question: contiguity is a property of the array, and whether `reshape` copies is what that property
  causes.
- `missing=` computed as a fraction rather than a count, so the number is comparable across sizes.
- `bytes=arr.nbytes` last — the dtype is already in the line, and this is the number that decides how much
  memory traffic the timing is really measuring.

```text
tidy       shape=(100000, 7) dtype=float64 contiguous=True reshape_is_view=True missing=1.0% bytes=5,600,000
strided    shape=(100000, 7) dtype=float64 contiguous=False reshape_is_view=False missing=1.0% bytes=5,600,000
float32    shape=(100000, 7) dtype=float32 contiguous=True reshape_is_view=True missing=1.0% bytes=2,800,000
```

**What it means.** Three arrays that print the same shape and would look identical in a benchmark's log.
One of them makes `reshape` copy. One of them is half the bytes, so it moves through memory twice as fast
for reasons that have nothing to do with the code being measured. `describe_the_input` on every benchmark
array, printed above the timings, turns "why is this 30% slower in production" into something you can see
before you publish.

It does not catch the first failure — a generator expression that does no work has no input to describe.
**That one is caught by consuming the result**, and by disbelieving any number that is thousands of times
better than the thing it replaced.

## In production

**What a professional writes instead of the teaching version.** The benchmark's inputs are built by a
single fixture that states its assumptions, and the benchmark refuses to run on data that does not match:

```python
import numpy as np


def benchmark_input(
    *,
    n: int,
    missing: float,
    contiguous: bool,
    dtype: np.dtype = np.dtype(np.float64),
    seed: int = 20260902,
) -> np.ndarray:
    """Build a benchmark array, with every property that changes the answer named."""
    rng = np.random.default_rng(seed)
    wide = rng.normal(9000, 2000, n * 2).astype(dtype).reshape(-1, 14)
    arr = np.ascontiguousarray(wide[:, :7]) if contiguous else wide[:, :7]
    k = int(arr.size * missing)
    if k:
        positions = rng.choice(arr.size, k, replace=False)
        arr[np.unravel_index(positions, arr.shape)] = np.nan
    assert arr.flags.c_contiguous == contiguous
    assert abs(np.count_nonzero(np.isnan(arr)) / arr.size - missing) < 0.01
    return arr
```

**Line by line:**

- **Keyword-only arguments** — `n`, `missing`, `contiguous`, `dtype`, `seed`. Every one of them changes the
  measured number, and being keyword-only means the call site reads as a description of the data.
- `contiguous` as an explicit parameter rather than an accident of how the array was built — the point of
  failure two is that layout is usually inherited silently, so here it is chosen out loud.
- The **two assertions at the end**, which are the whole reason this is a function rather than four lines in
  a script. They fail loudly if a future edit accidentally makes every array contiguous, or if the missing
  fraction drifts because `choice` was swapped for `integers`.
- `np.unravel_index(positions, arr.shape)` to place the missing values — `rng.choice` gives flat positions
  and this turns them into a tuple of row and column arrays, so the assignment goes through `arr` itself.
  Writing through `arr.reshape(-1)` instead would work for the contiguous case and **silently do nothing**
  for the strided one, because that reshape returns a copy
  ([2.1](../02-the-bug/2.1-ravel-changed-it-flatten-did-not.md)). This is the same trap the part is about,
  met while writing the fixture for it — and the second assertion is what would have caught it.
- `seed` with a default and a name, so two runs compare and a third can deliberately differ
  ([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)).

Built at `n=7_000, missing=0.30` both ways, and described with `describe_the_input`:

```text
built True shape=(1000, 7) dtype=float64 contiguous=True reshape_is_view=True missing=30.0% bytes=56,000
built False shape=(1000, 7) dtype=float64 contiguous=False reshape_is_view=False missing=30.0% bytes=56,000
```

Same size, same dtype, same missing fraction — and one of them makes `reshape` copy. That is the whole
point of building the input through a function that names its properties.

**What changes at scale.** Every one of these three grows teeth. A lazy expression that did no work becomes
a query builder, a dataframe operation that has not executed yet, or a coroutine that was never awaited —
and in each case the benchmark reports a number for building a plan. Layout stops being about one slice and
becomes about whether the whole system passes columns or rows, which is a design decision worth a hundred
per cent of throughput either way. And the missing fraction becomes every property of real data at once:
how skewed it is, how many categories, how long the strings, how often the cache is cold.

The habit that survives all three is the same: **the benchmark's input is part of the benchmark, and it is
described in the output.** Teams that print the shape, dtype, layout, missing fraction and seed above every
timing catch these in review. Teams that print a number get to find out in production.

**The failure that only appears with real data.** A team benchmarked a scoring function at 12 ms per batch
and shipped it. Production ran at 40 ms. The benchmark had built its feature matrix with
`np.random.rand(n, d)` — contiguous, `float64`, no missing values. The real matrix arrived as a slice of a
wider array with about 20% missing. All three failures at once, and each one on its own would have been
explained away as noise. Together they were a factor of three, and the only reason it was ever found was
that somebody printed `.flags` on the production array.

**The review comment a senior engineer leaves.** *"This benchmark builds its own array with `rng.normal`,
so it is contiguous and has no missing values — neither of which is true of what we pass in. Use the
fixture, run it at our real missing fraction, and print `arr.flags.c_contiguous` above the timings. Also
`lambda: (score(r) for r in rows)` never runs; wrap it in `list()` or you are timing the `yield`."*

**The interview question.** *"Your benchmark says the new version is a thousand times faster. What do you
do?"* The answer is: disbelieve it and go looking for the reason, because a factor of a thousand between
two implementations of the same algorithm almost always means one of them did not run. Say what you would
check — that the result is consumed, that both produce the same output, that the timed region contains the
work. Then broaden it: even when the number is plausible, ask whether the input resembles production —
shape, dtype, layout and how much of it is missing — because those change the answer without changing the
code, and a benchmark's array is almost always tidier than a real one.

## Check yourself

**Run this now.** Catch failure one in your own code:

```python
import timeit

data = list(range(1_000_000))
print(
    f"{min(timeit.repeat(lambda: (x * 2 for x in data), number=100, repeat=5)) / 100 * 1e6:8.2f} us"
)
print(
    f"{min(timeit.repeat(lambda: sum(x * 2 for x in data), number=3, repeat=5)) / 3 * 1e6:8.2f} us"
)
```

The first line times a generator expression and the second consumes it. The ratio between them is the size
of the lie, and it should be large enough to be funny.

**Answer out loud, without scrolling up:**

   different, and which line inside `summarise` pays for it?

   number too high or too low, and what would you do about it?
