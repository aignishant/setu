# 2.3 — Streaming a file line by line: the log you cannot hold

## One-line answer

An open file is already a reader that hands out one line at a time, so `for line in handle:` walks a
file of any size in a fixed, tiny amount of memory — and the moment you write `.read()` or
`.readlines()` you have asked for the whole thing instead.

---

## The story

The deli has kept every order slip for a year, in a filing cabinet in the back. The owner wants to
know how many orders there were.

You could take the whole year out and pile it on the table. The pile does not fit on the table.

What you actually do is open the top drawer, take the first slip, add one to a running count, drop
the slip in the recycling, and take the next. The drawer stays where it is. Your hands hold one slip.
At the end you have a number, and the room looks exactly as it did when you started.

This is the same choice as [2.2](2.2-a-list-against-a-generator.md), with one difference that makes
it real rather than a demonstration: **the drawer is not in your house.** The slips live on disk, and
whether you hold one or a million is now a question about a machine with a fixed amount of memory
rather than about elegance.

Today's four slips still fit in one hand:

```text
milk
  Milk
eggs
Eggs.
```

A file of a million of them is 6.44 megabytes on disk and 57 megabytes in Python, and that gap is
what this document is about.

---

## The idea in plain language

Open a file in Python and you get a **file object**. That object is already an iterator, in the exact
sense of [1.1](../01-iterators/1.1-iterable-and-iterator.md): it has a position, it hands out one
line per request, and it is exhausted when the file runs out. Nobody has to build it.

So this is the whole technique, and it is three lines:

```
with path.open(encoding="utf-8") as handle:
    for line in handle:
        ...
```

`for line in handle:` reads one line at a time. Not one *character* — the file object reads a block
from disk into a buffer behind the scenes and hands out lines from the buffer, which is why this is
fast as well as small. Day 16 is about that buffer; today you only need to know that the loop's
memory cost is one line, not one file.

The three things people write instead, and what each of them costs:

- `handle.read()` — the whole file as one string. Memory: the whole file.
- `handle.readlines()` — a list of every line. Memory: the whole file, plus a list object, plus one
  string object per line. **This is the most expensive of the three**, and it is the one that looks
  the most like the streaming loop.
- `path.read_text()` — the whole file as one string, with the file opened and closed for you. Memory:
  the whole file.

None of them is wrong. Each is right when the file is small and you want it all. The mistake is
reaching for one out of habit on a file whose size you do not control.

Two words that will come up. To **stream** is to process data as it arrives, one piece at a time,
without holding the whole. **Back pressure** is what stops a fast producer from overwhelming a slow
consumer; in a `for` loop over a file there is no back-pressure problem at all, because the loop only
asks for the next line when it is ready for it. That property is free here and expensive everywhere
else, which is worth noticing.

One caution the plan cares about: this is `PY-11`'s named example — *streaming a 2 GB log
line-by-line without loading it* — and the reason the plan names it is that the failure is invisible
in development. A 5 MB sample file makes every one of the four spellings above look identical.

## The mechanism

First, build the file, then walk it both ways and measure. Run this once and read your own numbers:

```python
"""A million slips on disk, counted twice: eager, then streamed."""

import itertools
import tracemalloc
from pathlib import Path

path = Path("data/slips_big.txt")
path.parent.mkdir(parents=True, exist_ok=True)

if not path.exists():
    cycle = itertools.cycle(["milk", "  Milk", "eggs", "Eggs."])
    with path.open("w", encoding="utf-8") as handle:
        for _ in range(1_000_000):
            handle.write(next(cycle) + "\n")

print("file on disk MB:", round(path.stat().st_size / 1048576, 2))

tracemalloc.start()
text = path.read_text(encoding="utf-8")
lines = text.splitlines()
eager_count = sum(1 for line in lines if line.strip())
eager_peak = tracemalloc.get_traced_memory()[1]
tracemalloc.stop()
del text, lines

tracemalloc.start()
with path.open(encoding="utf-8") as handle:
    lazy_count = sum(1 for line in handle if line.strip())
lazy_peak = tracemalloc.get_traced_memory()[1]
tracemalloc.stop()

print("eager count:", eager_count, "peak MB:", round(eager_peak / 1048576, 2))
print("lazy  count:", lazy_count, "peak MB:", round(lazy_peak / 1048576, 4))
```

Run on Python 3.12.12 on 2026-09-01:

```
file on disk MB: 6.44
eager count: 1000000 peak MB: 57.17
lazy  count: 1000000 peak MB: 0.0329
```

**Line by line:**

- `itertools.cycle([...])` — repeats the four slips forever, so the file is built from the same four
  the whole day has used. `cycle` is itself a generator-like reader, which is why `next(cycle)` works.
- `if not path.exists():` — the file is built once and kept. Rebuilding it on every run would be
  slow, and it would also make the two measurements below share a cold or warm disk cache
  inconsistently.
- `path.stat().st_size` — the size **on disk**, 6.44 MB. Hold that number against the 57 MB below.
- `path.read_text(encoding="utf-8")` then `.splitlines()` — the eager version, and it holds two full
  copies at once for a moment: the single big string and the list of a million separate strings.
  That is where 6.44 MB on disk becomes 57 MB in memory. Each of the million small strings carries
  its own object header, and that overhead dwarfs the four to six characters of actual text.
- `del text, lines` — released before the second measurement, or the second `tracemalloc` peak would
  include them and report the mistake from [2.2](2.2-a-list-against-a-generator.md)'s first failure.
- `with path.open(encoding="utf-8") as handle:` — `encoding` typed out, never the platform default
  ([Day 7, 1.1](../../../day-07-strings/parts/01-text/1.1-a-string-is-code-points.md)). On Windows the
  default is not UTF-8, so leaving it off makes the same code give different answers on different
  machines.
- `sum(1 for line in handle if line.strip())` — the whole count in one expression, with **no list
  anywhere.** `handle` is the reader, the generator expression filters and counts, and `sum` pulls
  one line at a time.
- `if line.strip()` — skips blank lines, using the method from
  [Day 7, 2.1](../../../day-07-strings/parts/02-methods/2.1-normalising-strip-and-case.md). It also
  quietly means the count is of *non-empty* lines, which is a decision worth writing in a docstring
  rather than leaving in a filter.
- **0.0329 MB against 57.17 MB** — about seventeen hundred times less, for the same answer. The lazy
  figure is not zero because the buffer and one line still exist; it is fixed, which is the property
  that matters. Ten times the file, same 0.03 MB.

Now the reusable version, which is what actually goes in a module:

```python
"""A generator that hands out cleaned, non-empty lines from a file."""

from collections.abc import Iterator
from pathlib import Path


def iter_slips(path: Path) -> Iterator[str]:
    """Yield each non-empty line of `path`, stripped, one at a time.

    The file is opened when the first item is requested and closed when the
    generator is exhausted or discarded.
    """
    with path.open(encoding="utf-8") as handle:
        for line in handle:
            cleaned = line.strip()
            if cleaned:
                yield cleaned


path = Path("data/slips.txt")
path.parent.mkdir(parents=True, exist_ok=True)
path.write_text("milk\n\n  Milk\neggs\nEggs.\n", encoding="utf-8")

print(list(iter_slips(path)))
print("count:", sum(1 for _ in iter_slips(path)))
```

**Line by line:**

- `-> Iterator[str]` — the return annotation says what the caller gets: a reader of strings, walkable
  once ([Day 10, 1.6](../../../day-10-functions/parts/01-the-signature/1.6-the-signature-is-the-contract.md)).
  Writing `-> list[str]` here would be a lie the type checker would believe.
- `from collections.abc import Iterator` — the runtime home of the name. `typing.Iterator` still works
  and is the older spelling; the `collections.abc` one is what current code uses, and Day 19 explains
  the split.
- `with path.open(...)` **inside** the generator — the file is opened on the first request, not when
  `iter_slips(path)` is called, because nothing in a generator body runs until then
  ([2.1](2.1-yield-the-function-that-pauses.md)). The docstring says so, because a caller cannot see
  it from the signature.
- `cleaned = line.strip()` then `if cleaned:` — clean once, test the result. Writing
  `if line.strip(): yield line.strip()` would do the same work twice and, worse, could drift apart
  when somebody edits one of them.
- `yield cleaned` — one line out, then the function pauses **inside the `with` block**, which is why
  the file stays open between requests. That is required for the next line to be readable, and it is
  the cost discussed in [2.5](2.5-when-a-generator-is-wrong.md).
- `sum(1 for _ in iter_slips(path))` — a **fresh** call, not the generator from the line above, which
  is already exhausted ([1.3](../01-iterators/1.3-exhaustion.md)). `_` is the conventional name for a
  value you are deliberately ignoring.
- The output is `['milk', 'Milk', 'eggs', 'Eggs.']` and `count: 4`. The blank line is gone and
  `  Milk` has lost its spaces; the full stop on `Eggs.` is still there, because stripping whitespace
  is not the same job as `clean_title`
  ([Day 10, 3.2](../../../day-10-functions/parts/03-the-module/3.2-designing-clean-title.md)).

## When it breaks

**The line that still has its newline on the end:**

```text
>>> with open("data/slips.txt", encoding="utf-8") as h:
...     first = next(h)
...
>>> first
'milk\n'
>>> first == "milk"
False
```

**What it means.** Iterating a file gives each line **including its line ending**, so every
comparison against a clean string fails and every dictionary key is subtly wrong. There is no error;
you simply get zero matches. The fix is `line.rstrip("\n")` when you want to keep leading spaces, or
`line.strip()` when you do not. Choosing between those two is a real decision: `strip()` would also
destroy the two leading spaces on `  Milk`, which on some data is the thing you were trying to
measure.

**Reading a file that is not UTF-8:**

```text
$ uv run python -c "
from pathlib import Path
p = Path('data/latin.txt')
p.write_bytes('caf\xe9\n'.encode('latin-1'))
print(p.read_text(encoding='utf-8'))
"
Traceback (most recent call last):
  File "<string>", line 4, in <module>
    return f.read()
           ^^^^^^^^
  File "<frozen codecs>", line 322, in decode
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 3: invalid continuation byte
```

**What it means.** The bytes on disk are not what you told Python they were. Note **position 3** —
the error names the exact byte, which is how you find the one bad row in a million-line file. With
`.read_text()` the whole read fails and you get nothing; with a streaming loop the failure happens on
the line that contains the byte, so everything before it has already been processed. That is a real
argument for streaming that has nothing to do with memory.

**The `readlines()` that looks like streaming:**

```text
>>> import tracemalloc
>>> tracemalloc.start()
>>> with open("data/slips_big.txt", encoding="utf-8") as h:
...     n = sum(1 for line in h.readlines() if line.strip())
...
>>> round(tracemalloc.get_traced_memory()[1] / 1048576, 2)
52.66
>>> tracemalloc.stop()
```

**What it means.** Twelve characters — `.readlines()` — and the 0.03 MB became 52.66 MB. The loop still
says `for line in`, the code still reads as a stream, and the file is entirely in memory before the
first line is examined. This is the version that passes code review, because it looks right. The only
defence is to know that a bare `handle` is already iterable and that anything added after it is
asking for the whole file.

## In production

**The professional version of this function never opens the file itself if it can avoid it.** A
generator that takes an already-open handle — `def iter_slips(handle):` — can be tested with
`io.StringIO("milk\n  Milk\n")` and needs no temporary directory, no fixture and no cleanup. That is
the seam from
[Day 10, 3.3](../../../day-10-functions/parts/03-the-module/3.3-pure-functions-and-the-seam.md)
applied to files: the caller does the reaching. The version that takes a `Path` is then a two-line
wrapper for convenience, and the interesting logic is testable without touching a disk.

**What changes at 2 GB is that the line lengths stop being safe.** A streaming loop holds one line,
which is fine until a corrupt or hostile file contains a single line of 2 GB with no newline in it.
Then "one line at a time" is the whole file, and the memory guarantee you were relying on is gone.
Real log processors either read fixed-size blocks with `iter(lambda: h.read(65536), b"")`
([1.4](../01-iterators/1.4-iter-with-a-sentinel.md)) or cap the line length and treat anything longer
as a data error. This is not a theoretical concern; it is how a log parser gets taken down by a
single malformed entry.

**The failure that only appears with real data is the encoding on somebody else's machine.** A
pipeline that works for a year breaks on one file exported from a system that used a different
encoding, and the traceback points at your reader rather than at the export. The professional habit
is to state the encoding explicitly, to decide in advance what to do about bad bytes, and to write
that decision down: `errors="strict"` (the default) fails loudly on the offending line, while
`errors="replace"` substitutes a marker and keeps going. Both are defensible; silently inheriting the
platform default is not.

**The review comment a senior engineer leaves.** On `lines = path.read_text().splitlines()` at the
top of a loader: *"This holds the file twice — once as a string, once as a list of lines. On the
sample it is 6 MB, on the production export it is 57 MB, and it grows with the input. Iterate the
handle directly and yield; if a later stage needs random access, make that stage ask for a list so
the cost is visible where it is chosen."*

**The interview question.** *"How do you process a file bigger than memory?"* The answer that lands
is the loop plus the reason: a file object is an iterator, so `for line in handle` holds one line,
and the peak memory is fixed rather than proportional to the file. The follow-up that separates
people is *"what breaks that guarantee?"* — a file with no newlines, `readlines()` slipped into the
middle, or a downstream `sorted()` that collects everything anyway. Naming one of those unprompted
shows you have run this on something real.
