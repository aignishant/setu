# 4.2 — The streaming reader `textutils` needed

## One-line answer

The second half of Phase 1's gate is that the module works on a file it could never hold, which means
one generator that takes an open handle, one that deduplicates without materialising, and a test that
proves the memory claim rather than asserting it in a docstring.

---

## The story

The deli owner asks one last thing before Phase 1 closes: *"can your tidy-up work on the whole
archive?"*

Everything built so far works on the four slips on the counter. `clean_title` takes one slip.
`clean_titles` takes a handful and hands back a handful. Both are right, and both assume somebody has
already got the slips out and put them on the table.

The archive is the filing cabinet from [2.3](../02-generators/2.3-streaming-a-file.md), and it does
not fit on the table. So the question is not whether the tidying is correct. It is whether anything in
the toolkit can be pointed at the cabinet at all, or whether every tool secretly requires the table.

The four slips are still the test case, because a tool that works on four and cannot work on four
million is broken, and a tool that works on four million and gets the four wrong is worse:

```text
milk
  Milk
eggs
Eggs.
```

---

## The idea in plain language

Everything in `textutils.py` up to now is **eager**: it takes a container and hands back a container.
That is correct for what Day 10 was doing, and it has a hard ceiling — the largest input is the
largest thing that fits in memory.

Today's three additions raise that ceiling, and they do it by changing what crosses the boundary
rather than by changing the cleaning:

- `iter_titles(handle)` takes an **already-open handle** and yields cleaned lines. It never opens
  anything, so it can be tested with `io.StringIO` and pointed at a 2 GB file with the same code.
- `unique_titles(titles)` takes any iterable and yields the first appearance of each key. It is lazy
  in and lazy out, and it holds one set of keys — the honest exception from
  [2.5](../02-generators/2.5-when-a-generator-is-wrong.md).
- `titles_matching(titles, predicate)` filters lazily with the caller's own test function, which is
  the one place in this module where a lambda at the call site is right
  ([3.3](../03-lambda-and-map/3.3-where-a-lambda-hurts.md)).

Chained, they are the pipeline from [2.4](../02-generators/2.4-yield-from-and-the-pipeline.md): three
stages, one title in flight, and one place that decides to collect.

Two design decisions are worth stating out loud, because both are the sort of thing that gets
defaulted rather than chosen.

**Why `iter_titles` takes a handle and not a path.** A function that opens its own file needs a real
file to test, which means a temporary directory, a fixture and cleanup
([Day 2, 3.2](../../../day-02-quality-gate/parts/03-pytest/3.2-fixtures-and-tmp-path.md)). A function
that takes a handle is tested with two lines and no disk. The caller does the opening, which is the
seam argument from
[Day 10, 3.3](../../../day-10-functions/parts/03-the-module/3.3-pure-functions-and-the-seam.md).

**Why the memory promise gets a test.** A docstring that says "peak memory does not grow with the
file" is a claim, and Principle 7 says a behaviour is not done until a test can go red when it
regresses. Memory is a behaviour. The test is a `tracemalloc` assertion on a large synthetic input,
and it goes red the day somebody "simplifies" the generator into a list comprehension.

## Why Setu needs it

- **It is the second acceptance criterion of the gate** ([4.1](4.1-ten-functions-fully-tested.md)),
  and it is the one that decides whether Module 1 produced a toy or a tool.
- **Day 27 reads a real dataset**, and the loader it writes is this shape with a CSV parser in the
  middle. Day 33 runs `.str` operations across a million titles. Both assume a stream exists.
- **Day 162's RAG pipeline is load → chunk → embed → store**, four lazy stages with one collection at
  the end. This is that pipeline with three stages and no model, built where a mistake costs nothing.
- **Principle 5's currency is RAM.** A free-tier machine has a few gigabytes, so "works on a file it
  cannot hold" is not a stretch goal in this project. It is the normal case from Day 26 onwards.

## The mechanism

The three additions, wired into a pipeline. **The bodies are still yours** — this block is the
assembly and the test, not the solution:

```python
"""How the three new functions compose, and what the pipeline costs."""

import io

from setu.textutils import iter_titles, titles_matching, unique_titles

RAW = """milk

  Milk
eggs
Eggs.
milk
"""

handle = io.StringIO(RAW)

pipeline = titles_matching(
    unique_titles(iter_titles(handle)),
    lambda title: len(title) > 3,
)

print("type before anything runs:", type(pipeline).__name__)
print("result:", list(pipeline))
```

**Line by line:**

- `io.StringIO(RAW)` — a string that behaves like an open text file, including being iterable line by
  line. **This is why `iter_titles` takes a handle**: the test needs no `data/` directory, no
  `tmp_path` fixture and no cleanup.
- The `RAW` triple-quoted string contains a blank line on purpose, so `iter_titles`'s "skips empty
  lines" promise has something to skip, and a repeat of `milk` at the end so `unique_titles` has
  something to drop.
- `titles_matching(unique_titles(iter_titles(handle)), ...)` — assembled inside out, exactly like
  [2.4](../02-generators/2.4-yield-from-and-the-pipeline.md)'s three stages. Read it from the innermost
  call outwards and it is the order the data flows.
- `lambda title: len(title) > 3` — a lambda as an argument, one expression, never named. This is
  [3.3](../03-lambda-and-map/3.3-where-a-lambda-hurts.md)'s rule being satisfied rather than
  described.
- `type(pipeline).__name__` prints `generator` — **nothing has been read from the handle yet.** Three
  generators exist and the file position is still at zero.
- `list(pipeline)` is the one line that collects, and it is the only one. Everything above it is a
  plan.

**Line by line:**

- `import io` and `io.StringIO` in every test — **no test in this file touches a disk.** That is a
  property of the functions, not of the tests, and it is what the handle-shaped signature bought.
- `test_iter_titles_is_a_reader_not_a_list` — asserting the *second* `list()` is empty looks like
  testing a bug. It is testing a contract: the annotation says `Iterator`, so a caller may only walk
  it once, and this test goes red if somebody "helpfully" changes the return to a list.
- `test_unique_titles_keeps_input_order` — the comment about three items is the real content. An
  order test with two items passes an implementation that returns `sorted(set(...))`, which is wrong.
- `test_unique_titles_compares_by_key_not_by_string` — asserting *which* of the two survives is the
  part people leave out, and it is the part that catches a body that yields the cleaned form instead
  of the original.
- `test_titles_matching_does_not_call_the_predicate_after_the_caller_stops` — the predicate records
  its own calls, which is how you assert on something that has no return value to inspect. This is
  the standard technique for testing laziness, and it is the same instrument as the `print` in
  [2.1](../02-generators/2.1-yield-the-function-that-pauses.md), turned into an assertion.
- `test_iter_titles_peak_memory_does_not_grow_with_the_file` — the only test here that would be
  unusual in an ordinary codebase, and it exists because the docstring made a memory promise. **The
  instruction to break it on purpose is not optional**: a memory test you have never seen fail is a
  test you do not know is wired up.
- Every one of these fails with `NotImplementedError` before you start, which is Principle 7's red
  state.

## When it breaks

**The reader that was handed a path:**

```text
$ uv run python -c "
from pathlib import Path
import io
def iter_titles(handle):
    for line in handle:
        yield line.strip()
print(list(iter_titles(Path('data/slips.txt'))))
"
Traceback (most recent call last):
  File "<string>", line 6, in <module>
  File "<string>", line 4, in iter_titles
TypeError: 'WindowsPath' object is not iterable
```

**What it means.** A `Path` is not a file; it is a name for one. The error is the "not iterable"
message from [1.1](../01-iterators/1.1-iterable-and-iterator.md), and the fix is at the **call site**:
`with path.open(encoding="utf-8") as handle:`. This error is the cost of the handle-shaped signature,
and it is a good trade — it fails immediately and loudly, whereas the path-shaped version would have
made every test need a temporary directory forever.

**The pipeline that was assembled after the file was closed:**

```text
$ uv run python -c "
import io
def iter_titles(handle):
    for line in handle:
        yield line.strip()
with io.StringIO('milk\neggs\n') as handle:
    titles = iter_titles(handle)
print(list(titles))
"
Traceback (most recent call last):
  File "<string>", line 8, in <module>
  File "<string>", line 4, in iter_titles
ValueError: I/O operation on closed file.
```

**What it means.** The generator was **created** inside the `with` block and **consumed** outside it.
Because nothing in a generator body runs until the first request
([2.1](../02-generators/2.1-yield-the-function-that-pauses.md)), the reading happens after the block
has closed the handle. This is the single most common bug with handle-shaped generators, and the fix
is to move the consumption inside the block — or to have the function open the file itself, which
brings back the testing cost. Choosing between those two is a real decision, and this project chooses
the handle plus a two-line wrapper for callers who want a path.

**The dedup that lost the order:**

```text
>>> def wrong_unique(titles):
...     yield from set(titles)
...
>>> list(wrong_unique(["milk", "eggs", "milk", "bread"]))
['eggs', 'milk', 'bread']
```

**What it means.** Three correct titles in an order nobody asked for, and the order is not even
stable between runs on different data
([Day 8, 2.1](../../../day-08-containers/parts/02-sets-and-dicts/2.1-a-set-is-a-hash-table.md)). It
also loads everything into the set at once, so the laziness is gone too. A two-item test would pass
this. The three-item test with the duplicate in the middle is what catches it, which is why the
`TODO(me)` above says so.

**The memory test that passed because the file was small:**

```text
$ uv run python -m pytest tests/test_textutils.py::test_iter_titles_peak_memory -q
1 passed
```

**What it means.** Nothing. A memory test over four lines passes for the list version and the
generator version alike, so it asserts only that four strings fit in a megabyte. The number of lines
in that test is doing all the work, and it has to be large enough that the eager version would fail.
That is why the `TODO(me)` names a hundred thousand: at four lines the test is theatre, and at a
hundred thousand it is a gate.

## In production

**The professional shape is exactly the one the gate asks for: a lazy core, an eager edge, and one
line that chooses.** Every serious data tool is built this way. `pandas.read_csv(chunksize=...)`
returns an iterator; `csv.reader` takes a handle rather than a path; a database cursor streams and the
caller decides whether to `fetchall`. Writing your own module the same way is not imitation — it is
what makes it composable with theirs.

**What changes at scale is that the `with` block moves up.** In a small script the file is opened and
consumed in the same function. In a real pipeline the opening happens in one place, the stages are
assembled in another, and the consuming loop is somewhere else again — and the "I/O operation on
closed file" error above becomes a genuinely hard bug, because the three places are three files
apart. The professional answer is that whoever opens the resource owns the loop that consumes it, and
that ownership is written down: `contextlib.closing`, a context manager of your own (Day 16), or a
function that takes the handle and does the whole job before returning.

**The failure that only appears with real data is the growing `seen` set.** `unique_titles` holds one
key per distinct title, which is nothing on four slips and is a real number on a hundred million rows
with high cardinality — and unlike the file, it does not stream. On a genuinely large deduplication,
production systems either sort first and compare neighbours, or accept approximation with a Bloom
filter, or push the whole job into a database with an index. The important part today is smaller: the
docstring says which resource grows and with what, so the next person can see the ceiling before they
hit it.

**The review comment a senior engineer leaves.** On a pull request adding the three functions:
*"`titles_matching` takes a predicate but does not say what happens if the predicate raises — with a
generator, the exception surfaces in the consumer's loop, three frames away from the call that
supplied the function. Either document that, or catch and re-raise with the title attached. And add
the row number: at ten million titles, `ValueError` with no context is not something anybody can
act on."*

**The interview question.** *"How would you design a text-processing function so it works on a file
bigger than memory?"* The answer that lands is the signature before the body: take an already-open
handle or an iterable rather than a path, yield rather than return a list, and put the one
materialising call in the caller — then say what that buys, which is testability with `StringIO` and
a peak memory that does not grow. If you add that you would test the memory claim with `tracemalloc`
rather than asserting it in a docstring, you are describing something you have shipped.
