# 3.2 — `is` versus `==`, small-int caching, and why interning is not a promise

## One-line answer

`is` asks whether two names refer to **one object** and `==` asks whether two objects hold **equal
values** — and because the interpreter caches small integers and short strings, `is` on those appears
to work during testing and fails on real data, which makes it one of the most reliably
production-only bugs in Python.

---

## The story

You have a 500-rupee note in your wallet. I have a 500-rupee note in mine.

Are they **the same amount**? Yes. Either one buys the same bag of groceries, and if we swapped them
neither of us would be better or worse off. In every way that matters to a shopkeeper, they are
interchangeable.

Are they **the same note**? No. Mine has a fold in the corner and yours does not, and more to the
point, if I spend mine this afternoon, yours is still sitting in your wallet.

Those are two different questions, and English uses the same word for both, which is why people mix
them up. Python does not mix them up. `==` asks *is this worth the same?* and `is` asks *is this
literally the same one?*

Here is what it costs to ask the wrong one. A service checks a status code that came back from
another system:

```text
if code is 200:
    handle_success()
```

Every test passes. Every check by hand works. It ships.

In use, some requests are handled correctly and some are not, with no pattern anybody can see.
Eventually somebody spots that the failures all came through one particular route — the one where the
code arrives as text and gets turned into a number with `int()`, rather than being typed as `200`
straight into the source file.

`200 is 200`, written twice in the same file, is `True`, because Python quietly keeps one copy of
small numbers and both of those resolve to it. `int("200") is 200` is `False`, because the conversion
built a **new** 200.

Both are 200. `==` says so. `is` asks the other question, gets an honest answer, and the branch is
skipped.

The tests used numbers typed into the file. Real traffic used numbers parsed from text. **No amount
of testing with typed-in numbers could have found this**, because with typed-in numbers the wrong
operator gives the right answer.

Modern Python does try to warn you — `SyntaxWarning: "is" with a literal. Did you mean "=="?` — which
is the language reaching out to stop precisely this. It is also very easy to miss in a busy log.

---

## The idea in plain language

### Two different questions

- **`a is b`** — are these the same object? Compares identity, `id(a) == id(b)`
  ([1.1](../01-objects/1.1-identity-type-value.md)). Never overridable, always cheap, always exact.
- **`a == b`** — do these hold equal values? Calls the object's `__eq__`, which a class can define
  ([2.5](../02-containers/2.5-hashability.md)).

The rule is short:

| Use | For |
|---|---|
| `is` / `is not` | `None`, `True`, `False`, and any deliberate singleton |
| `==` / `!=` | **everything else** — numbers, strings, containers, your own objects |

That is the whole rule. The rest of this document is why the exceptions are tempting and why they are
still wrong.

### Why `is` sometimes appears to work on values

Two interpreter optimisations make `is` give the "right" answer by accident.

**Small-integer caching.** The interpreter pre-creates integer objects for a small range — commonly
about −5 to 256 — and reuses them. So two names for `100` are usually one object, and two names for
`1000` usually are not.

**String interning.** Short strings that look like identifiers are shared, and the compiler folds
constant expressions, so two identical literals in one file are often one object. A string built at run
time usually is not ([1.4](../01-objects/1.4-strings-are-immutable.md)).

Both are **implementation details**. They differ between Python implementations and can change between
versions. Code that relies on them is code that works until it does not, with no warning and no
version note anybody read.

### Why `is None` is right, and required

`None` is a **singleton** — exactly one instance exists in the whole process. So identity and equality
give the same answer, and identity is:

- **Faster**, because it is a pointer comparison with no method call.
- **Correct even when a class lies.** A class can define `__eq__` to return `True` for anything,
  including comparisons with `None`. NumPy arrays and pandas Series famously return an *array* of
  booleans from `==`, so `if arr == None:` raises rather than answering. `arr is None` always works.

That second reason is the important one. `is None` is not a micro-optimisation; it is the only form
that cannot be subverted, which is why every codebase, style guide and linter insists on it.

The same applies to `True` and `False`, though in practice you rarely compare to them at all —
`if flag:` is better than `if flag is True:`
([1.3](../01-objects/1.3-numbers-and-bool.md)).

## Why Setu needs it

- **[3.1](3.1-the-mutable-default-argument.md)'s fix depends on `is None`**, and getting it wrong —
  using truthiness — silently discards a caller's empty list.
- **NumPy and pandas override `==` to be element-wise** (Days 20–35). From Day 21 onward,
  `x == None` on an array does not return a boolean at all, and `x is None` is the only thing that
  works.
- **[Day 1, 1.1](../../../day-01-pins/parts/01-versions/1.1-semantic-versioning.md)'s string-comparison
  trap** is the same family: an operator that gives a plausible answer for the wrong reason.
- **Every optional parameter from Day 10 onward** (`PY-10`) is `param=None` plus `if param is None`.
  It is the most-used idiom in the whole plan.
- **`E711`/`E712` in this project's selected rules**
  ([Day 2, 1.2](../../../day-02-quality-gate/parts/01-linting/1.2-choosing-rule-families.md)) flag
  `== None` and `== True`, so the linter enforces this from today.

## The mechanism

Watch the caching produce the false confidence:

```python
"""Small integers are cached. Parsed integers are not. Same value, different objects."""

for value in (5, 100, 256, 257, 1000):
    a = value
    b = int(str(value))
    print(f"{value:>5}: a == b -> {a == b}    a is b -> {a is b}")

print()
literal_a = 257
literal_b = 257
print("two literals in one line of source:", literal_a is literal_b)
print("parsed from text                  :", 257 is int("257"))
```

**Line by line:**

- `b = int(str(value))` — round-trip through text, which is exactly what happens to data from a file,
  an environment variable ([Day 3, 1.2](../../../day-03-keys-and-budget/parts/01-secrets/1.2-dotenv-and-os-environ.md))
  or a JSON payload. **It forces a new object to be built.**
- `a == b` is `True` for every row — the values are equal, always.
- `a is b` is `True` for the small values and `False` for the large ones. **The boundary is an
  implementation detail** and the exact cut-off is not something to rely on or memorise; the lesson is
  that a boundary exists at all.
- The last two lines contrast source literals with parsed values, which is the story: same expression
  shape, opposite answers, decided by where the number came from.
- Running this on a different Python implementation can give different answers in the middle rows. That
  variability *is* the argument.

Now strings, where the behaviour is even less predictable:

```python
"""Interning is an optimisation, not a guarantee."""

import sys

literal_1 = "setu"
literal_2 = "setu"
folded = "se" + "tu"
built = "".join(["s", "e", "t", "u"])
interned = sys.intern("".join(["s", "e", "t", "u"]))

pairs = [
    ("two identical literals", literal_1, literal_2),
    ("compile-time folded   ", literal_1, folded),
    ("built at run time     ", literal_1, built),
    ("explicitly interned   ", literal_1, interned),
]
for label, left, right in pairs:
    print(f"{label}: is -> {left is right:<6} == -> {left == right}")

print()
spaced_1 = "project setu"
spaced_2 = "project setu"
print("literal with a space  : is ->", spaced_1 is spaced_2)
```

**Line by line:**

- `"se" + "tu"` — the compiler folds two adjacent constants into one literal at compile time, so it is
  typically the same object.
- `"".join([...])` — built at run time, so typically a **different** object with an equal value. This
  is the string version of `int("200")`.
- `sys.intern(...)` — asks the interpreter to return the shared copy, forcing identity. It exists as a
  genuine memory optimisation for programs holding millions of repeated strings, **not** as a way to
  make `is` safe for comparisons.
- The `==` column is `True` on every row. The `is` column is not. **That is the entire argument for
  using `==` on values.**
- `"project setu"` with a space — strings that do not look like identifiers may not be interned, and
  the answer here can differ between versions and contexts. Any behaviour you observe is a fact about
  today's interpreter, not about the language.

And the case where `is` is not merely preferred but required:

```python
"""`is None` is the only form a class cannot subvert."""


class Weird:
    """A class whose __eq__ answers True to everything - legal, and not rare."""

    def __eq__(self, other: object) -> bool:
        return True

    __hash__ = None  # type: ignore[assignment]


w = Weird()
print("w == None :", w == None)  # noqa: E711
print("w is None :", w is None)

print()


class ElementWise:
    """Like a NumPy array: __eq__ returns a container, not a bool."""

    def __init__(self, values: list[int]) -> None:
        self.values = values

    def __eq__(self, other: object) -> list[bool]:  # type: ignore[override]
        return [v == other for v in self.values]

    __hash__ = None  # type: ignore[assignment]


arr = ElementWise([1, 2, 3])
print("arr == 2 :", arr == 2)
try:
    if arr == None:  # noqa: E711
        print("unreachable")
except ValueError as exc:
    print("if arr == None ->", type(exc).__name__, exc)
print("arr is None:", arr is None)
```

**Line by line:**

- `def __eq__(self, other): return True` — a class can define equality however it likes. `w == None`
  returns `True` for an object that is obviously not `None`, so **a `== None` check is a check the
  class controls.** `w is None` cannot be subverted; identity is not overridable.
- `__hash__ = None` — defining `__eq__` makes a class unhashable unless you also define `__hash__`
  ([2.5](../02-containers/2.5-hashability.md)); setting it explicitly here documents the intent.
- `# noqa: E711` — this project's linter flags `== None`
  ([Day 2, 1.2](../../../day-02-quality-gate/parts/01-linting/1.2-choosing-rule-families.md)), so the
  demonstration needs an explicit, coded suppression
  ([Day 2, 1.3](../../../day-02-quality-gate/parts/01-linting/1.3-fix-and-noqa-as-debt.md)).
- `ElementWise.__eq__` returning a **list** rather than a bool — this is exactly what NumPy and pandas
  do, deliberately, because element-wise comparison is what you want from an array. It means `arr == 2`
  gives `[False, True, False]`.
- `if arr == None:` — the condition is a list, and while a plain list is simply truthy, NumPy raises
  `ValueError: The truth value of an array with more than one element is ambiguous`. That message is
  one you will meet many times from Day 21, and **`is None` is the fix every time.**
- `arr is None` prints `False` without drama. One object comparison, no `__eq__`, no ambiguity.

## When it breaks

**The story, with the language trying to help:**

```text
>>> code = int("200")
>>> code is 200
<stdin>:1: SyntaxWarning: "is" with a literal. Did you mean "=="?
False
```

**What it means.** The warning fires because `is` against a **literal** is essentially always a
mistake. It is a warning rather than an error because the construct is legal. Treat it as an error —
a project can turn warnings into errors in its test configuration, which is a genuinely good idea for
exactly this class of thing.

**The array comparison, which you will meet repeatedly:**

```text
>>> import numpy as np
>>> arr = np.array([1, 2, 3])
>>> if arr == None:
...     pass
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
ValueError: The truth value of an array with more than one element is ambiguous.
  Use a.any() or a.all()
```

**What it means.** `==` returned an array of booleans, and `if` cannot reduce it to one truth value.
`arr is None` is the correct check. The plan's own `PY-04` example is the same shape — `if df:` raises
while `if len(df):` does not — and the general lesson is that **`==` is a method call and a class
decides what it means.**

**The linter catching it before it runs:**

```text
E711 Comparison to `None` should be `cond is None`
 --> src/setu/validate.py:18:8
E712 Comparison to `True` should be `cond is True` or `if cond:`
 --> src/setu/validate.py:24:8
```

**What it means.** Both are pycodestyle rules in this project's selected `E` family. They exist
because these two comparisons are almost never what anybody meant, and the linter is the cheapest
place to catch them ([Day 2, 1.1](../../../day-02-quality-gate/parts/01-linting/1.1-what-a-linter-is.md)).

**The cached-integer illusion, live:**

```text
>>> a = 256; b = 256; a is b
True
>>> a = 257; b = 257; a is b
False
```

**What it means.** Two lines that differ only in a value, giving different answers. On some
implementations both may be `True`. **Every one of those results is an implementation detail**, and
code depending on any of them is broken in a way no test on the current interpreter will reveal.

**And the one that looks like a caching bug:**

```text
>>> cache = {}
>>> cache[("ai",)] = 1
>>> key = tuple(["ai"])
>>> key in cache
True
>>> key is list(cache)[0]
False
```

**What it means.** The dictionary found the entry because lookup uses `hash` and `==`, **not** `is`
([2.5](../02-containers/2.5-hashability.md)). Two distinct tuple objects with equal contents are the
same key. That is exactly the desired behaviour, and it is a good reminder that containers are built on
`==`, so a class with a broken `__eq__` breaks every container it goes into.

## In production

**The rule is enforceable by tooling, so enforce it.** `E711` and `E712` catch `== None` and
`== True`; the `SyntaxWarning` catches `is` against a literal; turning warnings into errors in your
test configuration catches the rest. This is the argument from
[Day 2, 4.2](../../../day-02-quality-gate/parts/04-the-gate/4.2-local-gate-versus-remote-gate.md): a
rule that depends on everyone remembering is not a rule. Put it in the gate and stop thinking about it.

**`is None` is the only safe null check in any codebase using array libraries**, which after Day 20 is
this one. NumPy and pandas override `==` deliberately and correctly — element-wise comparison is the
point of an array — with the consequence that `x == None` either raises or returns something that is
not a boolean. The habit of writing `is None` everywhere costs nothing and removes a whole category of
bug before it exists.

**Identity comparison has genuine uses beyond `None`, and they are worth recognising.** Sentinel
objects — a module-level `_MISSING = object()` used to distinguish "not supplied" from "supplied as
None" ([3.1](3.1-the-mutable-default-argument.md)) — are compared with `is`, because their whole
purpose is to be unique. Checking whether two references point at the same cache entry or the same
open connection is also an identity question. The rule is not "never use `is`"; it is **use `is` when
you genuinely mean the same object, and never as a shortcut for equality.**

**What changes at scale:** interning becomes a deliberate memory technique. A program holding tens of
millions of strings drawn from a small vocabulary — log levels, country codes, column names — can save
substantial memory by interning them so duplicates share one object, and pandas' categorical dtype
(Day 34, `PD-13`) is the same idea formalised for a column. The point worth carrying is that interning
is a **memory** optimisation whose visible side effect is that `is` starts returning `True` more often
— which is precisely why treating that side effect as a semantic guarantee is backwards.

**The review comment a senior engineer leaves.** On `if value == None:` — *"`is None`. And once we're
using NumPy, `== None` on an array won't even return a boolean."* On `if code is 200:` — *"That's
comparing identity to a literal. It works today because small ints are cached and will break the first
time the value is parsed rather than written."*

**The interview question.** *"When would you use `is` instead of `==`?"* The short answer — singletons,
`None` above all — is table stakes. The answer that lands gives the *reason* rather than the rule:
`is` compares identity and cannot be overridden, so it is the only check a class cannot subvert, which
matters enormously with libraries that define `==` to be element-wise. Then give the failure mode in
the other direction: `is` on values appears to work because of small-integer caching and string
interning, so it passes every test written with literals and fails the first time the value is parsed
from input — a bug that is essentially undiscoverable by testing. If you can add that interning is an
implementation detail that varies by version and implementation, you are describing something you have
been bitten by rather than something you have read.
