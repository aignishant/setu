# 4.1 — The standard that decided `0.1`: *IEEE 754*

## One-line answer

*IEEE 754* is the standard that made floating-point arithmetic **the same on every machine** — it
fixes the bit layout, the rounding rule, and what happens when you divide by zero — and the price of
that agreement is that most of the decimal fractions you type do not exist, which is why
[1.3](../01-objects/1.3-numbers-and-bool.md)'s `0.1 + 0.2` is not `0.3` on your laptop, on a server,
or on any machine you will ever use.

## The story

Two research groups run the same simulation code, compiled from the same source, on two different
machines. The results diverge in the fourth decimal place, then the third, then the first. Nobody has
a bug: both machines are doing exactly what their hardware manuals promise. They simply do not
promise the same thing.

This was ordinary before the mid-1980s. Machines disagreed about how many bits the exponent got,
whether there was a hidden leading bit, what happened when a result was too small to represent —
some flushed it to zero, some kept going into a gradual underflow — and what a division by zero
should do. Some halted the program. Some returned the largest representable number, on the theory
that it was the closest available answer. Numerical code was therefore written *per machine*, and
porting it meant re-deriving its error bounds from scratch.

The standard ended that argument by making the arithmetic **exactly specified**: not merely "about
this accurate", but *this bit pattern, this rounding rule, this result, on every conforming machine*.
The subtle part is that it did not make floating point accurate. It made it **predictable**, which is
a completely different and far more useful property. `0.1 + 0.2` still is not `0.3` — but it is
wrong by the same amount everywhere, and that amount can be reasoned about, tested for, and bounded.

That is the trade the standard made on your behalf, and every surprising float you meet for the rest
of this plan is a consequence of it.

---

## The idea in plain language

A `float` is not a number with a decimal point. It is **three integers** packed into 64 bits, naming
a value in the form:

```text
(-1)^sign  ×  1.mantissa  ×  2^(exponent - 1023)

 64 bits:  [ s ][    exponent    ][               mantissa                ]
             1          11                          52
```

Three ideas explain everything else.

**The base is two, not ten.** A fraction is representable exactly only if it is a sum of halves,
quarters, eighths and so on. `0.5` is exact. `0.75` is exact. `0.1` is not — in binary it repeats
forever, exactly the way `1/3` repeats forever in decimal. The standard cannot store an infinite
expansion, so it stores the nearest 53-bit value and the difference is gone before your arithmetic
even begins. **Nothing was lost in the addition; the loss happened when the literal was parsed.**

**There is a hidden bit.** Since every normalised binary number starts with a `1`, that `1` is not
stored — the format gets a free 53rd bit of precision. This is why the mantissa field is 52 bits but
the precision is 53, and why `exact(1.0)` in the demo below reports a mantissa of exactly zero.

**Some values are not numbers.** The exponent value `0x7FF` is reserved: with a zero mantissa it
means infinity, with a non-zero mantissa it means `nan` — *not a number*. These exist so that
arithmetic never has to stop. Dividing by zero produces `inf` rather than crashing; `inf - inf`
produces `nan`; and `nan` is defined to compare **unequal to everything, including itself**. That
last rule is not a quirk — it is how the standard says "this value is the residue of a question that
had no answer", and it is why [3.2](../03-identity-trap/3.2-is-versus-equals.md)'s distinction
between `is` and `==` has a genuinely strange case hiding in it.

**Rounding has a rule, and the rule is not the one you learned.** The default is *round to nearest,
ties to even*: a value exactly halfway between two representable numbers goes to the one whose last
bit is zero. Always rounding halves up would bias every long summation upward; ties-to-even makes the
bias cancel. This is the standard choosing statistics over the playground rule.

## The mechanism

The standard specifies, bit for bit, what a `binary64` looks like. Python will hand you those bits.

```python
import struct

(bits,) = struct.unpack("<Q", struct.pack("<d", 0.1))
print(format(bits, "064b"))
print((0.1).hex())
```

**Line by line:**

- `struct.pack("<d", 0.1)` — take the float and give me its **bytes**, exactly as they sit in memory.
  `d` is the format character for a `binary64` double, which is what every Python `float` is; `<` is
  little-endian, specified explicitly so the output does not depend on the machine — the same reason
  the standard exists at all.
- `struct.unpack("<Q", ...)` — read those same eight bytes back as an unsigned 64-bit integer. `Q` is
  "unsigned long long". Nothing has been converted; the bits are reinterpreted. This is the whole
  trick, and it is why the tuple unpacking `(bits,) =` is there: `unpack` always returns a tuple.
- `format(bits, "064b")` — binary, zero-padded to 64 places. Read it in three pieces: `0` is the
  sign, `01111111011` is the exponent field, and the rest is the mantissa. That exponent field is
  `1019` in decimal, and `1019 - 1023 = -4` — which is the `p-4` in the line below it.
- `(0.1).hex()` — Python's own view of the same thing: `0x1.999999999999a` × 2⁻⁴. The repeating
  `999...` is the binary expansion of one tenth repeating, and the final `a` is where it was rounded
  to fit. **That `a` is the entire bug**, sitting in plain sight, before any arithmetic has happened.

Run it, and the 64 bits appear with the exponent field in the middle:

```text
0011111110111001100110011001100110011001100110011001100110011010
0x1.999999999999ap-4
```

Now decode it back into an exact value, using integers so nothing is approximated twice:

```python
from fractions import Fraction

BIAS = 1023
MANTISSA_BITS = 52

sign = bits >> 63
exponent = (bits >> MANTISSA_BITS) & 0x7FF
mantissa = bits & ((1 << MANTISSA_BITS) - 1)

significand = 1 + Fraction(mantissa, 1 << MANTISSA_BITS)
print(significand * Fraction(2) ** (exponent - BIAS))
```

**Line by line:**

- `bits >> 63` — shift the sign bit down to position zero. It is the highest bit, so a 63-place shift
  leaves exactly it.
- `(bits >> MANTISSA_BITS) & 0x7FF` — shift the exponent field down past the 52 mantissa bits, then
  mask off everything above it. `0x7FF` is eleven ones, the exact width of the field, so the mask is
  the field's definition written as a number.
- `bits & ((1 << MANTISSA_BITS) - 1)` — `1 << 52` is a one followed by 52 zeros, so subtracting one
  gives 52 ones: the mask that keeps only the mantissa. This idiom is worth recognising on sight; it
  is how every bit field in every binary format is extracted.
- `1 + Fraction(mantissa, 1 << MANTISSA_BITS)` — the hidden leading bit, made explicit. The stored
  mantissa is the fractional part; the standard says an implied `1.` sits in front of it. Miss this
  line and every decoded value is out by a factor of two.
- `Fraction` rather than float division — the whole point is to compute the value **exactly**. Using
  `mantissa / 2**52` would round the answer with the same mechanism we are trying to inspect, which
  would be circular.
- `Fraction(2) ** (exponent - BIAS)` — the bias subtracted. The exponent field is stored as an
  unsigned number with 1023 added, so that the encoding sorts in the same order as the values it
  represents. Negative exponents give a `Fraction` with a power of two in the denominator, which is
  why this must be `Fraction(2)` and not `2`.

It prints:

```text
3602879701896397/36028797018963968
```

That fraction is the number your program actually holds when you type `0.1`. Its denominator
is 2⁵⁵. There is no ten anywhere in it.

## The demo

One project, one feature: **a microscope that shows the exact value behind any float**. It implements
the standard's §3.4 encoding and nothing else — no arithmetic, no rounding modes, no formatting
library.

```text
float-microscope/
├── microscope.py        # decode binary64 into its three fields and its exact value
└── test_microscope.py   # the standard's consequences, asserted
```

`microscope.py`, in full:

```python
"""IEEE 754 binary64, decoded: the three fields, and the exact value they name."""

import struct
from fractions import Fraction

BIAS = 1023
MANTISSA_BITS = 52


def fields(value: float) -> tuple[int, int, int]:
    """The sign, raw exponent and raw mantissa of a binary64, straight out of its 64 bits."""
    (bits,) = struct.unpack("<Q", struct.pack("<d", value))
    sign = bits >> 63
    exponent = (bits >> MANTISSA_BITS) & 0x7FF
    mantissa = bits & ((1 << MANTISSA_BITS) - 1)
    return sign, exponent, mantissa


def exact(value: float) -> Fraction:
    """The exact rational this float names. No float ever stands for the decimal you typed."""
    sign, exponent, mantissa = fields(value)
    if exponent == 0x7FF:
        raise ValueError("inf and nan are not rationals")
    if exponent == 0:  # subnormal: no implicit leading 1
        significand = Fraction(mantissa, 1 << MANTISSA_BITS)
        power = 1 - BIAS
    else:
        significand = 1 + Fraction(mantissa, 1 << MANTISSA_BITS)
        power = exponent - BIAS
    magnitude = significand * Fraction(2) ** power
    return -magnitude if sign else magnitude


def report(value: float) -> str:
    sign, exponent, mantissa = fields(value)
    return (
        f"{value!r}\n"
        f"  sign={sign} exponent={exponent} (2^{exponent - BIAS}) mantissa={mantissa}\n"
        f"  hex     {value.hex()}\n"
        f"  exact   {exact(value)}"
    )
```

**Line by line:** — `fields` is the mechanism above; only what is new is walked through here.

- `if exponent == 0x7FF: raise ValueError(...)` — the reserved exponent. `inf` and `nan` have no
  rational value, so the function refuses rather than returning something plausible. A decoder that
  quietly returned a huge number for `inf` would be lying in exactly the way this part is about.
- `if exponent == 0:` — **subnormals**, the standard's most-argued-over feature. When the exponent
  field is all zeros there is *no* implicit leading `1`, and the exponent is fixed at `1 - BIAS`.
  This is what lets values shrink gradually toward zero instead of falling off a cliff, and it is
  the branch every hand-written float decoder forgets. `exact(5e-324)` — the smallest positive double
  — goes through here.
- `power = 1 - BIAS` rather than `0 - BIAS` — the off-by-one that makes subnormals join up smoothly
  with the smallest normal number. It looks like a typo and is load-bearing.
- `-magnitude if sign else magnitude` — sign is applied at the end, as a separate field. Floating
  point is sign-and-magnitude, not two's complement, which is why `-0.0` exists as a distinct bit
  pattern from `0.0` while still comparing equal to it.
- `report` returns a string instead of printing — so the tests can assert on it and a caller can log
  it. A demo function that prints is a demo function nobody can test.

`test_microscope.py`, in full:

```python
"""The standard's consequences, asserted."""

from decimal import Decimal
from fractions import Fraction

from microscope import exact, fields


def test_one_tenth_is_not_one_tenth():
    assert exact(0.1) != Fraction(1, 10)
    assert exact(0.1) == Fraction(Decimal(0.1))


def test_the_famous_sum():
    assert 0.1 + 0.2 != 0.3
    assert exact(0.1) + exact(0.2) != exact(0.3)


def test_the_implicit_leading_one_is_real():
    _, exponent, mantissa = fields(1.0)
    assert (exponent, mantissa) == (1023, 0)
    assert exact(1.0) == Fraction(1, 1)


def test_a_half_is_exact_because_two_is_the_base():
    assert exact(0.5) == Fraction(1, 2)
    assert exact(0.75) == Fraction(3, 4)
```

**Line by line:**

- `exact(0.1) != Fraction(1, 10)` — the assertion the whole standard is about, stated as a test that
  can go red. If a future Python made this pass, the format would have changed underneath you.
- `exact(0.1) == Fraction(Decimal(0.1))` — the independent check. `Decimal(0.1)` constructs the
  **exact** decimal expansion of the float (not the decimal `0.1`), and `Fraction` of that is exact
  too, so this compares the decoder against the standard library's own view of the same bits. Two
  routes, one answer.
- `assert 0.1 + 0.2 != 0.3` followed by the same claim on exact rationals — the pair matters. The
  first line is the symptom everyone has seen; the second shows the symptom is not in the addition,
  it is in the three literals, each of which was already a different number than it appeared.
- `(exponent, mantissa) == (1023, 0)` — `1.0` has a mantissa of exactly zero. The value is `1.0`
  because of the *implied* leading bit, so this single assertion is the hidden bit's whole existence
  proof.
- `exact(0.5)` and `exact(0.75)` — the counter-examples. Not all fractions are inexact; halves and
  quarters are perfect, because the base is two. Without these two lines a reader could walk away
  believing floats are randomly wrong, which is the wrong lesson entirely.

**What this demo deliberately leaves out.** The five rounding modes, the exception flags (invalid,
overflow, underflow, inexact) that the standard requires hardware to raise, the `binary32` and
`binary16` formats, decimal floating point, and every arithmetic operation. It decodes what a float
*is*; it never computes with one — because the encoding is the standard's foundational claim and
everything else in the document is built on it.

## When it breaks

Three failures, all of them the standard behaving exactly as specified.

```python
print(float("nan") == float("nan"))
print(1e308 * 10)
print(1e308 * 10 - 1e308 * 10)
```

```text
False
inf
nan
```

`nan != nan` is required by the standard. It means every containment test on a list of floats can
fail to find a value that is in the list, `sorted()` on data containing a `nan` returns an order that
is not sorted, and a `set` can hold two `nan`s that look identical. `1e308 * 10` did not raise: it
**overflowed to infinity**, silently, and carried on. The subtraction of two infinities then produced
`nan`, which is how a real computation dies — not at the overflow, but three steps later when the
`nan` reaches a comparison and quietly makes a branch go the wrong way.

Then the two errors you will actually see in a traceback:

```text
ValueError: cannot convert float NaN to integer
```

Raised by `int(float("nan"))`. This is usually the *end* of a long chain: something overflowed or
divided zero by zero, produced `nan`, and it travelled through your program until it met a function
that needed a real number. The traceback points at the innocent line that could not cope, never at
the line that created the `nan`.

```text
TypeError: unsupported operand type(s) for +: 'decimal.Decimal' and 'float'
```

Raised by `Decimal(0.1) + 0.1`. `Decimal` refuses to mix with `float` precisely because the mixture
would silently reintroduce binary rounding into a value chosen to avoid it. This error is the
standard library defending the boundary for you.

**The smallest fixes:** use `math.isnan(x)`, never `x == float("nan")`. Compare with
`math.isclose(a, b)` — or `abs(a - b) < tol` with a tolerance you chose deliberately — instead of
`==`. Sum long sequences with `math.fsum` rather than `sum`. And keep money in `Decimal` or in
integer minor units, converting at the boundary and never in the middle.

## What did not survive

**Extended precision quietly disappeared.** The 1985 standard allowed an 80-bit extended format,
which x87 hardware used for intermediate results. That produced *double rounding*: the same
expression could give different answers depending on whether a value stayed in a register or was
spilled to memory, which is the exact class of unpredictability the standard existed to abolish.
Modern SSE/AVX code paths compute in 64 bits throughout, and the extended format survives mainly as
a historical explanation for old bug reports.

**Almost nobody uses the other rounding modes.** The standard requires four, plus ties-away in 2008.
Round-to-nearest-even is the default and, in practice, the only one most programmers ever meet.
Interval arithmetic — the technique the directed modes were designed for — never became mainstream.

**Decimal floating point did not take over.** The 2008 revision added `decimal64` and `decimal128`
with real hardware support on some server processors, aimed squarely at financial computation. The
industry mostly kept using integer minor units or software decimals like Python's `Decimal` instead.
The feature is in the standard and largely unused outside a few domains.

**Machine learning walked away from the precision guarantees entirely.** This is the biggest live
divergence and it matters directly to this plan's later phases. Training runs use `float32`,
`bfloat16` — which keeps `float32`'s exponent range but has only 7 mantissa bits — and now 8-bit
formats, precisely because the standard's accuracy is *more* than gradient descent needs and the
memory bandwidth is worth more than the digits. Meanwhile `-ffast-math`-style compiler flags let
numerical code opt out of the standard's guarantees for speed, in exchange for reintroducing exactly
the machine-dependent behaviour of the 1970s. When a model trains on one accelerator and produces
different numbers on another, this is why.

**What has survived completely intact** is the encoding, the special values, and the round-to-nearest
default. That trio is nearly forty years old, is in every CPU and GPU you will ever use, and is the
reason your laptop and a data-centre machine agree about `0.1 + 0.2`.

## In production

**What a professional writes instead of the teaching version.** Never `==` between computed floats —
`math.isclose(a, b, rel_tol=1e-9)` with a tolerance that was *chosen*, not copied. Never `float` for
money — integer cents, or `Decimal` with an explicit context. Never `sum()` over a long sequence of
similar-magnitude floats where accuracy matters — `math.fsum`, which is exact, or a compensated
summation. And every `nan` check is `math.isnan`, because the equality test that looks correct is
guaranteed by this standard to be wrong.

**What changes at scale.** Summing a million floats accumulates error proportional to the number of
additions; the pairwise summation NumPy uses internally is much better than a naïve loop, which is
one reason a hand-written Python loop over an array is both slower *and* less accurate than the
vectorised call. In training, small gradients underflow to zero in `float16` — which is why mixed
precision uses **loss scaling**: multiply the loss by a large constant so gradients land inside the
representable range, then divide it back out. That trick is a direct consequence of the exponent
field being narrow.

**The failure mode that only appears with real data.** A pipeline runs correctly for months, then one
record contains an empty field that becomes `0/0`, and a `nan` enters. It does not crash. It
propagates: any arithmetic touching it produces `nan`, comparisons against it are all `False`, so
filters silently drop rows, `argmax` returns an arbitrary index, and a metric quietly becomes
meaningless while every log line stays green. Finding it means bisecting the pipeline for the first
stage whose output contains a `nan` — which is why production code asserts `np.isfinite(...).all()`
at stage boundaries rather than at the end.

**The review comment a senior engineer leaves.** On `if total == expected:` — *"These are computed
floats. Use `math.isclose` and say what tolerance is acceptable and why."* On a schema with
`price: float` — *"That is money in binary floating point. Integer minor units, please, before this
reaches a ledger."*

**The interview question.** *"Why is `0.1 + 0.2 != 0.3`?"* The answer that separates a memorised fact
from understanding is that **nothing goes wrong in the addition** — `0.1` and `0.2` are already not
those values when they are parsed, because the standard's base is 2 and one tenth has no finite
binary expansion; the addition of two already-approximate values then rounds once more. The follow-up
is usually *"so how would you compare them?"*, and the answer after that is *"and what would you do
if these were prices?"* — where "use a float with a tolerance" is the wrong answer and "do not use
floats for money at all" is the right one.
