# 1.3 — The columns that did not match

## One-line answer

When you stack frames whose columns are not identical, pandas keeps **every** column either side
had and fills the gaps with blanks — so a column missing from one piece is not an error, it is a
half-empty column, and a column whose name was typed slightly differently becomes two.

---

## The story

The person with the fridge pad always writes down which aisle a thing is in, because they hate
walking the shop twice. Milk, two, aisle 3. Bread, one, aisle 11.

The person on their phone does not. Eggs, six. Rice, one. They will find them.

Copied onto one sheet, the aisle column is filled in for the top half and empty for the bottom half.
Nobody is confused by this, because a person reading it can see what happened.

The second time, something less friendly happens. The pad says *need* at the top of its quantity
column. The phone note says *Need*. Copied onto one sheet, there are now two quantity columns, each
filled in for half the rows, and the person who adds up the first one gets a total for half the
shopping.

---

## The idea in plain language

Stacking two frames does not require them to have the same columns.

The result has **every column name that appeared in any of the pieces**, and each row is filled in
for the columns its own piece had. Where a piece had no such column, the cell is blank.

Two words for what "blank" is here. `NaN` is the value pandas uses for *missing* — literally "not a
number", borrowed from floating-point arithmetic, and used as a placeholder in every kind of column
([Day 26, 2.5](../../../day-26-frames-and-copy-on-write/parts/02-the-str-dtype/2.5-the-missing-value-in-a-text-column.md)).
A **dtype** is the one kind of value a column holds
([Day 26, 1.4](../../../day-26-frames-and-copy-on-write/parts/01-the-two-objects/1.4-one-dtype-per-column.md)),
and that is where the second surprise lives: a whole-number column cannot hold `NaN`, so when a stack
puts blanks into one, pandas widens the column to hold decimals instead. The counts you had as `2`
and `1` come back as `2.0` and `1.0`.

Matching is done **by name and only by name**. Two pieces that list their columns in a different
order stack correctly, because pandas looks up `need` by the word `need`, not by "the second column".
And two pieces that spell a name differently do not stack at all in any useful sense: `need` and
`Need` are two different names, so the result has both of them, each half empty, and no error
anywhere. Capitalisation, a trailing space, a hyphen where the other file used an underscore — each
of these silently doubles a column.

There is a switch that changes the rule: `join="inner"` keeps only the columns **every** piece had,
and drops the rest. That is not usually what you want, because it deletes real data — the aisles that
were written down — in order to make the shape tidy. It is worth knowing because it is exactly one
word away from the default.

The thing to take from this part is that a stack has **two** counts worth checking, not one. The rows
you can predict ([1.1](1.1-two-lists-one-under-the-other.md)). The columns you cannot, and a stack
that produced more columns than any of its pieces had is telling you something.

## The mechanism

One list has an aisle column and the other does not:

```python
import pandas as pd

fridge = pd.DataFrame(
    {
        "item": pd.Series(["milk", "bread"], dtype="str"),
        "need": [2, 1],
        "aisle": pd.Series(["03", "11"], dtype="str"),
    }
)
phone = pd.DataFrame({"item": pd.Series(["eggs", "rice"], dtype="str"), "need": [6, 1]})

stacked = pd.concat([fridge, phone], ignore_index=True)
print(stacked)
print()
print(stacked.dtypes)
print()
print("columns in :", list(fridge.columns), list(phone.columns))
print("columns out:", list(stacked.columns))
```

**Line by line:**

- `aisle` is declared `dtype="str"` because aisle numbers are labels, not quantities. `"03"` as a
  whole number is `3`, and the leading zero is gone forever
  ([Day 27, 1.4](../../../day-27-reading-and-writing/parts/01-the-csv/1.4-dtype-at-read-time.md)).
- `ignore_index=True` so the printout has clean row labels and this part can be about the columns
  ([1.2](1.2-the-index-that-came-along.md)).
- `stacked.dtypes` printed rather than described. The interesting question is whether `need` survived
  as a whole-number column, and the answer here is yes — because `need` was present in **both**
  pieces, so no blanks were introduced into it.
- `list(fridge.columns)` beside `list(stacked.columns)` — the output's columns are the **union** of
  the inputs', in the order they were first seen. Not sorted, not the first frame's order, not the
  longest frame's order: first seen.

```text
    item  need aisle
0   milk     2    03
1  bread     1    11
2   eggs     6   NaN
3   rice     1   NaN

item       str
need     int64
aisle      str
dtype: object

columns in : ['item', 'need', 'aisle'] ['item', 'need']
columns out: ['item', 'need', 'aisle']
```

Now the version where the *missing* column is a number:

```python
import pandas as pd

fridge = pd.DataFrame({"item": pd.Series(["milk", "bread"], dtype="str"), "need": [2, 1]})
late = pd.DataFrame(
    {"item": pd.Series(["oats"], dtype="str"), "aisle": pd.Series(["07"], dtype="str")}
)

mixed = pd.concat([fridge, late], ignore_index=True)
print(mixed)
print()
print(mixed.dtypes)
print()
print("need values:", mixed["need"].tolist())
```

**Line by line:**

- `late` is a note somebody added without a quantity — they wrote the thing down and not how many.
  That is an ordinary way for a piece to be missing a column.
- `need` is `int64` in `fridge` and absent from `late`, so the stack has to put a blank in the oats
  row. `int64` has no way to represent a blank, so pandas **promotes the whole column to
  `float64`** ([Day 28, 4.3](../../../day-28-selection-and-alignment/parts/04-alignment/4.3-the-nan-that-changed-the-dtype.md)).
- `mixed["need"].tolist()` prints `[2.0, 1.0, nan]`. The two counts that were whole numbers before
  the stack are decimals after it, and nothing said so.

```text
    item  need aisle
0   milk   2.0   NaN
1  bread   1.0   NaN
2   oats   NaN    07

item         str
need     float64
aisle        str
dtype: object

need values: [2.0, 1.0, nan]
```

The printed list is `[2.0, 1.0, nan]`. It matters less than it looks for arithmetic — `2.0 == 2` is
`True` and the sum is unchanged — and more than it looks everywhere else: a dtype check fails, a
database write of a float into an integer column fails, and a report prints `2.0` cartons of milk.

The switch that keeps only the shared columns:

```python
import pandas as pd

fridge = pd.DataFrame(
    {
        "item": pd.Series(["milk", "bread"], dtype="str"),
        "need": [2, 1],
        "aisle": pd.Series(["03", "11"], dtype="str"),
    }
)
phone = pd.DataFrame({"item": pd.Series(["eggs", "rice"], dtype="str"), "need": [6, 1]})

print(pd.concat([fridge, phone], ignore_index=True, join="inner"))
```

**Line by line:**

- `join="inner"` keeps the **intersection** of the pieces' columns rather than the union, so `aisle`
  is dropped because `phone` did not have it.
- The word `inner` means the same thing here as it does in `merge`
  ([2.2](../02-merging/2.2-the-four-hows-on-four-rows.md)): keep only what both sides had. What
  differs is *what* it applies to — columns here, rows there.
- This deletes data that was successfully written down. Use it when a downstream step genuinely
  requires a rectangle with no blanks, and never as a way of silencing the `NaN`s.

```text
    item  need
0   milk     2
1  bread     1
2   eggs     6
3   rice     1
```

## When it breaks

**The column name that was typed twice:**

```text
$ uv run python -c "
import pandas as pd
fridge = pd.DataFrame({'item': pd.Series(['milk', 'bread'], dtype='str'), 'need': [2, 1]})
typo = pd.DataFrame({'item': pd.Series(['eggs', 'rice'], dtype='str'), 'Need': [6, 1]})
oops = pd.concat([fridge, typo], ignore_index=True)
print(oops)
print()
print('columns:', list(oops.columns))
print('total  :', oops['need'].sum())
"
```

```text
    item  need  Need
0   milk   2.0   NaN
1  bread   1.0   NaN
2   eggs   NaN   6.0
3   rice   NaN   1.0

columns: ['item', 'need', 'Need']
total   : 3.0
```

**What it means.** One capital letter produced two columns. Every row is filled in for exactly one of
them, both are `float64` because both are half blank, and `oops["need"].sum()` is `3.0` when the real
answer is `10`.

**Nothing raised, and the column that was asked for exists.** That is the whole difficulty: a
`KeyError` would have stopped the program, and instead a plausible, small, wrong number came out.

**The smallest fix** is to normalise the names before stacking, not after:

```python
import pandas as pd


def stack(pieces: list[pd.DataFrame]) -> pd.DataFrame:
    tidy = [piece.rename(columns=str.lower) for piece in pieces]
    out = pd.concat(tidy, ignore_index=True)
    grew = set(out.columns) - set.intersection(*(set(p.columns) for p in tidy))
    if grew:
        raise ValueError(f"the pieces do not agree on their columns; only some have {sorted(grew)}")
    return out
```

**Line by line:**

- `piece.rename(columns=str.lower)` — `rename` accepts a **function** as well as a mapping, so
  `str.lower` is applied to every column name. `need` and `Need` become the same name and stack into
  one column. It does not fix a trailing space; `str.strip` composed with `str.lower` does, and
  **Day 33** is where that composition is built properly.
- `set.intersection(*(...))` — the names present in **every** piece. Unpacking with `*` is what lets
  it take any number of pieces rather than exactly two.
- `grew` is the difference between the union and the intersection: the columns some pieces have and
  others do not. On this data it is empty after the rename, and on genuinely ragged input it names
  exactly what disagrees.
- The function **raises rather than filling**, because at the point of a stack a column that only
  half the pieces have is nearly always a bug in the reading step, not a fact about the world.

**The one that looks safe and is not — a stack that quietly changed a dtype:**

```text
$ uv run python -c "
import pandas as pd
a = pd.DataFrame({'item': pd.Series(['milk'], dtype='str'), 'need': [2]})
b = pd.DataFrame({'item': pd.Series(['oats'], dtype='str'), 'aisle': pd.Series(['07'], dtype='str')})
out = pd.concat([a, b], ignore_index=True)
print('before:', a['need'].dtype)
print('after :', out['need'].dtype)
print('equal? ', out['need'].iloc[0] == 2)
"
```

```text
before: int64
after : float64
equal?  True
```

**What it means.** The value still compares equal to `2`, so every test that asserts on the *value*
passes. Only a test that asserts on the **dtype** catches it — which is exactly what a schema check
is for ([Day 26, 5.2](../../../day-26-frames-and-copy-on-write/parts/05-the-module/5.2-asserting-the-schema.md)).

## In production

**What a professional writes instead of the teaching version.** They do not stack raw pieces at all.
They give every piece the same shape first, and the shape is written down once:

```python
import pandas as pd

SCHEMA: dict[str, str] = {"item": "str", "need": "int64", "aisle": "str"}


def conform(piece: pd.DataFrame) -> pd.DataFrame:
    """Give one piece exactly SCHEMA's columns, in SCHEMA's order, with SCHEMA's dtypes."""
    tidy = piece.rename(columns=str.lower)
    unexpected = set(tidy.columns) - set(SCHEMA)
    if unexpected:
        raise ValueError(f"unexpected columns {sorted(unexpected)}; SCHEMA has {list(SCHEMA)}")
    for name, dtype in SCHEMA.items():
        if name not in tidy.columns:
            tidy[name] = pd.Series(pd.NA, index=tidy.index, dtype=dtype)
    return tidy[list(SCHEMA)].astype(SCHEMA)
```

**Line by line:**

- `SCHEMA` is the same dictionary Day 26's module used and Day 27 handed to `read_csv` as `dtype=`
  ([Day 27, 1.4](../../../day-27-reading-and-writing/parts/01-the-csv/1.4-dtype-at-read-time.md)).
  One definition, three uses; that is what stops the pieces drifting apart.
- The **unexpected** check runs before anything is added. A column nobody planned for is a signal
  that the source changed, and it is far cheaper to hear about it here than to find a half-empty
  column in a model's features.
- The missing columns are added **explicitly, with the right dtype**, rather than being allowed to
  appear as `float64` blanks during the stack. `pd.NA` is pandas' own missing marker and, unlike
  `NaN`, it does not force a numeric column to become decimal.
- `tidy[list(SCHEMA)]` reorders the columns, so every conformed piece is column-for-column
  identical. `pd.concat` does not need this — it matches by name — but a human reading two pieces
  side by side does.
- `.astype(SCHEMA)` is last, so the dtypes are asserted rather than inherited from whatever the file
  happened to contain.

**What changes at scale.** `pd.concat` looks at every piece's columns before it allocates anything,
so a hundred pieces that disagree in a hundred different ways produce a hundred-and-something-column
result and a frame that is mostly blank. That is not slow — it is *wasteful*: a mostly blank
`float64` column costs eight bytes per row whether or not there is anything in it, so a million-row
stack with fifty accidental duplicate columns is four hundred megabytes of nothing.

There is also an ordering cost people meet late. The column order of the output depends on the order
the pieces are listed in, because the union is built in first-seen order. A pipeline whose file list
comes from a directory listing therefore has a column order that depends on filenames, and a
downstream step that reads columns positionally — a `to_numpy()`, a CSV written without a header —
breaks when a file is added. `pd.concat(..., sort=True)` alphabetises the columns instead, and
selecting `df[list(SCHEMA)]` after the stack fixes it properly.

**The failure that only appears with real data.** A data feed changed a column from `customer_id` to
`customerId` in one region's export. The stack kept both, each about half full. The model that
consumed the table treated the column as a feature, its imputer filled the blanks with the median,
and the model's accuracy dropped by a couple of points — small enough to be blamed on drift, and it
was, for a quarter. What found it was a check that compared the union of the pieces' columns to their
intersection, which is four lines and would have failed on the first run.

**The review comment a senior engineer leaves.** *"This `pd.concat` takes whatever columns the files
happen to have. Conform each piece to `SCHEMA` first and assert the union equals the intersection,
otherwise one renamed column upstream silently becomes two half-empty ones here — and check the
dtypes after, because a column missing from one piece will have promoted `int64` to `float64`."*

**The interview question.** *"What happens if the frames you concatenate have different columns?"*
You get the union, with `NaN` where a piece had no such column, and no error. Then the part that
shows experience: an integer column that gains blanks is promoted to float, so the dtypes of the
result are not the dtypes of the pieces; matching is by name, so any difference in capitalisation or
whitespace produces two columns instead of one; and `join="inner"` keeps only the shared columns,
which fixes the shape by deleting data. The defence is to conform each piece to a declared schema
before stacking and to compare the union of the pieces' column names against their intersection.
