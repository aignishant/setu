# 3.2 — `CategoricalDtype` — the order written down

## One-line answer

`pd.CategoricalDtype(categories=SIZES, ordered=True)` is the object that holds the allowed values **in
the order they belong in**, and `astype` on that object is the one line that puts the order into the
column instead of leaving it in your head.

---

## The story

The flat's whiteboard by the door already has a key in the corner — the one from
[2.1](../02-the-category-dtype/2.1-two-arrays-instead-of-one.md), where somebody got tired of writing
"dry goods" and wrote a short mark instead.

The pack sizes ended up on a strip of card stuck to the fridge, for a different reason. Two people
typed the list up on different evenings. One wrote the sizes in the order they come off the shelf and
the other wrote them alphabetically, so the printout came out differently depending on who had typed.
One of them settled it on a card, once, and stuck it up:

```text
small · medium · large
```

That card holds no shopping. It holds three words, in one order, and it settles an argument. Anybody
typing the list reads the card instead of guessing, and when the flat starts buying a bigger pack the
card gets rewritten once and everybody's printouts change together.

What went up on the fridge is not data. It is a **rule about the data**, and it was worth writing down
separately because more than one person and more than one evening depend on it.

---

## The idea in plain language

pandas has an object that is exactly that card, and it is called `CategoricalDtype`.

A **dtype** is the promise a column makes about every value it holds
([Day 26, 1.4](../../../day-26-frames-and-copy-on-write/parts/01-the-two-objects/1.4-one-dtype-per-column.md)).
Most dtypes are one word — `int64`, `float64`, `str` — because the promise is short. A categorical
column's promise is longer, so its dtype is an object with contents rather than a name, and it holds
two things:

**The categories.** The list of values this column is allowed to contain, in a chosen order. It is a
list, so it has an order whether you thought about the order or not.

**The `ordered` flag.** One yes-or-no answer to the question *does that order mean anything?* When it
is `False`, pandas will use the list order to arrange groups but will refuse to use it to compare
values. When it is `True`, the order is a claim about the world — the first entry really is less than
the second — and pandas will use it for everything.

Both of those already exist on every categorical column. `astype("category")` builds the dtype for you
by taking the distinct values, sorting them alphabetically and setting `ordered` to `False`. That is a
**guess**, and a reasonable one for a column of names. For a column of steps, as
[3.1](3.1-nominal-and-ordinal.md) showed, the guess is wrong and nothing tells you.

Building the dtype yourself replaces the guess with a **declaration**. Nothing about the values changes;
what changes is what pandas is allowed to conclude about them.

Two details are worth knowing before the code.

**The list you supply is the authoritative list, not the observed one.** It says which values are
allowed, not which values happen to be present in the file you have today. A value in the data that is
not in the list has no place to go, so it becomes a **blank** — pandas' word for a missing value
([Day 30, 1.2](../../../day-30-missing-data/parts/01-what-missing-means/1.2-nan-the-number-not-equal-to-itself.md)).
That is one of the most expensive behaviours on this day and
[4.1](../04-the-traps/4.1-the-value-that-is-not-a-category.md) is entirely about it.

**The list belongs at module level, written once.** Two frames that were given the same dtype object
have the same categories in the same order, so their small per-row numbers — the **codes**, the
positions into the category list ([2.1](../02-the-category-dtype/2.1-two-arrays-instead-of-one.md)) —
mean the same thing. Two frames that each inferred their own dtype from their own data do not, and
nothing warns you.

## The mechanism

Write the card down, then apply it.

```python
import pandas as pd

SIZES = ["small", "medium", "large"]
SIZE_DTYPE = pd.CategoricalDtype(categories=SIZES, ordered=True)

size = pd.Series(["large", "small", "medium", "large"], dtype="str").astype(SIZE_DTYPE)
print(size)
print()
print("categories :", size.cat.categories.tolist())
print("codes      :", size.cat.codes.tolist())
print("ordered    :", size.cat.ordered)
print("dtype      :", repr(size.dtype))
```

**Line by line:**

- `SIZES` is a module-level constant in the real order, not alphabetical order. It is a plain list of
  plain strings, so a person who does not know pandas can read it — the same property the card has.
- `pd.CategoricalDtype(...)` — the constructor. It stores the list and the flag and touches no data, so
  you can build it before you have read a single row. That is the whole point of a declaration.
- `categories=SIZES` passed by keyword. It happens to be the first positional argument, but a bare list
  at a call site does not say what it is.
- `ordered=True` — the claim. Without it the object is still built and still fixes the category order,
  and still refuses `<`. Leaving it off is the usual way to do nine tenths of this work for none of the
  benefit.
- `.astype(SIZE_DTYPE)` — the dtype object handed to `astype` where a dtype name usually goes. This
  returns a new Series; the original is untouched, because pandas 3.0 does not change an object in
  place from an expression like this
  ([Day 26, 3.1](../../../day-26-frames-and-copy-on-write/parts/03-copy-on-write/3.1-every-result-behaves-like-a-copy.md)).
- `repr(size.dtype)` rather than `str(size.dtype)`. The short form prints just `category` and hides
  everything that matters here; the `repr` prints the category list and the flag.

```text
0     large
1     small
2    medium
3     large
dtype: category
Categories (3, str): ['small' < 'medium' < 'large']

categories : ['small', 'medium', 'large']
codes      : [2, 0, 1, 2]
ordered    : True
dtype      : CategoricalDtype(categories=['small', 'medium', 'large'], ordered=True, categories_dtype=str)
```

**Look at the line `Categories (3, str): ['small' < 'medium' < 'large']`.** Those `<` signs are pandas
telling you the flag is set; an unordered column prints the same line with commas
([2.1](../02-the-category-dtype/2.1-two-arrays-instead-of-one.md)). One character of punctuation
separates a column that can be compared from one that cannot, and it is printed every time you display
the Series, which makes it the fastest check you have.

The codes are `[2, 0, 1, 2]` for the values `large, small, medium, large`. `large` is now the **third**
entry, so its code is `2`; the alphabetical version of this same column had `large` first with a code
of `0`. Same words, different numbers underneath.

The picture is the one [2.1](../02-the-category-dtype/2.1-two-arrays-instead-of-one.md) drew — codes
pointing at a category list — with one thing added. The category list is no longer a by-product of the
data; it is `SIZE_DTYPE`, written once at module level, and the arrows between its three entries now
mean *less than* rather than merely *before*.

Often the column is already categorical by the time you get to it, and re-running `astype` from scratch
is not what you want. `reorder_categories` rewrites the card in place of the guessed one:

```python
import pandas as pd

SIZES = ["small", "medium", "large"]

already = pd.Series(["large", "small", "medium", "large"], dtype="str").astype("category")
print("inferred  :", already.cat.categories.tolist(), "ordered:", already.cat.ordered)
print("codes     :", already.cat.codes.tolist())

fixed = already.cat.reorder_categories(SIZES, ordered=True)
print("reordered :", fixed.cat.categories.tolist(), "ordered:", fixed.cat.ordered)
print("codes     :", fixed.cat.codes.tolist())
print("values    :", (fixed.astype("str") == already.astype("str")).all())
```

**Line by line:**

- `.astype("category")` first, deliberately, to produce the alphabetical guess this block then fixes.
  This is the state a frame arrives in when somebody upstream converted it without thinking about order.
- `.cat.reorder_categories(SIZES, ordered=True)` — the same set of values in a different order. It
  renumbers every code so that the values stay put. It is not `rename_categories`, which changes what
  the words *are* and leaves the codes alone; the two are easy to confuse and do opposite things.
  `ordered=True` is passed here as well, because `reorder_categories` will happily give you a correctly
  ordered list with the flag still off.
- `(fixed.astype("str") == already.astype("str")).all()` — the check. Convert both back to text so the
  comparison is about the words rather than the dtypes, compare elementwise, then reduce to one answer
  with `.all()`
  ([Day 28, 2.1](../../../day-28-selection-and-alignment/parts/02-masks/2.1-a-comparison-makes-a-column.md)).
  If this printed `False`, values would have moved rather than been renumbered.

```text
inferred  : ['large', 'medium', 'small'] ordered: False
codes     : [0, 2, 1, 0]
reordered : ['small', 'medium', 'large'] ordered: True
codes     : [2, 0, 1, 2]
values    : True
```

**Every code changed and no value changed.** That is the sentence to keep. Anything that has stored
`.cat.codes` from before this call is now holding numbers that point at the wrong words, which is the
failure [2.1](../02-the-category-dtype/2.1-two-arrays-instead-of-one.md) warns about.

On the year's file — the same four items, three aisles and three sizes repeated two hundred and forty
thousand times, built with a seeded generator so these numbers reproduce
([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md))
— the declaration is one entry in an `astype` dictionary:

```python
import pandas as pd

from year import a_year

SIZES = ["small", "medium", "large"]
SIZE_DTYPE = pd.CategoricalDtype(categories=SIZES, ordered=True)

year = a_year().astype({"size": SIZE_DTYPE})
print("dtype:", repr(year["size"].dtype))
print("bytes as str    :", a_year().memory_usage(deep=True)["size"])
print("bytes as ordered:", year.memory_usage(deep=True)["size"])
print()
print(year.groupby("size", observed=True)["price"].agg(["count", "mean"]).round(2))
```

**Line by line:**

- `from year import a_year` — the seeded builder written out in [3.1](3.1-nominal-and-ordinal.md), kept
  in one file so every part of this day measures the same frame. Copying the body into each script is
  how byte counts stop matching.
- `.astype({"size": SIZE_DTYPE})` with a **dictionary**, naming the column. A bare
  `astype(SIZE_DTYPE)` would try to convert every column in the frame, including `price`.
- `a_year()` called a second time on the byte-count line, to measure the untouched `str` column: a fresh
  frame from the same seed, so it is the same data. `memory_usage(deep=True)["size"]` follows what the
  column points at rather than counting a pointer
  ([1.2](../01-the-repeated-word/1.2-what-memory-usage-actually-counts.md)).
- `observed=True` on the `groupby`, stated rather than defaulted, because on a categorical column the
  other setting produces a group for every declared category including ones no row uses
  ([Day 31, 4.5](../../../day-31-groupby/parts/04-the-keys/4.5-observed-and-the-aisle-nobody-visited.md)).

```text
dtype: CategoricalDtype(categories=['small', 'medium', 'large'], ordered=True, categories_dtype=str)
bytes as str    : 3199894
bytes as ordered: 240148

        count  mean
size
small   80121   3.2
medium  79894   3.2
large   79985   3.2
```

Two things happened from one line. The column went from **3 199 894 bytes to 240 148** — the saving
[2.2](../02-the-category-dtype/2.2-astype-category-and-the-saving-measured.md) is about, which comes
along free. And the report now reads small, medium, large, which is what the flat asked for in
[3.1](3.1-nominal-and-ordinal.md) and did not get.

Last, the behaviour that costs people afternoons. The card lists three sizes. Here is what happens to
a value that is not on it:

```python
import pandas as pd

SIZE_DTYPE = pd.CategoricalDtype(categories=["small", "medium", "large"], ordered=True)

raw = pd.Series(["large", "small", "Medium", "family"], dtype="str")
typed = raw.astype(SIZE_DTYPE)
print(typed.tolist())
print("blank before:", int(raw.isna().sum()))
print("blank after :", int(typed.isna().sum()))
print("codes       :", typed.cat.codes.tolist())
```

**Line by line:**

- `"Medium"` with a capital M and `"family"` are the two realistic ways a value goes off the card: one
  is the same value typed differently, one is genuinely new. Both arrive in real files constantly.
- `raw.isna()` before and `typed.isna()` after — `isna` marks every blank
  ([Day 30, 2.1](../../../day-30-missing-data/parts/02-finding-it/2.1-isna-and-notna.md)), and comparing
  the two counts is the only way to see what the conversion did.
- `.cat.codes` last, because it shows the mechanism: a blank in a categorical column is the code `-1`,
  the one number that points at nothing.

```text
['large', 'small', nan, nan]
blank before: 0
blank after : 2
codes       : [2, 0, -1, -1]
```

**Two values went in and two blanks came out.** The frame did not shrink and no row was dropped; two
rows now say "unknown" where they previously said something. That is the whole trap, and
[4.1](../04-the-traps/4.1-the-value-that-is-not-a-category.md) is where it gets the treatment it
deserves.

## When it breaks

`reorder_categories` will not accept a different set of values, only a different order of the same
ones:

```text
$ uv run python -c "
import pandas as pd
size = pd.Series(['large', 'small', 'medium', 'large'], dtype='str').astype('category')
print(size.cat.reorder_categories(['small', 'medium', 'large', 'family'], ordered=True))
"
```

```text
Traceback (most recent call last):
  File "<string>", line 4, in <module>
  File ".venv\Lib\site-packages\pandas\core\accessor.py", line 127, in f
    return self._delegate_method(name, *args, **kwargs)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File ".venv\Lib\site-packages\pandas\core\arrays\categorical.py", line 3025, in _delegate_method
    res = method(*args, **kwargs)
          ^^^^^^^^^^^^^^^^^^^^^^^
  File ".venv\Lib\site-packages\pandas\core\arrays\categorical.py", line 1338, in reorder_categories
    raise ValueError(
ValueError: items in new_categories are not the same as in old categories
```

**What it means.** `reorder_categories` renumbers; it does not add or remove, so the list you pass must
be a permutation of the list already there. This error is almost always a good thing: it fires when
your declared list and the list the data produced have drifted apart, which is a real disagreement you
wanted to know about. The fix is not to force the list through — it is to decide which of the two is
right. If the data is right, `.cat.add_categories` extends the list
([2.4](../02-the-category-dtype/2.4-a-category-is-not-a-text-column.md)). If the card is right, the row
holding `family` is a data-quality finding
([4.1](../04-the-traps/4.1-the-value-that-is-not-a-category.md)).

The second failure is louder than it looks, and most people never see it because it goes to standard
error while they are reading standard output. Converting a value that is not in the categories emits a
deprecation warning in pandas 3.0.5. Run with `-W error` and it becomes a traceback:

```text
$ uv run python -W error -c "
import pandas as pd
SIZE_DTYPE = pd.CategoricalDtype(categories=['small', 'medium', 'large'], ordered=True)
print(pd.Series(['large', 'family'], dtype='str').astype(SIZE_DTYPE))
"
```

```text
  File ".venv\Lib\site-packages\pandas\core\arrays\categorical.py", line 504, in __init__
    codes = _get_codes_for_values(values, dtype.categories)
            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File ".venv\Lib\site-packages\pandas\core\arrays\categorical.py", line 3045, in _get_codes_for_values
    warnings.warn(
pandas.errors.Pandas4Warning: Constructing a Categorical with a dtype and values containing non-null
entries not in that dtype's categories is deprecated and will raise in a future version.
```

**What it means.** pandas agrees that silently turning a real value into a blank is a bad idea, and has
scheduled the behaviour for removal — `Pandas4Warning` is the class it uses for changes landing in
pandas 4. Today the conversion still happens and still produces blanks; in a future version this exact
line will raise. So your code is on a clock, and the value-checking function below is worth writing
now. More usefully, **the warning is a free data-quality check you already have**:
`warnings.simplefilter("error", Pandas4Warning)`, after
`from pandas.errors import Pandas4Warning`, turns this one warning into a raised exception — catchable
as `except Pandas4Warning`, because a warning class inherits from `Exception`. That line belongs in a
test or a pipeline entry point, never in analysis code, where it would turn every unrelated pandas
deprecation into a crash.

## In production

**What a professional writes instead of the teaching version.** Not `astype(SIZE_DTYPE)` scattered
through the code. One registry of the columns that have a declared order, and one function that applies
it and refuses anything the declaration does not cover:

```python
import pandas as pd

SIZES = ["small", "medium", "large"]
SIZE_DTYPE = pd.CategoricalDtype(categories=SIZES, ordered=True)
ORDERED_DTYPES = {"size": SIZE_DTYPE}


def apply_orders(
    frame: pd.DataFrame, dtypes: dict[str, pd.CategoricalDtype] = ORDERED_DTYPES
) -> pd.DataFrame:
    """Return a copy of `frame` with each named column carrying its declared ordered dtype."""
    out = frame.copy()
    for column, dtype in dtypes.items():
        if column not in out.columns:
            raise KeyError(f"{column!r} is not a column of this frame")
        unknown = sorted(set(out[column].dropna().unique()) - set(dtype.categories))
        if unknown:
            raise ValueError(f"{column}: values with no place in the declared order: {unknown}")
        out[column] = out[column].astype(dtype)
        if out[column].dtype != dtype:
            raise TypeError(f"{column}: dtype is {out[column].dtype!r}, expected {dtype!r}")
    return out
```

**Line by line:**

- `ORDERED_DTYPES` as a dictionary rather than one constant per column. A pipeline has several of these
  columns, and a caller who wants a different set passes one instead of editing the module.
- `frame.copy()` first, so the function never changes the frame it was handed. A function that quietly
  edits its argument is the hardest kind of bug to find in a pipeline of eight steps.
- `if column not in out.columns: raise KeyError` — the declaration names a column that is not there.
  Without this check a renamed upstream column silently skips its own type, and the failure surfaces
  three steps later as a wrong sort.
- `set(...unique()) - set(dtype.categories)` — the values present that the card does not list. This is
  the check `astype` will not do for you, and it turns the silent blank above into a stated refusal.
  `.dropna()` comes before `.unique()` so a genuinely missing value is not reported as an unknown
  category, and `sorted(...)` makes the message identical every run so a test can assert on it
  ([Day 18, 3.3](../../../day-18-exceptions/parts/03-your-own/3.3-the-message-is-an-interface.md)).
- `if out[column].dtype != dtype` after the conversion, comparing against the **dtype object**. This is
  the subtle one. `dtype == "category"` is `True` for an unordered dtype and for one whose categories
  are in the wrong order, so `assert col.dtype == "category"` passes on exactly the columns you were
  trying to catch. Comparing against `SIZE_DTYPE` compares the category list and the flag as well.

**What changes at scale.** `astype(SIZE_DTYPE)` still builds the wide `str` column first and reads every
value. On the year's file that is a full pass over 3.2 million bytes to produce 240 thousand, and the
peak memory is the sum of both. The professional answer is to declare at the boundary:
`read_csv(..., dtype={"size": SIZE_DTYPE})` hands pandas the dtype before the column exists, so the wide
version is never built
([Day 27, 1.4](../../../day-27-reading-and-writing/parts/01-the-csv/1.4-dtype-at-read-time.md)). Parquet
goes further and stores the categories in the file
([Day 27, 3.2](../../../day-27-reading-and-writing/parts/03-parquet/3.2-the-round-trip-that-keeps-dtypes.md)),
which [3.3](3.3-comparing-and-sorting-an-ordered-category.md) checks.

**The failure that only appears with real data.** A team built their ordered dtype from the data —
`sorted(df["size"].unique())` reordered by hand once — and committed the resulting list. It was correct
for eleven months. Then a supplier started shipping a fourth pack, and every row of that pack became a
blank. No row was dropped and the row count did not move, so no count-based test fired. The only signal
was one group in a weekly report quietly shrinking, and by the time anybody traced it the blanks were in
three months of cached Parquet. **The category list must come from whatever authority says which packs
exist, not from last month's file.**

**The review comment a senior engineer leaves.** *"This is `astype('category')`, so the categories are
whatever this file happened to contain, sorted alphabetically, and `ordered` is `False`. `size` is
ordinal. Declare a module-level `CategoricalDtype` with the real order, apply it in the loader, and
check the values against it — today a value off the list becomes a blank and nothing here would
notice."*

**The interview question.** *"How do you tell pandas that a category column has a meaningful order?"*
Build a `pd.CategoricalDtype` with `categories=` in the order you mean and `ordered=True`, keep it as a
module-level constant, and apply it with `astype`. The follow-ups that separate use from reading: the
category list is the **allowed** list, not the observed one, so a value outside it becomes a blank
rather than an error; and `dtype == "category"` is `True` for an unordered dtype, so the check that
actually checks compares against the dtype object.
