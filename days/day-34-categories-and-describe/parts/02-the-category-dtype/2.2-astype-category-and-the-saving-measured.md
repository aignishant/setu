# 2.2 — astype(category), and the saving measured

## One-line answer

`astype("category")` on the flat's aisle column takes it from 3 520 412 bytes to 240 045 — **fourteen
and a half times smaller** — and the new figure is exactly the codes plus the categories plus the
index, with nothing unaccounted for.

---

## The story

Somebody in the flat rewrote the whiteboard with a key in the corner, and everybody agreed it looked
better.

Then the flatmate who had been writing it out the long way asked the fair question: **did that
actually help, or does it just look tidier?**

So they counted. The old board, written out in full for a week's shop, was four lines of about forty
characters each. The new board is a key — three words, twenty characters, written once at the top —
and then four lines of one character each.

A hundred and sixty characters became twenty-four. It helped. And the interesting part is not that
it helped; it is that **the second number splits cleanly into two pieces you can point at**. Twenty
characters of key, four characters of list. Add a fifth line to the shop and you know exactly which
of the two grows, and by how much.

That is the whole of this part. Not "categories save memory" — a saving somebody counted, split into
its pieces, with the pieces adding up.

---

## The idea in plain language

[2.1](2.1-two-arrays-instead-of-one.md) described the layout: a **categorical** column is stored as
two things rather than one. The **categories** are the distinct values, each written down once. The
**codes** are one small whole number per row, saying which of the categories that row holds.

This part turns that description into a measurement, and there are only three quantities in it.

**The codes cost one byte per row**, as long as there are fewer than a hundred and twenty-seven
distinct values. One byte, whatever the words are: `dry goods` and `d` cost the same.
[2.3](2.3-the-code-width-and-where-the-saving-stops.md) is about what happens when that stops being
true.

**The categories cost whatever the distinct values cost, once**, and that does not change when the
table gets longer. A year of shopping and a decade of shopping have the same three aisles.

**The index costs whatever it costs** — a hundred and thirty-two bytes on a frame with default row
labels, because a `RangeIndex` stores a start, a stop and a step rather than the row numbers
themselves ([1.2](../01-the-repeated-word/1.2-what-memory-usage-actually-counts.md)).

So a categorical column costs `rows × 1` plus a small constant. The same column as text costs
`rows × (average word length + 8)`, because the PyArrow layout stores the characters end to end and
an eight-byte offset per row saying where each value starts
([1.1](../01-the-repeated-word/1.1-the-same-short-word-over-and-over.md)). Both are `rows ×`
something. **The conversion does not change the shape of the arithmetic; it changes the number you
multiply by**, and the ratio between those two numbers is the saving. It is the same ratio at
twenty-four thousand rows and at two million four hundred thousand, which is what makes it safe to
extrapolate.

One term needs defining before the code. `astype` is the method that returns **a new object with a
different dtype**
([Day 20, 2.4](../../../day-20-arrays-and-dtypes/parts/02-dtypes/2.4-astype-and-the-copy.md)). It
never changes the thing you called it on, and that is the single most common reason a conversion
appears not to have worked — see *When it breaks*.

## The mechanism

Start from the year file [1.1](../01-the-repeated-word/1.1-the-same-short-word-over-and-over.md)
built, and convert one column.

```python
import numpy as np
import pandas as pd

ITEMS = ["milk", "bread", "eggs", "rice"]
AISLES = ["bakery", "dairy", "dry goods"]
SIZES = ["small", "medium", "large"]


def a_year(n: int = 240_000) -> pd.DataFrame:
    """A year of the flat's shopping: the same few words, over and over."""
    rng = np.random.default_rng(34)
    return pd.DataFrame(
        {
            "item": pd.Series(rng.choice(ITEMS, n), dtype="str"),
            "aisle": pd.Series(rng.choice(AISLES, n), dtype="str"),
            "size": pd.Series(rng.choice(SIZES, n), dtype="str"),
            "price": np.round(rng.uniform(0.40, 6.00, n), 2),
        }
    )


year = a_year()
smaller = year.astype({"aisle": "category"})
before = year.memory_usage(deep=True)["aisle"]
after = smaller.memory_usage(deep=True)["aisle"]
print("dtype before :", year["aisle"].dtype)
print("dtype after  :", smaller["aisle"].dtype)
print("bytes before :", before)
print("bytes after  :", after)
print("saved        :", before - after)
print("ratio        :", round(before / after, 1))
print()
print("whole frame before:", year.memory_usage(deep=True).sum())
print("whole frame after :", smaller.memory_usage(deep=True).sum())
```

**Line by line:**

- `a_year` is repeated in full rather than imported, because a part has to be readable on its own.
  The seed is `np.random.default_rng(34)`, the day number, and **the draws happen in the order the
  columns are written** — move a column and every column after it changes
  ([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)).
- `year.astype({"aisle": "category"})` with a **dictionary**, naming the one column. A bare
  `year.astype("category")` would convert every column in the frame including `price`, which is a
  different and worse idea — *When it breaks* shows what that costs.
- `smaller` is a new frame, and `year` still holds the text version. That is the only reason the
  before and the after can be printed side by side in one script.
- `memory_usage(deep=True)["aisle"]` — the frame's per-column report, indexed by column name.
  `deep=True` makes no difference to either of these two dtypes, and is written anyway because the
  default is the one that lies
  ([1.2](../01-the-repeated-word/1.2-what-memory-usage-actually-counts.md)).
- `round(before / after, 1)` — the ratio, which is the number worth remembering. The absolute saving
  depends on how big your file happens to be; the ratio does not.

```text
dtype before : str
dtype after  : category
bytes before : 3520412
bytes after  : 240045
saved        : 3280367
ratio        : 14.7

whole frame before: 11580375
whole frame after : 8300008
```

**Three and a quarter million bytes gone, from one line of code on one column.** The whole frame
dropped from 11.6 MB to 8.3 MB, and it did not drop by the same factor because three of its four
columns were left alone.

Now pull `240045` apart. This is the step that turns the saving from a claim into arithmetic:

```python
aisle = a_year()["aisle"].astype("category")
codes = aisle.cat.codes.to_numpy()
category_bytes = aisle.cat.categories.memory_usage(deep=True)
index_bytes = aisle.index.memory_usage(deep=True)

print("rows            :", len(aisle))
print("codes dtype     :", codes.dtype)
print("codes bytes     :", codes.nbytes)
print("categories      :", aisle.cat.categories.tolist())
print("category bytes  :", category_bytes)
print("index bytes     :", index_bytes)
print("the three added :", codes.nbytes + category_bytes + index_bytes)
print("reported        :", aisle.memory_usage(deep=True))
```

**Line by line:**

- `a_year()["aisle"]` selects the column as a Series, so this measurement includes the index. The
  frame reported `240045` and the Series will report `240177`; the difference is the 132-byte index,
  which the frame lists on its own row instead
  ([1.2](../01-the-repeated-word/1.2-what-memory-usage-actually-counts.md)).
- `.cat.codes.to_numpy().nbytes` — `nbytes` is NumPy's own size for the block, so this is the codes
  array measured with pandas out of the way
  ([Day 20, 1.2](../../../day-20-arrays-and-dtypes/parts/01-the-block/1.2-shape-dtype-and-the-rest.md)).
- `.cat.categories.memory_usage(deep=True)` — the categories are an `Index`, and an Index answers
  the memory question the same way a Series does.
- The three are added by hand rather than trusted. **If the sum does not match the reported figure,
  something is stored that this part has not accounted for**, which is exactly the gap worth finding
  before you build a memory budget on it.

```text
rows            : 240000
codes dtype     : int8
codes bytes     : 240000
categories      : ['bakery', 'dairy', 'dry goods']
category bytes  : 45
index bytes     : 132
the three added : 240177
reported        : 240177
```

**Exact.** 240 000 + 45 + 132, and nothing else in there.

The `45` is worth one more look, because it is the whole of the text in this column. `bakery`,
`dairy` and `dry goods` are twenty characters. Each value also carries an eight-byte offset, which
is twenty-four more. And there is one extra byte, because PyArrow keeps a **validity bitmap** — one
bit per value saying whether it is present, rounded up to a whole byte. Twenty plus twenty-four plus
one is forty-five, and the bitmap does not reach two bytes until the ninth category.

Doing all three text columns at once shows the shape of a real conversion:

```python
converted = year.astype({"item": "category", "aisle": "category", "size": "category"})
was = year.memory_usage(deep=True)
now = converted.memory_usage(deep=True)
for name in ["item", "aisle", "size", "price"]:
    print(f"{name:6s} {was[name]:>9d} -> {now[name]:>9d}   {was[name] / now[name]:6.1f}x")
print(f"{'TOTAL':6s} {was.sum():>9d} -> {now.sum():>9d}   {was.sum() / now.sum():6.1f}x")
```

**Line by line:**

- One `astype` call with three entries, not three calls. Each `astype` builds a whole new frame, so
  three calls make two frames nobody wanted.
- `price` is in the loop **without being converted**, so its row is the control. A row that does not
  move is how you know the other rows moved for the reason you think.
- `was.sum()` and `now.sum()` include the `Index` row, which at 132 bytes against eleven megabytes
  does not matter here. On a frame with a real string index it would.

```text
item     2939937 ->    240050     12.2x
aisle    3520412 ->    240045     14.7x
size     3199894 ->    240041     13.3x
price    1920000 ->   1920000      1.0x
TOTAL   11580375 ->   2640268      4.4x
```

**The three columns each shrank by about thirteen times; the frame shrank by four and a half.** That
gap is the honest headline. `price` did not move, and it is now 73% of what is left. **Once the
repeated words are fixed, the frame is mostly numbers**, and no dtype trick makes a float64 smaller
without throwing away precision.

Now the extrapolation, which is the part people get wrong by hand-waving:

```python
def aisle_column(n: int) -> pd.Series:
    """Just the aisle column, at whatever size, from the same seed."""
    rng = np.random.default_rng(34)
    return pd.Series(rng.choice(AISLES, n), dtype="str")


for n in [24_000, 240_000, 2_400_000]:
    plain = aisle_column(n)
    small = plain.astype("category")
    text_rate = plain.memory_usage(deep=True) / n
    code_rate = small.memory_usage(deep=True) / n
    print(f"{n:>9d} rows   str {text_rate:6.3f} b/row   category {code_rate:6.3f} b/row")

print()
plain = aisle_column(240_000)
layouts = [
    ("object", plain.astype("object")),
    ("str", plain),
    ("category", plain.astype("category")),
]
for label, column in layouts:
    rate = column.memory_usage(deep=True) / 240_000
    print(f"{label:9s} {rate:6.2f} bytes a row   {rate * 100_000_000 / 1e9:6.3f} GB at 100M rows")
```

**Line by line:**

- `aisle_column` builds only the one column, so its numbers differ slightly from `a_year()`'s. That
  is not noise — **the seed pins the result only when the code around it is identical**
  ([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)).
- Three sizes an order of magnitude apart, and each one divided by `n`. One measurement is a number;
  three at different sizes are a **rate**, and only a rate can be extrapolated.
- `astype("object")` in the second loop deliberately rebuilds the pandas-2 layout: one pointer per
  row, one separate Python string object behind each pointer
  ([Day 26, 2.1](../../../day-26-frames-and-copy-on-write/parts/02-the-str-dtype/2.1-text-used-to-be-object.md)).
- `rate * 100_000_000` — one hundred million rows, stated as a multiplication rather than assumed.
  **The assumption is that the rate holds**, which the first loop is the evidence for, and which is
  only true while the number of distinct values stays at three.
- `/ 1e9` to give gigabytes. Ten to the ninth, not two to the thirtieth — say which you mean, since
  the two differ by 7%.

```text
    24000 rows   str 14.662 b/row   category  1.007 b/row
   240000 rows   str 14.669 b/row   category  1.001 b/row
  2400000 rows   str 14.667 b/row   category  1.000 b/row

object     55.67 bytes a row    5.567 GB at 100M rows
str        14.67 bytes a row    1.467 GB at 100M rows
category    1.00 bytes a row    0.100 GB at 100M rows
```

**Both rates are flat across a hundredfold change in size.** The text rate is the average word length
of 6.67 plus the eight-byte offset. The category rate is one byte a row, converging on it from above
as the fixed 177 bytes get diluted.

The plan's headline for `PD-13` is *8 GB down to 300 MB on one column*, a ratio of about
twenty-seven. **The measurement here brackets it rather than reproducing it**, and that is the
honest answer: against the old `object` layout the ratio is 55.7, against the modern `str` layout it
is 14.7, and twenty-seven sits between them. Which one you get depends on the dtype you started from
and on how long the words are, since every extra character adds one to the text rate and nothing to
the category rate.

## When it breaks

The conversion that was thrown away:

```text
$ uv run python -c "
import numpy as np
import pandas as pd
rng = np.random.default_rng(34)
year = pd.DataFrame({'aisle': pd.Series(rng.choice(['bakery', 'dairy', 'dry goods'], 240_000), dtype='str')})
year['aisle'].astype('category')
print('after the astype line  :', year['aisle'].dtype, year.memory_usage(deep=True)['aisle'])
year['aisle'] = year['aisle'].astype('category')
print('after assigning it back:', year['aisle'].dtype, year.memory_usage(deep=True)['aisle'])
"
```

```text
after the astype line  : str 3520340
after assigning it back: category 240045
```

**What it means.** Nothing raised, nothing warned, and the first line did nothing at all. `astype`
returns a new Series and pandas 3.0 never changes an object in place from an expression like that
([Day 26, 3.1](../../../day-26-frames-and-copy-on-write/parts/03-copy-on-write/3.1-every-result-behaves-like-a-copy.md)).
The result was built, measured by nobody, and thrown away.

This is the most common way a memory fix appears not to work, and the tell is that the number did not
move **at all**. The smallest fix is the assignment, and the habit that prevents it entirely is
`frame.astype({...})` returning a frame you name. The `3520340` here is also not the `3520412` from
the mechanism, because this script builds one column and `a_year` builds four.

The conversion applied to everything:

**What it means.** `astype("category")` will happily convert a float column, and here it even made
it smaller — 484 620 bytes against 1 920 132, because a year of prices rounded to the penny only has
561 distinct values. **The bytes went down and the column stopped being a number.** A bare
`frame.astype("category")` looks like a memory optimisation and is actually a schema change, and the
failure surfaces somewhere else entirely: in the `describe()` that no longer reports a mean
([5.1](../05-describe/5.1-eight-numbers-for-a-column.md)), or in a model that receives 561 labels
where it expected a price. **Convert the columns you named, never the frame.**

One last one worth recognising on sight: the dtype is spelled `category`, singular. Writing
`astype("categorical")` ends in `TypeError: data type 'categorical' not understood`, raised by
NumPy rather than pandas, because pandas hands any string it does not recognise to `np.dtype` as a
last resort. That is why the message talks about a data type and never mentions categories.

## In production

**What a professional writes instead of the teaching version.** Not a `print` of a before and after.
The conversion and the evidence for it belong in one function that returns a frame you can assert
on:

```python
import pandas as pd


def categorise(frame: pd.DataFrame, columns: list[str]) -> tuple[pd.DataFrame, pd.DataFrame]:
    """Convert the named columns to `category`, and return the frame with a per-column saving."""
    missing = sorted(set(columns) - set(frame.columns))
    if missing:
        raise KeyError(f"columns not in the frame: {missing}")
    before = frame.memory_usage(index=False, deep=True)
    converted = frame.astype(dict.fromkeys(columns, "category"))
    after = converted.memory_usage(index=False, deep=True)
    report = pd.DataFrame(
        {
            "dtype": converted.dtypes.astype("str"),
            "bytes_before": before,
            "bytes_after": after,
            "ratio": (before / after).round(2),
        }
    ).rename_axis("column")
    return converted, report
```

**Line by line:**

- It returns **both** the frame and the report. A conversion whose saving nobody recorded is one
  nobody can defend in a review, and a report printed to standard output is one nobody can test.
- `missing` is checked first and raises `KeyError` with a sorted list. `astype` on an absent column
  raises its own error much later inside pandas, with a message that names the dtype rather than the
  caller's mistake. Sorting makes the message identical every run, so a test can match on it
  ([Day 18, 3.3](../../../day-18-exceptions/parts/03-your-own/3.3-the-message-is-an-interface.md)).
- `dict.fromkeys(columns, "category")` builds `{"item": "category", "aisle": "category", ...}` from
  the list. It is the dictionary form of `astype`, which is the form that converts only what it was
  asked to.
- `index=False` on both measurements, so the index does not appear as a phantom column in a
  per-column table.
- `converted.dtypes.astype("str")` — `dtypes` is a Series of dtype *objects*, and putting those
  straight into a frame gives a column that prints fine and compares strangely
  ([Day 26, 2.4](../../../day-26-frames-and-copy-on-write/parts/02-the-str-dtype/2.4-dtypes-equals-object-finds-nothing.md)).
- `ratio` rather than `saved`. The absolute saving is a property of this file's size; the ratio is a
  property of the data, and it is the one that still means something next quarter.

**What changes at scale.** The teaching version converts after the read, so the wide `str` column
existed in memory first — the memory you were trying not to spend, plus a full pass to find the
distinct values and sort them. At a hundred million rows that peak is what kills the job, not the
steady state. Convert at the boundary instead:
`pd.read_csv(path, dtype={"aisle": "category"})` builds the categorical column directly
([Day 27, 1.4](../../../day-27-reading-and-writing/parts/01-the-csv/1.4-dtype-at-read-time.md)), and
Parquet's dictionary encoding hands pandas one without a conversion at all
([Day 27, 3.1](../../../day-27-reading-and-writing/parts/03-parquet/3.1-columns-on-disk-with-types.md)).
On the year file the two routes land within a few hundred bytes of each other — 2 640 656 read as
categories against 2 640 268 converted afterwards — so the only reason to choose is the peak.

**The failure that only appears with real data.** A nightly job converted six text columns on read
and its memory graph flattened beautifully. Two months later it began failing on one input file. The
column was a free-text `note` field that had been empty until an upstream release started populating
it, at which point `astype("category")` built a category list of several million distinct strings and
the "optimised" column became larger than the text one. **Nothing about the code changed; the
cardinality did.** That is [2.3](2.3-the-code-width-and-where-the-saving-stops.md), and it is why a
conversion belongs behind a guard rather than in a list of column names.

**The review comment a senior engineer leaves.** *"The 4.4× on the frame is the number to put in the
description, not the 14.7× on the column — `price` is 73% of what is left and no dtype change
touches it. Also, `astype` here runs after the read, so the peak is unchanged; move it into the
`read_csv` call and measure again."*

**The interview question.** *"You convert a text column to categorical. How much do you save, and
how would you know?"* The answer is a rate, not a factor: text costs the average value length plus
an eight-byte offset per row, a categorical costs one byte per row while there are fewer than a
hundred and twenty-seven distinct values, plus the distinct values once. For the aisle column that
is 14.67 bytes a row against 1.00. The follow-up that separates people who have done it from people
who have read about it: **the frame does not shrink by 14.7×** — it shrank by 4.4×, because the
numeric columns were already efficient and are now most of what is left.
