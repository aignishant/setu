# 5.3 — `tests/test_select.py` — asserting a promise you cannot see

## One-line answer

Every claim in this module is invisible in the returned values — view or copy, whose data changed,
what the filter rejected — so each one needs an assertion that fails loudly when it stops being true.

---

## The story

A landlord and a tenant walk round a flat before the tenant moves in.

They do not simply look at it. They write things down: a mark on the kitchen wall, a scratch on the
worktop, the reading on the electricity meter. It takes twenty minutes and neither of them enjoys it.

A year later the tenant moves out and there is a disagreement about the scratch. The list settles it
in seconds, because the scratch was written down at a moment when nobody had any reason to lie about
it.

The thing worth noticing is which items are on that list. Nobody writes down "the flat has a floor".
They write down the things that will be **invisible later** and that somebody will later have an
opinion about. The list is not a description of the flat; it is a record of exactly the facts that
would otherwise be arguable.

---

## The idea in plain language

You met tests on [Day 2, 3.1](../../../day-02-quality-gate/parts/03-pytest/3.1-the-test-that-can-go-red.md),
and Principle 7 has been asking every day since for at least one test that can go red. This day's
tests are unusual in what they check.

Most tests assert values: this function returns 8946. Some of today's do that. But the module's
important promises are not about values at all:

- `week` returns something that **shares memory** with the month.
- `week` returns something that **cannot be written to**.
- `week_copy` returns something that shares **nothing**.
- `fill_missing` **does not change** the array it was given.
- `select_usable`'s three counts **add up** to the number of days it looked at.
- `tally_visits` counts **every** visit, including the repeats.

Print the results of all six and they look identical to a broken version of the same module. That is
what makes them worth asserting: a promise nobody can see is a promise that will be broken by an
innocent-looking edit six months from now, and nothing will notice.

Three tools do all the work.

**`np.shares_memory(a, b)`** turns "is this a view" into a boolean
([2.2](../02-the-view-trap/2.2-how-to-tell-base-and-shares-memory.md)). It is the only honest way to
assert the view-or-copy promise, because shapes and values cannot tell you.

**A `before` copy** turns "did this function change my array" into a comparison. Copy the input,
call the function, and assert the input still equals the copy.

**`pytest.raises(..., match=...)`** asserts that a refusal happens **and** that it is the refusal you
meant ([Day 18, 4.4](../../../day-18-exceptions/parts/04-in-anger/4.4-pytest-raises.md)). A bare
`pytest.raises(ValueError)` passes when the function raises for a completely different reason,
including a typo in the test itself.

One more idea, and it is the one that makes the difference between a test suite and a decoration.
**A test you have never seen fail is not yet a test.** After the suite is green, break the module on
purpose — remove one line — and watch which tests go red. If none do, the assertion was never wired
to the behaviour it claims to check.

## Why Setu needs it

- **Day 25's phase gate** is a measured claim about speed, and a measurement with no test can drift
  without anyone noticing.
- **Day 44's pipelines** break in exactly the way `test_fill_missing_leaves_the_caller_alone` checks
  for, and that test is the one that survives into every project after this one.
- **Day 91's leakage rule** is enforced by a test that asserts the train and test arrays do not share
  memory — the same `np.shares_memory` assertion, doing far more important work.
- **Day 172's eval harness** is this idea at scale: the things worth asserting are the ones that do
  not show up in the output.
- **Day 226's review** asks which of your tests have ever failed, and "all of them, on purpose, once"
  is the answer that ends the conversation.

## The mechanism

The whole suite. It is long because the module makes several promises, and short per promise.

```python
"""Day 21's eval: every promise the selection module makes, asserted."""

from __future__ import annotations

import numpy as np
import pytest

from setu.select import (
    MISSING,
    fill_missing,
    select_usable,
    tally_visits,
    usable,
    week,
    week_copy,
)

MONTH = np.array(
    [
        [8213, 10442, 6180, MISSING, 12007, 9631, 7204],
        [7788, 9120, 11345, 8402, 6733, 14210, 5096],
        [9004, 8765, 7621, 10188, 9950, 8317, 11002],
        [6540, 12488, 9873, 7106, 8899, 10540, 9218],
    ]
)


@pytest.fixture
def month() -> np.ndarray:
    return MONTH.copy()
```

**Line by line:**

- `from setu.select import MISSING, ...` — importing the sentinel rather than typing `-1` in the
  fixture. If the module's convention changes, the tests follow it instead of silently testing the old
  one.
- `MONTH` at module level, then `MONTH.copy()` in the fixture — **the fixture is the important part.**
  Several of these tests write to the month, and a shared module-level array would carry those writes
  into every later test in whatever order pytest happened to run them.
- `@pytest.fixture` — pytest calls this function for each test that names `month` as a parameter
  ([Day 2, 3.2](../../../day-02-quality-gate/parts/03-pytest/3.2-fixtures-and-tmp-path.md)), so every
  test gets a fresh copy.
- `-> np.ndarray` on the fixture — the type hint is for the reader and the checker; pytest ignores it.

The two promises that values cannot show:

```python
def test_week_is_a_view_and_cannot_be_written_to(month):
    peek = week(month, 0)
    assert np.shares_memory(month, peek)
    assert peek.flags.writeable is False
    with pytest.raises(ValueError, match="read-only"):
        peek[0] = 1


def test_week_copy_is_detached(month):
    kept = week_copy(month, 0)
    assert not np.shares_memory(month, kept)
    assert kept.base is None
    kept[0] = 1
    assert month[0, 0] == 8213
```

**Line by line:**

- `np.shares_memory(month, peek)` — the view promise, asserted directly. Nothing about `peek`'s values
  or shape would have told you.
- `peek.flags.writeable is False` — `is False`, not `== False` or `not peek.flags.writeable`. The flag
  is a genuine `bool`, and `is` says so; the loose forms would also pass for `0` or an empty array.
- `pytest.raises(ValueError, match="read-only")` — asserting the **behaviour** as well as the flag. The
  flag is how it is implemented; the raise is what a caller experiences, and testing both means a
  future change of mechanism still has to keep the promise.
- `kept.base is None` **and** `not np.shares_memory(...)` — two different questions
  ([4.3](../04-fancy-indexing/4.3-fancy-indexing-always-copies.md)), and `week_copy` promises both. A
  copy that had a base pointing at a temporary would pass the second and fail the first.
- `kept[0] = 1` then `month[0, 0] == 8213` — the detachment, demonstrated rather than inferred. **This
  is the assertion that would catch a future `week_copy` that quietly stopped copying.**

The promise about the caller's data:

```python
def test_fill_missing_leaves_the_caller_alone(month):
    before = month[0].copy()
    filled = fill_missing(month[0])
    assert np.array_equal(month[0], before)
    assert filled[3] == 8946
    assert not np.shares_memory(month, filled)


def test_fill_missing_with_out_writes_in_place(month):
    row = month[0]
    returned = fill_missing(row, out=row)
    assert returned is row
    assert month[0, 3] == 8946


def test_fill_missing_refuses_when_nothing_is_usable():
    with pytest.raises(ValueError, match="no usable days"):
        fill_missing(np.array([MISSING, MISSING]))
```

**Line by line:**

- `before = month[0].copy()` — the landlord's list. Without the `.copy()` this would be a view of the
  row, so it would change alongside it and the assertion would pass no matter what the function did.
  **That is the single most common way this test is written wrong.**
- `np.array_equal(month[0], before)` — element-by-element comparison returning one bool, rather than
  `==`, which returns a mask and cannot be asserted directly
  ([3.3](../03-boolean-masks/3.3-and-or-not-and-why-and-raises.md)).
- `filled[3] == 8946` — the value promise, and the only place in these tests where a number is
  checked. Integers compare exactly; a float mean would need
  `np.testing.assert_allclose` with a stated tolerance.
- `returned is row` — identity, not equality
  ([Day 4, 3.2](../../../day-04-objects/parts/03-identity-trap/3.2-is-versus-equals.md)). `out=` promises
  to write into the array you supplied and hand the same object back, and `==` would pass for a copy
  holding equal values.
- `pytest.raises(ValueError, match="no usable days")` — `match` is a regular expression searched
  against the message. Without it, this test would also pass if `fill_missing` raised a `ValueError`
  about shapes, which is a different bug wearing the same exception class.

The promises about counting:

```python
def test_the_three_categories_cover_every_day(month):
    selection = select_usable(month[0])
    assert selection.total_seen == month[0].size
    assert (selection.kept, selection.missing, selection.out_of_range) == (6, 1, 0)


def test_out_of_range_is_counted_separately():
    counts = np.array([50, 8213, 99_999, MISSING])
    selection = select_usable(counts)
    assert (selection.kept, selection.missing, selection.out_of_range) == (1, 1, 2)
    assert selection.total_seen == counts.size


def test_tally_counts_repeats():
    visits = np.array([0, 0, 0, 3, 3, 6])
    counted = tally_visits(visits, 7)
    assert counted.sum() == visits.size
    assert counted.tolist() == [3, 0, 0, 2, 0, 0, 1]
```

**Line by line:**

- `selection.total_seen == month[0].size` — **the invariant.** It says the three categories are a
  partition: every day is counted once and no day is counted twice. It would catch the `~keep` bug
  from [5.2](5.2-view-or-copy-on-purpose.md), where a missing day is also counted as out of range.
- `(kept, missing, out_of_range) == (6, 1, 0)` — the three numbers asserted as **one tuple**, so a
  failure message shows all three and you can see which one moved. Three separate asserts stop at the
  first.
- `counts = np.array([50, 8213, 99_999, MISSING])` — a fixture built for this test alone: one below the
  floor, one fine, one above the ceiling, one missing. **A test that needs a specific shape of data
  builds it rather than reusing the month.**
- `counted.sum() == visits.size` — the tally invariant, and the assertion that catches
  [4.4](../04-fancy-indexing/4.4-repeated-positions-and-the-lost-update.md)'s lost update. The buffered
  version would give a sum of 3 against a size of 6.
- `counted.tolist() == [...]` — comparing as a Python list rather than with `==` on the arrays, so the
  assertion produces a boolean and a readable failure message.
- `usable`'s own test asserts `mask.dtype == np.bool_` — that the function returns a **mask** and not
  values, which is the difference between something you can combine and something you can only read.

## When it breaks

**Break it on purpose, which is the point of the exercise.** Remove the two lines in `week` that make
the view read-only, so it returns `month[index]` directly:


**What it means.** One line removed, one test red, and pytest printed the whole flags block so you can
see `WRITEABLE : True` where the promise said `False`. Notice what did **not** fail: the values are
identical, `shares_memory` is still `True`, and every other test passes. Without this assertion the
change would have gone in, and the first symptom would have been somebody's month quietly changing
three modules away.

**The test that cannot fail:**

```text
$ uv run python -c "
import numpy as np


def bad_test(month):
    before = month[0]
    month[0, 0] = -999
    assert np.array_equal(month[0], before), 'the array changed!'
    print('passed, and the array definitely changed')


bad_test(np.arange(28).reshape(4, 7))
"
passed, and the array definitely changed
```

**What it means.** `before = month[0]` is a view, so it changed alongside the array it was supposed to
be a record of ([2.1](../02-the-view-trap/2.1-a-slice-does-not-copy.md)). The assertion compares the
array with itself and can never fail. This is today's view trap appearing inside the test that exists
to catch today's view trap, and it is much commoner than it sounds — **`before` is always a `.copy()`**.

**The `raises` that caught the wrong thing:**

```text
$ uv run python -c "
import numpy as np
import pytest


def test_refuses_bad_input():
    with pytest.raises(ValueError):
        np.array([1, 2, 3]).reshape(2, 5)
    print('passed - but on which ValueError?')


test_refuses_bad_input()
" 2>&1 | tail -2
passed - but on which ValueError?
```

**What it means.** The test intended to check that *our* validation rejects something, and it passed
because NumPy raised a `ValueError` about reshaping instead. Every `pytest.raises` in this suite has a
`match=`, and the pattern is chosen from **our** message rather than from a library's, so the
assertion is about our behaviour ([Day 18, 3.3](../../../day-18-exceptions/parts/03-your-own/3.3-the-message-is-an-interface.md)).

## In production

**What a professional writes instead of the teaching version.** They add a property test for the
invariant, so the partition is checked on data nobody thought of:

```python
import numpy as np
import pytest

from setu.select import MISSING, select_usable, tally_visits


@pytest.mark.parametrize("seed", range(20))
def test_categories_partition_any_input(seed):
    rng = np.random.default_rng(seed)
    counts = rng.integers(-1, 70_000, size=rng.integers(1, 50))
    selection = select_usable(counts)
    assert selection.total_seen == counts.size
    assert selection.values.size == selection.kept
    assert not np.shares_memory(counts, selection.values)


@pytest.mark.parametrize("seed", range(20))
def test_tally_never_loses_a_visit(seed):
    rng = np.random.default_rng(seed)
    members = int(rng.integers(1, 12))
    visits = rng.integers(0, members, size=rng.integers(0, 200))
    counted = tally_visits(visits, members)
    assert counted.sum() == visits.size
    assert counted.size == members
```

**Line by line:**

- `@pytest.mark.parametrize("seed", range(20))` — twenty runs, each a separate test with its own name,
  so a failure names the seed that produced it
  ([Day 2, 3.3](../../../day-02-quality-gate/parts/03-pytest/3.3-markers-and-exit-code-five.md)).
- `np.random.default_rng(seed)` — **seeded**, so a failure is reproducible. Random test data with an
  unrecorded seed is a test that fails once and can never be debugged
  ([Day 20, 4.2](../../../day-20-arrays-and-dtypes/parts/04-random/4.2-the-seed-is-part-of-the-result.md)).
- `rng.integers(-1, 70_000, size=rng.integers(1, 50))` — a random length as well as random values, so
  the one-element and near-empty cases turn up on their own. The range straddles both thresholds and
  the sentinel.
- `selection.values.size == selection.kept` — the record's array and its count must agree. It is the
  kind of thing that is obviously true when written and quietly stops being true when someone adds a
  filter.
- `visits = rng.integers(0, members, size=rng.integers(0, 200))` — a size that can be **zero**, so the
  empty case is covered without a test written specially for it
  ([3.5](../03-boolean-masks/3.5-the-mask-that-matched-nothing.md)).
- Both tests assert an **invariant** rather than a value: the counts partition the input, and the
  tally conserves visits. Invariants survive changes to the code that values do not.

**What changes at scale.** Test data grows and the useful assertions stay the same shape. Two habits
carry over. First, the invariant tests move to a property-based tool that generates awkward inputs
deliberately rather than randomly, and the seeded parametrize above is the cheap version of that.
Second, the memory promises become the important ones: on a 4 GB array, `np.shares_memory` in a test
is the only practical way to assert that a pipeline stage did not silently start copying, and a
regression there is a production incident rather than a slowdown. On very large arrays,
`np.shares_memory` can take a long time deciding, so tests use `max_work=np.inf` deliberately or run
on a small fixture with the same code path.

**The failure that only appears with real data.** A suite tested a filter on a fixture where every
row passed. The filter's empty-selection branch was never executed by any test, and it contained a
`nan`. It ran for eight months before a customer with no qualifying rows arrived. The fix was one
parametrized case with an input that matches nothing — and the general lesson is that **the branch
your fixture never takes is the branch that fails in production**.

**The review comment a senior engineer leaves.** *"`assert np.array_equal(result, expected)` on
floats will fail on somebody else's machine; use `np.testing.assert_allclose` with a stated `rtol`.
And `before = arr[0]` in the mutation test is a view, so that assertion can never fail — it needs a
`.copy()`."*

**The interview question.** *"How do you test that a function does not modify its input?"* Copy the
input first, call the function, then assert the input still equals the copy — and the copy has to be
a real `.copy()`, because in NumPy `before = arr[0]` is a view that changes along with the array and
makes the assertion vacuous. For the related promise, that a returned array is genuinely detached,
`np.shares_memory(original, result)` is the assertion, since shapes and values cannot distinguish a
view from a copy. The answer that shows real practice is the last step: break the function on purpose
and confirm the test goes red, because an assertion that has never failed has not been shown to be
connected to anything.
