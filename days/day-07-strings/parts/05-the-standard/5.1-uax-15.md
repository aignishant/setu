# 5.1 — The annex that decides when two strings are the same: *UAX #15*

## One-line answer

*Unicode Standard Annex #15* defines the four normalization forms — NFC, NFD, NFKC, NFKD — that give
**equivalent text a single binary representation**, which is the only reason a program can decide
that two strings which look identical on screen actually are identical; and its most important
practical rule is that two of those four forms destroy information on purpose.

---

## The citation

| Field | Value |
|---|---|
| **Title** | *"Unicode Standard Annex #15: Unicode Normalization Forms"* |
| **Version cited** | Revision 57, dated 2025-07-30 |
| **Identifier** | `UAX #15` (an annex is a normative part of the Unicode Standard, not a separate paper) |
| **Canonical URL** | <https://www.unicode.org/reports/tr15/> — fetched 2026-08-25 |
| **Implemented in this repo by** | `unicodedata`, whose table version is reported by `unicodedata.unidata_version` |

The annex's own summary, verbatim:

> "This annex describes normalization forms for Unicode text. When implementations keep strings in a
> normalized form, they can be assured that equivalent strings have a unique binary representation."

**What to actually read.** The **Introduction** and the table of the four forms — that is perhaps a
page and it is most of what a working engineer needs. Then, if you ever store user-supplied text,
read the section on the **Normalization Stability Policy**, because it explains why a guarantee made
decades ago can never be revised and why that is a feature.

---

## The story

A support ticket says a user cannot log in. The username is right there in the database, character
for character identical to what they typed. The lookup returns nothing.

The user's name contains an *é*. Their laptop produced it as a single character — `U+00E9`, LATIN
SMALL LETTER E WITH ACUTE. The web form on their phone produced it as **two** characters: a plain
`e` followed by `U+0301`, COMBINING ACUTE ACCENT, which the renderer draws on top of the `e`. On
screen, both are `é`. There is no font, no colour, no spacing difference. They are simply different
byte sequences that a human is incapable of telling apart.

Every layer of the stack behaves correctly. The database compares bytes and finds no match. The form
submitted exactly what the keyboard produced. The user typed their own name. And no amount of
`.strip()`, `.lower()` or "sanitising input" will fix it, because nothing is dirty — there are two
legitimate spellings of the same text, and both are correct.

The annex exists to make that decidable. It defines a canonical form and a procedure for reaching it,
so a program can ask *are these the same text?* and get a defensible answer instead of a byte
comparison that happens to be wrong.

---

## The idea in plain language

Two definitions do all the work, and the difference between them is the whole subject.

**Canonical equivalence** means two sequences represent *the same characters* — they should always
look and behave identically. `é` as one code point and `e` + combining acute are canonically
equivalent. Any conforming process may substitute one for the other, at any time, without asking.

**Compatibility equivalence** is weaker: two sequences that mean the same thing but *differ in
appearance or formatting*. The ligature `ﬁ` and the two letters `fi` are compatibility-equivalent.
So are `①` and `1`, and the superscript `²` and `2`. Replacing one with the other **loses
information** — visual, semantic, or both.

From those two relations, four normalization forms:

| Form | What it does | Reversible? |
|---|---|---|
| **NFD** | Canonical **D**ecomposition — split everything into base + marks | yes |
| **NFC** | Canonical Decomposition, then canonical **C**omposition — recombine | yes |
| **NFKD** | Compatibility (**K**) Decomposition | **no** |
| **NFKC** | Compatibility Decomposition, then canonical Composition | **no** |

The `K` is the letter to watch. `K` forms are *lossy*: `ﬁ` becomes `fi` and never comes back, `①`
becomes `1`, the micro sign `µ` becomes the Greek letter `μ`. That is not a bug — it is the declared
purpose, because those forms exist for *matching*, where you want a search for "file" to find "ﬁle".
Using a `K` form to "clean up" text you intend to store is how the meaning gets deleted.

**Why decompose before composing.** NFC is defined as decomposition *followed by* composition, which
sounds circular. It is not: decomposing first puts every combining mark into a canonical **order** —
sorted by combining class — so that `q` + dot-above + dot-below and `q` + dot-below + dot-above end
up as the same sequence before anything is recombined. Without that pass, two canonically equivalent
strings could compose into two different results, and the whole guarantee would fail.

**The guarantee is permanent.** The annex promises that a string normalized under one version of
Unicode stays normalized under every future version. To keep that promise the composition rules were
frozen at Unicode 3.1.0 and can never be changed. Your normalized data does not rot.

## The mechanism

NFD — the first and simplest form — is two passes, and the annex specifies both.

**Pass one: recursive canonical decomposition.** Replace each character by its canonical
decomposition, repeatedly, until nothing decomposes further. `unicodedata.decomposition` returns the
mapping as text, prefixed with a tag like `<compat>` when the mapping is a *compatibility* one — which
NFD must skip.

**Pass two: canonical ordering.** Every combining mark carries a *combining class*, a small integer.
Within each run of marks, sort them by that class — **stably**, so marks with equal class keep their
relative order, because for equal classes the order is meaningful.

```python
import unicodedata

print(unicodedata.decomposition("é"))       # e-acute
print(unicodedata.decomposition("ﬁ"))       # the fi ligature
print(unicodedata.combining("́"), unicodedata.combining("e"))
```

**Line by line:**

- `unicodedata.decomposition("é")` — that is `e`-acute — returns the string `'0065 0301'` — space-separated hex code points,
  as text, exactly as they appear in the Unicode Character Database. It is a *table lookup*, which is
  the point: normalization is data, not cleverness, and the data ships with Python.
- `unicodedata.decomposition("ﬁ")` — the `fi` ligature — returns `'<compat> 0066 0069'`. The `<compat>` tag is the whole
  distinction between canonical and compatibility equivalence, expressed as five characters in a data
  file. An implementation of NFD that forgets to check for `<` silently becomes NFKD and starts
  destroying ligatures.
- `unicodedata.combining("́")` returns `230`; `unicodedata.combining("e")` returns `0`. A class
  of zero means **starter** — a character that is not a combining mark. That test is what divides the
  string into runs in the code below.

Now the algorithm itself, from the annex:

```python
import unicodedata


def decompose(char: str) -> str:
    mapping = unicodedata.decomposition(char)
    if not mapping or mapping.startswith("<"):
        return char
    return "".join(decompose(chr(int(code, 16))) for code in mapping.split())


def canonical_order(text: str) -> str:
    out: list[str] = []
    run: list[str] = []
    for char in text:
        if unicodedata.combining(char):
            run.append(char)
        else:
            out.extend(sorted(run, key=unicodedata.combining))
            run = []
            out.append(char)
    out.extend(sorted(run, key=unicodedata.combining))
    return "".join(out)
```

**Line by line:**

- `if not mapping or mapping.startswith("<")` — two exits in one condition: no decomposition at all,
  or a compatibility one. Both mean "leave this character alone" for NFD. Dropping the second half is
  the single most common bug in a hand-written normalizer, and it is invisible until a ligature
  appears in real data.
- `decompose(chr(int(code, 16)))` — **recursive**, because decompositions are not flat. A character
  can decompose into a character that itself decomposes; the annex requires you to keep going until
  nothing changes. A single non-recursive pass produces output that is *nearly* right, which is worse
  than obviously wrong.
- `int(code, 16)` — the table gives hex text, so base 16 must be stated. `int(code)` would raise on
  `'0301'`... quietly succeed, actually, and give the decimal 301, which is a different character
  entirely. Explicit base, always.
- `if unicodedata.combining(char):` — non-zero means a combining mark, so it joins the current run;
  zero means a starter, which ends the run. The annex's runs are exactly "a starter followed by the
  marks that attach to it".
- `sorted(run, key=unicodedata.combining)` — Python's sort is **stable**, which the annex requires:
  marks with equal combining class must keep their input order, because at equal class the order
  carries meaning. Using an unstable sort here would produce a valid-looking string that is not NFD.
- `out.extend(...)` after the loop — the final run, when a string ends with combining marks. Forget
  this line and the last accented character in every string is silently dropped; the test suite in
  the demo catches it because `"café"` ends exactly that way.

## The demo

One project, one feature: **NFD, implemented from the annex's algorithm, checked against CPython's
implementation of the same annex**. No composition, no compatibility forms, no case folding.

```text
nfd-from-scratch/
├── nfd.py        # recursive canonical decomposition + canonical ordering
└── test_nfd.py   # every case checked against unicodedata, the reference implementation
```

`nfd.py`, in full:

```python
"""UAX #15's canonical decomposition, implemented from the algorithm."""

import unicodedata


def decompose(char: str) -> str:
    """Recursively apply the canonical decomposition mapping. Compatibility mappings are skipped."""
    mapping = unicodedata.decomposition(char)
    if not mapping or mapping.startswith("<"):
        return char
    return "".join(decompose(chr(int(code, 16))) for code in mapping.split())


def canonical_order(text: str) -> str:
    """Sort each run of combining marks by combining class, stably (UAX #15, canonical ordering)."""
    out: list[str] = []
    run: list[str] = []
    for char in text:
        if unicodedata.combining(char):
            run.append(char)
        else:
            out.extend(sorted(run, key=unicodedata.combining))
            run = []
            out.append(char)
    out.extend(sorted(run, key=unicodedata.combining))
    return "".join(out)


def nfd(text: str) -> str:
    """Normalization Form D: decompose fully, then put the marks in canonical order."""
    return canonical_order("".join(decompose(char) for char in text))
```

**Line by line:** — `decompose` and `canonical_order` are the mechanism above; only what is new here
is walked through.

- `nfd(text)` composes the two passes in the annex's order and no other. Decompose *then* reorder:
  reordering first would sort marks that have not been produced yet, since a decomposition can emit
  new combining marks into the middle of the string.
- `"".join(decompose(char) for char in text)` — a generator rather than a list comprehension inside
  `join`, so nothing intermediate is materialised. On a document-sized string this is the difference
  between one pass and a second full copy.
- The function takes and returns `str`, never `bytes`. Normalization is defined over code points; a
  normalizer that accepted bytes would have to guess an encoding first, and guessing is how the
  original bug in the story happened.

`test_nfd.py`, in full:

```python
"""Checked against CPython's unicodedata, which implements the same annex."""

import unicodedata

import pytest
from nfd import nfd

SAMPLES = [
    "café",
    "café",
    "ẛ̣",
    "Amélie",
    "Ångström",
    "q̣̇",
]


@pytest.mark.parametrize("text", SAMPLES)
def test_agrees_with_cpython(text):
    assert nfd(text) == unicodedata.normalize("NFD", text)


def test_canonical_equivalence_is_the_point():
    composed, decomposed = "café", "café"
    assert composed != decomposed
    assert nfd(composed) == nfd(decomposed)


def test_marks_are_reordered_by_combining_class():
    assert nfd("q̣̇") == nfd("q̣̇")


def test_compatibility_mappings_are_not_canonical():
    assert nfd("ﬁ") == "ﬁ"
    assert unicodedata.normalize("NFKD", "ﬁ") == "fi"
```

**Line by line:**

- Every sample is written with **escapes**, never with literal accented characters. A test file whose
  meaning depends on its own encoding — and on your editor not "helpfully" normalising it on save —
  is a test that can pass or fail for reasons that have nothing to do with the code.
  `"café"` says precisely which five code points are meant, in any editor, forever.
- `"ẛ̣"` is the annex's own hard case: a character that decomposes recursively *and* has a
  following mark that must be reordered. It is in the list because the easy samples pass even with a
  single-pass implementation.
- `test_canonical_equivalence_is_the_point` asserts **both** directions: that the two strings are
  genuinely different first, then that normalization makes them equal. Without the first assertion,
  a normalizer that returned a constant would pass.
- `test_marks_are_reordered_by_combining_class` compares two *differently ordered* inputs to each
  other rather than to a literal. The claim is that canonical ordering is a canonical form — that it
  is the same for both — which is exactly what the annex promises and what a literal expected-value
  would state less clearly.
- `test_compatibility_mappings_are_not_canonical` is the guard on the `<` check. It asserts NFD leaves
  the ligature alone **and** that NFKD does not, so a regression that starts decomposing compatibility
  mappings turns this test red immediately.

$ uv run --with pytest python -X utf8 -m pytest -q

$ uv run python -X utf8 -c "

for s in ['café', 'café']:

Those first two lines are the story's bug, printed. Two strings that `repr` renders identically, one
of length 4 and one of length 5, converging on the same 5-character sequence. The screen could never
have told you; the annex can.

**What this demo deliberately leaves out.** Composition (the C in NFC), the compatibility forms, the
quick-check optimisation that lets a real implementation skip strings already in normal form, and —
most visibly — the **algorithmic Hangul decomposition**, which the standard specifies arithmetically
rather than in the decomposition table. That omission is not hidden; it is the failure below.

## When it breaks

Add one Korean syllable to the sample list and the demo's central claim fails:

```python
import unicodedata

from nfd import nfd

hangul = "가"  # one Korean syllable
print("table says:", repr(unicodedata.decomposition(hangul)))
print("mine   :", [hex(ord(c)) for c in nfd(hangul)])
print("cpython:", [hex(ord(c)) for c in unicodedata.normalize("NFD", hangul)])
```

```text
table says: ''
mine   : ['0xac00']
cpython: ['0x1100', '0x1161']
```

The decomposition table is **empty** for that character, so the implementation above correctly
concludes there is nothing to decompose — and is wrong. Hangul syllables are decomposed by an
*arithmetic* rule in the standard rather than by table lookup, because there are more than eleven
thousand of them and enumerating the mappings would bloat the database. A normalizer built by reading
only the table handles every Latin, Greek and Cyrillic case perfectly and silently mishandles an
entire writing system.

The second failure has no error message at all:

```python
import unicodedata

user_typed = "café"  # e + combining acute, from a phone keyboard
in_database = "café"  # a single code point, from a laptop
print(user_typed == in_database, len(user_typed), len(in_database))
print(unicodedata.normalize("NFC", user_typed) == in_database)
```

```text
False 5 4
True
```

No exception, no traceback, no log line — a lookup that returns nothing and a user who cannot sign
in. This is the class of bug that reaches production, because every test written by a developer typing
on one keyboard uses one spelling.

**The smallest fix:** normalize at the boundary. Every string entering the system gets
`unicodedata.normalize("NFC", s)` once, at the edge, before it is stored, hashed or compared — never
scattered through the code where half the call sites will forget. And for the Hangul case: use the
standard library's implementation rather than your own, which is exactly what
[4.2](../04-normalising/4.2-unicode-normalisation.md) told you to do.

## What did not survive

**The compatibility forms escaped their purpose.** NFKC and NFKD were designed for *matching* — build
a search key, compare it, throw it away. In practice they became a general-purpose "clean up weird
characters" tool, and applied to data being stored they quietly delete meaning: `①` becomes `1`, `²`
becomes `2`, the ligature `ﬁ` becomes `fi`, and mathematical alphanumerics collapse into plain
letters, which destroys formulas. Current practice is narrow and worth memorising: **NFC for
storage, a K form only for a comparison key you do not keep.**

**The composition rules had to be frozen, imperfections included.** To make the stability promise —
normalized text stays normalized forever — the composition version was fixed at Unicode 3.1.0. Every
composition decision made then is permanent, and characters added since can never gain a canonical
composition. The guarantee was worth the price, but it means the annex contains known-suboptimal
mappings that will never be corrected.

**Normalization did not turn out to be closed under concatenation.** Joining two NFC strings does not
always give an NFC string — a combining mark at the start of the second piece can need reordering
against the end of the first. Systems that normalize on input and assume everything downstream stays
normalized are relying on something the annex does not promise.

**And normalization never solved the problem people reach for it to solve.** Two strings that look
identical are not necessarily canonically equivalent: Latin `a` and Cyrillic `а` are *different
characters* that many fonts render identically, and no normalization form will ever merge them —
correctly, because they are different letters. That threat is the subject of a different document
(the confusables data of UTS #39), and the security failures that follow from confusing the two are
still shipping today. Meanwhile identifier handling moved on to `NFKC_Casefold` and, for usernames
and passwords, to the PRECIS framework, after the earlier stringprep approach proved unworkable.

## In production

**What a professional writes.** One normalization boundary, at the edge of the system, in NFC:
incoming text is normalized once and stored normalized. Comparison keys — for dedup, for search, for
a cache — are built with a documented, deliberately lossy pipeline, typically `NFKC` plus `casefold`,
stored *alongside* the original rather than replacing it. The original is what you display; the key
is what you match on. Conflating those two is what deletes a user's data.

**What changes at scale.** Normalization is not free — it is a table lookup per code point, and on a
document-sized corpus it is measurable. Real implementations use the annex's *quick check* property,
which lets them scan a string and skip it entirely when it is already in normal form, and most text
is. That optimisation is why normalizing everything at the boundary is affordable. The other scale
effect is a search index: if documents are indexed in one form and queries normalized in another,
recall drops for exactly the accented terms your users care most about, and no error is ever logged.

**The failure that only appears with real data.** A dedup job runs on a corpus and reports 3% fewer
unique records after a library upgrade. Nothing in the code changed — but `unicodedata.
unidata_version` did, and the new Unicode version assigned characters that previously normalized to
themselves. Pinning `python` exactly (Principle 4) covers the interpreter; the Unicode database rides
along with it, which is one of the less obvious things a pin is protecting.

**The review comment a senior engineer leaves.** On `if title_a == title_b:` for user-supplied text —
*"Byte comparison on text from two different sources. Normalize both to NFC at the boundary, and say
in the docstring which form this function expects."* On `unicodedata.normalize("NFKC", name)` before
an insert — *"That is the lossy form. You are storing `1` where the user wrote `①`. NFC to store,
NFKC only for the match key."*

**The interview question.** *"Two strings print identically but `==` says they differ. What is going
on and what do you do?"* The answer that shows real experience names canonical equivalence, says
`unicodedata.normalize("NFC", ...)` at the boundary rather than at every comparison, and then adds the
part that gets you the job: *"and if they still differ after normalization, they are probably
confusables — different characters that look alike — which normalization is not allowed to fix."*
