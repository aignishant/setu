# 6.2 — `tests/test_select.py`: the test that can go red

## One-line answer

The day's test file asserts what each function does **and** what it does not do — that `flag` leaves
its argument alone, that an empty result is allowed, that a duplicated index is refused — and one
deleted word proves the whole suite can fail.

---

## The story

Somebody rewrites `restock` to be tidier. The old version selected the rows to change and then
assigned through `.loc`; the new one filters first and writes to the filtered frame, which reads
better and is one line shorter.

The tests pass. Every one of them.

They pass because the test asserted on the frame the function *returned*, and the function returned
a frame with the right numbers in it — it just happened to be a different frame from the one the
write was supposed to land on.

The bug shipped, and it was not caught by a missing test. It was caught by a test that checked the
wrong object.

---

## The idea in plain language

A test suite for selection code has to assert three kinds of thing, and most suites only do the
first.

**What the function returns.** The obvious one: `restock` gives back counts raised to the minimum.

**What the function does *not* do.** That `flag` leaves the caller's frame unchanged. That `restock`
does not modify its argument. **These are the assertions that catch a mutation**, and they are the
ones people leave out, because nothing about the returned value is wrong.

**What the function refuses.** That an unknown item raises. That a duplicated index raises. These use
`pytest.raises` with `match=`, and the `match=` is what stops the test passing on a failure for a
different reason ([Day 27, 5.3](../../../day-27-reading-and-writing/parts/05-the-module/5.3-the-round-trip-test.md)
showed exactly that going wrong).

There is a fourth thing this suite asserts that most do not: **that an empty result is allowed.**
`dear_items` with a high threshold returns nothing, and there is a test saying so — because
[2.5](../02-masks/2.5-the-mask-that-matched-nothing.md) established that the empty case is the one
that never occurs in development and always occurs in production.

And the rule that makes all of it worth anything, which is Principle 7: **a test nobody has watched
fail is not a test.** The end of this part changes one method call in the module and counts what goes
red.

- **[6.1](6.1-the-select-module.md)** wrote the promises in prose and in checks; this writes them in a

## The mechanism

The fixture, and the ordinary assertions:

```python
"""Selection is by label, alignment is explicit, and nothing loses a row without saying so."""

from __future__ import annotations

import pandas as pd
import pytest

from setu import select as sel


@pytest.fixture
def shop() -> pd.DataFrame:
    return pd.DataFrame(
        {
            "item": pd.Series(["milk", "bread", "eggs", "rice"], dtype="str"),
            "need": [2, 1, 6, 1],
            "price": [1.15, 1.40, 0.32, 2.05],
            "aisle": pd.Series(["07", "03", "07", "11"], dtype="str"),
        }
    ).set_index("item")


def test_rows_for_keeps_the_order_asked_for(shop: pd.DataFrame) -> None:
    assert list(sel.rows_for(shop, ["rice", "milk"]).index) == ["rice", "milk"]


def test_rows_for_names_every_unknown_item(shop: pd.DataFrame) -> None:
    with pytest.raises(sel.SelectionError, match="tea, coffee"):
        sel.rows_for(shop, ["milk", "tea", "coffee"])
```

**Line by line:**

- The fixture returns a **fresh frame per test**. That is not tidiness: several tests here check that
  a function did not mutate its argument, and a shared frame would let one test's mutation pass
  another's assertion ([Day 2, 3.2](../../../day-02-quality-gate/parts/03-pytest/3.2-fixtures-and-tmp-path.md)).
- `["rice", "milk"]` in the order test is deliberately **not** the frame's order, so the assertion
  fails if `rows_for` ever returns the frame's order instead of the caller's
  ([1.2](../01-label-and-position/1.2-loc-by-label.md)).
- `match="tea, coffee"` — **both** unknown labels, in one string. That asserts the "collect them all"
  behaviour rather than just "it raised", so a version that raised on the first unknown would go red
  ([6.1](6.1-the-select-module.md)).
- `sel.SelectionError` rather than `ValueError` — the specific class, so a plain `ValueError` from
  somewhere else in the function does not satisfy this test.

The assertions about what does **not** happen:

```python
def test_flag_does_not_touch_the_caller_frame(shop: pd.DataFrame) -> None:
    before = list(shop.columns)
    sel.flag(shop)
    assert list(shop.columns) == before


def test_restock_writes_through_loc_and_the_write_lands(shop: pd.DataFrame) -> None:
    out = sel.restock(shop, 3)
    assert out["need"].tolist() == [3, 3, 6, 3]
    assert shop["need"].tolist() == [2, 1, 6, 1]
```

**Line by line:**

- `sel.flag(shop)` is called and **the result is thrown away**. The test is not about the result; it
  is about the argument. A linter may object to an unused return value, and that objection is the
  point being made.
- `before` is captured *before* the call, so the comparison is against a real prior state rather than
  against a hard-coded list that could drift from the fixture.
- `test_restock_...` has **two** assertions and the second is the important one. The first checks the
  return value — which a chained-assignment version would also pass, because it returns `out` either
  way. The second checks that `shop` is untouched.
- `[2, 1, 6, 1]` — the fixture's original values, asserted explicitly. **This is the assertion the
  story's tidier rewrite would have failed**, and the reason to write it is that nothing about the
  returned frame reveals the bug.

The refusals and the empty case:

```python
def test_dear_items_can_return_nothing(shop: pd.DataFrame) -> None:
    """An empty frame is a valid answer, and it keeps its columns and dtypes."""
    nothing = sel.dear_items(shop, threshold=99.0)
    assert len(nothing) == 0
    assert list(nothing.columns) == ["need", "price", "aisle"]
    assert str(nothing["need"].dtype) == "int64"


def test_duplicate_index_is_refused_with_the_labels_named(shop: pd.DataFrame) -> None:
    doubled = pd.concat([shop, shop.loc[["milk"]]])
    with pytest.raises(sel.SelectionError, match="milk"):
        sel.assert_unique_index(doubled, "doubled")


def test_combine_result_is_int64_not_float64() -> None:
    """Alignment promotes to float64; the module converts back, which proves no blank survived."""
    mine = pd.Series([2, 1], index=["milk", "bread"], name="need")
    theirs = pd.Series([1, 3], index=["milk", "tea"], name="need")
    assert (sel.combine(mine, theirs).dtypes == "int64").all()
```

**Line by line:**

- The empty test asserts **three** things, and only the first is about emptiness. The columns and the
  dtype matter because an empty frame that lost its schema behaves differently downstream
  ([2.5](../02-masks/2.5-the-mask-that-matched-nothing.md)).
- `pd.concat([shop, shop.loc[["milk"]]])` — the duplicate is made the way duplicates actually arrive,
  by stacking ([5.3](../05-reindexing/5.3-duplicate-labels.md)), rather than by constructing a
  contrived index.
- `shop.loc[["milk"]]` with **double brackets**, so it is a one-row frame rather than a Series and
  `concat` produces a frame ([1.2](../01-label-and-position/1.2-loc-by-label.md)).
- The dtype test's docstring explains *why* it is a test rather than a formality: the `astype("int64")`
  in `combine` can only succeed if `fill_value=0` removed every blank
  ([4.3](../04-alignment/4.3-the-nan-that-changed-the-dtype.md)), so **asserting the dtype is
  asserting that no blank survived**, which is a much harder property to check directly.
- `(... .dtypes == "int64").all()` — `dtypes` is a Series, so comparing it gives a Series of booleans
  and `.all()` reduces that to one answer ([2.1](../02-masks/2.1-a-comparison-makes-a-column.md)).

## When it breaks

**The mutation — one method call, changed.** In `src/setu/select.py`, change `restock` from this:

```text
    out.loc[below, "need"] = minimum
```

to this, which is what somebody tidying up would write:

```text
    out[below]["need"] = minimum
```

**Line by line:**

- The two lines select the same rows and the same column and assign the same value. One is a single
  `loc` call; the other is a filter followed by a write
  ([3.1](../03-writing/3.1-assigning-through-loc.md)).
- This is the story at the top of this part, and it is the single most common pandas bug there is.

Then run the suite:

```text
$ uv run pytest tests/test_select.py -q
```

**One test red, and read what stopped it.**

The failure is **`SelectionError: restock did not take effect`** — the module's own post-check from
[6.1](6.1-the-select-module.md), raised inside the function before it could return anything. The test
never got to compare a value; the function refused to hand one back.

Underneath, pandas' `ChainedAssignmentError` appears as a **warning**. It is a good message and it
names the fix. It is also, on its own, not a failure: `1 failed, 13 passed, 1 warning` — and had the
module lacked its three-line check, that line would have read `14 passed, 1 warning`, with the bug
shipped and a warning in the log that nobody reads.

**That is the argument for the post-check, demonstrated rather than asserted.** The test suite alone
would not have caught it either: `test_restock_...`'s first assertion is about the returned frame,
and a version that silently did nothing still returns a frame — one with the *original* counts, which
would have failed the first assertion here but would pass in any function whose job is less easy to
check.

Put `.loc` back and all fourteen pass.

## In production

**What a professional writes instead of the teaching version.** The no-mutation property is checked
once, generically, rather than one test per function:

```python
import pandas as pd
import pytest

from setu import select as sel

PURE = [
    pytest.param(lambda f: sel.flag(f), id="flag"),
    pytest.param(lambda f: sel.restock(f, 3), id="restock"),
    pytest.param(lambda f: sel.dear_items(f), id="dear_items"),
]


@pytest.mark.parametrize("call", PURE)
def test_leaves_its_argument_alone(call, shop: pd.DataFrame) -> None:
    """Every public function returns a new frame and modifies nothing it was given."""
    before = shop.copy(deep=True)
    call(shop)
    pd.testing.assert_frame_equal(shop, before)
```

**Line by line:**

- `PURE` is a **list of the functions that promise not to mutate**, and adding a function to the module
  means adding a line here. That is the mechanism that stops the eighth function being the one nobody
  tested.
- `id="flag"` on each param, so a failure names the function rather than `PURE1`
  ([Day 2, 3.3](../../../day-02-quality-gate/parts/03-pytest/3.3-markers-and-exit-code-five.md)).
- `shop.copy(deep=True)` — **`deep=True` stated**, because under Copy-on-Write a shallow copy shares
  data until written to ([Day 26, 3.2](../../../day-26-frames-and-copy-on-write/parts/03-copy-on-write/3.2-the-copy-that-has-not-happened-yet.md))
  and the whole point here is to hold an independent snapshot.
- `assert_frame_equal(shop, before)` — the **whole frame**, including dtypes, rather than a column
  list. A function that changed a value without changing the columns would slip past
  `list(shop.columns) == before`, which is what the teaching version checks.
- The lambdas supply each function's other arguments, so one test body covers three different
  signatures.

**What changes at scale.** Three things.

**The empty-input case needs its own parameterised sweep.** Every function here should be run against
a zero-row frame and asserted not to raise, because that is the input that never appears in
development ([2.5](../02-masks/2.5-the-mask-that-matched-nothing.md)). It is three lines with
`parametrize` and it finds more real bugs than any single hand-written test.

**Property-based testing earns its place here more than almost anywhere.** The properties are easy to
state — the output of `onto_shelf` always has exactly `len(SHELF)` rows; `combine` with `join="inner"`
never returns more rows than the smaller input, given unique indexes; `restock(f, n)["need"].min() >=
n` — and a library such as Hypothesis will find the frames that break them, including the empty one,
the single-row one and the all-duplicate one.

**And the mutation should be automated.** Changing one line by hand and counting the red tests is the
manual version of **mutation testing**, where a tool makes hundreds of small changes and reports which
ones the suite failed to notice. A suite that survives a mutation is a suite with a gap, and the
report is a list of the gaps. It is expensive to run and it belongs on a schedule rather than in
every pull request.

**The failure that only appears with real data.** A team's selection tests all used a three-row
fixture with a unique index, and passed for a year. Production data arrived with a duplicated key
after an upstream retry, `combine` multiplied the rows, and the daily total roughly doubled for the
affected keys. **There was a `test_combine_refuses_a_duplicated_index` in the suite** — and it tested
`combine`, while the code path in production called `align` directly, because somebody had inlined it
for speed. The lesson is that a test protects the function it names, not the behaviour it describes,
and that a rule worth testing is worth enforcing at one entry point
([6.1](6.1-the-select-module.md)).

**The review comment a senior engineer leaves.** *"Good coverage of the happy paths and I like the
empty-result test. Two gaps: nothing asserts that `dear_items` leaves its argument alone — it copies
now, but a future edit could drop that — and the `pytest.raises` on line 62 has no `match=`, so it
will pass if the function starts raising for a completely different reason."*

**The interview question.** *"How do you test code that manipulates DataFrames?"* Assert three things,
not one: what the function **returns**; what it **does not do**, which usually means asserting the
input frame is unchanged, because mutation is the failure that the return value cannot reveal; and
what it **refuses**, with `pytest.raises(..., match=...)` so the test cannot pass on the wrong error.
Then the two habits that matter more than coverage: **test the empty input**, because it is the case
production produces and development never does; and **mutate the module to watch the suite go red**,
because a suite that has never failed is not evidence of anything. If they ask for a specific example,
chained assignment is the best one — it produces a correct-looking return value and changes nothing,
so only an assertion on the original object catches it.
